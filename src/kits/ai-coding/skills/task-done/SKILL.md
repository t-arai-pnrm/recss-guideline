---
name: task-done
description: 完了したタスクの報告を確かめてアーカイブし、教訓とプロジェクトの規約を見直す。利用者が呼ぶ。
argument-hint: <タスクのスラッグの一部>
disable-model-invocation: true
---

`tasks/` の直下（`tasks/archive/` を除く）から、名前に「$ARGUMENTS」を含むタスクを探す。複数見つかったら、一覧を示して選んでもらう。

1. 終了の条件を確かめる。1つでも満たさなければ、満たしていない条件を示して止まる。draft なら `/task-start` で計画を整えて `/task-approve` で承認し、未完了の手順があれば `/task-start` で続けるよう案内する。
   - plan.md の status が approved である（draft なら、承認されていない変更が残っている）。
   - 手順がすべて `[x]`（検証済み）である。
   - 「完了の報告」に、brief の今の完了条件がすべて行として入っていて、「不合格」の行がない。
   - 報告の判定には現在の計画に対する証拠がある。過去の結果を使っている行には、今回の変更の影響を受けない根拠がある。根拠がなければ「未確認」に戻す。
2. 「未確認」の行と、値の対応表に残っている種類「仮」の値を一覧にして、人の確認結果を受け取る。未確認が残る間はアーカイブしない。
   - 人が合格と判定した項目は、回答と日付を証拠に添えて、報告を合格に更新する。不合格なら続けるべき対応を示して止まる。
   - 仮の値については、確定した値を尋ねる。値を変える場合は、`/task-start` で計画を更新し、承認と検証をやり直すよう案内して止まる。同じ値を正式に採用する場合は、人の判断を記録し、値の種類を「トークン」か「例外」に更新する。
3. 決定ログとこのセッションのやりとりから、AI が誤った点と、人が直した点を拾う。`tasks/lessons.md` の先頭に、ファイルの書式で追記する。原因は、コンテキスト不足、権限不足、性能不足の3つの観点で探す。複数に当たるならすべて書き、決まらなければ「未確定」と書く。性能不足とする前に、テストの期待値や指示どうしの食い違い、ツールの不具合でないかを確かめる。
4. 規約を見直す。どちらも、人の確認を得てから書き換える。
   - 教訓ごとに、同じ誤りを防ぐために書き足す先を提案する（`CLAUDE.md`、Stylelint の設定、テスト、brief や plan のひな形）。
   - `CLAUDE.md` に、モデルが守れるようになって要らなくなった指示や、本書のルールと重なる指示があれば、消す案を出す。
5. plan.md の status を done にし、`tasks/<slug>/` を `tasks/archive/<slug>/` に移す。
