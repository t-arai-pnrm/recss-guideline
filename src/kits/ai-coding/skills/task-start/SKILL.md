`tasks/` の直下から、名前に「$ARGUMENTS」を含むディレクトリを探す。`tasks/archive/` は探さない。

- 引数が空なら、進行中のタスクを、各 plan.md の status と一緒に一覧にして、どれを進めるかを尋ねる。
- 複数見つかったら、一覧を示して選んでもらう。
- 見つからなければ、`/task-new` でタスクを作るよう案内して止まる。
- brief.md がなければ、止まって人に書いてもらう。

## ファイルの役割

- `brief.md`：人が書く。読み取り専用で、編集しない。
- `refs/`：人が用意する。読み取り専用。brief の「参考ファイル」の表で用途を確かめてから読む。
- `plan.md`：AI が書く。ただし、`status: approved` を書くのは `/task-approve` だけ。人が「懸念・確認事項」の回答欄に書いた内容は消さない。
- `tasks/lessons.md`：過去の教訓。着手する前に読む。

## 手順

1. brief.md と `tasks/lessons.md` を読む。plan.md があれば読む。brief の「参考ファイル」の表に従って、必要な `refs/` を読む。
2. plan.md の status が done なら、完了していることを伝えて止まる。空、draft、approved、done 以外の status は書き換えず、利用者に確認して止まる。
3. このセッションで受けた回答や修正依頼を確認する。plan がなければ、初回の計画の材料にする。plan がある場合、回答欄が空の問いに対する回答は、「<日付> チャットで回答：<内容>」と回答欄に写し、決定ログにも日付付きで記録する。人が書いた回答と食い違う場合は、上書きせず確認して止まる。
4. 回答と修正依頼を plan に反映する。承認済みの値、方針、スコープ、完了条件、触るファイルが変わるなら、「止まる条件」の1つ目に従って draft に戻し、影響を受ける検証結果も未確認に戻す。回答の記録だけで計画が変わらない場合は、status を変えない。
5. 確認事項を判定する。実装に必要な値や振る舞いが回答によって決まり、plan に反映されている問いは、解決済みとする。「未定」という回答だけでは解決済みにしない。人が選んだ暫定案が値の対応表に種類「仮」として記録されている問いは、その案で進めることを `/task-approve` で承認してから実装に使う。
6. plan.md の有無と status で分ける。計画の編集と確認依頼は、未解決の問いがあっても行える。

### plan.md がない、または status が空のとき

1. コードベースを調べる。再利用できる部品、トークン、`CLAUDE.md` のプロジェクトの規約を探す。`DESIGN.md` があれば読む。recss-guideline スキルがあれば、このタスクに関係する章を読む。
2. brief に Figma の URL があり、Figma の MCP が使えるときは、その node-id のデザインを読む。Figma を読むのは、この段階だけ。`get_design_context` が返すコード（React、Tailwind、絶対配置の座標）は値を読むために使い、そのまま写さない。
   - Figma の指定がないとき（既存のコードの修正、不具合の修正など）や、MCP が使えないとき（未認可、呼び出しの上限）は、brief、既存のコード、`refs/` を根拠に計画する。Figma の指定があるのに突き合わせられなかった項目は、plan と完了の報告に「未確認」と書く。Figma の指定がないタスクでは、デザインとの比較を必須にせず、brief の完了条件で検証する。
3. [templates/plan.md](templates/plan.md) の形で plan.md を書き、status を draft にする。
   - 値の対応表に、実装で使う値と根拠をすべて書く。トークンに当たらない値は「例外」とし、理由を書く。
   - brief にない値は推測で埋めず、「懸念・確認事項」に宛先、選択肢、推奨を書く。
   - デザインの値や見た目が `DESIGN.md` の判断と食い違うとき（accent をボタンの背景に使っている、決めた変種にない見た目の部品があるなど）は、どちらかに合わせて埋めず、「懸念・確認事項」に書く。
   - 手順ごとに、検証（実行するコマンドと、期待する結果）を書く。
   - 触るファイルごとに影響範囲を書く。
4. 宛先がデザイナーやディレクターの問いがあれば、[confirm-request の手順](../confirm-request/SKILL.md)で、宛先ごとの確認依頼の文面を作る。
5. 止まって、plan のレビューを頼む。確認依頼を作ったときは、送るのは人であることを伝える。

### status が draft のとき

- 実装には進まない。
- 未解決の問いが残っていれば、一覧にして示す。宛先がデザイナーやディレクターなら、[confirm-request の手順](../confirm-request/SKILL.md)で確認依頼の文面を作る。
- 確認事項の回答が「未定」なら、仮の案を、選択肢の中から推奨と理由を添えて示し、人に選んでもらう。人が選んだら、値の対応表に種類「仮」として書き、「未確定の点」として決定ログに残す。仮の値で進めるかどうかは、人が `/task-approve` で承認して決める。
- 共通の手順で反映した回答や修正依頼を重ねて記録しない。更新した plan を示して、もう一度レビューを頼んで止まる。
- 承認は、人が `/task-approve` で行うと案内する。チャットで「よさそう」と言われても、status を書き換えない。

### status が approved のとき

1. 実装に必要な値や振る舞いが未解決なら、一覧にして示し、止まる。種類「仮」の値は、その案で進めることが承認されている場合だけ使う。
2. 未完了（`- [ ]`）の最初の手順を選ぶ。全手順が検証済みなら「終えるとき」へ進む。
3. 影響範囲が全ページに及ぶ手順（トークン、ベーススタイル、レイヤーの順番、コンポジションの変更）は、変更内容と影響範囲について人の確認が決定ログに記録されていることを確かめる。記録がなければ、着手する前に確認を求めて止まる。同じ内容について確認済みなら、繰り返し尋ねない。
4. plan の値の対応表と方針に沿って実装する。承認済みの計画で足りる間は、`get_design_context` を呼び直さない。新しい情報が必要になったときは「止まる条件」に従って計画を見直す。デザインを再取得して plan との差が見つかった場合も、draft に戻して承認し直す。
5. 1つの手順を終えたら、その手順の検証を実行する。期待する結果と一致したら `- [x]` にする。通らなければ直す。実行できなかった検証は「未確認」と記録し、`- [x]` を付けずに止まる。
6. 判断、検証結果、つまずいた点を、決定ログに日付付きで追記する。次の手順があれば、同じ流れで続ける。

### status が done のとき

完了していることを伝えて止まる。

## 止まる条件

次のどれかに当たったら、作業を止めて、理由と選択肢を示す。

- 方針、スコープ、完了条件、触るファイルの範囲、値の対応表が変わる：status を draft に戻し、変わる点を決定ログに書く。変更の影響を受ける手順の `[x]` を `[ ]` に戻し、「完了の報告」があれば、影響を受ける行の判定を「未確認」に戻す。影響範囲を判断できなければ、全手順と全報告を未確認に戻す。過去の証拠は履歴として残し、今回の判定とは分ける。内容と検証を変えずに手順を分けたり順番を入れ替えたりするだけなら、決定ログに書いて続ける。
- brief と plan にない値（色、余白、カンプのない幅での振る舞い、状態の見た目）が要る：推測せず、「懸念・確認事項」に書く。宛先がデザイナーやディレクターなら、[confirm-request の手順](../confirm-request/SKILL.md)で確認依頼の文面も作る。回答で値の対応表が変わるときは、status を draft に戻し、承認し直してから続ける。
- 同じ失敗が2回続く、または同じ箇所の修正が3巡に達した：立てた仮説と試したことを、決定ログに書く。
- 検査を通すために、ルールを無効にする、テストの基準画像を更新する、検査を飛ばす必要がある：実行しない。

## 終えるとき

1. plan の全手順が検証済みであることを確認する。未完了の手順があれば、完了とは報告せず、残っている手順と次に必要な対応を示して止まる。
2. 現在の brief の完了条件を、1つずつ確かめる。
   - lint とビルドを実行する。
   - 確かめる幅のすべてで、表示とはみ出しを確かめる。宣言が適用されているかは、`getComputedStyle` で計算値を読んで確かめる。
   - デザインとの比較が完了条件にある場合は、同じ幅のスクリーンショットを撮り、Figma の `get_screenshot` の画像と並べる。Figma を使えないときは、`refs/` の画像と並べるか、「未確認」と書く。
   - recss-guideline スキルの「レビューするとき」の手順で、変更した CSS をレビューする。
3. plan.md の「完了の報告」を、今回の結果で更新する。「完了条件 | 判定（合格／不合格／未確認） | 証拠」の表に、現在の brief の完了条件をすべて入れる。過去の結果を使う場合は、今回の変更の影響を受けない根拠を添える。実行していない検査と、人の判定を受けていない項目は「未確認」と書き、「問題なし」と書かない。値の対応表に種類「仮」の値が残っていれば、対応する確認事項とともに一覧にする。
4. 不合格、未確認、仮の値が残っていれば、残っている項目と次に必要な対応を示す。
5. 完了の確認とアーカイブは `/task-done` で行うよう案内する。
