ベーススタイルには、リセットの上に、プロジェクト全体で共通にしたい既定を書きます。本書でベーススタイルに書くのは、ルート要素の色と行の高さ、下線の位置、二重のフォーカスリング、スクロールの挙動、モーダル表示中の背面固定、`interpolate-size`、フレックスアイテムとグリッドアイテムの最小幅です。ベーススタイルは `base` レイヤーに置き、セレクタは `:where()` で包まずにそのまま書きます。グローバルに書くと問題になる指定は、「[8-3 グローバルに書いてはいけないもの](/reset/global-pitfalls/)」で説明します。

どれも、コンポーネントごとに書くと抜け漏れが出やすく、しかもリセットCSSには入れにくい指定です。

## リセットとベーススタイルの分担

リセットCSSとベーススタイルは、どちらもサイト全体に適用される土台ですが、役割が違います。リセットCSSは、どのプロジェクトでも同じように使える汎用の部品です。ベーススタイルは、そのプロジェクトで決めたこと（色、フォント、フォーカスの見せ方、動きの扱いなど）を書く場所です。

本書が推奨するリセットCSSのkiso.css（「[8-1 壊さないリセット](/reset/kiso/)」）には、あえて入れていない指定があります。モーダル表示中に背面のスクロールを止める指定は、リセットCSSの範囲かどうかで判断が分かれるので入れていません。`interpolate-size` も、既存のサイトで意図しないアニメーションを起こすおそれがあるので見送っています。どちらも、各プロジェクトのベーススタイルで指定します。

反対に、kiso.cssがすでに指定しているものは、ベーススタイルに書き足しません。このページでは、kiso.cssを読み込んだうえで、さらにベーススタイルに書くものと、プロジェクトごとに検討するものを挙げます。グローバルな `@keyframes` もベーススタイルに置きますが、これは「[18-6 @keyframesを設計する](/motion/keyframes/)」で扱います。

ベーススタイルのセレクタは、`:root` や `:focus-visible` のように素のまま書きます。`base` レイヤーはコンポーネントを置く `components` レイヤーより順位が低いので、ベーススタイルの指定は、詳細度と関係なくコンポーネントのクラス1つで上書きできます（「[4-3 カスケードレイヤーで順位を決める](/cascade/layers/)」）。`:where()` で包んで詳細度を0にする必要はなく、包まないほうがセレクタを読みやすく保てます。

レイヤーを使えない環境では、この前提が成り立ちません。CMSのテーマのCSSと共存する場合のように、自分のCSSもレイヤーなしで書くときは、読み込む順番と詳細度だけで優先順位が決まるので、ベーススタイルのセレクタを `:where()` で包んで詳細度を0にします。その書き方は「[4-2 セレクタで詳細度を設計する](/cascade/selectors/)」で説明します。{/* CMSの節を公開したらリンクする: /operations/cms/ */}

## ルート要素の色と文字

ルート要素には、ページ全体の背景色、文字色、行の高さを指定します。値はどれもトークンで持ち、ベーススタイルではそれを参照するだけにします。

```css title="🙆‍♂ Recommended: ルート要素に背景色、文字色、行の高さを指定する"
@layer base {
  :root {
    background-color: var(--background--base);
    color: var(--foreground--base);
    line-height: var(--leading--normal);
  }
}
```

色は、`--color--neutral--50` のような色そのものを表すトークン（プリミティブ）ではなく、`--background--base` のような役割を表すトークン（セマンティクス）で指定します。ダークモードの値は役割のトークンの側で `light-dark()` を使って切り替えるので、ベーススタイルの指定は配色にかかわらず同じです。トークンの2層の設計は「[10-4 デザイントークン](/components/design-tokens/)」、配色の切り替えは「[15-4 ダークモード](/color-media/dark-mode/)」で説明します。

`body` ではなく `:root` に指定するのは、行の高さを `rlh` 単位の基準にするためです。`rlh` はルート要素の行の高さを表す単位なので、`body` に `line-height` を指定しても `rlh` の値は変わりません。このページで後に出てくる `scroll-padding-block-start` の代替値の `4rlh` も、ルート要素の行の高さを前提にしています。また、ルート要素の背景色は、ページの領域の外側（スクロールしすぎたときに見える部分など）にも描かれます。

行の高さは1.5以上にします。kiso.cssも `:root` に `line-height: 1.5` を指定していますが、本文の読みやすさに合わせて、プロジェクトの値で上書きします。値の決め方は「[14-3 行の高さとハーフレディング](/typography/line-height/)」で説明します。

`font-family` と `font-weight` は、Webフォントを使うときだけ指定します。使わない場合は、kiso.cssの `sans-serif` とデフォルトの太さで足ります。Webフォントを使う場合は、`font-family: var(--font-family--inter)` のようにフォントスタックのトークンを参照し、デザインに合わせて `font-weight` も決めます。フォントの選び方は「[14-1 フォントを指定する](/typography/fonts/)」で扱います。

`-webkit-font-smoothing: antialiased` も、プロジェクトごとに検討するものです。macOSのブラウザで、文字の描画をグレースケールのアンチエイリアシングに切り替えるプロパティで、標準のプロパティはありません。「サブピクセルアンチエイリアシングを有効にする」という説明を見かけますが、実際は逆で、サブピクセルを使わない描画にする指定です。macOS 10.14以降はOSがサブピクセルアンチエイリアシングを使わなくなったので、今の効果は、文字が少し細く描かれることです。{/* 要確認: 出典なし */}フォントによっては細くかすれて見えるので、一律には指定しません。デフォルトの描画では太字が太りすぎて見える場合は、太字の要素にだけ指定する方法もあります。

## リンクの下線の位置

下線は、`text-underline-offset` で文字から少し離します。文字と下線の間が詰まっていると、ディスレクシアのある人などにとって、文字が判読しにくくなるという指摘があります。

```css title="🙆‍♂ Recommended: 下線を文字の大きさの25%離す"
@layer base {
  :root {
    text-underline-offset: 25%;
  }
}
```

`text-underline-offset` は継承されるので、ルート要素に1回書けば、リンクにも `u` 要素や `ins` 要素にも適用されます。値はパーセントで指定します。パーセントは、下線を描く要素（リンクなら、リンク自身）の `1em` に対する割合です。相対値のまま継承されるので、見出しの中のリンクのように大きな文字でも、下線までの距離がリンク自身の文字の大きさに比例します。

ルート要素に `0.25em` と書くと、比率は保たれません。`em` の値は指定した要素（ここではルート要素）で絶対的な長さに計算されてから継承されるので、ルート要素の文字の大きさが16pxなら、32pxの見出しの中のリンクでも下線までの距離は4pxのままです。パーセントの値はSafari 18.2から使えるので、本書の対象のブラウザ（Safari 18系の最終版以降）で動作します。

kiso.cssは、リンクの下線をデフォルトで消し、下線の太さをフォントの指定に合わせています（`text-decoration-thickness: from-font`）。下線の位置は指定していないので、ベーススタイルで決めます。リンクに下線を戻すときは、`text-decoration-line: revert` を使います（「[8-1 壊さないリセット](/reset/kiso/)」）。

## フォーカスリングの色と形

フォーカスリングは、キーボードで操作するユーザーに、いまどこにフォーカスがあるかを伝える表示です。ブラウザのデフォルトのリングは、ブラウザごとに見た目が異なり、サイトの配色によっては見えにくいことがあります。ブランドカラーのような1色でリングを描くと、同じ色の背景の上では消えてしまいます。

そこで本書では、`:focus-visible` のときに、2色を重ねたリングを表示します。要素のすぐ外側を背景色（`Canvas`）、その外側を文字色（`CanvasText`）にすると、背景の明るさにかかわらず、どちらか一方は背景と区別できます。

```css title="🙆‍♂ Recommended: :focus-visible に二重のフォーカスリングを定義する" from="reset/focus-ring"
@layer base {
  :focus-visible {
    --_b--ring-width: 3px;
    --_b--ring-offset: 3px;

    box-shadow: 0 0 0 calc(var(--_b--ring-offset) + var(--_b--ring-width)) Canvas;
    outline: var(--_b--ring-width) solid CanvasText;
    outline-offset: var(--_b--ring-offset);
  }
}
```

外側のリングは、太さ3pxの `outline` です。`outline-offset` で要素から3px離し、その隙間を `box-shadow` で埋めています。`box-shadow` の広がりは隙間とリングの太さを足した6pxですが、外側の3pxは `outline` に隠れるので、見えるのは要素のすぐ外側の3pxだけです。接頭辞の `--_b--` は、コンポーネントの内部用のプロパティと名前が重複しないように付けています。

色に使っている `Canvas` と `CanvasText` はシステムカラーで、ブラウザが決める背景色と文字色です。強制カラーモードでは、互いにコントラストが取れた2色の組み合わせに切り替わります。ダークモードでは、`color-scheme` に `dark` を含めたときだけ、暗い背景と明るい文字の組み合わせに切り替わります。

強制カラーモードでは `box-shadow` が `none` になりますが、`outline` は残ります。リングの本体を `outline` で描くのはこのためで、`box-shadow` だけで描いたリングは強制カラーモードで消えます。

## スムーススクロールの有効化

ページ内リンクで移動するときのスムーススクロールは、ルート要素に `scroll-behavior: smooth` を1行書けば実現できます。手軽なので広く使われていますが、この書き方には副作用があります。

```css title="🙅‍♂ Not Recommended: スムーススクロールを一律に有効にする" issue="behavior"
/* 🙅‍♂ Not Recommended */
@layer base {
  :root {
    scroll-behavior: smooth;
  }
}
```

まず、Tabキーでフォーカスを移したときのスクロールまでなめらかになり、キーを続けて押すと動きが追いつかず、もたつきます。JavaScriptの `scrollTo()` も、デフォルトの動きがなめらかなスクロールに変わるので、サードパーティのスクリプトにも影響します。さらに、動きを減らす設定をしているユーザーにも、アニメーションが適用されます。

```css title="🙆‍♂ Recommended: 読み込みが終わった後、ページ内リンクの移動先があり、キーボード操作中でないときだけ有効にする"
@layer base {
  :root {
    &[data-loaded="true"]:has(:target):not(:has(:focus-visible)) {
      @media (prefers-reduced-motion: no-preference) {
        scroll-behavior: smooth;
      }
    }
  }
}
```

この指定は、4つの条件がそろったときだけスムーススクロールを有効にします。1つ目は、動きを減らす設定がないこと（`prefers-reduced-motion: no-preference`）です。2つ目は、ページの読み込みが終わっていること（`[data-loaded="true"]`）です。3つ目は、ページ内リンクの移動先（URLのフラグメントが指す要素）があること（`:has(:target)`）です。4つ目は、キーボード操作などでフォーカスリングを表示している要素がないこと（`:not(:has(:focus-visible))`）です。

ページ内リンクをクリックすると、移動先が `:target` になってからスクロールが始まるので、このときはなめらかに動きます。一方、Tabキーでフォーカスを移しているときは `:focus-visible` の要素があるので、アニメーションせずに一度でスクロールします。キーボード操作のもたつきは起きません。

`data-loaded` 属性は、ページの読み込みが終わったときに、JavaScriptでルート要素へ付けます。

```js title="🙆‍♂ Recommended: 読み込みが終わったら、ルート要素に data-loaded 属性を付ける"
window.addEventListener("load", () => {
  document.documentElement.dataset.loaded = "true";
});
```

この条件がないと、ほかのページから `#section` のようなフラグメント付きのURLで来たときや、そのURLで再読み込みしたときに、表示した直後のページがなめらかにスクロールします。ユーザーはページ内リンクを操作していないので、この動きは不自然です。読み込みが終わるまではスムーススクロールを無効にしておけば、移動先へは一度でスクロールします。`DOMContentLoaded` ではなく `load` イベントを使うのは、画像などの読み込みが続いている間は、移動先へのスクロールが終わっていないことがあるからです。JavaScriptが動かない環境では、スムーススクロールが無効になるだけで、ページ内リンクは使えます。

以前の私は、CSSではなくJavaScriptの `scrollIntoView()` でスムーススクロールを実装していました。現在は、スクロールそのものはこの条件付きの指定に任せ、JavaScriptでは属性を付けるだけにしています。ただし、特定のリンクだけスムーススクロールを無効にするような細かい制御には、今でもJavaScriptが必要です。

## 固定ヘッダーに隠れる移動先

固定ヘッダーがあるページでは、ページ内リンクで移動した先の見出しが、ヘッダーの下に隠れてしまいます。ページをスクロールさせているルートに `scroll-padding-block-start` を指定すると、スクロールで内容を見せる範囲から、ブロック方向の始点側の指定した分が除かれます。移動先の要素は、除いた範囲のすぐ下に表示されます。

```css title="🙆‍♂ Recommended: スクロールで見せる範囲から、ヘッダーの高さを除く"
@layer base {
  :root {
    scroll-padding-block-start: var(--site-header--block-size, 4rlh);
  }
}
```

`--site-header--block-size` は、固定ヘッダーの高さを受け取るカスタムプロパティです。高さはJavaScriptで測ってルート要素に渡します。測り方と、ヘッダーを固定する条件に合わせて指定を絞る方法は、「[11-7 固定ヘッダー](/layout-practice/sticky-header/)」で説明しています。値が渡されないときの代替値 `4rlh` は、ルート要素の行の高さの4倍です。ユーザーが文字サイズを大きくすれば、余白も一緒に大きくなるので、スクリプトが動かない環境でも、多くのヘッダーの下から見出しを出せます。

この指定は、Tabキーでフォーカスを移したときのスクロールにも反映されます。Chromeで、高さ64pxのヘッダーの下に入った入力欄へフォーカスを移すと、指定したページでは入力欄が見える位置までスクロールし、指定しないページではヘッダーの下に隠れたままでした。

移動先の要素の側に余白を付ける書き方もあります。

```css title="🙅‍♂ Not Recommended: 移動先とフォーカスした要素の側に余白を付ける" issue="behavior"
/* 🙅‍♂ Not Recommended */
@layer base {
  [id],
  :focus {
    scroll-margin-block-start: 4rlh;
  }
}
```

ページ内リンクの移動先とフォーカスした要素は、この書き方でも隠れません。違いが出るのは、Spaceキーなどで1画面ずつ送るときです。`scroll-padding` は、スクロールで見せる範囲そのものを狭めるので、送る量からヘッダーの分が除かれます。`scroll-margin` は要素の側の余白なので、送る量はビューポートの高さのままで、送るたびに、直前の画面で見えていた最後の行がヘッダーの下に入ります。Chromeで高さ64pxのヘッダーのページを試すと、Spaceキーで送る量は、`scroll-padding-block-start` を指定すると64px少なくなりました。{/* 要検証: ブラウザ。Firefox と Safari で、Space キーで送る量に scroll-padding が反映されること */}キーボードでページを読み進めるユーザーにとって、この差は大きいので、本書はスクロールする側の `scroll-padding` を選びます。

2つを両方に指定すると、余白は足し合わされます。Chromeで、ルートの `scroll-padding-block-start` を64px、移動先の `scroll-margin-block-start` を30pxにすると、移動先はビューポートの上端から94pxの位置に止まりました。ヘッダーの高さを除くのは `scroll-padding` だけにし、移動先の要素には `scroll-margin` を足しません。

## モーダル表示中の背面のスクロール

モーダルのダイアログを開いている間は、背面のページがスクロールしないようにするのが一般的です。以前は、`body` を `position: fixed` にしたり、`dialog` の `open` 属性で判定したりする方法が使われていました。

```css title="🙅‍♂ Not Recommended: open 属性を持つ dialog で、背面のスクロールを止める" issue="behavior"
/* 🙅‍♂ Not Recommended */
@layer base {
  body:has(dialog[open]) {
    overflow: hidden;
  }
}
```

この書き方には2つの問題があります。`open` 属性は、モーダルでない `show()` で開いたダイアログにも付くので、背面を操作できるはずのダイアログでもスクロールが止まります。また、`body` に指定した `overflow` は、`position: sticky` の要素の動きを妨げることがあります。

```css title="🙆‍♂ Recommended: モーダルが開いている間、ルート要素のスクロールを止める"
@layer base {
  :root {
    &:has(:modal) {
      overflow: hidden;
    }
  }
}
```

`:modal` は、`showModal()` や `command="show-modal"` でモーダルとして開いたダイアログに一致する擬似クラスです（全画面表示にした要素にも一致します）。ルート要素に指定した `overflow` はビューポートに伝わるので、`position: sticky` の要素にも影響しません。この方法で背面を止められるのは、ページがルートスクローラー（ビューポート）でスクロールしている場合です。ラッパーの要素をスクロールさせる作りでは止まらないので、ページのスクロールを入れ子にしない理由とあわせて「[11-10 ページのスクロールとルートスクローラー](/layout-practice/root-scroller/)」で説明しています。

スクロールを止めるとスクロールバーが消え、その幅の分だけコンテンツが横にずれます。kiso.cssが `:root` に指定している `scrollbar-gutter: stable` は、スクロールバーの有無にかかわらずその幅の領域を確保するので、ダイアログを開閉してもレイアウトはずれません。

`overflow: hidden` の代わりに `overflow: clip` を使う方法もあります。FirefoxとSafariで確かめたところ、`:root` の `overflow: clip` でも背面のスクロールは止まりました。それでも本書は `hidden` のままにします。ルートに指定した `overflow` はビューポートに伝わり、ビューポートでは `clip` が `hidden` として扱われるので、ルートでは2つの値の働きは変わりません。値を替えても得られるものがなく、`hidden` なら、`clip` で背面を固定できなかった古い版のFirefoxでも同じように止まります。また、iOSのSafariでは、この方法でも背面のスクロールを完全には止められません。完全に止める必要がある場合は、JavaScriptを併用します。ダイアログそのものの実装は、「[17-6 開閉するUI](/interaction/disclosure/)」で扱います。

## スクロールバーの領域と見た目

`scrollbar-gutter: stable` は、ページの内容が増えてスクロールバーが現れたときのずれも防ぎます。kiso.cssが指定しているので、ベーススタイルで書き足す必要はありません。

<Baseline id="scrollbar-gutter" />

Safariは18.2で対応したので、本書が対象とするブラウザ（Safari 18系の最終版以降）では、すべて動作します。スクロールバーの幅をJavaScriptで測って余白を補う処理は不要です。

一方、スクロールバーの色や太さは、できるだけ変えません。スクロールバーの見た目はOSやユーザーの設定で決まるもので、サイトごとに変えると操作の一貫性が損なわれます。強制カラーモードでは、指定した色によってスクロールバーが見えなくなるおそれもあります。

デザインの都合でどうしても変える場合は、強制カラーモードでないとき（`forced-colors: none`）に限り、標準の `scrollbar-color` と `scrollbar-width` で指定します。どちらも、2025年12月までにすべての主要なブラウザで使えるようになりました。

```css title="🙆‍♂ Recommended: スクロールバーを変えるなら、強制カラーモードでないときだけにする"
._scroller {
  overflow-x: auto;

  @media (forced-colors: none) {
    scrollbar-color: var(--foreground--muted) var(--background--surface);
    scrollbar-width: thin;
  }
}
```

## interpolate-sizeの有効化

`interpolate-size: allow-keywords` は、`auto` や `fit-content` のようなキーワードで決まる大きさと、数値の大きさの間でアニメーションできるようにするプロパティです。`block-size: 0` から `block-size: auto` への変化も、トランジションでなめらかにつなげられます。

```css title="🙆‍♂ Recommended: 動きを減らす設定がないときだけ、キーワードの大きさへの補間を有効にする"
@layer base {
  :root {
    @media (prefers-reduced-motion: no-preference) {
      interpolate-size: allow-keywords;
    }
  }
}
```

このプロパティは継承されるので、`:root` に1回書けば文書全体で有効になります。アニメーションのための指定なので、動きを減らす設定をしていないとき（`prefers-reduced-motion: no-preference`）に限ります。

便利な機能ですが、kiso.cssには入れていません。`transition: all` のように対象を限定しないトランジションを書いた既存のコードでは、これまで一瞬で切り替わっていた大きさの変化までアニメーションするからです。`interpolate-size` の初期値が数値だけを補間する `numeric-only` になっているのも、既存のサイトとの互換性のためです。影響を判断できるのはプロジェクトの側なので、ベーススタイルで有効にします。

本書では `transition: all` を使わないので、この問題は起きません（「[18-4 トランジションの基本と中断](/motion/transitions-and-keyframes/)」）。

<Baseline id="interpolate-size" />

`interpolate-size` に対応しているのはChrome系のブラウザだけです。対応していないブラウザでは、大きさが一瞬で切り替わるだけで、機能は損なわれません。そのため、プログレッシブ・エンハンスメントとして使えます。

## フレックスアイテムとグリッドアイテムの最小幅

最後に、全称セレクタに `min-inline-size: 0` を指定します。フレックスやグリッドのレイアウトで起きがちな、原因の分かりにくいはみ出しを防ぐ指定です。

```css title="🙆‍♂ Recommended: すべての要素の最小幅を0にする"
@layer base {
  *,
  ::before,
  ::after {
    min-inline-size: 0;
  }
}
```

`min-inline-size`（`min-width`）の初期値 `auto` は、通常は0として扱われます。ところが、フレックスアイテムとグリッドアイテムでは、中身の最小幅（`min-content`）として扱われます。そのため、長い英単語やURL、ブラウザが最小幅を決めている `input`、横にスクロールさせる表を含むアイテムは、それ以上縮まずに親からはみ出します。

文字列の折り返しは、kiso.cssの `overflow-wrap: anywhere` で解決できます。しかし、入力欄や表のはみ出しは残ります。全称セレクタで最小幅を0にすると、こうした要素も親の幅まで縮みます。

副作用がまったくないわけではありません。縮ませたくない要素まで縮むことがあるので、アイコンのような要素には、個別に `flex-shrink: 0` などを指定します。それでも私は、原因の分かりにくいはみ出しを調べるより、「縮みすぎる」という目に見える問題を直すほうが簡単で合理的だと考えています。

既存のサイトの修正では、この `min-content` によるはみ出しを直す依頼が繰り返しあります。そのため、新しく作るサイトでは既定で防いでおきます。はみ出しを防ぐほかの書き方は、「[11-3 サイズと内容の変化に耐える](/layout-practice/defensive/)」で説明します。

## ベーススタイルのまとめ

ここまでの指定をまとめると、次のとおりです。すべて `base` レイヤーの中に、素のセレクタで書きます。Webフォントを使う場合は、`font-family` と `font-weight` の指定を足します。

```css title="🙆‍♂ Recommended: ベーススタイルを base レイヤーに素のセレクタでまとめる"
@layer base {
  *,
  ::before,
  ::after {
    min-inline-size: 0;
  }

  :root {
    background-color: var(--background--base);
    color: var(--foreground--base);
    line-height: var(--leading--normal);
    text-underline-offset: 25%;
    scroll-padding-block-start: var(--site-header--block-size, 4rlh);

    @media (prefers-reduced-motion: no-preference) {
      interpolate-size: allow-keywords;
    }

    &[data-loaded="true"]:has(:target):not(:has(:focus-visible)) {
      @media (prefers-reduced-motion: no-preference) {
        scroll-behavior: smooth;
      }
    }

    &:has(:modal) {
      overflow: hidden;
    }
  }

  :focus-visible {
    --_b--ring-width: 3px;
    --_b--ring-offset: 3px;

    box-shadow: 0 0 0 calc(var(--_b--ring-offset) + var(--_b--ring-width)) Canvas;
    outline: var(--_b--ring-width) solid CanvasText;
    outline-offset: var(--_b--ring-offset);
  }
}
```

`scrollbar-gutter: stable` は、kiso.cssが指定しているので、ここには含めていません。`data-loaded` 属性を付けるJavaScriptは、スムーススクロールの節のものを使います。`--site-header--block-size` を渡すJavaScriptは、「[11-7 固定ヘッダー](/layout-practice/sticky-header/)」のものを使います。kiso.cssを使わない場合は、`:root` に書き足します。
