リセットやベーススタイルのように、サイト全体に適用されるグローバルのCSSには、3種類の指定を書きません。クラス1つで上書きできない詳細度の高い指定、レイアウトを一律に決めてほかの要素を壊すプロパティ、そしてフォーカスリングを消すような、アクセシビリティを損なう指定です。

ここでいう「重い指定」は、処理の重さではなく、影響の範囲が広く、後から保守しにくくなる指定のことです。グローバルのCSSは、すべてのコンポーネントの前提になります。一度入り込むと、その影響を打ち消す指定が、各所で必要になります。

## 詳細度の高い指定

ベーススタイルでよく見かけるのが、リンクの色を次のように指定する書き方です。

```css title="🙅‍♂ Not Recommended: 詳細度が0.1.1になるリンクの指定" issue="behavior"
/* 🙅‍♂ Not Recommended */
a:link,
a:visited {
  color: var(--foreground--accent);
}
```

このセレクタの詳細度は、タイプセレクタの `a` と擬似クラスの `:link` を合わせて0.1.1です。この指定がレイヤーの外にあると、コンポーネントの中でリンクの色を変えようとして、`a` のタイプセレクタや `._main-link` のようなクラスを1つ書いても、詳細度0.0.1や0.1.0では勝てません。結局、意味のないセレクタを重ねて詳細度を上げたり、`!important` を付けたりする対応が増えます。

カスケードレイヤーを使えば、この問題は起きません。レイヤーの順番は詳細度より先に比べられるので、`base` レイヤーの指定は、詳細度と関係なく `components` レイヤーの指定に負けます。ベーススタイルは `base` レイヤーに置き、セレクタは素のまま書きます。

```css title="🙆‍♂ Recommended: base レイヤーに素のセレクタで書く"
@layer base {
  a {
    &:any-link {
      color: var(--foreground--accent);
    }
  }
}
```

リンクの判定には、`:link` と `:visited` を並べる代わりに、どちらにも一致する `:any-link` を使います。ベーススタイルの指定は、すべて `base` レイヤーの中に書き、レイヤーの外には置きません。レイヤーの外の指定は、どのレイヤーの指定よりも優先されるので、詳細度を下げてもコンポーネントから上書きできなくなるからです。

レイヤーを使えない環境では、詳細度がそのまま優先順位になります。CMSのテーマのCSSと共存するために自分のCSSもレイヤーなしで書く場合は、ベーススタイルのセレクタを `:where(a:any-link)` のように `:where()` で包み、詳細度を0にします。`:where()` で包む書き方と、`:where()` と `:is()`、`:has()` の詳細度の違いは「[4-2 セレクタで詳細度を設計する](/cascade/selectors/)」で説明します。{/* CMSの節を公開したらリンクする: /operations/cms/ */}

リセットCSSの詳細度にも注意が必要です。ベーススタイルを `:where()` で書いても、リセットCSSがタイプセレクタのまま書かれていると、レイヤーを使わない環境ではリセットのほうが勝ってしまいます。リセットCSSは、kiso.cssのように詳細度が0のものを選びます（「[8-1 壊さないリセット](/reset/kiso/)」）。IDセレクタや `!important` の扱いは、「[4-1 カスケード・詳細度・継承](/cascade/cascade-basics/)」で説明します。

## ほかの要素を壊すプロパティ

`display`、`position`、`margin` のようなレイアウトのプロパティは、色や文字のプロパティと比べて、影響が大きく破壊的です。極端な例ですが、次のような指定があるとします。

```css title="🙅‍♂ Not Recommended: レイアウトのプロパティを要素全体に指定する" issue="behavior"
/* 🙅‍♂ Not Recommended */
div {
  display: block flex;
}

* {
  position: relative;
}
```

すべての `div` に `display: block flex` を指定すると、中身を縦に積むだけのはずの `div` まで、子要素が横に並んでしまいます。全称セレクタに `position: relative` を指定すると、絶対配置の要素はどれも直近の親要素を基準に配置されます。基準にしたかった祖先の要素が、基準にならなくなります。

ここまで極端な例は少ないものの、実務では、次のような指定をときどき見かけます。

```css title="🙅‍♂ Not Recommended: リンクの表示や段落の幅を、要素のセレクタで全体に決める" issue="behavior"
/* 🙅‍♂ Not Recommended */
a {
  display: inline flow-root;
}

p {
  max-inline-size: 40em;
}
```

すべての `a` を `inline flow-root`（`inline-block`）にすると、リンク全体がひとつの箱になり、文章の中のリンクが行をまたいで自然に折り返せなくなります。`p` に最大幅を指定すると、カードの中の説明文やフォームの注意書きのように、別の文脈に置いた段落まで幅が制限されます。どちらも、別の文脈で使うたびに打ち消しの指定が必要になります。

レイアウトに関わるプロパティは、文脈によって、何を指定すべきか、あるいは指定すべきでないかが変わります。ベーススタイルでレイアウトを決めると、ほかの文脈で `unset` や `revert` による打ち消しが頻発し、打ち消し忘れによる不具合も起きやすくなります。レイアウトは、その文脈を知っているコンポーネントやコンポジションの側で指定します。

```css title="🙆‍♂ Recommended: 本文の行の長さは、本文のコンポーネントで決める"
@scope (.scoped.article-body) to (.scoped) {
  p {
    max-inline-size: 40ic;
  }
}
```

この例では、段落の最大幅を、記事の本文を表すコンポーネントの中だけで指定しています。`@scope` で範囲を限っているので、カードの説明文やフォームの注意書きには影響しません。単位の `ic` は全角文字1字分の幅で、`40ic` はおよそ全角40字分です。行の長さを文字数で決めたい本文には、この単位が合います。

「[8-2 ベーススタイルに書くもの](/reset/base-styles/)」で説明した、全称セレクタの `min-inline-size: 0` は、この原則の例外です。`min-inline-size` の初期値 `auto` は、フレックスアイテムとグリッドアイテム以外では、もともと0として扱われます。そのため、ほとんどの要素のレイアウトは変わらず、変わるのは、はみ出しの原因になっていたアイテムの最小幅だけです。また、リセットCSSでデフォルトの余白を消すような指定は、最低限の前提をそろえるための「平坦化」で、新しいレイアウトを足す指定とは区別します。

## アクセシビリティを損なう指定

グローバルのCSSで最も避けたいのは、アクセシビリティを損なう指定です。典型的な例が、フォーカスリングを消す `outline: none` です。

```css title="🙅‍♂ Not Recommended: フォーカスリングを消す" issue="behavior"
/* 🙅‍♂ Not Recommended */
:focus {
  outline: none;
}
```

フォーカスリングを消すと、キーボードで操作するユーザーは、いまどこにフォーカスがあるのか分からなくなります。クリックしたときにリングが出るのを嫌って書かれることが多い指定ですが、現在のブラウザは、主に `:focus-visible` のとき（キーボードで操作したときなど）にだけリングを表示します。マウスでクリックしたボタンにリングが出続ける状況は、基本的に起きません。リングの見た目を変えたいなら、消すのではなく、8-2で説明した二重リングのように定義し直します。

なお、kiso.cssは、`tabindex="-1"` を持つ要素がフォーカスされたときだけ、`outline` を消しています。スキップリンクの移動先の `main` のように、プログラムでフォーカスを移した要素に、リングが出ないようにするための例外です。

リストのマーカーを消すときの `list-style: none` にも注意が必要です。SafariとVoiceOverの組み合わせでは、`list-style: none` を指定した `ul` や `ol` が、リストとして読み上げられないことがあります。マーカーは、`list-style-type` に空の文字列を指定して消します。

```css title="🙅‍♂ Not Recommended: list-style: none でマーカーを消す" issue="behavior"
/* 🙅‍♂ Not Recommended */
ul {
  list-style: none;
}
```

```css title="🙆‍♂ Recommended: 空の文字列を指定してマーカーを消す"
@layer base {
  ul,
  ol,
  menu {
    list-style-type: "";
  }
}
```

`role="list"` を付けて、リストであることを伝え直す方法もあります。しかし、すべてのリストに属性を足すのは冗長です。`list-style-type: ""` なら、CSSだけで済みます。kiso.cssを使っていればこの指定は済んでいるので、コンポーネントで書き直す必要はありません。

行の高さを小さくしすぎる指定も避けます。コーディングしやすいからと、ベーススタイルで `line-height: 1` にする例がありますが、改行したときに行が重なって読めなくなることがあります。デザイン上は1行でも、内容の変更や画面の幅、機械翻訳によって改行は起こりえます。ベースの行の高さは1.5以上にして、各要素に継承させます。行の高さの決め方は、「[14-3 行の高さとハーフレディング](/typography/line-height/)」で説明します。

## color-schemeの指定

最後に、`color-scheme` にも注意が必要です。ダークモードに対応していないのに、`:root` に `color-scheme: light dark` を指定しているサイトがあります。海外製のリセットCSSやフレームワークから、そのまま持ち込まれていることもあります。

```css title="🙅‍♂ Not Recommended: ダークモードに対応していないのに color-scheme を指定する" issue="behavior"
/* 🙅‍♂ Not Recommended */
:root {
  color-scheme: light dark;
}
```

この指定があると、ユーザーがダークモードを使っているとき、ブラウザのデフォルトの背景色や文字色、フォームの部品などが暗い配色になります。暗くなるのは、サイトの側で色を指定していない部分だけです。背景色だけを白に指定して文字色を指定していないと、文字色だけが明るい色に切り替わり、背景色との区別がつかず、文字を読めなくなることがあります。ダークモードに対応しないなら、この指定は取り除きます。

反対に、暗い背景だけのサイトでは、HTMLに `<meta name="color-scheme" content="dark">` を書いておきます。ユーザーの外観モードにかかわらず、スクロールバーなどのブラウザの部品も暗い見た目になり、体験が一貫します。明るい背景だけのサイトでは、何も指定しなくてかまいません。ダークモードに対応する場合は、`color-scheme` の指定と、両方のモードの色の定義を必ずセットで用意します。色の定義の仕方は、「[15-4 ダークモード](/color-media/dark-mode/)」で扱います。

## グローバルのCSSを変えるときの確認

グローバルのCSSの変更は、すべてのページに影響します。レビューでは、ベーススタイルが `base` レイヤーの中にあるかを確認します。レイヤーを使えない環境なら、セレクタが `:where()` で包まれているかを確認します。あわせて、レイアウトのプロパティが要素全体に指定されていないか、`outline` やリストのマーカーの消し方に問題がないかも確かめます。

AIにベーススタイルを書かせた場合も同じです。AIは、レイヤーの外に `a:hover` のような詳細度の高いセレクタを書いたり、`outline: none`、`list-style: none` を含めたりしがちです。生成されたコードは、この節の3つの観点で必ず確認します。レビューの進め方は、「[19-2 レビューの進め方](/operations/review/)」で説明します。
