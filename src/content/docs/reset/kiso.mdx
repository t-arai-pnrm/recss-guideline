リセットCSSには、私が作って公開しているkiso.cssを使い、`reset` レイヤーに読み込みます。kiso.cssは、すべてのセレクタの詳細度を0にし、和文向けの初期値を入れ、ブラウザの便利なデフォルトは残すという3つの方針で作っています。目標は「リセットCSSがなくても、レイアウトが大きく崩れない」ことです。

ほかのリセットCSSを使う場合も、以下は選ぶときの基準になります。

## リセットCSSは何を上書きするのか

作者がCSSを書いていない要素の見た目は、CSSの初期値とブラウザのデフォルトスタイル（UAスタイルシート）の2層で決まります。初期値は、仕様がプロパティごとに定めた値で、`display` なら `inline` です。それでも `div` がブロックとして並ぶのは、UAスタイルシートが `div { display: block; }` を指定しているからです。作者のCSSは、この2層の上にもう1層を重ねて値を変えます。リセットCSSは作者のCSSの最初の1枚で、UAスタイルシートの値のうち、ブラウザごとに異なるものや毎回変えるものを上書きします。

リセットCSSの考え方は、どこまで上書きするかをめぐって変わってきました。2000年代半ばには、`*` ですべての要素の `margin` と `padding` を0にする書き方が広まりました。2006年のYUI Resetと2008年のEric MeyerのReset CSSは、`*` を使わずに要素を列挙し、消す範囲を絞っています。2010年代はじめのNormalize.cssは、役に立つデフォルトスタイルは残し、ブラウザ間の差と不具合だけを直す方針に転じました。kiso.cssは、この残す方針を引き継いでいます。

本書では、初期値、ブラウザのデフォルトスタイル、リセットCSSの値、ベーススタイルの値をまとめて「デフォルト値」と呼んでいます（「[2-3 保守しやすさを最優先にする](/design-mindset/maintainability/)」）。リセットCSSの値は、このうち作者のCSSの側で最初に決まるデフォルト値で、ベーススタイルやコンポーネントはその上に書きます。

## リセットCSSが土台を壊すとき

リセットCSSはすべての要素に適用されるので、その性質はサイト全体に及びます。よくある問題は、消しすぎること、詳細度が高いこと、欧文を前提にしていることの3つです。

```css title="🙅‍♂ Not Recommended: 便利なデフォルトまで一律に消すリセット" issue="behavior"
/* 🙅‍♂ Not Recommended */
* {
  margin: 0;
  padding: 0;
}

input,
button {
  appearance: none;
}

ul {
  list-style: none;
}
```

このリセットでは、ボタンの `padding` まで消えるので、ボタンを置くたびに余白を指定し直すことになります。`input` への `appearance: none` はさらに危険で、チェックボックスやラジオボタンの見た目がなくなり、画面から消えてしまいます。`list-style: none` には、SafariのVoiceOverで、リストとして読み上げられないことがあるという問題もあります。これは「[8-3 グローバルに書いてはいけないもの](/reset/global-pitfalls/)」で説明します。

リセットの詳細度にも問題があります。`svg:not([fill])` のように、タイプセレクタと擬似クラスを組み合わせたリセットの詳細度は0.1.1です。この指定があると、アイコンの色を `.icon` のようなクラス1つでは上書きできません。私も以前、使っていたリセットCSSのこの指定のせいで、アイコンの色を上書きできませんでした。

日本語のサイトでは、もうひとつ問題があります。海外で作られたリセットCSSの多くは欧文の組版を前提にしていて、和文と英数字の間隔や約物の詰め、禁則の扱いを含んでいません。そのため、日本語のサイトを作るたびに、同じ調整を足すことになります。

## kiso.cssの設計

kiso.cssは、こうした問題を避けるために作ったリセットCSSです。名前は日本語の「基礎」から取っています。名前のとおり、リセットは基礎の部分だけにとどめ、破壊的な指定はしません。

何を消して何を残すかは、「毎回指定し直すことになるか」で決めています。リンクの下線やリストのマーカーは、デザインの上でほぼ毎回消すのでリセットします。見出しの太さやボタンの `padding` は、消しても結局また指定することになるので残します。

それぞれの指定には、なぜそうするのかを英語のコメントで書いています。リセットCSSは中身を知らないまま使われがちですが、土台の挙動を決めるものです。導入する前に、一度ソースを読んでおくことをおすすめします。

kiso.cssは、レイヤーの順序を宣言したうえで、`@import` で `reset` レイヤーに読み込みます。`reset` は、トークンだけを置く `tokens` の次に弱いレイヤーです。そのため、ベースやコンポーネントの指定は、詳細度とは関係なくリセットより優先されます。

```css title="🙆‍♂ Recommended: kiso.cssを reset レイヤーに読み込む"
@layer tokens, reset, base, vendors, compositions, pages, components, patterns, utilities;
@import url("kiso.css") layer(reset);
@import url("./base/generic.css") layer(base);
```

CMSのように、レイヤーに入っていない外部のCSSと共存する環境では、レイヤーを使わないことがあります。判断の基準は「[4-3 カスケードレイヤーで順位を決める](/cascade/layers/)」で説明します。その場合も、kiso.cssは `@import url("kiso.css");` とレイヤーなしで読み込み、ほかのCSSより前に置けば成り立ちます。`!important` を付けた一部の指定を除き、詳細度が0なので、後から書いた指定に負けるからです。

## 詳細度を0にする

kiso.cssは、ほとんどのセレクタを `:where()` で包んでいます。`:where()` は、中に書いたセレクタの詳細度を0にする擬似クラスです。リセットの指定はどれも詳細度が0になるので、タイプセレクタ1つ、クラス1つで上書きできます。

```css title="🙆‍♂ Recommended: リストのリセットを :where() で包み、詳細度を0にする"
:where(ul, ol, menu) {
  padding-inline-start: unset;
  list-style-type: "";
}
```

kiso.cssが `:where()` を使うのは、カスケードレイヤーを導入できない環境でも、上書きしやすくするためです。本書のようにレイヤーを使う場合は、レイヤーの順序と `:where()` の両方で、リセットを弱くしていることになります。一方、プロジェクトで書くベーススタイルは配布物ではないので、レイヤーを使う場合は `base` レイヤーに素のセレクタで書きます（「[8-2 ベーススタイルに書くもの](/reset/base-styles/)」）。

反対に、リセットCSSが `:where()` を使っていないと、ベーススタイルを `:where()` で書いても、レイヤーを使わない環境では、タイプセレクタのまま書かれたリセットのほうが詳細度で勝ちます。その結果、ベーススタイルが打ち消されます。リセットCSSを選ぶときは、詳細度が0かどうかを必ず確認します。

`:where()` で包んでいない指定は3種類です。全称セレクタで指定した `box-sizing: border-box`、`::placeholder` のような擬似要素、`!important` を付けた `[hidden]` と `[tabindex="-1"]:focus` の指定です。全称セレクタは、もともと詳細度が0です。擬似要素は、`:where()` の中に書けません。`!important` は、`:where()` で包んだ、閉じた状態のダイアログとポップオーバーを隠す指定にも付けています。`hidden` 属性を持つ要素や閉じたダイアログが、ほかのスタイルで `display` を指定されても、表示されてしまわないようにするためです。ページ内検索で開けるように、`hidden="until-found"` はこの対象から外しています。

`!important` を付けた宣言では、レイヤーの優先順位が逆転します。そのため、`reset` レイヤーの `!important` は、`reset` より後に宣言した `base` 以降のレイヤーの `!important` より強くなります。`reset` より前の `tokens` に同じ要素と同じプロパティの `!important` があれば、そちらが `reset` より強くなりますが、`tokens` にはトークンの定義だけを置く運用なので、通常は起きません。仕様上の順位と、本書の運用上の前提は別のものです。この仕組みは「[4-1 カスケード・詳細度・継承](/cascade/cascade-basics/)」で説明します。「必ず隠す」という目的には、この強さが合っています。

同じ強さは、`[tabindex="-1"]:focus` の `outline: none !important` にもあります。`tabindex="-1"` を持つ要素にフォーカスを移すと、`:focus-visible` に一致していても `outline` が消え、`base` や `components` のレイヤーに `!important` を付けて書いても戻せません。影響の範囲は「[8-3 グローバルに書いてはいけないもの](/reset/global-pitfalls/)」で説明します。

## 和文向けの初期値を入れる

kiso.cssは、日本語のサイトのための初期値を `:root` に入れています。どれも継承されるプロパティなので、`:root` に1回書けば文書全体に適用されます。

```css title="🙆‍♂ Recommended: 継承する和文向けの初期値を、:root に1回だけ書く"
:where(:root) {
  text-spacing-trim: trim-start;
  text-autospace: normal;
  line-break: strict;
  overflow-wrap: anywhere;
}
```

`text-spacing-trim: trim-start` は、括弧や句読点のような約物が隣り合ったときのアキと、行頭の約物のアキを詰めます。`text-autospace: normal` は、和文と英数字の間に小さなアキを入れます。kiso.cssを公開した2025年6月の時点では、初期の挙動がブラウザによって異なっていたので、値を明示しました。本書の原稿で、和文と英数字の間にスペースを手で入れないのも、この指定に任せるためです。

`line-break: strict` は、小書きの仮名（「ッ」や「ゃ」など）の前で改行しない、厳格な禁則を適用します。行末に余白が出やすくなる面はありますが、読み誤りを防ぐほうを優先しています。`overflow-wrap: anywhere` は、URLや長い英単語のように、途中に折り返せる位置がない文字列も途中で折り返します。`break-word` ではなく `anywhere` を選んでいるのは、要素の最小幅の計算にも反映され、フレックスやグリッドの中ではみ出すのも防げるからです。

`text-spacing-trim` に対応しているのは、Chrome系のブラウザだけです。対応していないブラウザでは指定が無視されるだけで、表示が崩れることはありません。組版の指定は、こうしたプログレッシブ・エンハンスメントとして使いやすい機能の代表です。

要素ごとの指定もあります。日本語の文書（`:lang(ja)`）では `em` を太字にし、`i`、`cite`、`em`、`dfn`、`address` の斜体を解除しています。日本語では強調を太字で表すのが一般的で、斜体はあまり使わないからです。反対に、`pre`、`time`、入力欄には `text-autospace: no-autospace` を指定しています。等幅のそろいが崩れたり、日付の表記や入力中の文字にアキが入ったりするのを防ぐためです。

一方で、本文のプロポーショナル詰め（`palt`）やカーニング、`word-break: auto-phrase` は入れていません。本文はベタ組みのほうが読みやすく、これらは見出しなどに限って指定するものだからです。見出しの組版はベーススタイルで指定します。値の選び方は、「[14-2 和文組版を整える](/typography/japanese-typesetting/)」で説明します。

## ブラウザの便利なデフォルトは残す

kiso.cssは、ブラウザのデフォルトスタイルのうち、役に立つものを残します。見出しの太さと大きさ、ボタンの `padding`、ダイアログの `margin` などです。ダイアログの `margin: auto` は、位置を `inset: 0` で四辺に固定し、幅と高さを `auto` 以外にすれば、中央に配置できます。モーダルのダイアログは、ブラウザのデフォルトスタイルが四辺の `inset` を0にし、幅と高さを `fit-content` にしているので、`margin: auto` が残っていれば画面の中央に置かれます。消すとかえって不便です。一方、ポップオーバーの `margin` は、アンカーポジショニングで配置するときの邪魔になるので、リセットしています。アンカーを使わずにポップオーバーを画面の中央に置くときは、`margin: revert` で戻します（「[7-11 アンカーポジショニングの基礎](/layout/anchor-basics/)」）。

フォームの部品には `1px` の実線の枠線を付け、枠線の色は文字色に合わせています。文字色やフォントは、親要素から継承させています。スタイルを当てていない状態でも入力欄の範囲が分かり、デザインで枠線を付けるときも色を変えるだけで済みます。枠線を消したいときは、`border: none` ではなく `border-color: transparent` にします。強制カラーモードでは透明な枠線にも色が付くので、背景色が消えても部品の範囲が分かるからです。強制カラーモードへの対応は、「[15-5 強制カラーモードとコントラスト](/color-media/forced-colors/)」で説明します。

チェックボックスやラジオボタンの `appearance` には触れていません。色を変えたいだけなら `accent-color` で足ります。見た目を作り直す場合だけ、その部品に個別に `appearance: none` を指定します。フォーム部品の作り方は、「[17-7 フォーム部品](/interaction/forms/)」で扱います。

反対に、kiso.cssがリセットしたスタイルを使いたい場面もあります。CMSで入力する記事の本文のように、リストのマーカーを表示したい場所です。この場合は値を書き直さず、`revert` でブラウザのデフォルトに戻します。次の例の本文エリアのクラス `wysiwyg` と `@scope` の書き方は、「[19-5 CMSのWYSIWYG本文にスタイルを当てる](/operations/wysiwyg/)」で説明します。

```css title="🙆‍♂ Recommended: 本文の中だけ、リストのマーカーを戻す"
@scope (.wysiwyg) {
  ul,
  ol {
    padding-inline-start: revert;
    list-style-type: revert;
  }
}
```

`revert` は、サイトのCSSの指定を取り除いた値に戻すキーワードです。ユーザーのスタイルがない一般的な環境では、ブラウザのデフォルトスタイルの値に戻ります。`disc` や `40px` のような値を覚えて書き直す必要がなく、「デフォルトに戻したい」という意図もコードに残ります。マーカーを表示する場所がなくならないように、`padding-inline-start` も一緒に戻しています。

## kiso.cssの値を変えたいとき

kiso.cssの初期値がプロジェクトに合わないときは、kiso.cssのファイルを書き換えず、`base` レイヤーで上書きします。たとえばkiso.cssは、`line-height` を1.5にしています。WCAGの達成基準1.4.12は、ユーザーが行間を1.5倍に変えても内容が損なわれないことを求めるもので、初期値を1.5にする要件ではありません。達成基準1.4.8（AAA）は、段落内の行間を1.5倍以上にすることを求めるので、1.5はこの基準を満たす値です。プロジェクトのトークンで1.6にしたいなら、ベーススタイルの `:root` で指定し直します。`base` レイヤーは `reset` レイヤーより強いので、詳細度を気にする必要はありません。

```css title="🙆‍♂ Recommended: kiso.cssの値は base レイヤーで上書きする"
@layer base {
  :root {
    line-height: var(--leading--normal);
  }

  h1 {
    margin-block: unset;
  }
}
```

`h1` の `margin-block` と `font-size` は、kiso.cssがあえて指定しているものです。セクションの中に置いた `h1` のデフォルトスタイルが、ブラウザの変更で変わったことへの対応です。ただし、余白を `gap` で管理するプロジェクトでは不要なので、上の例のようにベーススタイルで打ち消します。

本体を書き換えずにおけば、kiso.cssを新しいバージョンに更新しても、プロジェクトでの変更は失われません。変更点がベーススタイルに集まるので、そのプロジェクトがリセットの何を変えているのかも一目で分かります。ベーススタイルに何を書くかは、「[8-2 ベーススタイルに書くもの](/reset/base-styles/)」で説明します。
