デザインを再現するときに目指すのは、デザインカンプとの1pxの一致（ピクセルパーフェクト）ではなく、デザインの意図が損なわれないことです。情報の優先順位、要素のまとまり、全体の雰囲気が、どの環境で見ても伝わり、内容がどれだけ変わっても読めて操作できる状態を目指します。

そのためには、カンプを完成した設計図ではなく、デザイナーとの対話の出発点として扱います。デザイントークンを共通の言葉にし、カンプからは読み取れない意図を確かめ、実装の側からよりよい方法を提案します。

## ピクセルパーフェクトが成り立たない理由

クライアントワークでは、「デザインカンプをピクセルパーフェクトに再現してほしい」と求められることがあります。ピクセルパーフェクトとは、デザイナーが作った静的なカンプと、ブラウザでの表示を、1pxのずれもなく一致させることです。デザイナーが1pxの差にこだわって作ったデザインを、そのとおりに実装したいと考えるのは自然なことです。

しかし、Webページの表示は、ビューポートの幅、OSが選ぶフォント、ユーザーの文字サイズの設定のように、実装者が決められない多くの条件に左右されます。ある環境でカンプと一致しても、それはその環境での一致にすぎません。

カンプの画像をブラウザの表示に重ねて、ずれを確かめるChromeの拡張機能もあります。余白の取り違えを見つけるには便利な道具で、私も実装の確認に使っています。ただし、それはカンプと同じ幅、同じ文字量、同じ文字サイズで見たときの確認にすぎません。重ねてぴったり合ったとしても、ほかの条件での見え方は保証されません。

そのため、何をもって再現できたとするかは、1pxの一致ではなく、デザイナーと合意した意図で決めます。表示を左右する条件と、どの環境でも合格点を取るための書き方は、「[1-1 CSSはブラウザへの「提案」である](/principles/browser-suggestion/)」で説明しています。

## デザインカンプは対話の出発点

デザインカンプは、特定の画面の幅で、特定の文字量のときの見た目を切り取った静止画です。見出しが3行になったら、ボタンの文言が長くなったら、カードの数が増えたらどうなるのかは、カンプだけでは分かりません。

FigmaのAuto Layoutを使ったカンプなら、内容の量が変わったときの振る舞いを、ある程度は読み取れます。それでも、ユーザーが文字サイズを変えたときの見え方や、カンプのない幅での配置、ホバーやフォーカスのときの細かな振る舞いまでは表しきれないことが多く、実装の段階で決めることになります。実際にブラウザで動かしてみると、カンプでは気にならなかった余白が広すぎるように感じられることもあります。

これはデザイナーの仕事が不十分だからではありません。静止画のカンプと、条件によって変わるWebページの間には、必ず差があります。そのため、カンプを完成した設計図として書き写すのではなく、デザイナーと対話を始めるための出発点として扱います。

## デザイントークンを共通の言葉にする

デザイナーと実装者が対話するには、共通の言葉が要ります。その言葉になるのが、色、文字サイズ、余白といったデザインの値に名前を付けたデザイントークンです。トークンがあれば、「ここの余白は16pxと18pxのどちらか」ではなく、「ここの余白に合うトークンはどれか」を話し合えます。

カンプの値とトークンの値が少しずれているとき、カンプに合わせて、トークンにない値を書きたくなることがあります。たとえば、余白を8の倍数で決めているのに、カンプと1pxまで合わせようとして23pxと書く場合です。しかし、トークンは、サイト全体の一貫性を保つために決めたものです。1か所の見た目を合わせる目的で、トークンにない値を書くと、その一貫性が崩れます。トークンに従った結果として生じるわずかなずれは、受け入れるほうがサイト全体の品質を保てます。

Tailwind CSSは、決められた値の中からクラスを選んで書くので、トークンにない値が紛れ込みにくい道具です。素のCSSでも、トークンをカスタムプロパティとして定義し、値を直接書かずにトークンを参照すれば、同じ規律を保てます。トークンの名前の付け方と層の分け方は「[10-4 デザイントークン](/components/design-tokens/)」で説明します。

## 意図を理解して実装を提案する

トークンを共通の言葉にしたうえで、次に確かめるのは、その値が選ばれた意図です。なぜこの余白なのか、なぜこの色なのか、なぜこの配置なのかが分かると、カンプの値をそのまま書くよりも適した書き方を選べることがあります。

たとえば、余白のトークンは `16px` のように `px` で定義されていることが多いと思います。しかし、段落と段落の間の余白の意図が、前の段落との区切りを示すことであれば、余白は文字の大きさに合わせて変わるほうが意図に沿います。ユーザーがブラウザの文字サイズを大きくすると、文字は大きくなるのに、`px` で決めた余白は16pxのままなので、段落の区切りが相対的に狭く見えるからです。

```css title="🙅‍♂ Not Recommended: 段落の間の余白をカンプの値で固定する" issue="convention"
/* 🙅‍♂ Not Recommended */
._description {
  & > * + * {
    margin-block-start: 16px;
  }
}
```

```css title="🙆‍♂ Recommended: 段落の間の余白を、文字サイズの設定に合わせて rem で指定する"
._description {
  & > * + * {
    margin-block-start: calc(var(--spacing--sm) / 16 * 1rem);
  }
}
```

トークンの値はそのまま使い、単位だけを `rem` に変えています。`rem` で指定した余白は、ユーザーが文字サイズを大きくすると、文字と同じ割合で広がります。余白のトークンを単位なしの数値で定義し、使う場所で単位を選ぶ理由は「[10-4 デザイントークン](/components/design-tokens/)」で説明します。

デザイナーが行の高さを単位にして余白を決めている（バーティカルリズム）なら、ルート要素の行の高さを基準にする `rlh` 単位を使う方法もあります。`1rlh` は、ルート要素の `line-height` で計算した1行の高さです。

<Baseline id="rlh" />

```css title="🙆‍♂ Recommended: 段落の間の余白を1行の高さにそろえる"
._description {
  & > * + * {
    margin-block-start: 1rlh;
  }
}
```

どちらを選ぶかは実装者だけでは決められないので、意図の理解と提案をデザイナーに伝えて確かめます。たとえば、「この16pxの余白は段落の区切りだと理解しています。文字サイズの設定に合わせて変わるように、`rem` で実装してもよいでしょうか。ユーザーが文字を大きくしても、区切りの見え方が保たれます」と相談します。デザインの意図を理解したうえで、技術の面からよりよい実装を提案することは、実装者の専門性が生きる仕事です。

## 言葉にされていない前提をすり合わせる

共通の言葉があっても、言葉にされていない前提は残ります。カンプでは表しきれない部分を「あとはよしなに」と任されることは珍しくありません。このとき、実装者は意図を推測して実装しますが、その推測がデザイナーの考えと一致する保証はなく、食い違えば手戻りになります。

「よしなに」と言ったデザイナーにも、多くの場合、画面が狭くなればこの要素は折り返すはずだ、この画像は幅に合わせて伸び縮みするはずだ、といった想定があります。一方で、Figmaのようなデザインツールは値を固定の数値で表すので、デザイナーは固定の幅で並ぶと考え、実装者は幅に合わせて伸び縮みすると考える、といった食い違いが起きやすくなります。

そのため、こうだろうという推測で進めず、前提を言葉にして確かめます。実装の前に確かめておきたい項目は「[3-2 実装の前にデザイナーと確かめること](/design-reproduction/designer-questions/)」にまとめています。

## 実装はデザイナーとの協業

コーディングは、完成したカンプを書き写す作業ではありません。デザイントークンという共通の言葉を使い、デザイナーとの対話を重ねて、静止画のデザインを、さまざまな環境で動くWebページとして完成させる協業です。

この協業で実装者が担うのは、デザインの意図を理解し、技術の面からよりよい実装を提案することと、あいまいな指示の裏にある意図を確かめ、認識の食い違いをなくすことです。指示を待つのではなく、デザイナーと並んでよりよいユーザー体験を作る立場で、実装に関わることを勧めます。
