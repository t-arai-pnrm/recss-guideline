本書は、スタイルを素のCSSで書いています。ここでいう素のCSSは、CSSファイルにWeb標準の構文だけで書いたスタイルのことで、CSS-in-JSも、HTMLのクラス属性にユーティリティを並べるTailwind CSSも、Sassの独自の構文も使いません。その理由の要点は「[素のCSSで書く理由](/introduction/why-plain-css/)」にまとめました。この付録では、ほかの道具と比べた詳しい根拠を説明します。

CSS-in-JSやTailwind CSSは、とくに大規模なチームで、名前の衝突やCSSの肥大化を防ぐ有効な道具です。しかし、どの道具を選んでも、部品の分け方や値の渡し方を決める設計の判断はなくなりません。本書が題材にするWebサイト制作では、その判断を `@scope`、カスケードレイヤー、カスタムプロパティ、`:has()` のような擬似クラスで表すほうが単純で、静的なサイトとCMSのどちらにも同じ書き方を使えます。

比べる論点には、第4章「[カスケードを制御する](/cascade/)」と第10章「[コンポーネントとカスタムプロパティ](/components/)」で説明する `@scope`、カスケードレイヤー、公開プロパティが出てきます。それらの章を読んでから戻ると、比較の妥当性を自分で判断しやすくなります。

## CSS-in-JSとStyleXの仕組み

CSS-in-JSは、スタイルをJavaScriptの中に書く手法の総称です。styled-componentsのような多くのライブラリは、一意なクラス名をスタイルから生成して要素へ付けます。そのため、書く人がクラス名の衝突を心配する必要はありません。スタイルをマークアップと同じファイルに置けることも、よく挙げられる利点です。

Metaが開発したStyleXは、CSS-in-JSのなかでも、CSSをビルドの段階で生成する道具です。スタイルは `stylex.create()` に渡すJavaScriptのオブジェクトとして書き、プロパティと値の組み合わせごとに、ハッシュ化したクラス名を持つCSSへ変換されます。`color: 'blue'` のような同じ組み合わせは、どの部品で書いても同じ1つのクラスになるので、アプリケーションが大きくなってもCSSの量は頭打ちになります。生成されるクラスは、書いたスタイルから自動で作られるTailwind CSSのユーティリティのようなものです。

Metaは、StyleXを作った理由として、自社のサービスの規模でCSSを配信した結果、バンドルをまたいだ衝突、スタイルシートどうしの依存関係の管理、競合するルールの調整に苦労したことを挙げています。多くの開発者が同じアプリケーションの部品を書く環境では、名前の付け方や読み込みの順番を、人の注意だけで守り続けるのは困難です。名前の衝突やコードの肥大化を仕組みで防げる点で、こうした道具は大規模なチームに向いています。

## 型安全性はどこまで利点になるか

CSS-in-JSの利点として、型安全性もよく挙げられます。StyleXも、型安全なスタイルの記述を特徴に掲げています。TypeScriptでスタイルの値を型として扱えば、誤った値をエディタやビルドの段階で見つけられる、という考え方です。

ただし、この利点がどこまで決定的かには、疑問の余地があります。CSSそのものが、不正な値を受け付けない型付きの言語の性質を持っているからです。各プロパティは受け付ける値の文法を仕様で定めていて、`color: 16px` のように文法に合わない宣言を、ブラウザは解釈の段階で無視します。無視された宣言の代わりには、同じ要素に当てはまるほかの宣言が使われ、それもなければ継承した値か初期値になります。

2つの検査には違いもあります。ブラウザは無効な宣言を無視するだけで、誤りを知らせません。一方、TypeScriptの型検査は、コードを書いている段階で誤りを示します。

素のCSSでも、Stylelintのルール `declaration-property-value-no-unknown` を使えば、`color: 16px` のような値を書いた時点で見つけられます。本書のStylelintの設定でも、このルールを有効にしています（[19-1 Stylelintでルールを守る](/operations/stylelint/)）。

型の検査で誤りを見つけにくいのは、カスタムプロパティを通して渡す値です。登録していないカスタムプロパティはどんな値でも受け取り、`var()` で使う時点で初めて有効かどうかが決まります。Stylelintも、`var()` を含む値は検査しません。

StyleXには、部品が外から受け取ってよいプロパティと値の範囲を型で制限する仕組みもあり、部品の境界で値を検査する点では、素のCSSより厳密です。CSSでこれに近いことをするには、`@property` でカスタムプロパティに型を登録し、型に合わない値を無効にします（[10-5 公開プロパティと内部プロパティ](/components/custom-properties/)）。

## 道具を替えても残る設計の判断

いちばん大きな論点は、こうした道具を選んでも、アーキテクチャの設計からは逃れられないということです。CSS-in-JSは名前の衝突を仕組みで防ぎますが、スタイルのオブジェクトをどのファイルに置き、部品の間でどう共有し、どのスタイルを外から渡せるようにするかは、別に決める必要があります。CSSのアーキテクチャが、JavaScriptのアーキテクチャに置き換わるだけです。

StyleX自身も、設計の方針を持っています。要素のスタイルはその要素に付けたクラスだけで決めるという方針を掲げ、子孫セレクタのように離れた場所から当てるスタイルを避けるよう求めています。道具を選ぶことは、その道具が前提にしている設計を選ぶことでもあります。

命名の悩みが道具で小さくなっても、部品の範囲や外側の余白を決める判断が残ることは、「[2-1 CSS設計のマインドセット](/design-mindset/what-is-css-design/)」で説明しています。こうした判断は、スタイルをCSSファイルに書いても、JavaScriptのオブジェクトに書いても、同じように残ります。

判断が残るなら、選ぶのはそれを表す手段です。素のCSSなら、部品の範囲は `@scope` で、ベースとコンポーネントとユーティリティの優先順位はカスケードレイヤーで、外から変えてよい値はカスタムプロパティで表せます。状態による見た目の変化は、擬似クラスで表せます。どれもブラウザの仕組みなので、特定のフレームワークやビルドの道具に依存しません。

## スコープとグローバルなスタイル

CSS-in-JSの多くは、生成した一意なクラス名を付けて、スタイルが当たる範囲を部品の中に限ります。Web ComponentsのShadow DOMは、さらに強く分けます。ページに書いた通常のセレクタはShadow DOMの内側の要素に当たらず、境界を越えるのは、主に `color` やカスタムプロパティのような継承する値です。

一方で、Webサイトには、部品の外から当てたいスタイルもあります。リセットCSSや、本文の文字の大きさ、行の高さ、リンクの色のようなベースのスタイルは、ページ全体に当てたいものです。グローバルなスタイルとスコープを持つスタイルをどう混ぜるかは、CSSの設計でずっと続いてきた課題です。Shadow DOMで境界を閉じれば、部品のスタイルは外へ漏れませんが、ページのリセットCSSやユーティリティも内側に届かなくなります。

スコープを作るのに、ハッシュ化したクラス名が必須とは限りません。親のクラスを1つ決めて、その中にCSSをネストして書くだけでも、多くの場面で十分なスコープを作れます。

本書は、これを `@scope` でもう一歩進めます。ネストだけでは、入れ子にした別の部品の中の同じ要素にもスタイルが当たるからです。`@scope (.scoped.<名前>) to (.scoped)` と書けば、部品のセレクタは、ルートから、入れ子になった別の部品のルートの手前までにしか当たりません。

`@scope` は、部品のスタイルが外の要素に当たるのを防ぎますが、外のスタイルが中に入ってくるのは防ぎません。本書は、この性質をグローバルなスタイルとの共存に使います。リセットCSSとベースのスタイルは部品の中まで届かせ、それらと部品のスタイルの優先順位はカスケードレイヤーで決めます（[4-3 カスケードレイヤーで順位を決める](/cascade/layers/)）。

フレームワークが、部品のファイルにスコープ付きのCSSを書く仕組みを標準で備えていることもあります。Vueの単一ファイルコンポーネントの `<style scoped>` や、Astroのコンポーネントの `<style>` は、書いたセレクタに部品ごとの属性やクラスを足し、その部品のHTMLにだけ当たるように変換します。この仕組みを使う現場でも、本書の設計の原則と、公開プロパティで値を受け渡す方法はそのまま使えます。子要素の `._kebab`、内部プロパティの `--_prop`、カスケードレイヤー、コンテナ名の `--scoped` といった規約も残せます。

ただし、`@scope` の行を消してフレームワークのスコープに任せるだけでは、移植は終わりません。`@scope` を外すと、`:scope` や `&:is(:scope[data-variant="featured"] *)` は部品のルートを指さなくなるので、ルートのクラスを使ったセレクタに書き換えます。さらに、スタイルが当たる範囲の下限も、フレームワークごとに本書と違います。入れ子にした子の部品のルートと、スロットで受け取る内容の扱いは、使うフレームワークの仕様に合わせて書き直します。

Vueの例で、下限の違いを確かめます。一覧の部品の中に、カードの部品を入れ子にします。

```vue title="NewsList.vue（親の部品）"
<template>
  <ul class="list">
    <li><NewsCard /></li>
  </ul>
</template>

<style scoped>
.list { display: block grid; gap: 16px; }
.card { border: 1px solid; }
.title { font-weight: bold; }
</style>
```

```vue title="NewsCard.vue（子の部品）"
<template>
  <article class="card">
    <h3 class="title">…</h3>
  </article>
</template>

<style scoped>
.card { padding: 16px; }
</style>
```

Vueは、`<style scoped>` のセレクタの末尾に部品ごとの `data-v-…` 属性のセレクタを足し、その部品のテンプレートの要素に同じ属性を付けます。Vueの公式ドキュメントは、子の部品のルート要素には親と子の両方のscoped CSSが当たると説明しています。親が子のルートを配置できるようにするための仕様です。変換後のCSSとHTMLは、次のような形になります（属性の値は説明のための仮のものです）。

```css title="Vueが変換した後のCSS（イメージ）"
.list[data-v-1111] { display: block grid; gap: 16px; }
.card[data-v-1111] { border: 1px solid; }
.title[data-v-1111] { font-weight: bold; }
.card[data-v-2222] { padding: 16px; }
```

```html title="Vueが変換した後のHTML（イメージ）"
<ul class="list" data-v-1111>
  <li data-v-1111>
    <article class="card" data-v-2222 data-v-1111>
      <h3 class="title" data-v-2222>…</h3>
    </article>
  </li>
</ul>
```

親の `.title[data-v-1111]` は、子の部品の中の見出しには当たりません。一方、親の `.card[data-v-1111]` は、子の部品のルートの `<article>` に当たり、枠線が付きます。Vueでは、子の部品のルートまでが親のスコープに入ります。

本書の書き方では、同じ入れ子は次のようになります。

```css title="🙆‍♂ Recommended: 入れ子にした部品のルートは、下限で親のスコープから外れる"
@scope (.scoped.news-list) to (.scoped) {
  :scope {
    display: block grid;
    gap: 16px;
  }

  article {
    border: 1px solid;
  }

  ._title {
    font-weight: var(--font-weight--bold);
  }
}

@scope (.scoped.news-card) to (.scoped) {
  :scope {
    padding: 16px;
  }
}
```

```html
<ul class="scoped news-list">
  <li>
    <article class="scoped news-card">
      <h3 class="_title">…</h3>
    </article>
  </li>
</ul>
```

ルートは、Vueでは部品のテンプレートの要素がそのまま範囲になり、本書では `@scope` の前置きの `.scoped.<名前>` で指定します。下限は、Vueでは子の部品のルートの内側にあり、本書では `to (.scoped)` に当てはまる子の部品のルートそのものです。下限の要素はスコープの外なので、`news-list` の `article` と `._title` のルールは、`news-card` のルートにも、その中の見出しにも当たりません。Vueの例で親の `.card` が子のルートに枠線を付けたのとは、ここが違います。Vueに移植するときは、親の部品のセレクタが子の部品のルートにも当たるようになるので、セレクタを書き換えるときに、子のルートと同じクラスを親が選んでいないかを確かめます。スロットの内容も、受け持つ側が逆になります。Vueは、子の部品のスロットに渡した内容を、渡した親の部品のものとして扱うので、子の `scoped` のスタイルはデフォルトでは当たらず、当てるには `:slotted()` を使います。本書の書き方では、スロットの内容は子の部品のルートの内側に描画されるので、子の `@scope` が当たり、親の `@scope` は下限で止まります。

置き換えたときは、詳細度の変わり方に注意が要ります。Vueの `scoped` は、`.example` を `.example[data-v-f3f3eg9]` のように属性セレクタを足して変換するので、詳細度が属性セレクタ1つ分上がります。Astroも、デフォルトの設定では `data-astro-cid-*` の属性セレクタを足すので、同じように上がります。ただし、設定 `scopedStyleStrategy` を `"where"` にすれば、`:where()` で包んで詳細度を変えません。

`@scope` の仕組みは「[4-4 @scopeでスタイルを閉じ込める](/cascade/scope/)」で、ルートと下限の名前の付け方は「[9-4 @scopeとネストの使い分け](/notation/scope-and-nesting/)」で説明しています。Shadow DOMを使う場面は、「[10-8 Web Components](/components/web-components/)」で、中身をすべて自分で描く部品に限っています。

## 再利用できる部品と公開プロパティ

部品の再利用では、ユーティリティクラスの手法に難しさがあります。Tailwind CSSのようにHTMLのクラスでスタイルを書く手法では、使う側で背景色を自由に変えられるカードの部品を作りにくい場合があります。背景色のクラスは部品のマークアップの中に書かれているので、外から変えるには、部品の側に変更の手段を用意しなければなりません。

その手段の1つが、フレームワークの部品に `variant="accent"` のようなプロパティを持たせ、値ごとにクラスを切り替える方法です。選べる値を限ることは、見た目の一貫性を保つうえで利点にもなります。しかし、用意したバリエーションにない色を使うたび、部品の側で値と分岐を足すことになります。背景色をCSSのカスタムプロパティで受け取れるようにしておくほうが、はるかに単純で拡張しやすいと私は考えています。

```css title="🙆‍♂ Recommended: 背景色を公開プロパティで受け取り、文字色を背景色から決める"
@scope (.scoped.promo-card) to (.scoped) {
  :scope {
    --_background: var(--promo-card--background, var(--background--surface));

    background-color: var(--_background);
    color: oklch(from var(--_background) sign(0.7 - l) 0 h);
  }
}
```

```html
<article class="scoped promo-card" style="--promo-card--background: var(--background--inverse)">…</article>
```

使う側は、`style` 属性で `--promo-card--background` に色を渡すだけです。部品は、渡された値を内部プロパティ `--_background` に受けて使い、何も渡されなければデフォルトの背景色を使います。文字色は、相対カラー構文と `sign()` で背景の明度から黒か白に決めているので、背景色を変えるたびに文字色を指定し直す必要はありません（[15-3 背景から文字色を決める](/color-media/contrast-text/)）。

公開プロパティは、どんな値でも受け取れる入り口です。こうした入り口を用意しておけば、部品を作った時点では想定していなかったカスタマイズの要件にも、部品を壊さずに対応できます。ただし、どんな色でも文字との十分なコントラストが得られるわけではないので、本書では、渡す色をコントラスト比を確認したトークンに限ります。公開プロパティの名前の付け方と受け方は、「[10-5 公開プロパティと内部プロパティ](/components/custom-properties/)」で説明しています。

## 関心の分離と見た目のロジック

CSSは、値の計算や条件による切り替えの機能を増やしてきました。`calc()` や `clamp()` で値を計算し、`:has()` で子の状態に応じて親のスタイルを変えられます。値を条件で切り替える `if()` も、Chrome系のブラウザで使えるようになりました（[6-5 if()とattr()で条件と属性を値にする](/values/if-and-attr/)）。

そのため、関心の分離（役割の違うコードを分けて書く考え方）の捉え方も、見直す時期に来ています。CSSが複雑なロジックを持つべきではない、という批判があります。しかし私は、見た目に関するロジックはCSSが受け持つべきだと考えています。「なぜ状態が変わるのか」というアプリケーションのロジックはJavaScriptが、「状態が変わったときにどう見えるか」というプレゼンテーションのロジックはCSSが受け持つ、という分担です。この分担は、今後よりはっきりしていくはずです。

タブを切り替えるUIで考えると、クリックされたタブの `aria-selected` を `true` にするのがJavaScriptの役目です。選ばれているタブの見た目を `[aria-selected="true"]` のセレクタで決めるのが、CSSの役目です。JavaScriptは状態を変えるだけで、見た目の値を持ちません。

見た目とロジックの境目は、時代とともに移ってきました。CSS1（1996年）が定めた擬似クラスはリンクの `:link`、`:visited`、`:active` だけで、`:hover` はCSS2（1998年）で加わりました。ユーザーの操作に反応する表現は、当初はJavaScriptで書くものと考えられていました。{/* 要確認: 出典なし。:hover がかつて JavaScript の領域と見なされていたこと */}

本書も、状態による見た目の変化はできるだけCSSで書きます。状態はJavaScriptで付け外しするクラスではなく、擬似クラス、HTML要素の属性、ARIA属性、`data-*` 属性の順に検討して表します（[17-3 状態を属性で表す](/interaction/state-attributes/)）。

チェックされたラジオボタンを含むカードのように、子の状態で親の見た目を変える場合も、クラスを付ける処理を書かずに `:has()` で選べます。状態を表す情報を1か所にまとめれば、クラスの付け外しの書き漏らしで見た目と中身が食い違うこともなくなります。擬似クラスの仕組みと使い分けは、「[第5章 擬似クラスと擬似要素](/pseudo/)」で説明しています。

## Webサイト制作で素のCSSを選ぶ理由

ここまでの論点を本書の題材に当てはめた結論は、「[素のCSSで書く理由](/introduction/why-plain-css/)」にまとめています。静的なサイトとCMSで同じ書き方を使えることと、どの道具を使う現場でも役に立つ知識になることが主な理由です。そのページでは、フレームワークのスコープの仕組みを使う場合に、設計の原則と公開プロパティの受け渡しを残し、スコープの指定をフレームワークに合わせて書き換えることも説明しています。採用していない道具をAIに持ち込ませないルール `no-unrequested-css-framework` も、そのページで扱っています。

このルールが求めているのは、採用していない道具を持ち込まないことです。プロジェクトがTailwind CSSやCSS-in-JSを採用しているなら、その方針に従います。大規模なアプリケーションを多くの開発者で作り、ビルドの仕組みをJavaScriptのフレームワークにそろえられる現場では、StyleXのような道具の利点が大きくなります。{/* 要確認: 出典なし。StyleXのような道具の利点が大きくなる現場の条件 */}Tailwind CSSを使う現場で本書の考え方を生かす方法は、「[10-3 コンポジションとユーティリティ](/components/compositions-and-utilities/)」のコラムで説明しています。
