本書のルールは、ほかのプロジェクトで使うAIツールからも参照できます。AIツール向けの配布物は、スキル、MCPサーバー、`llms.txt` の3つです。Claude Codeなら、プラグインを1つ入れるだけで、スキルとMCPサーバーの両方が使えます。ほかのツールでは、スキルとMCPサーバーを別々に設定します。

AIに読ませても、生成されたコードがルールに沿うとは限りません。生成されたCSSをlintとレビューで確かめる手順は、「[20-8 生成したコードを確かめ、教訓を残す](/ai-coding/verify-output/)」で説明しています。このページの設定方法は、2026年10月時点の各ツールの公式ドキュメントにもとづいています。

## 配布物の内容

スキルは、Agent Skillsの形式（`SKILL.md` と参照用のファイル）でまとめたルールです。`SKILL.md` には、手順と章の索引だけを書いています。AIが誤りやすいルールの一覧と、章ごとのルール集は `references/` に分けているので、AIは必要な章のファイルだけを開きます。各ルールには、掲載しているページのURLを添えています。

MCPサーバーは、npmで公開する予定の `recss-guideline-mcp` です。ルールと本文のデータを同梱しているので、起動したあとはネットワークに接続しません。動かすにはNode.js 20.19以降が要ります。提供するツールは次の5つです。

| ツール | 返すもの |
| --- | --- |
| `search_rules` | 語句、章、強度、性質、AIが誤りやすいかで絞り込んだルールの一覧 |
| `get_rule` | IDで指定したルールの理由、補足、自動チェックの手段、掲載ページ |
| `get_page` | 節の本文。デモはCSSとHTMLのコードに、図は代替テキストに置き換えている |
| `list_chapters` | 部、章、節の目次と、章ごとのルールの数 |
| `lint_css` | 本書のStylelintの設定で検査した結果と、対応するルールのID |

`lint_css` は、本書のリポジトリにだけ当てはまる指定を外した設定で検査します。レイヤー名の制限は、プロジェクトで宣言したレイヤー名を `layers` に渡したときだけ検査します。本書のレイヤーの名前が、そのプロジェクトのものと同じとは限らないからです。

MCPサーバーの版は、本書の版と同じ番号です。このページの設定例は版を付けていないので、起動する版は本の版と一致するとは限りません。手元の本と同じ版のルールで判定させたいときは、`recss-guideline-mcp@<本書の版>` のように、`@` の後ろに本書の版を付けて固定します。本書の版は、付録F「[更新履歴](/appendix/changelog/)」の先頭の見出しで確かめられます。

`llms.txt` は、本文をAIに読ませるためのテキストです。MCPサーバーとスキルのどちらも使えないツールでは、URLを渡して本文を読ませます。

## Claude Code

Claude Codeでは、プラグインを入れます。プラグインには、スキル、MCPサーバーを起動する設定、レビューを分担する2つのサブエージェントの定義が入っています。先に本書のリポジトリをマーケットプレイスとして登録し、そこからプラグインを入れます。

```sh title="プラグインを入れる"
claude plugin marketplace add t-arai-pnrm/recss-guideline
claude plugin install recss-guideline@recss-guideline
```

セッションの中では、コマンドの先頭の `claude plugin` を `/plugin` に替えて実行します。プロジェクトの規約は `CLAUDE.md` に書きます。Claude Codeは、`CLAUDE.md` がなければ代わりに `AGENTS.md` を読みますが、これはv2.1.277以降の既定の設定での動作で、作業するディレクトリかその上に `CLAUDE.local.md` があるときは読みません。読まれない場合は、`CLAUDE.md` に `@AGENTS.md` と書いて読み込ませます。既定では自分のすべてのプロジェクトに入ります。チームで同じ設定を使うときは、プロジェクトの `.claude/settings.json` に次の設定をコミットし、そのプロジェクトを開いたメンバーに、同じマーケットプレイスとプラグインを使うよう促します。

```json title=".claude/settings.json"
{
  "extraKnownMarketplaces": {
    "recss-guideline": {
      "source": { "source": "github", "repo": "t-arai-pnrm/recss-guideline" }
    }
  },
  "enabledPlugins": {
    "recss-guideline@recss-guideline": true
  }
}
```

プラグインは、入れたときの版に固定されます。ほかの人が公開しているマーケットプレイスは、自動では更新されません。付録F「[更新履歴](/appendix/changelog/)」で変更点を確かめてから、`claude plugin update recss-guideline@recss-guideline` で更新します。MCPサーバーだけを使う場合は、`claude mcp add --scope user recss-guideline -- npx -y recss-guideline-mcp` で登録します。

## Claude DesktopとClaude.ai

Claude DesktopとClaude.aiのチャットでは、プラグインを入れると、スキルが使えます。プラグインに入っているMCPサーバーの設定は、チャットでは使われません。設定の「Customize」から「Plugins」を開き、マーケットプレイスの追加で `t-arai-pnrm/recss-guideline` を指定して、プラグインを入れます。スキルを使うには、「Settings」の「Capabilities」で、コードの実行とファイルの作成を有効にしておく必要があります。

MCPサーバーの検索や検査は、Claude Desktopでだけ、プラグインとは別に設定すれば使えます。Claude.aiは、手元で起動するMCPサーバーを使えません。Claude Desktopでは、MCPサーバーを設定ファイルに登録します。「Settings」の「Developer」にある「Edit Config」で `claude_desktop_config.json` を開き、次の設定を足してから、アプリを再起動します。この方法では、手元にNode.jsが入っている必要があります。

```json title="claude_desktop_config.json"
{
  "mcpServers": {
    "recss-guideline": {
      "command": "npx",
      "args": ["-y", "recss-guideline-mcp"]
    }
  }
}
```

## Cursor、Codex、GitHub Copilot

Claude Code以外のツールには、スキルを `skills` コマンドで入れます。コマンドを実行すると、入れる先のツールを尋ねられます。CursorとCodexとGitHub Copilotは、プロジェクトの `.agents/skills/` からスキルを読み込みます。`-g` を付けると、自分のすべてのプロジェクトで使えるように入れます。`skills` コマンドを動かすには、Node.js 22.20以降が要ります。

```sh title="スキルを入れる"
npx skills add t-arai-pnrm/recss-guideline
```

MCPサーバーは、ツールごとの設定ファイルに登録します。Cursorでは、プロジェクトの `.cursor/mcp.json` か、自分の `~/.cursor/mcp.json` に書きます。

```json title=".cursor/mcp.json"
{
  "mcpServers": {
    "recss-guideline": {
      "type": "stdio",
      "command": "npx",
      "args": ["-y", "recss-guideline-mcp"]
    }
  }
}
```

Codexでは、`codex mcp add recss-guideline -- npx -y recss-guideline-mcp` で登録します。設定は `~/.codex/config.toml` に書き込まれ、CLIとIDEの拡張機能で共有されます。

```toml title="~/.codex/config.toml"
[mcp_servers.recss-guideline]
command = "npx"
args = ["-y", "recss-guideline-mcp"]
```

VS CodeのGitHub Copilotでは、プロジェクトの `.vscode/mcp.json` に設定を書きます。VS Codeの形式では、最上位のキーを `mcpServers` ではなく `servers` にします。Cursorと同じ形のプロジェクトのルートの `.mcp.json` を読むのは、実験的な設定 `chat.mcp.workspaceRootConfig.enabled` を有効にしたときだけです（VS Codeのドキュメントで確認）。VS Codeは、Claude Codeの形式のプラグインもそのまま扱えます。設定の `chat.plugins.marketplaces` に `t-arai-pnrm/recss-guideline` を加えると、拡張機能のビューの `@agentPlugins` からプラグインを入れられます。

GitHub上で動くCopilotのコーディングエージェントは、リポジトリの「Settings」の「Copilot」にある、MCPサーバーの設定欄から登録します。ファイルからは読み込まれません。この設定では、使うツールを `tools` に並べる必要があります。どのツールも、同梱のデータを読むだけで、ファイルの書き込みやネットワークへの接続をしないので、5つすべてを許可してかまいません。

```json title="Copilotのコーディングエージェントの設定"
{
  "mcpServers": {
    "recss-guideline": {
      "type": "local",
      "command": "npx",
      "args": ["-y", "recss-guideline-mcp"],
      "tools": ["search_rules", "get_rule", "get_page", "list_chapters", "lint_css"]
    }
  }
}
```

## 入ったことを確かめる

MCPサーバーを設定したら、3つのことを確かめます。1つ目は、ツールが5つ見えることです。Claude Codeでは、`/mcp` で `recss-guideline` を選ぶと、`search_rules`、`get_rule`、`get_page`、`list_chapters`、`lint_css` の5つが表示されます。ほかのツールでは、MCPサーバーの設定の画面で、ツールの一覧を確かめます。

2つ目は、ルールを引けることです。AIに「`get_rule` で `query-range-syntax` を引いて」と頼むと、強度が「必須」であること、範囲構文で書くというルールの本文と理由、掲載しているページ（13-5「メディアクエリ」）のURLが返ります。

3つ目は、CSSを検査できることです。次のCSSを `lint_css` で検査させると、`display: flex` の1値の構文が1件の違反として返り、本書のルール `display-two-value-syntax` が添えられます。

```css title="🙅‍♂ Not Recommended: lint_css で検査する、1値の構文の display" issue="convention"
/* 🙅‍♂ Not Recommended */
.card {
  display: flex;
}
```

3つとも期待どおりなら、MCPサーバーは動いています。どれかが返らないときは、Node.jsの版（20.19以降）と、設定ファイルの場所を確かめます。

## MCPもスキルも使えない場合

MCPサーバーとスキルのどちらも読み込めないツールでは、本文のテキストかルール集のURLを、プロジェクトの `AGENTS.md` から参照させます。本文は `llms.txt` の形で、目次（`llms.txt`）、全文（`llms-full.txt`）、要約版（`llms-small.txt`）の3つを用意しています。どれも本書のURLの直下にあります（例：`https://t-arai-pnrm.github.io/recss-guideline/llms.txt`）。

ルールだけを読ませるときは、スキルに入っているルール集を、GitHubのURLで指定します。AIが誤りやすいルールの一覧（`references/ai-prone.md`）を毎回読ませ、ほかの章のファイルは必要なときに開かせます。

```md title="AGENTS.md（抜粋）"
## CSS

- CSSを書く前とレビューの前に、https://raw.githubusercontent.com/t-arai-pnrm/recss-guideline/main/plugin/skills/recss-guideline/references/ai-prone.md を読む。
- 関係する章のルールは、同じディレクトリの章ごとのファイルを読む。章の一覧は、1つ上の SKILL.md の「章の索引」にある。
- 判断の根拠には、ルールのIDを添える。
```

## レビューを軽いモデルと高性能なモデルで分担する

スキルにレビューを頼むと、本文の通読と、ルールとの照合を、別々のサブエージェントに分担させます。本文は章によって10万字を超えるので、通読を軽いモデルに任せ、判断を高性能なモデルで行えば、費用を抑えながら判断の質を保てます。読む係（`recss-guideline-reader`）は、担当した節のすべてのルールについて、対象のCSSに当たるかを1行ずつ書いた表を返します。判断する係（`recss-guideline-judge`）は、表に欠けがないかを確かめ、関係する章のルールを補足まで読み直してから、指摘を1件ずつ確かめます。

プラグインに入れるサブエージェントの定義には、モデルを書いていません。どのモデルで動かすかは、使う人の環境の設定で決まります。Claude Codeのプラグインには、2つの定義が入っています。スキルは、指定がなければ読む係を `haiku`、判断する係を `opus` で呼ぶように書いています。別のモデルを使いたいときは、プロジェクトの `CLAUDE.md` に「`recss-guideline-reader` は `sonnet` で呼ぶ」のように書きます。

Codexでは、判断をメインのセッションで行います。読む係の定義（リポジトリの `plugin/codex/agents/recss-guideline-reader.toml`）を `~/.codex/agents/` に置くと、読む係は推論を弱めて動きます。軽いモデルで読ませたいときは、`config.toml` の `[agents]` に既定のモデルを書きます。Codexのモデル名には版が入るので、新しい版が出たら書き換えます。

```toml title="~/.codex/config.toml"
[agents]
default_subagent_model = "gpt-6-luna"
```

CursorとGitHub Copilotには、サブエージェントの定義を用意していません。これらのツールでは、スキルに入っている依頼文（`references/review.md`）を汎用のサブエージェントに渡して、同じ分担でレビューします。

## 版をそろえる

スキル、プラグイン、MCPサーバーには、本書と同じバージョン番号を付けています。プラグインは、自分と同じ版のMCPサーバーを起動するので、スキルとMCPサーバーの内容がずれません。プラグインを使わずにMCPサーバーを設定する場合も、チームで共有する設定では `recss-guideline-mcp@<本書の版>` のように版を固定します。版を書かないと、起動するたびに最新の版を使うので、知らないうちにルールの内容まで変わりうるからです。

バージョン番号の上げ方は、付録F「[更新履歴](/appendix/changelog/)」の冒頭で説明しています。ルールを変えたり削除したりした版に上げるときは、更新履歴で変わったルールを確かめてから、プロジェクトの設定の版を書き換えます。
