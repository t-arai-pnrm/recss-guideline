この章では、ここまでの章で決めたルールを実務で守り続ける方法を扱います。ルールは、書いた時点では誰もが納得していても、案件の環境や人の入れ替わり、作業の分担によって少しずつ守られなくなります。これを防ぐには、環境に合わせた書き方と、ツールとレビューによる確認の仕組みが必要です。

環境によっては、ルールの前提そのものが成り立ちません。たとえばCMSの本体が出力するCSSは、本書のレイヤーの構成が前提にしている「すべてのCSSを自分で管理できる」という条件を満たしません。こうした環境では、ルールの目的を保ったまま書き方を変える必要があります。判断の基準は「[4-3 カスケードレイヤーで順位を決める](/cascade/layers/)」で説明しています。

この章の確かめ方は、AIが生成したCSSにもそのまま使います。AIに規約を読ませる準備と、タスクの単位で実装と検証を回す進め方は、第20章「[AIにコーディングさせる](/ai-coding/)」で扱います。

## この章で判断できるようになること

この章を読むと、ルールのうちStylelintで検出できるものと、レビューで人が確かめるものを切り分けられるようになります。レビューでは、内容の変化に耐えられるか、コンポーネントの境界を守っているかといった項目を、プロジェクト全体への影響が大きい順に確かめ、指摘を `MUST`、`IMO`、`Q` のどれとして伝えるかを決められます。ブラウザで崩れやすい条件を再現する手順と、崩れたときに開発者ツールで原因をたどる手順も身につき、既存のサイトでは、どの範囲から規約を入れるかを決められます。CMSの本文のように、本書のレイヤーの構成が前提にしている条件を満たさない環境では、ルールの目的を保ったまま書き方を変える範囲を判断できます。

## この章の節

この章は次の6つの節で構成します。

- [19-1 Stylelintでルールを守る](/operations/stylelint/)：本書の設定の要所、独自ルール、代わりの書き方を示す禁止リスト、エラーと警告の使い分け
- [19-2 レビューの進め方](/operations/review/)：理由と解決策をセットにした指摘、深刻度のラベル、影響の大きい順に確かめる順番
- [19-3 表示と操作を確かめる](/operations/verification/)：崩れやすい内容を入れたテストページ、5つの幅、200%の拡大、キーボードでの操作、強制カラーモードやグレースケールの再現
- [19-4 表示の崩れを開発者ツールで調べる](/operations/devtools/)：宣言が効かない、はみ出す、`sticky` が留まらない、コンテナクエリが効かないといった症状ごとに、開発者ツールで見る場所と仕組みを説明する節
- [19-5 CMSのWYSIWYG本文にスタイルを当てる](/operations/wysiwyg/)：本文エリアを囲む `@scope`、タイプセレクタによるスタイル、下限で切り離す独自ブロック、`rlh` で決めるブロック間の余白
- [19-6 既存のサイトに段階的に導入する](/operations/adoption/)：規約を適用する範囲、先に入れるルール、既存のCSSとの共存、Stylelintの段階的な適用、規約を入れる順番

トークンと公開プロパティの設計は[第10章「コンポーネントとカスタムプロパティ」](/components/)で説明しています。Stylelintで検査している記法の規約は[第9章「記法の規約」](/notation/)にまとめています。すべてのルールは、付録A「[ルール一覧](/appendix/rules/)」で確認できます。

## 初めて読むとき

初めて読むときは、基本の節の「[19-1 Stylelintでルールを守る](/operations/stylelint/)」と「[19-3 表示と操作を確かめる](/operations/verification/)」を読み、19-3のブラウザで条件を再現する確認を手元で試します。19-1の機械的な検査は、Node.jsを使えるプロジェクトがあれば、そこで試します。この章で確かめる力は、確認の項目を答えられることではなく、幅、拡大、キーボード、表示の設定を自分のブラウザで再現できることだからです。

## 最初に押さえるルール

次のルールを先に押さえ、ほかのルールは、該当する場面で付録A「[ルール一覧](/appendix/rules/)」から引けば足ります。

- [`run-stylelint-before-done`](/operations/stylelint/#rule-run-stylelint-before-done)：CSSを変更したらStylelintを実行し、エラーを残しません。
- [`no-disabling-to-silence`](/operations/stylelint/#rule-no-disabling-to-silence)：エラーや警告を消すことだけを目的に、ルールを無効にしたり検査を飛ばしたりしません。
- [`review-reason-and-solution`](/operations/review/#rule-review-reason-and-solution)：レビューの指摘には、理由と解決策を必ずセットで書きます。
- [`verify-text-resize-200`](/operations/verification/#rule-verify-text-resize-200)：ブラウザのズームと文字サイズの設定をそれぞれ200%にしても、内容が欠けず、操作できることを確かめます。
- [`verify-keyboard-and-display-settings`](/operations/verification/#rule-verify-keyboard-and-display-settings)：キーボードだけで操作し、強制カラーモード、動きを減らす設定、グレースケールの表示を再現して確かめます。

## 判断の問い

この章の内容で答えられる問いを1つ置きます。答えを開く前に、確かめる条件とその順番を書き出してください。

記事のカードのCSSに、置かれた幅が広いときに画像を左へ並べるコンテナサイズクエリを足しました。Stylelintはエラーと警告を1件も報告せず、ビルドも通っています。公開の前に、ほかに何を、どの順番で確かめますか。また、lintが通ったことだけで済ませられないのはなぜですか。

ブラウザで、内容、幅、拡大、キーボード、表示の設定の5つの条件を、この順に再現して確かめます。lintとレビューは書かれたコードを読む確認で、条件を再現して画面で確かめる確認とは、見つかるものが違うからです。Stylelintに任せられるのは、ルールのうち機械的に判断できる書き方だけです。見出しが長いときのはみ出しや、文字を200%にしたときの欠けは、記法が規約どおりでも起きます（「[19-1 Stylelintでルールを守る](/operations/stylelint/)」、「[19-3 表示と操作を確かめる](/operations/verification/)」）。

内容から始めるのは、内容の問題が狭い幅や拡大した表示でも同じ原因で現れやすく、先に直せば同じ原因を何度も見つけずに済むからです。長い見出し、折り返せない文字列、読み込めない画像を入れたテストページで崩れを直してから、320px、480px、768px、1024px、1280pxの5つの幅と、その間の幅を見ます。この変更はコンテナサイズクエリなので、ページの幅だけでなく、同じカードを本文の幅とサイドバーの幅に並べて確かめます。

この変更に固有の確認もあります。閾値ちょうどの幅とその前後の幅で、画像が左へ移る境目に、どちらの形でもない中間の状態が出ないかを見ます。画像を読み込めないときに、横に並べた形の文章の幅が崩れないかも見ます。画像を左へ移すのが表示の順番を入れ替える指定なら、`Tab` キーの移動と読み上げの順番が、見た目の順番と食い違わないかも確かめます。

拡大では、ページ全体のズーム、既定の文字サイズの変更、文字だけのズームを、それぞれ200%まで上げます。200%まで拡大しても内容と機能が失われないことはWCAGの達成基準1.4.4の要求で、3つの操作をそれぞれ確かめるのは、操作ごとに見つかる崩れが違うために本書が加えた手順です（`verify-text-resize-200`）。続けて、幅1280pxの画面を400%に拡大して横スクロールが出ないこと（`verify-reflow-400`）と、行の高さや字間を広げる上書きで文字が欠けないこと（`verify-text-spacing-override`）を確かめます。キーボードでは、すべてのリンクとボタンに届くか、フォーカスが見えるか、移動の順番が見た目の順番と合うかを見ます。最後に、強制カラーモードで境界やアイコンが消えないか、動きを減らす設定で大きな動きが止まるか、グレースケールで状態の違いが分かるかを確かめます（`verify-keyboard-and-display-settings`）。

## 手を動かす課題

判断の問いでは、確かめる条件と順番を挙げました。ここでは、第13章の「[手を動かす課題](/responsive/#手を動かす課題)」を終えたページで、まず第14〜18章の実装をカードに足し、そのうえで条件を実際に再現して、結果を記録します。

前半では、カードを仕上げます。文字は「[14-5 文字の役割と色](/typography/text-roles/)」のとおり、`css/tokens/typography.css` に役割のトークンを定義し、見出し、本文、日付を役割で指定します。見出しは、カードの幅が480px未満なら20px、480px以上なら24pxのままにし、日付は12pxにします。各カードの見出しの文字を `<a href="#news-1">` のようなリンクで囲み、「[17-1 ホバーとフォーカスを表す](/interaction/states-and-focus/)」のとおり、ホバーとキーボードのフォーカスで同じように下線を出し、見出しの末尾の矢印を右へ4px動かします。矢印の動きは、「[18-2 動きを減らす設定に対応する](/motion/reduced-motion/)」のとおり、動きを減らす設定がないときだけ付けます。最後に、背景色だけで描いたカードの範囲を、強制カラーモードでも見えるようにします（「[15-5 強制カラーモードとコントラスト](/color-media/forced-colors/)」）。

後半では、条件を厳しくして確かめます。サイドバーの1枚目の見出しを3行に折り返すほど長い文にし、主欄の1枚目の本文に、改行できない長い英字の文字列（URLなど）を入れます。そのうえで、「[19-3 表示と操作を確かめる](/operations/verification/)」の順に条件を再現します。条件は、内容、幅（320px、768px、1280px）、文字サイズの200%、キーボード、動きを減らす設定、強制カラーモードです。結果は `verification.md` に1条件1行で書きます。各行の期待した結果は、ブラウザで見る前に、閾値と設定から先に書きます。

合格の条件は、記録のすべての行に、使ったブラウザ、条件、期待した結果、観察した結果がそろっていることです。試していないブラウザや設定は、期待した結果を書いたうえで、観察した結果を「未確認」として行に残します。「確認済み」の印だけの行は、合格にしません。期待と違う結果が出た行は、原因を直して同じ条件で確かめ直し、直した内容を観察した結果の欄に書きます。

文字のトークンは、カードで使う役割だけを定義します。カードの見出しは、置かれた幅に合わせて20pxから24pxまで変わるので、両端の2つのサイズを、`title` と `headline` の2つの役割に分けています。

```css title="🙆‍♂ Recommended: カードで使う役割だけを、サイズと行の高さの組で定義する" use="complete" from="tasks/19-operations/css/tokens/typography.css"
:root {
  --font-size--xs: 12;
  --font-size--md: 16;
  --font-size--xl: 20;
  --font-size--xxl: 24;
  --leading--snug: 1.4;
  --leading--normal: 1.6;
  --leading--relaxed: 1.75;
  --text--headline--font-size: var(--font-size--xxl);
  --text--headline--leading: var(--leading--snug);
  --text--title--font-size: var(--font-size--xl);
  --text--title--leading: var(--leading--snug);
  --text--body--font-size: var(--font-size--md);
  --text--body--leading: var(--leading--relaxed);
  --text--caption--font-size: var(--font-size--xs);
  --text--caption--leading: var(--leading--normal);
}
```

カードでは、ルートに本文の役割を、見出しと日付にそれぞれの役割を指定します。見出しのリンクでは、ホバーとフォーカスで `--_hocus` を立て、リンク自身の下線は状態のセレクタに直接書き、擬似要素の矢印はスタイルクエリで動かします。矢印の移動とトランジションは `prefers-reduced-motion: no-preference` の中にだけ書くので、動きを減らす設定では、矢印は動かず、下線だけが出ます。キーボードでフォーカスしたときは、2つ目のフラグ `--_focus-visible` でトランジションを外し、一度で切り替えます。カードのルートの透明な枠線は、強制カラーモードで色が付き、背景色が消えてもカードの範囲を示します。

```css title="🙆‍♂ Recommended: 役割のトークン、ホバーとフォーカス、動きを減らす設定、強制カラーモードの枠線を足す" use="diff" from="tasks/19-operations/css/components/news-card.css"
@scope (.scoped.news-card) to (.scoped) {
  :scope {
    border: 1px solid transparent;
    font-size: calc(var(--text--body--font-size) / 16 * 1rem);
    line-height: var(--text--body--leading);
  }

  h2 {
    font-size: clamp(var(--text--title--font-size) / 16 * 1rem, 1.25cqi + 16 / 16 * 1rem, var(--text--headline--font-size) / 16 * 1rem);
    line-height: var(--text--title--leading);
  }

  a {
    --_hocus: --false;
    --_focus-visible: --false;

    &:focus-visible {
      --_hocus: --true;
      --_focus-visible: --true;

      text-decoration-line: underline;
    }

    &:any-link:hover {
      @media (any-hover) {
        --_hocus: --true;

        text-decoration-line: underline;
      }
    }

    &::after {
      content: "→" / "";
      display: inline flow-root;
      padding-inline-start: 0.25em;

      @container style(--_hocus: --true) {
        @media (prefers-reduced-motion: no-preference) {
```

矢印を動かすのはリンクではなく擬似要素なので、ホバーを受けるリンクの位置は変わりません（`hover-target-stays-still`）。新しく足した `typography.css` と、トランジションの時間を定義した `motion.css` は、`css/style.css` で `layer(tokens)` として読み込みます。カードの枠線は中身の幅を左右1pxずつ狭めますが、試す幅はどれも480pxの閾値から離れているので、結果は変わりません。

記録は、次のような形にします。観察した結果の欄は、自分のブラウザで見たとおりに書きます。

```text title="verification.md の例"

| --- | --- | --- | --- |

| Chrome | 幅768px | 主欄とサイドバーが縦に積まれ、どちらのカードの見出しも24px | （見たとおりに書く） |
| Chrome | 幅1280px | 主欄の見出しは24px、サイドバーは20px。日付はどちらも12px | （見たとおりに書く） |
| Chrome | 既定の文字サイズ200% | 見出しと本文が欠けず、重ならない | （見たとおりに書く） |
| Chrome | Tabキーで移動 | すべての見出しのリンクに届き、フォーカスリングと下線が見え、矢印が一度で右へ移る | （見たとおりに書く） |
| Chrome | 動きを減らす設定（reduce）でホバー | 下線は出るが、矢印は動かない | （見たとおりに書く） |
| Chrome | 強制カラーモード | カードの範囲が枠線で分かり、見出しのリンクと矢印が見える | （見たとおりに書く） |
```

768pxの行は、1280pxの行と期待した結果が違います。`sidebar` は、主欄の最小幅480px、サイドバーの320px、間隔の24pxを合わせた824pxより狭いと縦に積むので、768pxではサイドバーのカードも主欄と同じ幅に広がり、480pxの閾値を超えます。期待した結果は、このように `sidebar.css` と `news-card.css` の値から先に計算して書きます。

長い英字の文字列は、kiso.cssが `overflow-wrap: anywhere` を指定しているので、カードの幅で折り返されます。リセットCSSを替えたときに崩れる箇所なので、この行は残しておく価値があります。強制カラーモードの行は、透明な枠線を足す前と後で同じ条件を見比べると、直した効果を確かめられます。

記録の目的は、同じ条件をあとで再現できるようにすることです。どのブラウザで何を試し、何を試していないかが残っていれば、次の確認は試していない組み合わせから始められます。使ったルールは、`verify-worst-case-content`、`verify-text-resize-200`、`verify-keyboard-and-display-settings` です。

## この章の判断のまとめ

正解が1つに決まる書き方の違反はStylelintのエラーに、置き換え先を人が選ぶものは警告とレビューに任せ、内容や幅、利用者の設定で変わる見え方は、ブラウザで条件を再現して確かめます。宣言が効かないときは、開発者ツールで、取り消し線が引かれていればレイヤー、詳細度、スコープの近さ、出現順を、警告のアイコンが付いていれば綴りと値を、ルールが表示されなければセレクタと `@scope` の範囲を調べます。

規約を当てる範囲は、環境の前提で選びます。既存のサイトでは、ほかのページの表示を変えずに済む新しいコンポーネントと、変更で手を入れる箇所から適用します。CMSの本文のようにクラスを付けられない領域では、ルールの目的を保ったまま、その領域でだけ書き方を変えます。

## 次の章へ

この章で扱ったlint、レビュー、ブラウザでの確認は、書いたのが人かAIかに関係なく使います。ただ、AIに書かせると、確かめる前の段階で手戻りが生まれます。デザインにない値を推測で埋めたり、lintが通ったことを完了の根拠にしたりするからです。第20章「[AIにコーディングさせる](/ai-coding/)」では、AIに規約を読ませる準備から、計画を人が承認し、手順ごとに検証しながら実装させる進め方までを扱います。
