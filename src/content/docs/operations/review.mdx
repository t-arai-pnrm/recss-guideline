レビューの指摘には、必ず理由と解決策をセットで書きます。指摘には `MUST`、`IMO`、`Q` のラベルを付け、直さなければならないものと、好みの提案と、質問を区別します。レビューを通したコードには、レビュアーも責任を負います。

確認は、規約やデザイントークンのように、プロジェクト全体に影響する項目から順に進めます。AIが生成したCSSも、この節と同じ基準でレビューします。AIに書かせるときの準備と、生成されたコードに特有の確かめ方は、第20章「[AIにコーディングさせる](/ai-coding/)」で説明します。

## レビューの指摘に書く内容

「この書き方はダメです」だけでは、レビューになりません。書いた人は、何が問題なのかも、どう直せばよいのかも分からないからです。指摘を受けた人が自分で調べ直すことになり、同じ誤りを別の場所で繰り返しやすくなります。

```md title="🙅‍♂ Not Recommended: 理由も解決策もない指摘" issue="convention"
<!-- 🙅‍♂ Not Recommended -->
width: 100% は要りません。
```

```md title="🙆‍♂ Recommended: 理由と解決策をセットにした指摘"
[MUST] `._panel` の `width: 100%` は削除してください。ブロックレベルの要素は、指定しなくても親の幅いっぱいに広がります。左右に `margin` が付くと、はみ出しの原因にもなります（`no-redundant-width-100`）。
```

理由を書くと、指摘の正しさをレビュイーが自分で確かめられます。本書のルールに当てはまる指摘なら、ルールのIDを添えます。IDは章の構成が変わっても変えないので、ルールの詳しい説明をすぐに引けます。

レビュイーが書いたCSSは、レビューを通した時点で、レビュアーも責任を負います。「書いた人の責任」として見逃した誤りは、後から自分のチームの問題になります。承認するときは、自分が書いたコードと同じ基準で見ます。

## 指摘の深刻度ラベル

指摘には、深刻度のラベルを付けます。`MUST` は、仕様やコーディング規約に反するもの、バグが起きているもの、将来深刻な問題になりそうなもの、使いやすさやアクセシビリティを損なうものです。

`IMO`（in my opinion）は、好みが入りうる提案です。レビューが教義的になりすぎないよう気をつけます。ユーザーやクライアントのメリットになりにくい趣味の指摘は、`IMO` として扱うか、レビューとは別の機会に伝えます。たとえば、私はFlexboxとGridの使い分けについて普段から発信していますが、挙動に問題がなければ、レビューでは基本的に指摘しません。

本書のルールとの関係は次のとおりです。`display` の2値構文や論理プロパティは、本書では「必須」や「推奨」のルールです。しかし、それはプロジェクトで本書の規約を採用していることが前提です。規約として合意したものへの違反は `MUST` ですが、合意していないプロジェクトで同じことを求めるなら、それは `IMO` です。私も、ほかの人が書くコードに、合意のない2値構文を強制はしていません。

`Q` は、意図が読み取れない記述への質問です。たとえば、理由の分からない `position: relative` や `z-index: 3` があっても、誤りと決めつけずに質問します。書いた人にしか分からない事情がある場合もあるからです。答えが「なんとなく」なら、その宣言は消せますし、正当な理由があれば、それをコメントに残してもらいます。

```md title="🙆‍♂ Recommended: 意図が読み取れない記述には質問する"
[Q] `._media` の `position: relative` は、どの要素の配置の基準にするためのものでしょうか。子要素に `position: absolute` が見当たらないので、不要であれば削除できそうです。
```

## 確認する順番

CSSをレビューするときの確認の順番は、私が案件で使っているテンプレートのAI向けのスキルに、次のように定めています。上にあるものほど、プロジェクト全体への影響が大きいものです。

1. 仕様とプロジェクトの規約に従っているか
2. デザイントークンを使っているか（[10-4 デザイントークン](/components/design-tokens/)）
3. 対象のブラウザで動くか（[1-2 ブラウザサポートとプログレッシブ・エンハンスメント](/principles/browser-support/)）
4. 不要な記述や副作用のある上書きがないか（[2-3 保守しやすさを最優先にする](/design-mindset/maintainability/)）
5. グローバルのCSSに重い指定がないか（[8-3 グローバルに書いてはいけないもの](/reset/global-pitfalls/)）
6. 内容の変化に耐えられるか（[11-3 サイズと内容の変化に耐える](/layout-practice/defensive/)）
7. コンポーネントの境界を守っているか（[10-2 コンポーネントの境界を守る](/components/boundaries/)）
8. レスポンシブ対応の手段を正しい順番で選んでいるか（[13-1 検討する順番](/responsive/escalation/)）
9. コメントが「なぜ」を説明しているか（[9-10 コメントの書き方](/notation/comments/)）

インデントやプロパティの並び順は、この一覧に入れていません。整形はツールの仕事で、レビューで指摘するのは、自動化が機能していないときだけです。Stylelintの運用は「[19-1 Stylelintでルールを守る](/operations/stylelint/)」で説明しています。確認の項目をまとめた一覧は、付録D「[レビューのチェックリスト](/appendix/checklist/)」にあります。

指摘の強さは、レビュイーの習熟度に合わせて調整します。たとえば、デフォルト値に戻す `revert` や `unset` の使い分けは、`display` の初期値が `inline` であることのような基礎知識が前提になります。また、余白のトークンのように、レスポンシブの環境では単位の使い分けが絡んで二者択一で片付かないものは、あまり細かく指摘しません。

コードを読むだけでは、内容や幅、表示の設定が変わったときの見え方までは確かめきれません。ブラウザで条件を再現して確かめる手順は「[19-3 表示と操作を確かめる](/operations/verification/)」で、崩れを見つけたときに原因をたどる手順は「[19-4 表示の崩れを開発者ツールで調べる](/operations/devtools/)」で説明します。
