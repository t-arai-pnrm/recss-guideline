実装を終えたら、崩れやすい条件をブラウザで再現し、表示と操作を確かめます。デザインカンプのとおりの内容と幅で見て崩れていなくても、実際の内容、利用者の画面、利用者の設定はカンプと同じではないからです。再現する条件は、最悪の内容、幅、拡大とテキストの間隔、キーボード、表示の設定の5つです。

この節が扱うのは、コードを読んで確かめることではなく、条件を作って画面で確かめることです。コードの読み方と指摘の書き方は「[19-2 レビューの進め方](/operations/review/)」（理由と解決策を添えて指摘する）で、確認の項目の一覧は付録D「[レビューのチェックリスト](/appendix/checklist/)」で説明しています。チェックリストの「内容の変化に耐えられるか」のような項目を、どうやってブラウザ上で確かめるかが、この節の内容です。

## 確かめる条件と順番

確かめる順番は、内容、幅、拡大とテキストの間隔、キーボード、表示の設定です。内容の問題は、狭い幅や拡大した表示でも同じ原因で現れやすいので、私は内容から確かめています。たとえば、長い見出しで折り返さないカードは、狭い幅でも200%の拡大でもはみ出します。内容の問題を直してから幅や拡大を見れば、同じ原因を何度も見つけずに済みます。この順番は手間を減らすための目安で、変更の内容に応じて重点を変えます。フォーカスの表示やキーボードの操作を変えたときは、キーボードでの確認から始めます。

それぞれの条件で見るものは、次のとおりです。内容、幅、拡大とテキストの間隔では、はみ出し、重なり、欠けがないかを見ます。キーボードでは、すべての操作に届くか、フォーカスが見えるか、移動の順番が見た目の順番と合うかを見ます。表示の設定では、強制カラーモードで境界やアイコンが消えないか、動きを減らす設定で大きな動きが止まるか、色を抜いても状態の違いが分かるかを見ます。

実装の途中で毎回すべてを見る必要はありません。コンポーネントを1つ仕上げたときと、ページを組み上げたときに、この順番で通して確かめます。条件を再現する手間が小さいほど確認は続くので、テストページと開発者ツールの設定を、作業の最初に用意しておきます。

## 最悪の内容を入れたテストページを用意する

内容の変化は、内容を変えないと再現できません。カンプのダミーテキストは、デザインがきれいに見える長さで作られていることが多く、崩れる条件をほとんど含みません。そこで、コンポーネントごとに、崩れやすい内容を集めたテストページを用意します。

```html title="🙅‍♂ Not Recommended: カンプのダミーテキストだけで確かめる" issue="behavior"
<!-- 🙅‍♂ Not Recommended -->
<ul class="scoped card-list">
  <li class="scoped card">
    <img src="/images/sample.jpg" alt="" />
    <h3>タイトルが入ります</h3>
    <p>テキストが入ります。テキストが入ります。</p>
  </li>
  <!-- 同じカードをあと2枚 -->
</ul>
```

入れる内容は、見出しをカンプの2倍ほどの長さにしたもの、空白を含まない長いURLや英単語、読み込めない画像、空のリスト、そして項目が0件、1件、多数の場合です。長いURLや英単語は、日本語と違って途中で折り返されないので、はみ出しの原因になります。読み込めない画像は、縦横比を `aspect-ratio` や `width` と `height` の属性で確保していないと、領域の高さが変わり、下の要素の位置がずれます。テストページの画像には、本番と同じ `width` と `height` を書き、読み込めない画像は `src` だけを存在しないファイルにします。寸法を書き忘れたときの崩れは、読み込めないことによる崩れとは別の問題なので、同じ画像で試しません。

```html title="🙆‍♂ Recommended: 崩れやすい内容を1ページに並べる"
<h2>見出しが長い</h2>
<ul class="scoped card-list">
  <li class="scoped card">
    <img src="/images/sample.jpg" alt="" width="640" height="360" />
    <h3>見出しがカンプの2倍ほどの長さになり、狭い幅では3行以上に折り返すことを想定したカードの見出し</h3>
    <p>本文</p>
  </li>
</ul>

<h2>折り返せない文字列と、読み込めない画像</h2>
<ul class="scoped card-list">
  <li class="scoped card">
    <img src="/images/not-found.jpg" alt="読み込めない画像" width="640" height="360" />
    <h3>https://example.com/articles/2026/10/very-long-path-without-any-spaces-to-break</h3>
    <p>Pneumonoultramicroscopicsilicovolcanoconiosis</p>
  </li>
</ul>

<h2>0件、1件、7件</h2>
<ul class="scoped card-list"></ul>
<ul class="scoped card-list">
  <li class="scoped card"><!-- ... --></li>
</ul>
<ul class="scoped card-list">
  <!-- 7件のカード -->
</ul>
```

件数は、0件、1件、そしてグリッドの列数で割り切れない数を並べます。列数で割り切れる件数だけを見ると、最後の行が半端になったときの配置を確かめられないからです。0件のときに見出しや枠だけが残らないかも、ここで見ます。

テストページは、本番のページとは別に、開発環境でだけ表示されるページとして置きます。コンポーネントの見本を並べるツールを使っているなら、その中に崩れやすい内容の見本を1つ足すだけでも足ります。崩れたときの直し方は、次の3つの節にあります。内容の変化に耐える書き方は「[11-3 サイズと内容の変化に耐える](/layout-practice/defensive/)」（幅と高さを固定せず、内容に合わせる）で、はみ出しの扱いは「[11-4 はみ出しとスクロール](/layout-practice/overflow/)」（折り返すかスクロールさせるかを決める）で説明しています。件数に応じた配置は「[11-5 件数で配置を組み替える](/layout-practice/quantity-layouts/)」（`:has()` で件数を数える）にあります。

## 幅を変えて確かめる

幅は、320px、480px、768px、1024px、1280pxの5つで確かめます。本書のデモが表示に使っている幅と同じです。320pxは、WCAGの達成基準1.4.10（リフロー）が横スクロールなしで読めることを求める幅で、1280pxの画面を400%に拡大したときの幅にも当たります。幅を狭めた表示と400%に拡大した表示の違いは、後の「400%に拡大してリフローを確かめる」で説明します。

5つの幅で見るだけでは、その間の幅で起きる崩れを見落とします。ブレイクポイントの直前の幅では、切り替わる前のレイアウトに最も狭い幅が割り当てられるからです。Chromeの開発者ツールのデバイスモードで幅を自由に変えられるようにし、5つの幅を確かめた後に、320pxから1280pxまでゆっくり広げていきます。崩れた幅が見つかったら、その幅を数字で控えておくと、原因の宣言を探すときの手がかりになります。

ページの幅だけでなく、コンポーネントが置かれる場所の幅も変えます。コンテナサイズクエリで切り替えるコンポーネントは、ページが広くても、狭いサイドバーに置かれると狭いレイアウトで表示されます。テストページには、同じコンポーネントを本文の幅とサイドバーの幅に並べておきます。幅の変化にどの手段で対応するかの考え方は「[13-1 検討する順番](/responsive/escalation/)」（内容に合わせる手段から順に検討する）で説明しています。

ビューポートの高さも変えて確かめます。高さで表示が変わるのは、高さのメディアクエリで固定したヘッダーと、`svb` や `dvb` のようなビューポートの高さの単位で大きさを決めた要素です。横向きのスマートフォンでは高さが400px前後しかないので、デバイスモードで幅を800px前後、高さを400px前後にして、固定したヘッダーが本文を覆わないか、画面の高さに合わせた要素の内容が切れないかを見ます。本書は、ビューポートの高さが十分なときだけヘッダーを固定するルール（[`sticky-header-height-query`](/layout-practice/sticky-header/#rule-sticky-header-height-query)）を置いているので、閾値の前後の高さで、固定が外れることも確かめます。{/* 要確認: 出典なし。横向きのスマートフォンを想定した幅と高さの組み合わせ */}

高さの単位の違い（`svb`、`lvb`、`dvb`）は、アドレスバーが伸び縮みするスマートフォンのブラウザでしか差が出ません。デバイスモードでは、この差を確かめられないので、「補足と注意点」で挙げる実機の確認に回します。単位の選び方は「[6-2 ビューポート単位とコンテナ単位](/values/viewport-and-container-units/)」（基本は `svb` を使う）で、固定ヘッダーの条件は「[11-7 固定ヘッダー](/layout-practice/sticky-header/)」で説明しています。

## 拡大と文字サイズを200%にする

ページ全体のズーム、既定の文字サイズの変更、文字だけのズームの3つを、それぞれ200%まで上げて確かめます。WCAGの達成基準1.4.4（テキストのサイズ変更）は、支援技術なしで文字を200%まで拡大しても、内容や機能が失われないことを求めています。3つは別々の操作で、大きくなるものも、見つかる崩れも違います。

ページ全体のズームは、レイアウト、文字、画像をまとめて拡大します。1280pxの画面で200%にすると、ページから見た幅は640pxになるので、幅を狭めたときと同じブレイクポイントに切り替わります。ズームで崩れるものの多くは、前の「幅を変えて確かめる」の確認で見つかります。

既定の文字サイズの変更は、ブラウザの既定の文字サイズを変え、remやemで指定した値だけを大きくします。pxで指定した文字は大きくなりません。Chromeでは設定の「デザイン」にある「フォントサイズ」で（Chromeのヘルプで確認）、Firefoxでは設定の「フォント」で既定のサイズを変えます（Firefoxのヘルプで確認）。ここで見るのは、実装が既定の文字サイズに追従するかです。pxで固定した高さや幅の中にremの文字があると、文字だけが大きくなってはみ出します。文字サイズをpxやビューポート単位で決めている場合は、設定を変えても文字が大きくならないので、ここで見つかります。

文字だけのズームは、ページ全体を一律に拡大するのではなく、文字を拡大する操作です。ただし、emやremで指定した寸法も変わるため、要素の幅や配置は変わることがあります。Firefoxでは「表示」メニューの「ズーム」で「文字サイズだけ変更」を選んでからズームします（Firefoxのヘルプで確認）。{/* 要検証: ブラウザ。「文字サイズだけ変更」の日本語のUIでの表記（ヘルプは機械翻訳） */}既定の文字サイズの変更と違い、pxで指定した文字も大きくなるので、文字サイズがpxで決まっているかどうかは、この操作では分かりません。見るのは、文字が大きくなったときに、固定した大きさの箱の中で文字が切れたり重なったりしないかです。既定の文字サイズへの追従は、前の操作で確かめます。

実装の途中では、ルートの `font-size` を変えた表示も確かめます。開発者ツールで `:root` に `font-size: 200%` を指定すれば、設定の画面を開かずに切り替えられます。remで指定した文字、余白、コンテナサイズクエリの閾値がまとめて2倍になるので、部品が文字の大きさに追従するか、pxで固定した箱から文字がはみ出さないかを、手早く見られます。ただし、メディアクエリの中のremは、ルートの `font-size` ではなく、ブラウザの設定の文字サイズを基準にするので、ブレイクポイントは切り替わりません（「[13-2 ブレイクポイントの決め方](/responsive/breakpoints/#ブレイクポイントをremで書く)」）。メディアクエリで決まる表示は、利用者が見るものと違うので、この確認を既定の文字サイズの変更の代わりにはしません。

拡大したときは、文字が切れていないか、重なっていないかに加えて、操作できるかも確かめます。固定したヘッダーが画面の半分を覆い、本文を読めなくなる例はよくあります。高さを固定したボタンの中でラベルが2行になり、上下が切れていないかも見ます。

## 400%に拡大してリフローを確かめる

WCAGの達成基準1.4.10（リフロー）は、幅320 CSS px相当のビューポートで、縦と横の2方向にスクロールしなくても、情報や機能が失われないことを求めています。320 CSS pxは、幅1280 CSS pxのウィンドウでページを400%に拡大したときのビューポートの幅です。前の「幅を変えて確かめる」で320pxを見るのも、この基準に合わせたものです。ただし、デバイスモードで幅を320pxにするのと、ページを400%に拡大するのとでは、同じ幅でも見えるものが違います。

違いは高さに出ます。ページのズームは幅と同じ割合で高さも縮めるので、高さ800 CSS pxのウィンドウを400%にすると、ビューポートは幅320、高さ200 CSS px相当になります。高さ64pxの固定ヘッダーは、デバイスモードの幅320px、高さ700pxの画面では1割ほどですが、高さ200 CSS pxのビューポートでは3分の1を占めます。Cookieの同意の帯やチャットを開くボタンのように、画面に固定して重ねる部品も同じです。幅を狭めただけの確認では本文が読めても、400%では固定した部品が本文の多くを覆うことがあります。

再現するときは、ズームを100%に戻し、開発者ツールをウィンドウから切り離してから、コンソールで `window.innerWidth` が1280前後になるようにウィンドウの幅を合わせます。そのうえで、ページのズームを400%まで上げます。もう一度 `window.innerWidth` を見て、320前後になっていれば条件がそろっています。{/* 要検証: ブラウザ。400%にしたときの innerWidth の値（スクロールバーの幅を含むかどうか） */}

見るのは3点です。1つ目は、ページ全体に横スクロールが出ないことです。データの表、地図、図のように2次元の配置がないと意味が通らない部分は、その部分の中だけで横にスクロールさせてかまいませんが、その周りの見出し、検索欄、ページ送りは例外になりません。部分の中だけをスクロールさせる書き方は「[11-4 はみ出しとスクロール](/layout-practice/overflow/)」で説明しています。2つ目は、固定した部品が本文を覆いすぎないことです。本書はビューポートの高さが十分なときだけヘッダーを固定するので（「[11-7 固定ヘッダー](/layout-practice/sticky-header/)」）、400%では固定が外れていることを確かめます。3つ目は、`Tab` キーで移動したときに、フォーカスした要素が固定した部品の下に隠れないことです。これはWCAGの達成基準2.4.11「隠されないフォーカス（最低限）」の確認も兼ねます。

前の「拡大と文字サイズを200%にする」の確認とは、確かめる目的が違います。達成基準1.4.4は、文字を200%まで大きくしても読めて操作できるかを問う基準で、文字だけのズームのように、拡大の手段は問いません。達成基準1.4.10は、文字の大きさではなく、狭いビューポートで1方向のスクロールだけで読めるか、つまり1行を読むたびに横へスクロールしなくて済むかを問います。1280pxの画面を200%にしたときの幅は640pxなので、200%で崩れなくても、400%で横スクロールが出ることはあります。なお、縦書きのように横にスクロールする内容では、幅ではなく高さ256 CSS px相当（高さ1024 CSS pxのウィンドウを400%にした大きさ）で同じことを確かめます。

## テキストの間隔を広げて確かめる

WCAGの達成基準1.4.12（テキストの間隔）は、利用者が行の高さ、段落の後ろの余白、字間、語間を広げても、内容や機能が失われないことを求めています。作り手にその値で組むことを求める基準ではなく、利用者が上書きしたときに崩れないことを求める基準です。基準の値と行の高さの決め方との関係は「[14-3 行の高さとハーフレディング](/typography/line-height/)」（ベースの `line-height` を1.5以上にしておくと、上書きされたときの変化が小さい）で説明しているので、ここでは上書きを再現する手順を示します。

再現には、基準の4つの値を `!important` で指定するCSSを、開発者ツールでページに足します。行の高さを文字サイズの1.5倍、段落の後ろの余白を2倍、字間を0.12倍、語間を0.16倍にします。Chromeでは、Elementsパネルの「Styles」にある「New Style Rule」のボタンで、ページに一時的なスタイルシートを作り、そこに貼り付けます。{/* 要検証: ブラウザ。「New Style Rule」で作ったスタイルシートを開いて、セレクタごと貼り付けられること */}グレースケールの確認と同じく、プロジェクトのCSSに一時的に書いて確かめてもかまいませんが、確認が終わったら消します。

```css title="テキストの間隔を、達成基準1.4.12の値に上書きする"
* {
  line-height: 1.5 !important;
  letter-spacing: 0.12em !important;
  word-spacing: 0.16em !important;
}

p {
  margin-block-end: 2em !important;
}
```

本書は要素の間の余白を後ろの要素の `margin-block-start` に付けますが、このCSSは確認のための上書きなので、基準の言葉どおり段落の後ろに付けています。サイトのCSSのうち、レイヤーの中で `!important` を付けた宣言には、レイヤーの外にあるこの宣言は勝てません（「[4-1 カスケード・詳細度・継承](/cascade/cascade-basics/)」）。値が変わらない要素では、開発者ツールで勝っている宣言を確かめます。

上書きしたら、文字が切れていないか、隣の内容と重なっていないか、ボタン、見出し、タブ、バッジの中身が隠れていないかを見ます。崩れる箇所の多くは、`block-size` で高さを固定した箱や、`overflow: hidden` で切っている箱です。行の高さと字間が広がると、同じ文字数でも行数と幅が増え、決めた大きさに収まらなくなるからです。高さを中身に任せる書き方は「[11-3 サイズと内容の変化に耐える](/layout-practice/defensive/)」で説明しています。

和文には、この基準の値をそのまま当てはめられない部分があります。語間（`word-spacing`）は語の区切りの空白に加わる間隔なので、空白を入れない和文の部分は変わらず、英単語やURLの部分だけが広がります。字間の0.12倍は和文の字面を離すので、和文は読みにくい見た目になります。WCAGの解説書は、書き言葉でその間隔を使わない言語と文字は、使う間隔だけで基準を満たせるとし、日本語では段落の間の余白を一般に使わない例を挙げています。それでも、和文のページにも英字のボタンやURLが入るので、4つの値をまとめて上書きして確かめるのが簡単です。ここで見るのは読みやすさではなく、欠けや重なりがないかです。

## キーボードで操作する

マウスから手を離し、`Tab` キーと `Shift` + `Tab` キーで、ページの最初から最後まで移動します。見るのは3点で、すべてのリンクとボタンに届くか、今どこにフォーカスがあるかが見えるか、移動の順番が見た目の順番と合っているかです。開閉するメニューやダイアログでは、`Enter` キー、`Space` キー、`Esc` キーでの開閉も試します。

フォーカスが見えない原因は、多くの場合CSSにあります。`outline` を消したまま代わりの表示を用意していない、フォーカスリングが隣の要素や `overflow: hidden` の親に隠れる、といったものです。閉じたメニューの中のリンクにフォーカスが移り、画面に何も見えないまま `Tab` キーの操作が消費される例もあります。フォーカスの表し方は「[17-1 ホバーとフォーカスを表す](/interaction/states-and-focus/)」（要素自身の状態は状態のセレクタに書く）で説明しています。

移動の順番が見た目とずれるのは、`order` や `grid-template-areas`、`flex-direction: row-reverse` で、表示の順番をHTMLの順番から変えたときです。フォーカスが画面の右から左へ、下から上へ飛ぶ箇所があれば、HTMLの順番を見直します。合わせ方は「[11-12 表示順と読み上げ順を合わせる](/layout-practice/reading-flow/)」（HTMLの順番を正とし、CSSで並べ替えすぎない）で説明しています。

## 表示の設定を再現する

強制カラーモードと動きを減らす設定は、OSの設定を切り替えなくても、Chromeの開発者ツールで再現できます。コマンドメニューから「Rendering」パネルを開き、強制カラーモードは「Emulate CSS media feature forced-colors」で `active` を選びます。動きを減らす設定は、「Emulate CSS media feature prefers-reduced-motion」で `reduce` を選びます。項目の名前は、Chrome DevToolsのドキュメントによるものです。

強制カラーモードでは、背景色や `box-shadow` で描いた境界が消えます。ボタンやカードの範囲が分からなくならないか、背景画像やマスクで描いたアイコンが消えないかを見ます。対処の方法は「[15-5 強制カラーモードとコントラスト](/color-media/forced-colors/)」で説明しています。動きを減らす設定では、画面を大きく動かすアニメーションやスクロールの演出が止まるか、止めたときに内容が隠れたままにならないかを見ます。設定への対応は「[18-2 動きを減らす設定に対応する](/motion/reduced-motion/)」で説明しています。

最後に、ページをグレースケールで表示します。ホバーやフォーカス、選択中の状態を色の変化だけで表していると、色を抜いたときに状態の違いが分からなくなります。色の見え方には個人差があり、電子ペーパーの端末やOSのグレースケール表示で、色のない画面を使う人もいます。グレースケール表示は、色相の違いだけに頼っている箇所を見つける補助に使います。明るさの差が大きい2色は、形が同じでも色を抜いて区別できるので、区別できたことは、下線、形、アイコンが付いていることの証明にはなりません。それらの手がかりがあるかは、状態ごとの表示を見比べて別に確かめます。

本来はOSのグレースケール表示を使いますが、開発中は一時的にCSSで色を抜くのが手軽です。確認が終わったら、この宣言は消します。

```css title="一時的にページをグレースケールで表示する"
body {
  filter: grayscale(1);
}
```

`filter` を指定した要素は、`position: fixed` の子孫の包含ブロックになります。固定したヘッダーの位置がずれて見えたら、この宣言の影響を疑います。Chromeの開発者ツールでは、「Rendering」パネルの「Emulate vision deficiencies」で「Achromatopsia」を選ぶと、色を抜いた表示も再現できます。この選択肢は、Chrome DevToolsのドキュメントで確認しました。

## 補足と注意点

開発者ツールのエミュレーションは、OSの設定そのものではありません。強制カラーモードの色は、Windowsのテーマが選ぶ色と同じにはならず、動きを減らす設定も、OSのアニメーションの設定までは変えません。{/* 要検証: ブラウザ。エミュレーションと Windows の実際のハイコントラストテーマとの違い */}公開の前に一度は、Windowsのコントラストテーマや、iOSとmacOSの「視差効果を減らす」を実際に有効にして確かめます。

同じように、デバイスモードの幅はスマートフォンの実機ではありません。タッチの操作、ソフトウェアキーボードが開いたときの表示、アドレスバーの伸び縮みは、実機でしか確かめられません。開発者ツールで見つけられる崩れを先に直し、実機では開発者ツールで再現できない点だけを見ると、確認の時間を短くできます。

この節の確認は、AIが生成したコードにも同じように当てはまります。lintとレビューは書かれたコードを読む確認で、ブラウザで条件を再現する確認とは見つかるものが違います。テストページと開発者ツールの設定を用意しておけば、AIに直させた後の確認も同じ手順で繰り返せます。
