コンポーネントは、自分以外のことを何も参照しない状態で書きます。自分がどこに置かれ、周りに何があるかで決まるスタイルは、コンポーネントの外側に任せます。この章では、何をコンポーネントにするかの判定から始めて、この考え方にもとづくコンポーネントどうしの境界の引き方と、カスタムプロパティによる値の受け渡しを扱います。

私がコンポーネントを書くうえで目標としているのは、関係のない場所（たとえばフッター）へそのまま移しても崩れないことです。ルートに外側の余白を持たせたり、親から子の内部をセレクタで書き換えたりすると、この目標はすぐに果たせなくなります。親のCSSは子の内部構造に、子のCSSは親の置き方に依存するので、片方を直すともう片方も直すことになり、やがて詳細度の上書き合戦が始まります。

境界を守ったまま値をやり取りする手段が、カスタムプロパティです。子のコンポーネントは「外から変えてよい値」だけを公開プロパティとして用意し、親はその値を渡すだけにします。サイト全体で共有する値はデザイントークンにまとめ、別のコンポーネントの間で見た目をそろえたいときも、コンポーネントを統合せずにトークンを参照します。この考え方は、新しく作るサイトだけでなく、詳細度が破綻した既存のCSSを改修するときにも役立ちます。

以前は、置き場所に合わせて部品の見た目を変えるとき、親のCSSから子のクラス名を選んで上書きし、重なりの順は `z-index: 9999` のような大きな値で解決する書き方がよく使われていました。この章では、子が公開プロパティとして受け付ける値だけを親から渡し、重なりの順はトークンと `isolation` で決めます。命名の規則に頼っていた部品の範囲は、`@scope` で区切ります。

## この章で判断できるようになること

この章は、部品の責任の範囲と、部品の間で受け渡す値を決めるための章です。読み終えると、ある部品をコンポーネントにするか、コンポジションやユーティリティにするか、部品にしないかを、3つの問いから判断できるようになります。外側の余白や置き場所に応じたスタイルを見つけたときは、それをコンポーネント自身に書くか、外側に任せるかを決められます。値を外から変えたいときは、どれを公開プロパティとし、どれを内部プロパティやデザイントークンで持つかを選べます。幅やホバーの状態を子孫へ伝えるときは、スタイルクエリのフラグと `:has()` のどちらを使うかも判断できます。


## この章の節

章は次の8つの節で構成しています。各コンポジションの詳しい使い方は、第12章「[レイアウトコンポジション](/compositions/)」で説明しています。

- [10-1 何をコンポーネントにするか](/components/what-is-a-component/)：コンポーネントの定義、繰り返し使うか・すべての使用箇所（全インスタンス）で構造や属性を制御したいか・既知の構造の拡張があるかの3つの問い、コンポーネントにしないもの、子要素を分ける条件
- [10-2 コンポーネントの境界を守る](/components/boundaries/)：1つのコンポーネントを1つのファイルに書くこと、外部関連型のレイアウトをルートへ書かない理由、ほかのコンポーネントの内部を触らずに値を渡す方法、z-indexの扱い
- [10-3 コンポジションとユーティリティ](/components/compositions-and-utilities/)：stackやclusterなどの配置のパターンと、ユーティリティにする範囲
- [10-4 デザイントークン](/components/design-tokens/)：`--<分類>--<名前>` の命名と、余白・色・イージング・z-indexのトークンの設計
- [10-5 公開プロパティと内部プロパティ](/components/custom-properties/)：カスタムプロパティの命名、状態を表す接尾辞、`style` 属性での受け渡し、`@property` の使いどころ
- [10-6 スタイルクエリで状態を伝える](/components/style-queries/)：幅やホバーとフォーカスの状態を `--_density` や `--_hocus` のフラグとして1か所で立て、子孫を `@container style()` で切り替える書き方と、`:has()` との使い分け
- [10-7 置き場所と子の状態を伝える](/components/placement-and-child-states/)：置き場所の構造を公開プロパティのフラグで渡し、幅のフラグと組み合わせる書き方と、子の状態で親を変える `:has()`
- [10-8 Web Components](/components/web-components/)：カスタム要素をコンポーネントのルートにする書き方、JavaScriptがなくても動くHTMLを先に作る順番、Light DOMとShadow DOMの使い分け

コード例で使っている `@scope (.scoped.<名前>) to (.scoped)` の仕組みは「[4-4 @scopeでスタイルを閉じ込める](/cascade/scope/)」で、レイヤーの順序は「[4-3 カスケードレイヤーで順位を決める](/cascade/layers/)」で説明しています。クラス名の付け方は「[9-1 命名規則](/notation/naming/)」で扱います。`gap` と `margin` の使い分けは「[11-2 余白を設計する](/layout-practice/spacing/)」で、スタッキングコンテキストの仕組みは「[11-6 重なりと全幅](/layout-practice/layering/)」で扱います。この章のコード例では、説明に関係しない `@layer` の記述を省略しています。デモのCSSには省略せずに書いています。

## 最初に押さえるルール

次のルールを先に押さえ、ほかのルールは、該当する場面で付録A「[ルール一覧](/appendix/rules/)」から引けば足ります。

- [`no-other-component-internals`](/components/boundaries/#rule-no-other-component-internals)：ほかのコンポーネントのルートや内部の要素を、セレクタで選んで見た目を上書きしません。
- [`no-external-layout-on-root`](/components/boundaries/#rule-no-external-layout-on-root)：コンポーネントのルートに、`margin` や `grid-area` のような、置かれ方で決まるレイアウトの指定を書きません。
- [`public-property-naming`](/components/custom-properties/#rule-public-property-naming)：外から変えてよい値は、`--card--radius` のような `--<コンポーネント>--<プロパティ>` の公開プロパティにします。
- [`receive-public-property-with-fallback`](/components/custom-properties/#rule-receive-public-property-with-fallback)：公開プロパティはコンポーネント自身では宣言せず、`:scope` で内部プロパティに受けて、デフォルト値を `var()` のフォールバックに書きます。
- [`density-via-style-query`](/components/style-queries/#rule-density-via-style-query)：同じ閾値で見た目の変わる子要素が2つ以上あるときは、コンテナサイズクエリをフラグを宣言する1つのルールだけに書き、ほかの子孫はスタイルクエリでフラグを読みます。変わる要素が1つだけなら、フラグを作らず、その要素のルールにクエリを直接書きます。

## 判断の問い

この章の内容で答えられる問いを1つ置きます。答えを開く前に、どこを直すかを予想してください。

記事のカードをサイドバーにも縦に並べたところ、サイドバーではカードどうしの間隔を広げてほしいと言われました。間隔の指定は、カードのルート、カードの中、カードを並べる側のどこに書きますか。

<details>
{/* textlint-disable ja-technical-writing/ja-no-mixed-period */}
<summary>答えと解説</summary>
{/* textlint-enable ja-technical-writing/ja-no-mixed-period */}

カードを並べる側に書きます。サイドバーのリストに `gap` を指定するか、`stack` のようなコンポジションに間隔を渡します。カードどうしの間隔は、カードの置き方の問題で、それを知っているのは並べる側だからです（`parent-owns-child-placement`）。

カードのルートに `margin` を書くと、新着の一覧や関連記事のような、ほかの置き場所でも同じ余白が付きます（`no-external-layout-on-root`）。サイドバーのときだけ余白を変えるために、カードの中で置き場所を判定し始めると、カードが自分の置かれ方を知ることになり、境界を守れなくなります（「[10-2 コンポーネントの境界を守る](/components/boundaries/)」）。

</details>

## 手を動かす課題

判断の問いでは、間隔をどこに書くかを選びました。ここでは、「[最小の構成で始める](/introduction/quick-start/)」のお知らせのカードを2か所に置き、片方の置き場所でだけ見た目を変えます。第4章の課題を終えたファイルから始めてかまいません。

`index.html` に、主欄の `main` 要素と、サイドバーの `aside` 要素を置き、それぞれに `ul` でカードを2枚ずつ並べます。主欄では、カードどうしの間隔と、カードの内側の余白を、どちらも24pxにします。サイドバーでは、どちらも16pxにします。`news-card.css` には `main` や `aside` を書かず、置く側のCSSでもカードのクラスや `h2` を選ばないでください。

合格の条件は2つです。`news-card.css` を読んでも、カードがサイドバーに置かれることが分からないことと、サイドバーのための指定がどのファイルのどの行にあり、それが主欄のカードに影響しない理由を説明できることです。

<details>
{/* textlint-disable ja-technical-writing/ja-no-mixed-period */}
<summary>答えの例と解説</summary>
{/* textlint-enable ja-technical-writing/ja-no-mixed-period */}

カードどうしの間隔は並べる側が持ち、内側の余白はカードが公開プロパティで受け取ります。カードは、内側の余白を `--news-card--padding` で受け、`:scope` で内部プロパティに受けてデフォルト値を書きます。`tokens/sizes.css` には、16pxに当たる `--spacing--sm: 16;` を足しておきます。

```css title="🙆‍♂ Recommended: カードは内側の余白を公開プロパティで受け取る" use="diff" from="tasks/10-components/css/components/news-card.css"
@scope (.scoped.news-card) to (.scoped) {
  :scope {
    --_padding: var(--news-card--padding, calc(var(--spacing--md) * 1px));

    padding: var(--_padding);
  }
}
```

並べる側には、「[10-3 コンポジションとユーティリティ](/components/compositions-and-utilities/)」の `stack` を使います。`stack` のCSSを `css/compositions/stack.css` に置き、エントリーポイントで `layer(compositions)` として読み込みます。値は、置く側の `ul` の `style` 属性で渡します。カードの間隔は段落の間ではなく部品の間なので、文字の大きさに追従させず、pxで渡します（「[6-1 pxとremを使い分ける](/values/px-and-rem/)」）。サイドバーの `ul` に書いた `--news-card--padding` は、継承で中の2枚のカードにまとめて届きます。

```html title="index.html の body の中"
<main>
  <ul class="stack" style="--stack--gap: calc(var(--spacing--md) * 1px)">
    <li><article class="scoped news-card">…</article></li>
    <li><article class="scoped news-card">…</article></li>
  </ul>
</main>
<aside>
  <ul class="stack" style="--stack--gap: calc(var(--spacing--sm) * 1px); --news-card--padding: calc(var(--spacing--sm) * 1px)">
    <li><article class="scoped news-card">…</article></li>
    <li><article class="scoped news-card">…</article></li>
  </ul>
</aside>
```

サイドバーのための指定は、`aside` の中の `ul` の `style` 属性の1か所だけです。値は継承でその `ul` の子孫にしか届かないので、主欄のカードはデフォルト値の24pxのままです。カードの中で `aside` を判定していないので、3つ目の置き場所が増えても、カードのCSSは変わりません（`parent-owns-child-placement`、`receive-public-property-with-fallback`）。

答えの例のファイル一式は、[補足サイト](/book-support/index.html)のサンプル一式の `tasks/10-components/` にあります。

</details>

## 従来の設計手法との対応

{/* 要確認: 出典なし */}

この章の考え方は、[OOCSS](https://github.com/stubbornella/oocss/wiki)、[BEM](https://en.bem.info/methodology/)、[SMACSS](https://smacss.com/ja)、[FLOCSS](https://github.com/hiloki/flocss)といった従来のCSS設計の手法と、目指すところの多くが重なります。どの手法も、部品の責任の範囲を決め、ほかの場所へスタイルが影響しないようにしてきました。違うのは、その範囲を守る手段です。従来の手法は、命名の規則とファイルの分け方を人が守ることで範囲を保ち、本書は同じ役目の多くを `@scope` やカスケードレイヤーといったCSSの仕組みに任せています。

OOCSSは、Nicole Sullivanが提唱した手法で、構造と見た目の分離と、コンテナとコンテンツの分離を原則にしています。コンテナとコンテンツの分離は、部品の見た目を置き場所に依存させず、どこでも同じにする考え方です。これは、外部関連型のレイアウトをルートに書かず、関係のない場所へ移しても崩れないコンポーネントを目指す、「[10-2 コンポーネントの境界を守る](/components/boundaries/)」の考え方とほぼ同じです。

従来の手法が名前と読み込みの順番で範囲を管理していたのは、CSSにスコープとレイヤーの仕組みがなかったからです。BEMの `.block__element` という名前は、ページ全体で1つの名前空間の中で衝突を避けるためのものです。FLOCSSのレイヤーと `l-` や `c-` の接頭辞は、どのスタイルを優先するかを、ファイルの読み込み順と詳細度で管理するためのものです。どちらも、全員が規則を守っている間は機能しますが、誰かが名前を取り違えたり、詳細度の高いセレクタを書いたりすると崩れます。`@scope` はスタイルの届く範囲を、`@layer` は優先の順番をCSSの仕組みとして決めるので、名前は短くてよく、詳細度で上書きし合う必要もありません。ビルドの段階でスコープを作る方法も、名前の衝突を人の注意ではなく仕組みで防ぐという点で共通しています。CSS Modulesはクラス名を一意な名前に書き換え、Vueのscoped CSSは要素に属性を足してセレクタに属性セレクタを足します。

従来の手法に慣れている場合は、次の表で本書の書き方との対応を確かめてください。

| 従来の手法での書き方 | 本書での書き方 |
|---|---|
| BEMの `.block__element` | `@scope` の中の `._main-link` のような子要素のクラスか、タイプセレクタ（[9-2](/notation/variants/)） |
| BEMの修飾子 `.block--modifier` | `data-variant` などの属性（[9-2](/notation/variants/)） |
| SMACSSとFLOCSSの状態クラス `.is-active` | 擬似クラス、HTML要素の属性、ARIA属性（[17-3](/interaction/state-attributes/)） |
| FLOCSSのレイヤーと、ファイルの読み込み順 | `@layer` の順番（[4-3](/cascade/layers/)） |
| FLOCSSのComponentとProject（`c-`、`p-`） | `scoped <名前>` のコンポーネント（[10-1](/components/what-is-a-component/)） |
| SMACSSとFLOCSSのLayout（`l-`） | ヘッダーやフッターはコンポーネント、子の並べ方はコンポジション（[10-3](/components/compositions-and-utilities/)） |
| FLOCSSのUtility（`u-`） | `-` で始まるユーティリティ（[10-3](/components/compositions-and-utilities/)） |
| OOCSSのコンテナとコンテンツの分離 | 外部関連型のレイアウトをルートに書かない（[10-2](/components/boundaries/)） |

手段が仕様の側に移っても、何を1つの部品とみなし、その責任をどこまでとするかは、人が決めなければなりません。この判断を誤れば、名前の規則で範囲を守っていた頃と同じく、部品は置き場所に依存し、上書きが重なっていきます。この判断の基準は「[10-1 何をコンポーネントにするか](/components/what-is-a-component/)」で扱います。

## この章の判断のまとめ

部品を共通化したくなったら、見た目が似ているかではなく、HTMLの構造や属性、振る舞いを1か所で管理したいかを問い、見た目だけならトークンかパターンで共有します。外側の余白や幅、隣との重なり順のように置き場所で変わる指定は、コンポーネント自身ではなく、並べる側の `gap` やOuterの要素に書きます。親から子の見た目を変えたくなったら、子のクラスを選ばずに、子が公開しているプロパティへ値を渡します。

同じ閾値や同じ状態で複数の子孫が変わるなら、状態を1か所でフラグにしてスタイルクエリで読ませ、子の状態で親自身を変えるなら `:has()` を選びます。「判断の問い」のサイドバーの間隔は、置き場所で変わる指定を並べる側に書く例です。
