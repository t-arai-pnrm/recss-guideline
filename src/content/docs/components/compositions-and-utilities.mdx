要素を縦に積む、横に並べて折り返す、幅に応じて列数を切り替えるといった配置は、多くのコンポーネントに共通します。こうした配置は、コンポーネントから切り離した「コンポジション」（`stack`、`cluster`、`switcher` など）で扱います。コンポジションは配置だけを受け持ち、間隔や列数は公開プロパティで受け取ります。間隔のデフォルト値は0にして、使う側で指定します。

ユーティリティは、視覚的に隠す、数字の幅をそろえるといった、どこに付けても同じ意味を持つ単機能のクラスに限ります。余白や配置の調整は、まずコンポーネントのCSSで行い、それで足りなければコンポジションやユーティリティを検討します。見た目の断片をまとめるパターンには、コンポーネントが変えないプロパティだけを書きます。この節の最後には、Tailwind CSSのようなユーティリティファーストの手法との付き合い方をコラムとしてまとめました。

## 配置をコンポーネントごとに書くと起きること

タグの一覧、ボタンの並び、フッターのリンク集のように、「横に並べて、入りきらなければ折り返す」配置はサイトのあちこちに出てきます。これを各コンポーネントで毎回書くと、似た指定が少しずつ違う形で散らばります。

```css title="🙅‍♂ Not Recommended: 同じ配置をコンポーネントごとに書く" issue="behavior"
/* 🙅‍♂ Not Recommended */
.tag-list {
  display: block flex;
  flex-wrap: wrap;
  gap: 8px;
}

.button-group {
  display: block flex;
}

.button-group > * + * {
  margin-inline-start: 10px;
}
```

本書は、重複をむやみに恐れない立場です（「[2-3 保守しやすさを最優先にする](/design-mindset/maintainability/)」）。この例で問題なのは重複そのものより、守りの指定が抜けやすいことです。2つ目の `.button-group` には `flex-wrap: wrap` がないので、ボタンが増えたり画面が狭くなったりすると、はみ出します。間隔を子の `margin` で作っているので、仮に折り返せたとしても、2行目の先頭に余計な余白が残ります。

配置のたびに同じ注意点を思い出すのは、人とAIのどちらにとっても負担です。また、CSSを読まないと、その要素の子がどう並ぶのかが分かりません。配置をコンポジションにしておけば、守りの指定は1か所に集まり、HTMLのクラス名を見るだけで並び方の意図が読み取れます。

## コンポジションの書き方

コンポジションは、レイアウト上の再利用パターンをまとめたクラスです。`compositions` レイヤーに置き、名前は接頭辞のないkebab-caseにします。コンポジションが受け持つのは配置だけで、色や文字の大きさのような見た目は持ちません。

```css title="🙆‍♂ Recommended: 配置だけを受け持ち、間隔は公開プロパティで受け取る"
/**
 * 子要素を縦に積む。
 *
 * @prop {length} --stack--gap [0] - 子要素の間隔
 */
.stack {
  display: block flex;
  flex-direction: column;
  gap: var(--stack--gap, 0);
}

/**
 * 子要素を横に並べ、入りきらなければ折り返す。
 *
 * @prop {length}  --cluster--gap           [なし]   - 行と列の間隔（一括）。指定すると個別の指定より優先する
 * @prop {length}  --cluster--row-gap       [0]      - 行の間隔
 * @prop {length}  --cluster--column-gap    [0]      - 列の間隔
 * @prop {keyword} --cluster--justification [normal] - 主軸の配置
 * @prop {keyword} --cluster--alignment     [normal] - 交差軸の配置
 */
.cluster {
  display: block flex;
  flex-wrap: wrap;
  gap: var(--cluster--gap, var(--cluster--row-gap, 0)) var(--cluster--gap, var(--cluster--column-gap, 0));
  justify-content: var(--cluster--justification, normal);
  align-items: var(--cluster--alignment, normal);
}
```

この定義では、説明で使う宣言だけを書いています。`flex-wrap: balance` を対応している環境でだけ足す完全な定義は、「[12-3 cluster：子を横に並べ、入りきらなければ折り返す](/compositions/cluster/)」にあります。

使う側は、HTMLにクラス名を書き、間隔などの値を `style` 属性で渡します。`class="cluster"` とあれば、その要素の子が横に並んで折り返すことが、CSSを開かなくても分かります。

```html
<ul class="cluster" style="--cluster--gap: calc(var(--spacing--xxs) * 1px)">
  <li>…</li>
</ul>
```

コンポジションは、コンポーネントの中の要素に付けても、コンポーネントのルートに付けてもかまいません。コンポジションが決めるのは直下の子の並び方と間隔だけで、子の内部を指定しないからです。ただし、コンポジションを付けた要素では、そのルールに `display` や `gap` を書きません。コンポジションは `compositions` レイヤーにあり、後に並ぶ `components` レイヤーの同じプロパティの宣言に負けるからです（「[4-3 カスケードレイヤーで順位を決める](/cascade/layers/)」）。「[10-2 コンポーネントの境界を守る](/components/boundaries/)」で説明した「配置は置く側が持つ」という考え方を、再利用できる形にしたものです。

ファイルの先頭には、JSDocの形式で公開プロパティの一覧を書きます。`@prop {型} --名前 [デフォルト値] - 説明` の形で書いておけば、使う人は実装を読まずに、変えられる値とデフォルト値を確認できます。コメント全般の書き方は「[9-10 コメントの書き方](/notation/comments/)」で扱います。

## 主なコンポジション

私が使っている主なコンポジションは次のとおりです。stack、cluster、switcher、sidebarといった名前は、Every Layoutなどで広まった配置パターンの名前にならっています。それぞれの使い方、公開プロパティの一覧、内部の計算、使い分けは、第12章「[レイアウトコンポジション](/compositions/)」の各ページで詳しく説明しています。

| 名前 | 配置 | 主な公開プロパティ |
|---|---|---|
| [`stack`](/compositions/stack/) | 子を縦に積む | `--stack--gap` |
| [`cluster`](/compositions/cluster/) | 子を横に並べ、入りきらなければ折り返す | `--cluster--gap`、`--cluster--justification` |
| [`apart`](/compositions/apart/) | 子をインライン方向の両端に分け、入りきらなければ折り返す | `--apart--gap`、`--apart--column-gap`、`--apart--alignment` |
| [`switcher`](/compositions/switcher/) | 幅が閾値以上なら指定の列数で並べ、下回ったら1列にする | `--switcher--column-count`、`--switcher--column-min-width` |
| [`sidebar`](/compositions/sidebar/) | メインとサイドの2カラムにし、狭ければ縦に積む | `--sidebar--side-width`、`--sidebar--main-min-width` |
| [`grid`](/compositions/grid/) | 列の最小幅と最大数から、列数を自動で決める | `--grid--column-min-width`、`--grid--column-max-count`、`--grid--mode` |
| [`columns`](/compositions/columns/) | 上から下へ読むリストを段に分ける | `--columns--column-width`、`--columns--column-max-count` |
| [`masonry`](/compositions/masonry/) | 高さの違う子を、いちばん短い列へ順に詰める | `--masonry--column-min-width`、`--masonry--column-max-count` |
| [`pile`](/compositions/pile/) | すべての子を同じグリッドのセルに重ねる | `--pile--placement`、`--pile--alignment`、`--pile--justification` |
| [`primary-layout`](/compositions/primary-layout/) | コンテンツの最大幅とガターを決め、子ごとに全幅などの幅を選ばせる | `--primary-layout--content-max-width`、`--primary-layout--gutter` |
| [`prose`](/compositions/prose/) | 本文の流れの間隔を作り、子ごとに間隔を変えられるようにする | `--prose--space` |

幅によって列数や折り返しが変わるコンポジションも、メディアクエリは使いません。`flex-wrap: wrap` による折り返し、`auto-fit` と `minmax()` による列数の自動調整、`sign()` による閾値の判定で、幅の変化に対応します。「[13-1 検討する順番](/responsive/escalation/)」で説明した「イントリンシック」の段階を、部品として用意しておくわけです。子を重ねる `pile` は、ルートに `isolation: isolate` を指定して、重なりをコンポジションの中に閉じ込めています。

本文の段落の間隔を作る `prose` もコンポジションの1つです。`gap` ではなく2つ目以降の子の `margin-block-start` で間隔を作るので、子ごとに間隔を変えられます。本文の余白の設計とあわせて、「[11-2 余白を設計する](/layout-practice/spacing/)」でも扱っています。

## コンポジションの間隔のデフォルト値

コンポジションの間隔のデフォルト値は `0` にします。間隔は、コンポジションを置く文脈によって決まる値で、コンポジション自身では決められないからです。デフォルト値に余白のトークンを入れておくと、指定し忘れた箇所にも何となく余白が付き、デザインと合っていないことに気付きにくくなります。

`cluster` のように行と列の2方向の間隔を持つコンポジションでは、`--cluster--gap` で一括に、`--cluster--row-gap` と `--cluster--column-gap` で個別に指定できるようにします。`var(--cluster--gap, var(--cluster--row-gap, 0))` のようにフォールバックを連ねると、「一括の指定があればそれを、なければ個別の指定を、どちらもなければ0を使う」という意味になります。

間隔の値には、余白のトークンを単位に変換したものを渡します。上のHTMLの例では、`--spacing--xxs` を `calc(var(--spacing--xxs) * 1px)` でpxに変換しています。タグの間のような部品の間の間隔は、文字の大きさと連動させず、pxで渡します（「[6-1 pxとremを使い分ける](/values/px-and-rem/)」）。トークンを単位なしの数値で持つ理由は「[10-4 デザイントークン](/components/design-tokens/)」で説明します。

`switcher` のように、受け取った値から閾値などを計算するコンポジションでは、計算の途中の値を `--_c--` で始まる内部プロパティに置きます。`switcher` の中心は次の1行です。

```css
grid-template-columns: repeat(auto-fit, minmax(max(var(--_c--column-preferred-width), sign(100% - var(--_c--threshold)) * -100%), 1fr));
```

`--_c--threshold` は、「列の最小幅×列数＋列の間隔×（列数−1）」で求めた閾値です。`sign()` は、引数が正なら1、負なら-1を返す関数です。要素の幅が閾値より広ければ掛け算の結果は `-100%`、ちょうど閾値なら `0%` になり、どちらでも列の最小幅は1列あたりの幅の目安（`--_c--column-preferred-width`）のままです。閾値を下回ると `100%` になるので、列の最小幅が要素の幅いっぱいになり、1列に切り替わります。実際の列の幅は `1fr` で均等に広がります。

<Baseline id="abs-sign" name="abs() と sign()" />

`sign()` は、2025年6月にすべての主要なブラウザで使えるようになった関数です。本書の対象のブラウザ（Safari 18系の最終版以降）では動作します。内部プロパティの命名は「[10-5 公開プロパティと内部プロパティ](/components/custom-properties/)」で説明します。

次のデモでは、全体を `stack` で縦に積み、タグの一覧に `cluster` を、3つのパネルに `switcher` を使っています。パネルの中の見出しと本文も `stack` です。どのコンポジションにも、間隔は `style` 属性で渡しています。幅を480pxと768pxで比べると、3つのパネルが1列と3列の間で切り替わります。

<Demo title="stack、cluster、switcher を組み合わせ、間隔を style 属性で渡す" html={compositionsHtml} css={compositionsCss} />

`switcher` の閾値は「160px相当×3列＋16px相当×2」の512px相当です。デモのCSSのうち、コンポーネント（`composition-demo`）が書いているのは、タグとパネルの見た目だけです。並び方と間隔は、すべてコンポジションとHTMLの `style` 属性で決まっています。

`grid` も、内部プロパティで列の幅を計算するコンポジションです。`auto-fill` と `minmax()` だけで列数をブラウザに任せると、広い画面では列がいくらでも増えます。「列の数は幅に合わせて変えたいが、5列より多くはしたくない」という要件に応えるのが `grid` です。

```css title="🙆‍♂ Recommended: 列の最小幅と最大数から、列の幅を計算する"
/**
 * 列の最小幅と最大数から、列の数を自動で決める。
 *
 * @prop {keyword} --grid--mode             [auto-fill]             - repeat() のキーワード（auto-fill | auto-fit）
 * @prop {length}  --grid--column-min-width [calc(320 / 16 * 1rem)] - 列の最小幅（これより狭くなると列が減る）
 * @prop {integer} --grid--column-max-count [5]                     - 列の最大数
 * @prop {length}  --grid--gap              [なし]                  - 行と列の間隔（一括）。指定すると個別の指定より優先する
 * @prop {length}  --grid--row-gap          [0px]                   - 行の間隔
 * @prop {length}  --grid--column-gap       [0px]                   - 列の間隔（単位を付けて渡す）
 */
.grid {
  --_c--mode: var(--grid--mode, auto-fill);
  --_c--row-gap: var(--grid--gap, var(--grid--row-gap, 0px));
  --_c--column-gap: var(--grid--gap, var(--grid--column-gap, 0px));
  --_c--column-max-count: var(--grid--column-max-count, 5);
  --_c--column-min-width: var(--grid--column-min-width, calc(320 / 16 * 1rem));
  --_c--column-preferred-width: calc(
    (100% - var(--_c--column-gap) * (var(--_c--column-max-count) - 1)) / var(--_c--column-max-count)
  );

  /* 要素の幅より広い列ははみ出すので、min(100%, …) で要素の幅に収める */
  --_c--column-width: min(100%, max(var(--_c--column-min-width), var(--_c--column-preferred-width)));

  display: block grid;
  grid-template-columns: repeat(var(--_c--mode), minmax(var(--_c--column-width), 1fr));
  gap: var(--_c--row-gap) var(--_c--column-gap);
}
```

`--_c--column-preferred-width` は、最大の列数で並べたときの1列の幅です。要素の幅から列の間隔の合計を引き、最大の列数で割って求めます。`minmax()` の最小値には、この幅と列の最小幅の大きいほうを使います。広い場所では最大の列数で割った幅のほうが大きくなるので、それより多くの列は入りません。狭い場所では列の最小幅のほうが大きくなり、入らなくなった列から順に次の行へ折り返されます。

全体を `min(100%, …)` で包んでいるのは、要素の幅が列の最小幅より狭いときに、列が要素からはみ出さないようにするためです。たとえば列の間隔を24px相当にすると、960pxの場所では列の最小幅の320px相当のほうが大きいので2列に、2400pxの場所では最大の列数で割った幅のほうが大きいので5列になります。列の数を決めるキーワードのデフォルトを `auto-fit` ではなく `auto-fill` にしているので、アイテムが3つしかないときも、列の幅は5列のときのまま変わりません。空いた列を詰めて広げたい場面では、`--grid--mode: auto-fit` を渡します。2つのキーワードの違いは「[13-1 検討する順番](/responsive/escalation/)」で説明しています。

## ユーティリティにする範囲

ユーティリティは、単機能の補助クラスです。名前は `-` で始め、`.-visually-hidden` や `.-tabular-nums` のように付けます。段階のあるものは、`.-fluid-text--md` のように `--` の修飾で表します。命名の規則は「[9-1 命名規則](/notation/naming/)」で扱います。

ユーティリティは、レイヤーの順序で最後の `utilities` に置くので、コンポーネントのスタイルより優先されます。そのため、ユーティリティにしてよいのは、どこへ付けても同じ意味を持ち、コンポーネントの指定に勝っても困らないものだけです。視覚的に隠してスクリーンリーダーには読ませる `.-visually-hidden` は、その典型です。付けた以上は、どのコンポーネントの中でも確実に隠れなければ意味がありません。定義と、ほかの隠し方との使い分けは「[17-5 要素を隠す方法を選ぶ](/interaction/hiding-elements/)」で説明しています。

私が使っているテンプレートでは、アクセシビリティのための `.-visually-hidden` と、タイポグラフィのためのクラスをユーティリティにしています。後者には、中央揃えにする `.-text-center`、数字の幅をそろえる `.-tabular-nums`、行の上下のハーフレディングを削る `.-trim-both` などがあります。

```css title="🙆‍♂ Recommended: どこに付けても同じ意味を持つ単機能のクラス"
.-tabular-nums {
  font-variant-numeric: tabular-nums;
}

.-text-center {
  text-align: center;
  text-wrap: balance;
}
```

余白や配置の細かな調整は、まずコンポーネントのCSSで行います。コンポーネントのCSSだけで済まなければコンポジションかユーティリティを検討し、それでも静的な見た目の断片として残るなら、次に説明するパターンを考えます。

コンポジションとユーティリティの間には、もう1つ「パターン」という分類があります。パターンは、アイコンの大きさを決める `.icon` のような、静的で再利用できる見た目の断片で、`patterns` レイヤーに置きます。名前は `big-title` のような見た目ではなく、`section-heading` のような役割から付けます。同じ見た目が3回出てきたらパターンへの昇格を検討してよいという目安がありますが、回数だけで機械的に昇格させることはしません。「少しだけ角丸がほしい」「ここだけ影がほしい」といった都合だけで、パターンやコンポーネントを作らないようにします。

## パターンに書いてよいプロパティ

パターンには、重ねるコンポーネントが指定しないプロパティだけを書きます。`patterns` は `components` より後ろのレイヤーにあるので、パターンを付けた要素では、同じプロパティについてパターンの指定が勝ちます。カスケードは、詳細度より先にレイヤーの順番を比べるからです。コンポーネントの側でセレクタを子クラスに変えたり、属性セレクタを重ねたりして詳細度を上げても、結果は変わりません。

この強さの差は、バリエーションのスタイルや `@container` の中の指定にも及びます。次の例では、`feature-section` が見出しに、広い場所での大きな文字サイズと、`featured` のバリエーションの色を指定しています。しかし、見出しには `section-heading` のパターンが付いていて、パターンが `font-size` と `color` を持っています。コンポーネントの指定はどちらも反映されず、見出しはパターンの大きさと色のままです。

```css title="🙅‍♂ Not Recommended: コンポーネントが変えたいプロパティをパターンに書く" issue="behavior"
/* 🙅‍♂ Not Recommended */
@layer patterns {
  .section-heading {
    font-size: calc(24 / 16 * 1rem);
    font-weight: 700;
    color: var(--foreground--base);
    text-wrap: balance;
  }
}

@layer components {
  @scope (.scoped.feature-section) to (.scoped) {
    :scope {
      container: --scoped / inline-size;
    }

    /* h2 には class="section-heading" が付いている。どちらの指定も反映されない */
    h2 {
      @container --scoped (inline-size >= calc(640 / 16 * 1rem)) {
        font-size: calc(32 / 16 * 1rem);
      }

      &:is(:scope[data-variant="featured"] *) {
        color: var(--foreground--accent);
      }
    }
  }
}
```

コンポーネントの側で変える値は、パターンが公開プロパティとして受け取ります。名前は、コンポーネントの公開プロパティと同じ `--<パターン>--<プロパティ>` の形にします（「[10-5 公開プロパティと内部プロパティ](/components/custom-properties/)」）。パターンの中では、公開プロパティを `--_p--` で始まる内部プロパティに受け、デフォルト値を `var()` のフォールバックに書きます。公開プロパティそのものは宣言しません。パターンの中で宣言すると、その宣言も `patterns` レイヤーにあるので、コンポーネントから渡した値に勝ってしまいます。色のように置く場所ごとに決まる値は、パターンに書かず、コンポーネントに任せます。

```css title="🙆‍♂ Recommended: 変える値は公開プロパティで受け取り、色はコンポーネントに任せる"
/**
 * セクションの見出し。
 *
 * @prop {length} --section-heading--font-size [calc(var(--font-size--xxl) / 16 * 1rem)] - 文字の大きさ
 */
@layer patterns {
  .section-heading {
    --_p--font-size: var(--section-heading--font-size, calc(var(--font-size--xxl) / 16 * 1rem));

    font-size: var(--_p--font-size);
    font-weight: var(--font-weight--bold);

    @supports (word-break: auto-phrase) {
      text-wrap: balance;
      word-break: auto-phrase;
    }
  }
}

@layer components {
  @scope (.scoped.feature-section) to (.scoped) {
    :scope {
      --_heading-color: var(--foreground--muted);

      container: --scoped / inline-size;

      &[data-variant="featured"] {
        --_heading-color: var(--foreground--base);
      }
    }

    h2 {
      color: var(--_heading-color);

      @container --scoped (inline-size >= calc(640 / 16 * 1rem)) {
        --section-heading--font-size: calc(32 / 16 * 1rem);
      }
    }
  }
}
```

`feature-section` は、`h2` に `font-size` を直接書く代わりに、`--section-heading--font-size` に値を渡しています。パターンは、この公開プロパティを内部プロパティ `--_p--font-size` に受けて `font-size` に使うので、`@container` の条件を満たしたときだけ大きな文字になります。`color` はパターンが持たないので、コンポーネントの指定がそのまま反映されます。アイコンのパターン `.icon` なら、`--icon--size` を `--_p--size` に受けて `inline-size` に使い、`aspect-ratio: 1` と合わせてこの2つだけを持ちます。色は指定しません。SVGの側で `stroke="currentColor"` のように文字色を参照しておけば、アイコンの色は置かれたコンポーネントの文字色に従います。

`:hover` やフォーカスで色や背景が変わる見た目は、パターンにせず、コンポーネントにします。パターンに状態のスタイルを書くと、状態ごとの値もコンポーネントから変えられなくなるからです。状態を持つ時点で、静的な見た目の断片というパターンの定義からも外れます。また、パターンのセレクタを `:where()` で包んで詳細度を0にする必要はありません。強弱はレイヤーの順番で決まるので、詳細度を下げてもコンポーネントに対する強さは変わりません。

## パターンにするか、コンポーネントにするか

繰り返し使う見た目を、パターンにするかコンポーネントにするかは、次の3つの問いを順にたどって決めます。1つ目は、HTMLの構造を持つかです。子要素の並びや使う要素の種類まで決めたいなら、コンポーネントにします。2つ目は、ホバーやフォーカス、ARIA属性のような状態で見た目が変わるかです。変わるなら、コンポーネントにします。3つ目は、置かれた場所で変えたい値があるかです。あっても、公開プロパティで受け取れる値なら、パターンのままで足ります。

1つ目と2つ目の問いを「いいえ」で抜けた、構造と状態を持たない見た目だけが、パターンになります。`section-heading` は見出しの要素に重ねるだけで、状態で変わらず、大きさだけを公開プロパティで受け取るので、パターンです。反対に、押せる見た目は、ホバーとフォーカスで変わるので、要素を選ばずに付けたいものであってもパターンにしません。

たとえば、画像を選ぶ入力欄の `<label>` を、送信の `<button>` と同じ押せる見た目にしたい場面です。見た目を `.button-look` のようなパターンにすると、ホバーとフォーカスの指定が `patterns` レイヤーに入り、置かれたコンポーネントから状態の色を変えられなくなります。そこで、ルートに付ける要素を固定しないコンポーネントにします。

```html title="🙆‍♂ Recommended: 同じコンポーネントのルートを、button にも label にも付ける"
<button class="scoped action-control" type="submit">送信する</button>

<label class="scoped action-control">
  画像を選ぶ
  <input class="-visually-hidden" type="file" accept="image/*">
</label>
```

```css title="🙆‍♂ Recommended: 状態のスタイルを、要素を固定しないコンポーネントの中で完結させる"
@scope (.scoped.action-control) to (.scoped) {
  :scope {
    --_background: var(--background--inverse);
    --_background--hocus: color-mix(in oklab, var(--background--inverse) 80%, var(--background--base));

    background-color: var(--_background);
    color: var(--foreground--inverse);

    &:is(:focus-visible, :has(:focus-visible)) {
      background-color: var(--_background--hocus);
    }

    &:is(:any-link, :enabled, label):hover {
      @media (any-hover) {
        background-color: var(--_background--hocus);
      }
    }
  }
}
```

コンポーネントにしても、ルートに付ける要素は選べます。`<button>`、`<a>`、`<label>` のどれに付けても、ボタンとしての送信、リンクとしての移動、入力欄を開く動作のような、要素本来の意味と動作はそのまま残ります。ホバーは、リンクなら `:any-link`、ボタンなら `:enabled` に絞り、無効の状態がない `<label>` は条件を付けずに当てます（「[17-1 ホバーとフォーカスを表す](/interaction/states-and-focus/)」）。`<label>` の中の入力欄は視覚的に隠しているので、フォーカスはルートの `:has(:focus-visible)` で表します。名前を `button` にしないのは、`<button>` 以外の要素にも付けるからです（「[9-1 命名規則](/notation/naming/)」）。

## コラム：ユーティリティファーストとの付き合い方

本書は、素のCSSで書くことを前提にしています。私が使っているテンプレートの規約にも、「明示的な要求がない限り、Tailwind CSSやCSS-in-JSは使わない」と書いています。Web標準の機能だけで書いておけば、この本で説明しているカスケードレイヤーや `@scope` などの仕組みを、そのまま使えるからです。

とはいえ、実務でTailwind CSSの案件に関わることもあります。私は、Tailwind CSSをデザイントークンのlintとして優秀だと評価しています。あらかじめ定義した値の中から選んで書くので、トークンにない中途半端な値が紛れ込みにくいからです。

一方で、Tailwind CSSはGridのレイアウトが苦手です。`grid-template-areas` は任意の値として書けるものの扱いにくく、何でもFlexboxで組んだ実装になりがちです。私は素のCSSで `grid-template` を組んでから、AIにTailwind CSSの任意の値へ変換させることが多く、これは本末転倒だとも感じています。そこで、UIのコンポーネントはTailwind CSSで、レイアウトは素のCSSで書くという分担も有効だと考えています。

Tailwind CSSを使う場合も、この章の考え方はそのまま生かせます。コンポーネントのルートに外側の余白を持たせないこと、ほかのコンポーネントの内部をセレクタで選ばないこと、共有する値をトークンにまとめることは、道具に関係なくコンポーネントの境界を守るための原則です。
