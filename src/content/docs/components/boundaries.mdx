コンポーネントは、自分以外のことを何も参照しない状態で書きます。ルートには `padding` や `gap` のような、自分の中で完結するレイアウトだけを書きます。`margin` や `grid-area` のように周りとの関係で決まるレイアウトは、コンポーネントを置く側に任せます。ほかのコンポーネントの内部の要素はセレクタで選ばず、そのコンポーネントが公開しているカスタムプロパティを通じて値を渡します。自分の中の要素はタイプセレクタで選び、同じ種類の要素を役割で区別するときと、`div` と `span` に役割を示すときだけ子クラスを付けます。

z-indexも同じ考え方で扱います。ルートにはページ全体の重なり順を決める絶対的な値だけを、内部の要素には1か-1の相対的な値だけを、どちらもトークンで指定します。内部で相対的な値を使うコンポーネントは、ルートに `isolation: isolate` を指定して、重なりをコンポーネントの中に閉じ込めます。

この節では、何をコンポーネントにするかが決まったあとの、コンポーネントどうしの境界の守り方を扱います。何をコンポーネントにするかの判定は、「[10-1 何をコンポーネントにするか](/components/what-is-a-component/)」で説明しています。

初めて読むときは、最初の4つの見出しを読みます。1つのファイルに書くこと、ルートに書くレイアウトと置く側に任せるレイアウト、親から子へ公開プロパティで値を渡すこと、自分の中の要素をタイプセレクタで選ぶことです。タイプセレクタの細かな規約とz-indexは、その場面が来てから戻ってください。

## 1つのコンポーネントのCSSは1つのファイルに書く

コンポーネントのCSSは、必ずコンポーネントごとに1つのファイルに分けます。複数のコンポーネントのCSSを、1つのファイルに混ぜることはしません。ファイル名はルートの名前と同じ `product-card.css` のようにし、中にはそのコンポーネントの `@scope` だけを書きます。ルートの名前とファイル名を対応させる理由は、「[9-1 命名規則](/notation/naming/)」で説明しています。

小さなコンポーネントや、いつも一緒に使う部品は、近くのファイルに書き足したくなります。しかし、一度混ぜると、「どこに何が書いてあるか分からない」コードが簡単にできあがります。名前からファイルを開いても目当ての指定が見つからず、ファイルを消すとほかのコンポーネントの指定まで消えるので、使わなくなったコンポーネントを捨てることもできなくなります。

面倒に感じても、例外を作らずに必ず分けます。ファイルを1つ作る手間は、後から指定を探す手間や、混ざったファイルを分け直す手間よりずっと小さいからです。例外を1つ許すと、次に触る人もそれにならって書き足すので、混在はすぐに広がります。AIにコードを書かせるときも、既存のファイルへの追記ではなく、新しいファイルを作るように指示します。

AstroのようにCSSをコンポーネントのファイルの `<style>` に書く環境では、コンポーネントのファイルがそのまま1つの単位になります。この場合も、ほかのコンポーネントのスタイルを同じ `<style>` に書くことはしません。コンポジションも同じく、`stack.css`、`cluster.css` のように1つずつファイルを分けます。

## ルートに書くレイアウトと書かないレイアウト

「外部関連型のレイアウト」は私の造語です。レイアウトの指定には、`padding` や `grid-template` のように自分のスタイルだけで完結する「内部関連型」と、周りの要素との関係で成り立つ「外部関連型」があると考えています。外部関連型に当たるのは、次のようなプロパティです。

- `margin`：周りの要素との距離なので、置かれる場所によって必要な値が変わる
- `position: absolute` と `inset`：基準になる祖先の要素があって、初めて位置が決まる
- `flex`、`grid-area`、`justify-self`、`align-self`：親のFlexboxやGridの指定とセットで成り立つ
- `inline-size` と `block-size`（`width` と `height`）：多くの場合、親に決めさせたほうが使い回しやすい

カードのルートに書くものと、置く側が書くものの分担を、図にまとめます。

<Figure src="components/layout-inner-outer" alt="カードのルートと、置く側のコンポーネントの分担を示した図。破線で囲んだ置く側のコンポーネントの中に、2つの枠が並んでいる。左の枠はカードのルートで、内部関連型として、自分のスタイルだけで完結するdisplay、gap、padding、borderとborder-radius、grid-templateを挙げ、ルートに書くと示している。右の枠は外部関連型で、周りとの関係で成り立つmargin、inline-sizeとblock-size、position: absoluteとinset、flexとgrid-area、justify-selfとalign-selfを挙げ、置く側が書くと示している。右の枠から左の枠へ、矢印が向いている。" />

`min-inline-size` や `max-inline-size` は、文脈によって扱いが変わります。「このコンポーネントには最低でもこの幅が必要」のようにコンポーネント自身の決まりなら内部関連型、「親に対して最大50%」のように親との関係で決まるなら外部関連型です。`subgrid` は親がグリッドであることを前提にするので、両方の性質を持ちます。サブグリッドを使うカードは、並べる側のグリッドまで含めて1つのコンポーネントとして扱います。

外部関連型のレイアウトをルートに書くと、次のようなコンポーネントになります。

```css title="🙅‍♂ Not Recommended: ルートに幅と外側の余白を持たせる" issue="behavior"
/* 🙅‍♂ Not Recommended */
@scope (.scoped.news-card) to (.scoped) {
  :scope {
    inline-size: calc(50% - 12px);
    margin-block-start: 40px;
    padding: calc(var(--spacing--md) * 1px);
  }
}
```

このカードは、2列のグリッドの中で、前の要素から40px離れて置かれることを前提にしています。サイドバーに置けば半分の幅では狭すぎ、ページの先頭に置けば上に余計な余白ができます。置き場所ごとに `margin-block-start: 0` のような打ち消しを書くことになり、やがて打ち消しのための詳細度の競争が始まります。

外部関連型のレイアウトは、コンポーネントを置く側が持ちます。並べるときの間隔は親の `gap` で、特定の場所への配置や特別な余白は、親が子のコンポーネントを包む要素で指定します。この包む要素を、本書では「Outer」と呼びます。Outerは親のコンポーネントの子要素であり、単独のコンポーネントにはしません。

```css title="🙆‍♂ Recommended: 配置と外側の余白は、置く側のコンポーネントが持つ"
@scope (.scoped.news-section) to (.scoped) {
  :scope {
    & > * + * {
      margin-block-start: calc(var(--spacing--lg) * 1px);
    }

    & > * + ._banner-outer {
      margin-block-start: calc(var(--spacing--xl) * 1px);
    }
  }

  ul {
    display: block grid;
    grid-template-columns: repeat(auto-fit, minmax(min(100%, calc(240 / 16 * 1rem)), 1fr));
    gap: calc(var(--spacing--md) * 1px);
  }

  ._banner-outer {
    max-inline-size: calc(480 / 16 * 1rem);
  }
}

@scope (.scoped.news-card) to (.scoped) {
  :scope {
    padding: calc(var(--spacing--md) * 1px);
  }
}
```

```html
<section class="scoped news-section">
  <h2>お知らせ</h2>
  <ul>
    <li>
      <article class="scoped news-card">…</article>
    </li>
  </ul>
  <div class="_banner-outer">
    <aside class="scoped campaign-banner">…</aside>
  </div>
</section>
```

カードのルートには、内部関連型の指定しかありません。カードの幅はリストのグリッドが決め、キャンペーンのバナーの幅は `._banner-outer` が決めています。要素の間の余白は、前に要素があるときだけ `:scope` の中の `& > * + *` で付け、バナーの上だけを `& > * + ._banner-outer` で広げます。ルートは通常フローなので、バナーの上の余白はトークンの40pxのままで、ほかの間隔と足し合わされません。ルートをGridにして `gap` と `margin` を併用すると、バナーの上は `gap` の32pxと40pxを足した72pxになります。同じカードをサイドバーに置いても、サイドバー側のレイアウトに合わせて幅が決まるだけで、カードのCSSを直す必要はありません。

この形は、本書のスコープの基本形とも相性のよい書き方です。`@scope (.scoped.news-section) to (.scoped)` は、内側にある別の `.scoped` の要素でスコープを打ち切ります。打ち切る境界の要素そのものも範囲の外になるので、親のCSSからは子のコンポーネントのルートも選べません。親が子の配置を決めたければ自分の子要素であるOuterを用意するしかなく、書き方そのものが境界を守る仕組みになっています。スコープの書き方は「[4-4 @scopeでスタイルを閉じ込める](/cascade/scope/)」で説明しています。

同じ理由で、子のコンポーネントに `class` 属性を渡して、親から見た目や配置を変えることもしません。Astroなどのコンポーネントでは `class` を受け取れるようにするのは簡単ですが、許すと親が子のルートに自由にスタイルを当てられるようになり、どこまでが子の責任なのかが曖昧になります。

例外もあります。`position: fixed` で表示するモーダルは、ビューポートを基準に配置されることが明らかなので、ルートに外部関連型の指定を持たせてかまいません。ビューポートに粘着するグローバルヘッダーの `position: sticky` と `inset` も同じです。アイコンのような小さなグラフィックの要素は、自分で大きさを持つ必要があるので、`inline-size: 1em` のように親の文字サイズに追従する指定をルートに書きます。

## 親から子のコンポーネントの見た目を変える方法

親のコンポーネントが、置いた子の見た目を場所に合わせて変えたいことがあります。このとき、親のCSSで子のクラス名を選んで上書きするのは避けます。

```css title="🙅‍♂ Not Recommended: 親から子のコンポーネントの内部を上書きする" issue="convention"
/* 🙅‍♂ Not Recommended */
.hero .news-card {
  border-radius: 24px;
}

.hero .news-card ._title {
  font-size: calc(24 / 16 * 1rem);
}
```

この書き方には3つの問題があります。まず、子の元のスタイルより詳細度を高くしないと上書きできないので、詳細度の競争が始まります。次に、親のCSSが子の内部構造（`._title` という要素があること）に依存するので、子の構造を変えると親のCSSも直さなければなりません。最後に、子のCSSだけを読んでも、どこで見た目が変えられているのかが分かりません。

子のコンポーネントは、外から変えてよい値だけを「公開プロパティ」として用意します。親は、その公開プロパティに値を渡すだけにします。次の例では、カードが角丸の半径を `--news-card--radius` として公開し、デフォルト値を `var()` のフォールバックに書いています。

```css title="🙆‍♂ Recommended: 子は外から変えてよい値を公開プロパティにする"
@scope (.scoped.news-card) to (.scoped) {
  :scope {
    --_radius: var(--news-card--radius, var(--rounded--md));

    border-radius: var(--_radius);
  }
}
```

```html
<article class="scoped news-card" style="--news-card--radius: 24px">…</article>
```

値はカスタムプロパティを経由するので、セレクタの詳細度とは切り離されます。親は、子の中でその値がどこに使われているかに依存しません。子も、親のどこで値が定義されるかに依存せず、継承で値を受け取れればどこでもかまいません。子の構造を変えても、公開プロパティの名前さえ変えなければ親のCSSを直す必要はありません。名前の付け方と値の渡し方は「[10-5 公開プロパティと内部プロパティ](/components/custom-properties/)」で説明します。

なお、設計の記事には、別のブロックに入れたときの見た目を、入れられる側のファイルに書く考え方もあります。その要素を主体とするスタイルを1か所に集められるからです。本書では、見た目（色、角丸、文字の大きさ）は子のコンポーネント自身が持ち、配置と外側の余白は親が持つ、と分けます。子が自分の見た目を変える口は公開プロパティで用意し、親はその口から値を渡すだけにします。

ページのCSSから、置いた子のコンポーネントのルートを選ぶしかない場面もあります。その場合も、ルートに指定するのは公開プロパティの値と配置だけにし、子の内部の要素には触れません。

AIにコンポーネントの見た目の調整を頼むと、親のセレクタから子のクラスを選んで上書きするコードをよく書きます。生成されたコードに別のコンポーネントのクラス名が出てきたら、公開プロパティで書き直せないかを確認してください。

なお、stackやclusterのようなコンポジションは、直下の子の並び方と間隔を決めます。これは「配置は置く側が持つ」という考え方を再利用できる形にしたもので、子の内部には触れないので、この節の方針とは矛盾しません。

## コンポーネントの中の要素はタイプセレクタで選ぶ

コンポーネントの中の要素は、`ul` や `a` のようなタイプセレクタで選ぶことを基本にします。子クラスを付けるのは、メインのリンクとサブのリンクのように同じ種類の要素を役割で区別するときと、意味を持たない `div` と `span` に役割を示すときだけです。`@scope (.scoped.<名前>) to (.scoped)` の中のタイプセレクタは、そのコンポーネントの範囲にしか当たりません。範囲を限るためだけに、すべての要素へクラスを付ける必要はなくなりました。

`@scope` がなかったころは、要素にはすべてクラスを付けるのが安全な書き方でした。`.global-nav a` のように親のクラスと組み合わせたタイプセレクタは、入れ子にした別のコンポーネントのリンクにも当たります。詳細度も0.1.1に上がり、クラス1つのセレクタでは上書きできなくなります。この習慣を `@scope` の中に持ち込むと、要素の種類と同じ意味のクラス名が並びます。

```html title="🙅‍♂ Not Recommended: 要素の種類と同じ意味のクラスをすべての要素に付ける" issue="convention"
<!-- 🙅‍♂ Not Recommended -->
<nav class="scoped global-nav">
  <ul class="_list">
    <li class="_item"><a class="_link" href="/">ホーム</a></li>
    <li class="_item"><a class="_link" href="/news/">お知らせ</a></li>
  </ul>
</nav>
```

`_list` は `ul` と、`_link` は `a` と同じことを言っているだけです。HTMLを読めば分かる情報をクラス名で繰り返しても、セレクタから読み取れることは増えません。名前を考える手間と、HTMLとCSSの記述量が増えるだけです。AIにコンポーネントを書かせると、BEMの習慣から、このようにすべての要素へクラスを付けたコードがよく出てきます。

次の例では、ナビゲーションの中の `ul` と `li` を、タイプセレクタで選んでいます。どちらもコンポーネントの中で役割が1つしかないからです。`li` は複数ありますが、すべて同じ役割の項目なので、区別するクラスは要りません。「唯一」かどうかは、要素の数ではなく役割で判断します。

ただし、`div` と `span` には、1つしかなくても子クラスを付けます。この2つは、要素そのものが意味を持たない汎用の要素です。`ul` なら一覧、`a` ならリンクだと要素の種類から分かりますが、`div` や `span` からは何のための要素なのかを読み取れません。`._body` や `._badge` のようにクラスで役割を補えば、HTMLとCSSの両方から要素の役割が分かります。

```css title="🙆‍♂ Recommended: 共通のスタイルはタイプセレクタに、固有のスタイルは子クラスに書く"
@scope (.scoped.global-nav) to (.scoped) {
  ul {
    display: block flex;
    flex-wrap: wrap;
    gap: calc(var(--spacing--xs) * 1px);
  }

  a {
    display: block flow;
    padding-block: calc(var(--spacing--xs) * 1px);
    padding-inline: calc(var(--spacing--sm) * 1px);
    border-radius: var(--rounded--md);
  }

  ._main-link {
    color: var(--foreground--muted);
    font-weight: var(--font-weight--bold);
  }

  ._sub-link {
    background-color: var(--background--inverse);
    color: var(--foreground--inverse);
  }
}
```

```html
<nav class="scoped global-nav" aria-label="メイン">
  <ul>
    <li><a class="_main-link" href="/">ホーム</a></li>
    <li><a class="_main-link" href="/news/">お知らせ</a></li>
  </ul>
  <a class="_sub-link" href="/contact/">お問い合わせ</a>
</nav>
```

リンクには、メインとサブの2つの役割があります。役割を区別する必要があるので、それぞれに `._main-link` と `._sub-link` を付けます。余白や角丸のように両方に共通するスタイルは `a` に書き、子クラスにはそれぞれに固有のスタイルだけを書きます。クラスの名前は、`._main` のように役割だけにせず、`._main-link` のように要素の役割の語まで含めます。`._main` のような短い名前は、見出しや画像にも付けたくなり、同じ名前がどの要素を指すのかを決める取り決めが別に必要になるからです。CSSでは、`a._main-link` ではなく `._main-link` と書きます。タイプセレクタを足すと、詳細度を上げるだけのセレクタになります。

`@scope` の括弧の中のセレクタは詳細度に加わらないので、`a` の詳細度は0.0.1、`._main-link` は0.1.0です。子クラスの指定は、書いた順番にかかわらず `a` の指定に勝ちます。そのため、スコープの中のタイプセレクタは、`:where()` で包む必要がありません。ベーススタイルのタイプセレクタを `:where()` で包むのは、クラスのないあらゆる要素に当たる指定だからで、スコープの中の指定とは事情が違います。ベーススタイルの書き方は、「[8-2 ベーススタイルに書くもの](/reset/base-styles/)」で扱います。

タイプセレクタが当たるのは、ドーナツスコープの下限より手前の要素すべてです。同じコンポーネントの中で同じ種類の要素が入れ子になる場合、たとえば2階層のナビゲーションの中の `ul` には、外側の `ul` のスタイルも当たります。このとき `ul` はコンポーネントの中で2つの役割を持つので、リンクと同じように外側と内側の両方に `._main-list` と `._sub-list` のような子クラスを付けます。`ul` のタイプセレクタには、両方に共通するスタイルだけを書きます。CMSが出力する本文のように、任意のHTMLが入る領域は、別のコンポーネントにしてルートに `scoped` を付けます。下限で範囲が切れるので、外側のタイプセレクタは本文の `p` や `a` に届きません。

繰り返して並べる要素は、`ul` のような囲む要素を必ず用意します。囲む要素があれば、間隔を `gap` で決められます。JavaScriptから要素の一覧を取り出すときも、テンプレートで繰り返しを書くときも、囲む要素が起点になります。`<ul>` の直下に置ける表示用の要素は `<li>` だけなので、Outerが必要なときは `<li>` の中に置きます。

囲みのためだけの `div` が増えることも、必要以上に恐れません。`div` を減らすために、詳細度やセレクタの組み合わせで無理に同じ見た目を作ると、CSSが不安定で読みにくくなります。HTMLを平らに保つことを目的にして、1つの要素に親の子要素としての配置と子のコンポーネントのルートのような複数の役割を持たせると、どの指定がどの役割のものかをクラスから読み取れなくなります。1つの要素に1つの役割があれば、直す場所はクラスから決まります。ただし、リスト、見出し、ナビゲーションのように意味を持つ要素で足りる場面では、その要素を使います。`div` は、意味を持つ要素では表せない囲みにだけ使います。

ここまでが、コンポーネントの境界を守るための基本の道筋です。続く3つの見出しは、必要な場面が来てから読めば足ります。子要素のクラスの下にある要素を選ぶときと、タイプセレクタにホバーやフォーカスの状態を付けるときは、次の2つの見出しに戻ります。z-indexの見出しは、コンポーネントの中で要素を重ねるときに読みます。

## 子要素のクラスの下をタイプセレクタで選ばない

同じ種類の要素を、置かれた領域ごとに変えたくなったときは、その要素にクラスを付けます。領域の子要素のクラスとタイプセレクタを組み合わせて、`._summary p` のように選ぶことはしません。

```css title="🙅‍♂ Not Recommended: 領域の子要素のクラスとタイプセレクタで、段落を区別する" issue="convention"
/* 🙅‍♂ Not Recommended */
@scope (.scoped.product-detail) to (.scoped) {
  ._summary p {
    font-size: calc(18 / 16 * 1rem);
  }

  ._spec p {
    color: var(--foreground--muted);
  }
}
```

子孫結合子は深さを問わないので、`._summary p` は、`._summary` の中にあるすべての `p` に当たります。概要の中に注記の段落を足すと、注記の文字も大きくなります。どの `p` が対象なのかは、HTMLの入れ子をたどらないと分かりません。詳細度も0.1.1に上がるので、注記に `._note` を付けても、クラス1つのセレクタでは上書きできません。

```html title="🙆‍♂ Recommended: 役割の違う段落に、それぞれクラスを付ける"
<section class="scoped product-detail">
  <div class="_summary">
    <p class="_lead">軽くて丈夫な、毎日使えるリュックです。</p>
  </div>
  <div class="_spec">
    <p class="_spec-note">容量は20リットルです。</p>
  </div>
</section>
```

```css title="🙆‍♂ Recommended: 段落を、役割のクラスで選ぶ"
@scope (.scoped.product-detail) to (.scoped) {
  ._lead {
    font-size: calc(18 / 16 * 1rem);
  }

  ._spec-note {
    color: var(--foreground--muted);
  }
}
```

要素自身にクラスを付ければ、セレクタが要素の役割を表します。概要に注記を足しても、`._lead` を付けない限り大きな文字にはなりません。どのセレクタも詳細度は0.1.0なので、後から足したクラスとも書いた順番で比べられます。

領域の直下の要素を、その領域の配置や余白のために選ぶことはあります。そのときは、子要素のクラスのルールの中にネストして、`& > p` のように子結合子で書きます。直下に限れば、入れ子の奥の要素には届きません。ネストしておけば、直下の要素への指定が領域のスタイルの一部として1か所にまとまり、`._spec` のルールを読めば気付けます。`._spec > p` のように1つのセレクタに並べて書くと、領域のルールから離れた場所に置けてしまうので、この書き方はしません。ネストに書くのは、要素の間の余白や `grid-area` のように、親のレイアウトによって意味が決まる宣言だけです。色や文字の大きさのように要素自身で決まる宣言は、直下の要素でも、その要素にクラスを付けて書きます（「[9-6 ネストの判断基準](/notation/nesting-criteria/)」）。

```css title="🙆‍♂ Recommended: 領域の直下の要素は、領域のルールの中にネストして選ぶ"
@scope (.scoped.product-detail) to (.scoped) {
  ._spec {
    & > p + p {
      margin-block-start: 0.5lh;
    }
  }
}
```

例外は、CMSが出力する本文のように、マークアップにクラスを付けられない領域です。この領域には、前の見出しで述べたとおり別のコンポーネントにしてタイプセレクタで書くか、印刷のときだけ外部リンクにURLを添える指定のように、領域の中の要素をタイプセレクタで選びます（第16章の「印刷のスタイル」{/* 16-11の執筆後にリンクする: /decoration/print/ */}）。

ここまでの書き分けを、場面ごとにまとめます。

| 判断する場面 | 選ぶ書き方 | 例 |
|---|---|---|
| 同じ役割の要素に共通する見た目 | スコープの中のタイプセレクタ | `a`、`ul` |
| 役割によって違う見た目 | 要素自身の子要素のクラス | `._main-link`、`._spec-note` |
| 親のレイアウトによって決まる指定 | 子要素のクラスのルールの中で、直下の子へネストする | `._spec { & > p + p { … } }` |
| クラスを付けられない本文 | 例外として、領域の中をタイプセレクタで選ぶ | 別のコンポーネントにした本文、印刷のときの `._body a` |

## タイプセレクタに状態を付けるときの注意

タイプセレクタに擬似クラスを付けると、詳細度が逆転します。`a:focus-visible` の詳細度は0.1.1、`a:any-link:hover` は0.2.1で、どちらも `._sub-link` の0.1.0より高くなるからです。次の例では、ホバーしたときとキーボードでフォーカスしたときにリンクの文字色を変える指定を、共通のスタイルとして `a` の状態に書いています。サブのリンクは背景色と同じ色の文字になり、ホバーやフォーカスをしている間だけ読めなくなります。

```css title="🙅‍♂ Not Recommended: 共通の a の状態で、子クラスの色まで変える" issue="behavior"
/* 🙅‍♂ Not Recommended */
@scope (.scoped.global-nav) to (.scoped) {
  a {
    &:focus-visible {
      color: var(--foreground--base);
    }

    &:any-link:hover {
      @media (any-hover) {
        color: var(--foreground--base);
      }
    }
  }

  ._sub-link {
    background-color: var(--background--inverse);
    color: var(--foreground--inverse);
  }
}
```

状態のスタイルも、共通の部分と固有の部分に分けます。`a` の状態には、どちらのリンクにも同じ意味を持つ指定だけを書きます。次の例では、kiso.cssが消した下線を `revert` で戻しています。

色のように役割ごとに違う指定は、`._main-link` と `._sub-link` の状態に書き、同じ状態どうしで詳細度をそろえます。`._sub-link:focus-visible` の詳細度は0.2.0で、`a:focus-visible` の0.1.1に勝ちます。`._sub-link:any-link:hover` も0.3.0で、`a:any-link:hover` の0.2.1に勝ちます。

```css title="🙆‍♂ Recommended: 役割ごとに違う状態のスタイルは、子クラスの側に書く" from="components/type-selectors-in-scope"
@scope (.scoped.global-nav) to (.scoped) {
  a {
    &:focus-visible {
      text-decoration-line: revert;
    }

    &:any-link:hover {
      @media (any-hover) {
        text-decoration-line: revert;
      }
    }
  }

  ._main-link {
    &:focus-visible {
      color: var(--foreground--base);
    }

    &:any-link:hover {
      @media (any-hover) {
        color: var(--foreground--base);
      }
    }
  }

  ._sub-link {
    &:focus-visible {
      background-color: color-mix(in oklab, var(--background--inverse) 80%, var(--background--base));
    }

    &:any-link:hover {
      @media (any-hover) {
        background-color: color-mix(in oklab, var(--background--inverse) 80%, var(--background--base));
      }
    }
  }
}
```

次の2つのデモで、それぞれのリンクにポインターを重ねるか、Tabキーでフォーカスを移して比べてください。1つ目は共通の `a` の状態で文字色を変えているので、「お問い合わせ」の文字が背景に溶け込みます。2つ目は文字色の変更をメインのリンクだけに書いているので、サブのリンクは背景色だけが変わります。

## ルートと内部で分けるz-index

z-indexは、コンポーネントのルートと内部の要素で、指定してよい値の種類を分けます。ルートに指定するのは、ヘッダーやフッターのようにページ全体での重なり順を決める「絶対的なz-index」だけです。内部の要素に指定するのは、コンポーネントの中で前後を入れ替えるための「相対的なz-index」だけで、値は1か-1に限ります。

どちらの値も、数値を直接書かずにトークンで指定します。絶対的な値には `--z--header` のように役割の名前を付けたトークンを使い、相対的な値には `--z--forwards`（1）と `--z--backwards`（-1）を使います。重なり順はまずHTMLの順番で解決し、それで足りないときだけ相対的なz-indexを使います。本書のStylelintの設定では、1と-1も含めて、数値を直接書いたz-indexを `declaration-property-value-disallowed-list` で警告します。「相対的な値は1か-1だけ」と決めても、数値を書ける限り、いずれ誰かが `z-index: 2` と書き始めるからです。トークンの設計は「[10-4 デザイントークン](/components/design-tokens/)」で説明します。

```css title="🙆‍♂ Recommended: ルートには絶対的な値、内部には相対的な値をトークンで指定する"
@scope (.scoped.site-header) to (.scoped) {
  :scope {
    @media (height >= calc(600 / 16 * 1rem)) {
      position: sticky;
      inset-block-start: 0;
      z-index: var(--z--header);
    }
  }
}

@scope (.scoped.feature-card) to (.scoped) {
  :scope {
    position: relative;
    isolation: isolate;

    & > ._decoration {
      position: absolute;
      inset: 0;
    }
  }

  ._decoration {
    z-index: var(--z--backwards);
  }
}
```

内部の要素で相対的なz-indexを使うコンポーネントは、ルートに `isolation: isolate` を指定します。`isolation: isolate` は、その要素に新しいスタッキングコンテキストを作るプロパティです。これがないと、内部のz-indexは外側のスタッキングコンテキストの中で比べられ、ほかのコンポーネントの重なりと干渉します。z-indexを使う要素が、タブの1つの項目のように内部の区画の中で完結するなら、ルートではなくその区画に指定してもかまいません。どちらでも、重なりはコンポーネントの外へ漏れません。

とくに影響が大きいのは-1です。スタッキングコンテキストを作っていないルートの中で-1を指定すると、その要素は外側のコンテキストの背面に回り、ルートや親の背景の下に隠れてしまいます。次の2つのデモは、カードの背景と文字の間に円の飾りを置いたものです。1つ目はルートに `isolation: isolate` がないので、飾りは親のセクションの背景の下に隠れて見えません。

<Demo title="ルートに isolation: isolate がないと、z-index: -1 の飾りが親の背景に隠れる" html={zIndexHtml} css={zIndexBadCss} variant="not-recommended" />

2つ目は、ルートに `isolation: isolate` を指定したものです。飾りはカードの背景より手前、文字より奥に描かれます。カードの外にある要素とも干渉しません。

<Demo title="ルートに isolation: isolate を指定すると、飾りがカードの背景と文字の間に描かれる" html={zIndexHtml} css={zIndexCss} />

スタッキングコンテキストは、`opacity` や `transform`、`position` と数値のz-indexの組み合わせでも作れます。しかし、それらは見た目や包含ブロック、ページの中での重なり順にも影響します。`isolation` はスタッキングコンテキストを作るかどうかだけを決めるプロパティなので、ほかの手段より副作用が少なく済みます。意図してスタッキングコンテキストを作るときは、`isolation: isolate` を使います。

コンポーネントのルートそのものには、相対的なz-indexを持たせません。ルートに `margin` を持たせないのと同じ理由で、隣のコンポーネントより手前に出るかどうかは、置かれる場所で決まることだからです。次のカードは、置き場所にかかわらず、周りの要素より1つ手前に出る指定です。

```css title="🙅‍♂ Not Recommended: コンポーネントのルートに相対的な z-index を持たせる" issue="behavior"
/* 🙅‍♂ Not Recommended */
@scope (.scoped.promo-card) to (.scoped) {
  :scope {
    position: relative;
    z-index: var(--z--forwards);
  }
}
```

子のコンポーネントどうしの前後は、それらを並べる親のコンポーネントが決めます。外側の余白と同じく、親は子を包むOuterの要素を用意し、そこに相対的なz-indexを指定します。次の例では、HTMLで先に書いたカードを、後に書いた画像の手前に重ねています。

```css title="🙆‍♂ Recommended: 子のコンポーネントどうしの前後は、親が Outer の要素で決める"
@scope (.scoped.hero-section) to (.scoped) {
  :scope {
    display: block grid;
    isolation: isolate;

    & > ._card-outer,
    & > ._visual-outer {
      grid-area: 1 / 1;
    }
  }

  ._card-outer {
    z-index: var(--z--forwards);
  }
}
```

この形なら、カードのCSSに重なりの指定がないので、別の場所に置いても余計な重なりが生じません。親のルートにも `isolation: isolate` を指定し、Outerのz-indexを親の中に閉じ込めます。なお、ヘッダーのようにページ全体での順位を持つ絶対的なz-indexは、これまでどおりそのコンポーネントのルートに指定します。

トップレイヤーへ表示する `<dialog>` や `popover` 属性の要素に閉じる動きを付けるときは、いまは `z-index: var(--z--top)`（値は `calc(infinity)`）も指定しておきます。トップレイヤーの要素は、本来はz-indexと関係なく最前面へ描かれます。しかし、閉じるアニメーションの間も要素をトップレイヤーにとどめる `transition-property: overlay` は、Chromium系のブラウザでしか使えません。対応していないブラウザでは、閉じる途中で要素がトップレイヤーから外れ、z-indexの大きい要素の下に隠れることがあります。

ただし、`calc(infinity)` は何にでも勝てる値ではありません。トップレイヤーには勝てず、祖先のスタッキングコンテキストの中でしか比べられないので、z-indexを管理する必要はなくなりません。スタッキングコンテキストが作られる条件と、重なり順の決まり方は、「[11-6 重なりと全幅](/layout-practice/layering/)」で説明します。
