コンポーネントにするかは、見た目が似ているかではなく、HTMLの構造や属性、振る舞いをまとめて管理したいかで判断します。商品カードと記事カードは同じ形に見えても、載せる情報と変更される理由が違うので、別のコンポーネントにします。見た目をそろえたいだけなら、コンポーネントを統合せず、デザイントークンやパターンで共通化します。

この判断を、この節では順に組み立てます。まず、見た目が似ている部品を共通化してよいかを考え、次に本書でのコンポーネントの定義を示します。判定で迷ったときにたどる3つの問い、コンポーネントにしないもの、子要素を分ける条件は、その後で説明します。

## 見た目が似ているコンポーネントを共通化してよいか

見た目が似ている2つの部品を、1つのコンポーネントにまとめたくなることがあります。商品カードと記事カードは、画像、見出し、短い説明が縦に並び、見た目がほとんど同じです。そこで `card` という1つのコンポーネントを作り、商品か記事かは属性で切り替えようと考えます。ところが、商品カードは価格と在庫を、記事カードは公開日とカテゴリーを表示するので、載せる情報も、変更を頼まれる理由も違います。1つにまとめると、属性による分岐が増えて部品が肥大化し、片方が不要になっても切り離せなくなります。

判断の基準にするのは、見た目や大まかなジャンルではなく、機能まで同じかどうかです。載せる情報、今後増えていく要素、変更される理由がそろっていれば1つにまとめられますが、どれかが違えば分けておきます。見た目が似ているだけのものを共通化しない理由と、共通化を考え始める時期は「[2-3 保守しやすさを最優先にする](/design-mindset/maintainability/#共通化のタイミング)」で説明しています。

それでも見た目をそろえたいときは、コンポーネントを統合せず、同じデザイントークンを参照します。次の例では、2つのカードが余白と角丸と背景色のトークンを共有しています。「カードの背景色をすべて変えたい」という依頼にはトークンの値を変えるだけで対応でき、それぞれのカードは独立したまま保てます。

```css title="🙆‍♂ Recommended: 別のコンポーネントのまま、トークンで見た目をそろえる"
@scope (.scoped.product-card) to (.scoped) {
  :scope {
    padding: calc(var(--spacing--md) * 1px);
    border-radius: var(--rounded--lg);
    background-color: var(--background--surface);
  }
}

@scope (.scoped.article-card) to (.scoped) {
  :scope {
    padding: calc(var(--spacing--md) * 1px);
    border-radius: var(--rounded--lg);
    background-color: var(--background--surface);
  }
}
```

逆向きの誤りもあります。見た目が共通だという理由だけで、新しいコンポーネントを作ることです。次の例では、角丸と背景色を持つ箱を `rounded-box` というコンポーネントにして、商品カードの中身を包んでいます。

```css title="🙅‍♂ Not Recommended: 見た目だけをまとめた wrapper をコンポーネントにする" issue="convention"
/* 🙅‍♂ Not Recommended */
@scope (.scoped.rounded-box) to (.scoped) {
  :scope {
    padding: calc(var(--spacing--md) * 1px);
    border-radius: var(--rounded--lg);
    background-color: var(--background--surface);
  }
}
```

```html
<article class="scoped product-card">
  <div class="scoped rounded-box">
    <h3>リネンのシャツ</h3>
    <p class="_price">8,800円</p>
  </div>
</article>
```

`rounded-box` のルートにも `scoped` が付くので、`product-card` のスコープはそこで打ち切られます。商品カードのCSSからは、自分の見出しや価格を選べなくなります。この箱には、全インスタンスで管理したい構造、属性、振る舞いがありません。持っているのは見た目だけなので、トークンを参照すれば、箱を作らずに同じ見た目を書けます。

## コラム：見た目が色違いでも別物のもの

ゲームの「モンスターハンター」シリーズのリオレウスには、亜種や希少種などの派生種がいます。見た目は色違いのようでも、攻撃のパターンや弱点、手に入る素材はまったく違います。これらを「リオレウス」という1つにまとめると分岐が増え、不要になった派生種も捨てられなくなります。見た目が似ていても機能が違うものを分けておくほうが安全なのは、ゲームの敵も、Webの部品も同じです。

## コンポーネントの定義

本書のコンポーネントは、次の図の関係で捉えます。商品カードを例にすると、`product-card` の定義は1つだけです。商品ごとのカードは、その定義から作られるインスタンスです。インスタンスごとに変えてよい部分が入力点で、定義が使う側と交わす約束が契約です。

<Figure src="components/component-definition" alt="商品カードのコンポーネントの定義と、そこから作られるインスタンスを示した図。左の枠は、1つの定義である product-card。ファイルは1つで、入力点として、propsの商品名と価格、スロットの画像、data-variantのfeatured、公開プロパティの --product-card--accent が並んでいる。右には、定義から矢印で結ばれた3つのインスタンスがある。リネンのシャツ8,800円、ウールのコート24,000円、featuredで強調したコットンのシャツ6,800円。図の下の枠は契約で、使う側が依存する約束として、出力するHTMLの構造は定義が決めること、@scopeの内側の見た目は定義が受け持つこと、使う側は入力点だけで調整し中の構造には触れないことの3つが並んでいる。" />

本書では、コンポーネントを「単一の定義から管理され、差し替えられる入力点を持ち、構造・見た目・必要に応じて振る舞いの契約が明示された再利用の単位」と定義します。この定義の語を、商品カードに当てはめて順に確かめます。

単一の定義とは、Astroのコンポーネントのファイルのように、すべてのインスタンスの元になる定義が1つだけあることです。商品カードの見た目や構造を変えたいときは、この定義を1か所直せば、すべての商品カードに反映されます。

入力点は、インスタンスごとに差し替えてよい部分です。商品カードでは、商品名と価格を受け取るpropsと、画像を差し込むスロットが入力点です。`data-variant="featured"` で選ぶバリエーションと、外から強調色を変えるための公開プロパティ `--product-card--accent` も、入力点にあたります。

契約は、そのコンポーネントがどんなHTMLを出力し、どう見え、どう振る舞うかの約束です。商品カードの契約は、`<article>` 要素を出力すること、`@scope` の内側の見た目はコンポーネントが受け持つこと、使う側は中の構造に触れず入力点だけで調整することです。使う側は、この約束だけに依存します。

コンポーネントが役に立つのは、HTMLの構造、条件分岐、JavaScriptの振る舞いを1か所で管理したいときです。見た目だけなら、CSSのクラスを1つ書けば、すべての要素に同じスタイルが当たります。見た目を1か所で管理するためにコンポーネントを作る必要はありません。

CSSの側では、コンポーネントの契約を3つの仕組みで表します。ルートの `scoped <名前>` と `@scope` は、どこまでがそのコンポーネントの見た目の責任かという境界です。外から変えてよい値は、`--<コンポーネント>--<プロパティ>` の公開プロパティにして、CSSの入力点を明示します（「[10-5 公開プロパティと内部プロパティ](/components/custom-properties/)」）。バリエーションは `data-variant` のようなdata属性で受け取り、`:scope[data-variant="featured"]` のように選びます。

コンポーネントと似た言葉に、パターンがあります。本書のパターンは、`section-heading` のような静的で再利用できる見た目の断片で、HTMLの構造と入力点を持ちません（「[10-3 コンポジションとユーティリティ](/components/compositions-and-utilities/)」）。何度も使われる断片が、自動的にコンポーネントになるわけではありません。

## コンポーネントにするかを決める3つの問い

コンポーネントにするかは、3つの問いを順にたどって判定します。

1つ目は「繰り返し使うか」です。同じものを何度も使うなら、コンポーネントの有力な候補です。HTMLを複製して使うと、変更のたびにすべての箇所を手で直すことになり、直し漏れが起きやすいからです。ただし、繰り返し使っていても、CSSだけで十分に管理できるならコンポーネントにしません。段落はサイト中に100回以上出てきますが、`p` のスタイルで足ります。「3回出てきた」は、パターンへの昇格を検討する目安であって、コンポーネントにする目安ではありません。

2つ目は「全インスタンスで制御したいものがあるか」です。HTMLの構造、付けるクラス、ARIA属性、data属性、条件分岐、JavaScriptの振る舞い、そしてpropsやバリエーションのような入力点がこれに当たります。ボタンなら、`type` 属性のデフォルト値や、アイコンを付けたときの `aria-hidden` を全インスタンスでそろえたくなります。これらはCSSでは強制できません。CSSは書かれたHTMLを選ぶだけで、HTMLそのものを変えられないからです。1つの定義から全インスタンスを統制したいものがはっきりあるなら、この時点でコンポーネントにします。制御したいものはあるものの、HTMLを複製しても管理できる程度なら、3つ目の問いで決めます。

3つ目は「既知の要件として構造の拡張があるか」です。子要素の追加や構造の変更を根拠にできるのは、それがいまの要件、既存の実装、仕様書、既知の派生要件のどれかに書かれているときだけです。デザインカンプにアイコン付きのボタンがあるなら、ボタンの構造が拡張されることは既知の要件です。2つ目の問いで決めきれなかったものは、既知の構造の拡張があればコンポーネントにし、なければまだコンポーネントにしません。

3つの問いの答えと結論の関係は、次の表のとおりです。

| 繰り返し使うか | 全インスタンスで制御したいものがあるか | 既知の構造の拡張があるか | 結論 |
| --- | --- | --- | --- |
| 使わない | — | — | コンポーネントにしない。親のスコープの中に書く |
| 使う | ない（CSSだけで管理できる） | — | コンポーネントにしない。ベーススタイル、パターン、トークンで共通化する |
| 使う | はっきりある | — | コンポーネントにする |
| 使う | あるが、決め手に欠ける | ある | コンポーネントにする |
| 使う | あるが、決め手に欠ける | ない | まだコンポーネントにしない。要件が出た時点で切り出す |

「将来必要になりそう」「ほかの案件でよくある」という予測だけでは、コンポーネントにしません。使われない入力点と分岐が残り、定義を読む人がそれを維持し続けることになるからです。予測が当たったときは、その時点でコンポーネントに切り出します。親のスコープの中にタイプセレクタと子クラスで書いておけば、切り出す作業は、指定を新しいファイルへ移してルートに `scoped` を付けることが中心になります。{/* 要確認: 出典なし */}

## コンポーネントにしないもの

段落、区切り線、単純な見出し、見た目だけを共通化したwrapperは、原則としてコンポーネントにしません。どれも、全インスタンスで管理したいHTMLの構造や振る舞いを持たず、CSSだけで十分に管理できるからです。段落と区切り線は、ベーススタイルとトークンで整えます（「[8-2 ベーススタイルに書くもの](/reset/base-styles/)」）。セクションの見出しのように役割のある見た目が複数の場所で成り立っているなら、`section-heading` のようなパターンにします。

Atomic Designの用語で言えば、Button、Link、Iconのようなatomはコンポーネントになりやすく、Paragraph、Divider、単純なHeadingはコンポーネントにしないことが多い、という違いがあります。moleculeも、複数の要素のまとまりであるというだけでは、コンポーネントにする根拠として足りません。Alert、SearchBar、ButtonGroupはコンポーネントになりやすい一方、CardHeaderやCardFooterは、次に説明するように親の一部として扱います。

共通化の手段は、判定の結果に合わせて選びます。対象ごとの書き方は次の表のとおりです。

| 対象 | 例 | CSSでの書き方 |
| --- | --- | --- |
| コンポーネント | カード、ボタン、アコーディオン | 専用のファイルに `@scope (.scoped.<名前>) to (.scoped)` で書く |
| 親の中の区画 | カードの見出し、本文、フッター | 親のスコープの中で、タイプセレクタか子クラス（`._body`）で選ぶ |
| 文書要素 | 段落、区切り線、単純な見出し | ベーススタイルとトークンで整える |
| 静的な見た目の断片 | セクションの見出し、アイコンの大きさ | パターン（`.section-heading`） |
| 配置 | 縦に積む、横に並べて折り返す | コンポジション（`.stack`、`.cluster`） |
| 単機能の補助 | 視覚的に隠す、数字の幅をそろえる | ユーティリティ（`.-visually-hidden`） |
| 共有する値 | 余白、色、角丸 | デザイントークン（`--spacing--md`） |

トークンの設計は「[10-4 デザイントークン](/components/design-tokens/)」で、コンポジション、ユーティリティ、パターンは「[10-3 コンポジションとユーティリティ](/components/compositions-and-utilities/)」で説明しています。

## 子要素を別のコンポーネントに分ける条件

親のコンポーネントの中の子要素が、その親の中でしか意味を持たないなら、別のコンポーネントにしません。親が構造全体を持っているなら、見出し、本文、フッター、内側を包む要素などの区画は、まず親のローカルな要素として扱います。カードを `card-header`、`card-body`、`card-footer` のようなコンポーネントに細かく分けると、次のようになります。

```css title="🙅‍♂ Not Recommended: 親の中でしか意味を持たない区画をコンポーネントに分ける" issue="convention"
/* 🙅‍♂ Not Recommended */
@scope (.scoped.card-header) to (.scoped) {
  :scope {
    display: block flex;
    justify-content: space-between;
  }
}

@scope (.scoped.card-footer) to (.scoped) {
  :scope {
    display: block flex;
    justify-content: end;
  }
}
```

区画のルートにも `scoped` が付くので、カードのスコープは各区画で打ち切られます。カードの中の並びをカードのCSSだけで決められなくなり、区画ごとに公開プロパティを用意して値を渡すことになります。ファイルも区画の数だけ増えますが、どの区画もカードの外では使いません。

区画は親のスコープの中に書きます。次の例では、商品カードの `header` と `footer` をタイプセレクタで、意味を持たない `div` を `._body` で選んでいます。一方、フッターの中のボタンは別のコンポーネントです。ボタンはカードの外でも独立した役割を持ち、`type` 属性などを1つの定義から管理したいからです。子要素が親の外でも独立した責務と再利用の価値を持つなら、別のコンポーネントにしてかまいません。

```css title="🙆‍♂ Recommended: 区画は親のスコープの中で選び、独立した役割を持つ部品だけをコンポーネントにする" from="components/component-candidates"
@scope (.scoped.product-card) to (.scoped) {
  header {
    display: block flex;
    justify-content: space-between;
  }

  ._body {
    color: var(--foreground--muted);
  }

  footer {
    display: block flex;
    justify-content: end;
  }
}
```

```html
<article class="scoped product-card">
  <header>
    <h3>リネンのシャツ</h3>
    <p class="_price">8,800円</p>
  </header>
  <div class="_body">
    <p>風を通す麻の生地で仕立てた、秋口まで着られる長袖のシャツです。</p>
  </div>
  <footer>
    <button class="scoped button" type="button">カートに入れる</button>
  </footer>
</article>
```

次のデモでは、商品カードと記事カードが余白、角丸、背景色のトークンを共有しながら、別のコンポーネントとして書かれています。商品カードの見出し、本文、フッターはカードのスコープの中で選び、ボタンだけを別のコンポーネントにしています。カードのスコープはボタンのルートで打ち切られるので、カードのCSSはボタンの見た目に影響しません。

<Demo title="区画は親のスコープの中で選び、ボタンだけを別のコンポーネントにしたカード" html={candidatesHtml} css={candidatesCss} />

子のコンポーネントを置く場所の調整に使うOuterも、親の子要素として扱い、単独のコンポーネントにはしません。親と子の責任の分け方は「[10-2 コンポーネントの境界を守る](/components/boundaries/)」で説明しています。

## 行をそろえて並べる一覧と項目

カードを一覧に並べるとき、ふつうはカードをコンポーネントにし、並べ方は一覧の側で決めます。カードは一覧の外にも置けるからです。ただし、カードの中の見出しや抜粋の位置を、隣のカードとそろえるときは事情が変わります。

そろえるには、各カードを `subgrid` にして、一覧のグリッドの行に参加させます（「[7-9 Gridでアイテムをそろえる](/layout/grid-alignment/#サブグリッドでカードの行をそろえる)」）。このとき、カードの行は一覧の行なので、カードだけを一覧の外に取り出すと、そろえる相手がなくなります。また、コンテナにした要素は `subgrid` にできないので、カードを別のコンポーネントにして、置かれた幅で形を変えることもできません（「[13-4 コンテナの副作用とコンテナ単位](/responsive/container-units-and-side-effects/)」）。

そこで、`subgrid` で行をそろえる一覧は、一覧とカードを1つのコンポーネントにし、カードを子要素として書きます。一覧のルートに付けたコンポジションの値も、一覧のCSSから渡します。

```css title="🙆‍♂ Recommended: 一覧とカードを1つのコンポーネントにし、カードを一覧の行に参加させる"
@scope (.scoped.article-cards) to (.scoped) {
  :scope {
    --grid--column-min-width: calc(280 / 16 * 1rem);
    --grid--column-max-count: 2;

    & > ._card {
      grid-row: span 4;
    }
  }

  ._card {
    display: block grid;
    grid-template-rows: subgrid;
  }
}
```

```html
<ul class="scoped article-cards | grid">
  <li class="_card">
    <img src="…" alt="" width="640" height="360">
    <p class="_meta">…</p>
    <h3>…</h3>
    <p class="_excerpt">…</p>
  </li>
</ul>
```

カードの形を置かれた幅で切り替えるときは、一覧のルートをコンテナにし、カードがフラグを宣言します。カードを一覧の外に1つだけ置く場所があっても、1項目の一覧として置きます。フラグを宣言する書き方は「[13-3 コンテナサイズクエリ](/responsive/container-size-queries/)」で、そのフラグで子孫を切り替える書き方は「[10-6 スタイルクエリで状態を伝える](/components/style-queries/)」で説明しています。

## 判定に迷うまとまりの扱い

判定に迷うのは、小見出し（eyebrow）、見出し、リード文を組にしたセクションの導入のようなまとまりです。複数のセクションで繰り返し使い、見た目もそろっているので、コンポーネントにしたくなります。しかし、多くの場合、このまとまりに全インスタンスで管理したい構造や振る舞いはありません。デフォルトではコンポーネントにせず、各セクションの子要素として書き、見出しの見た目を共有したいなら `section-heading` のようなパターンにします。

次のどれかに当てはまるときは、セクションの導入をコンポーネントにしてかまいません。中央揃えと左揃えのようなバリエーションを明示的に管理したいとき、追加のボタンや補助の要素の有無を入力点として管理したいとき、チームの組み立ての流れの上でコンポーネントにしたほうが明確なときです。コンポーネントにしたら、ルートに `scoped section-intro` を付けて専用のファイルに書き、バリエーションはdata属性で、外から変えてよい値は公開プロパティで受け取ります。

迷ったときは、次の順で考えます。CSSだけで管理できるならコンポーネントにしません。1つの定義からHTMLや属性や振る舞いを制御したいなら、コンポーネントを検討します。親の中でしか意味を持たない部分は、親の中に残します。
