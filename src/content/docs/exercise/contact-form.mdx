お問い合わせのページに、フォームを作ります。項目は、お名前、メールアドレス、電話番号、お問い合わせの種類、お問い合わせ内容と、個人情報の取り扱いへの同意です。電話番号のほかは必須で、ラベルの横に紺の小さな「必須」の印を置きます。最後に、21-2で作った主ボタンの見た目で「送信する」のボタンを置きます（「[21-2 ボタンとセクション見出しを作る](/exercise/buttons/)」）。

各項目は、14px相当の太字のラベルの下に入力欄を置き、項目の間を24px空けます。入力欄は白い面にして、1pxの枠線で囲んで角を12px丸め、内側に上下12px、左右16pxの余白を取ります。メールアドレスの入力欄の下には、「例：name@example.com」と入力例を示します。お問い合わせ内容の入力欄は、4行分の高さから始め、入力に合わせて10行分まで伸ばします。フォームの幅は640px相当までです。

手元で進めるときは、開始版（[index.html](/exercise-files/contact-form/start/index.html)）から始め、中間版（[index.html](/exercise-files/contact-form/middle/index.html)）と見比べます。後半の要件の変更は、中間版から始めて、完成版（[index.html](/exercise-files/contact-form/finished/index.html)）と見比べます。サンプル一式のZIPでは、それぞれ `exercise/contact-form/start/`、`exercise/contact-form/middle/`、`exercise/contact-form/finished/` にあります。完成版には、誤りの文章を入力欄に関連付ける属性を切り替える `script.js`（[script.js](/exercise-files/contact-form/finished/script.js)）も、同じディレクトリにあります。準備は「[21-1 題材と準備](/exercise/setup/#手元で進める準備)」で説明しています。

## 予想する

本文を読む前に、「必須」の印をHTMLに書くか、CSSの生成コンテンツで入れるかを考えてみてください。送信ボタンには、21-2の `action-control` をそのまま付けられるでしょうか。21-2では `<a>` に付けていましたが、ここでは `<button>` に付けます。

入力欄の文字の大きさも予想します。デザインで入力欄の文字を14pxにしたいと言われたら、そのまま書いてよいでしょうか。

どの幅でも、項目は1列に並び、ラベルは入力欄の上に置かれます。お問い合わせ内容に5行以上入力すると、入力欄が伸び、10行を超えると中でスクロールします。送信ボタンは、ホバーとフォーカスのときに、21-2の主ボタンと同じ見た目に変わります。キーボードで操作すると、各入力欄にフォーカスリングが出れば完成です。

## 必須の印はHTMLに書く

「必須」の印は、ラベルの中の `<span>` としてHTMLに書きます。必須であることは、入力する人が知る必要のある情報なので、`::after` の生成コンテンツでは入れません（`no-meaningful-generated-content`）。入力欄には `required` 属性も付け、ブラウザにも必須であることを伝えます。

```html title="🙆‍♂ Recommended: 必須の印はラベルの中に書き、入力例は aria-describedby で入力欄に関連付ける" from="exercise/contact-form-1"
<div class="_field">
  <label class="_label" for="contact-email">メールアドレス <span class="_required">必須</span></label>
  <input class="_text-control" id="contact-email" type="email" name="email" autocomplete="email" required aria-describedby="contact-email-hint">
  <p class="_hint" id="contact-email-hint">例：name@example.com</p>
</div>
```

入力例の段落は、`aria-describedby` で入力欄に関連付けます。入力欄にフォーカスしたとき、スクリーンリーダーがラベルに続けて入力例を読み上げます。文字を入力する入力欄、`<select>`、`<textarea>` には、同じ見た目を付けるために `._text-control` のクラスを付けています。要素の種類は違っても、役割は同じ入力欄だからです。

## 送信ボタンにも action-control を付ける

送信ボタンは、`<button type="submit">` に21-2の `action-control` を付けるだけで作れます。21-2では、`<a>` と `<button>` のどちらにも付ける部品として名前を決め、ホバーの条件を `&:is(:any-link, :enabled):hover` にしていました。そのため、CSSは直しません（「[10-3 コンポジションとユーティリティ](/components/compositions-and-utilities/#パターンにするかコンポーネントにするか)」）。`disabled` にした送信ボタンは `:enabled` に当たらないので、押せない間はホバーしても見た目が変わりません。

## 入力欄の文字の大きさと高さ

入力欄の文字の大きさは、`max(16px, 1rem)` にします。iOSのSafariは、16px未満の入力欄にフォーカスするとページを拡大し、拡大はユーザーが縮小するまで戻りません（「[17-7 フォーム部品](/interaction/forms/#入力欄の大きさと文字サイズ)」）。デザインで14pxにしたいと言われたら、そのまま書かず、16pxで成り立つデザインにできないかを相談します。

```css title="🙆‍♂ Recommended: 入力欄の文字は16pxを下限にし、textarea の高さは行数で決める" from="exercise/contact-form-1"
@scope (.scoped.contact-form) to (.scoped) {
  ._text-control {
    padding-block: 12px;
    padding-inline: 16px;
    border-color: var(--border--strong);
    border-radius: var(--rounded--md);
    background-color: var(--background--surface);
    font-size: max(16px, 1rem);
  }

  textarea {
    --_rows: 4lh;
    --_max-rows: 10lh;

    box-sizing: unset;
    inline-size: -webkit-fill-available;
    inline-size: stretch;
    min-block-size: var(--_rows);

    @supports (field-sizing: content) {
      max-block-size: var(--_max-rows);
      resize: none;
      field-sizing: content;
    }
  }
}
```

お問い合わせ内容の `<textarea>` は、`field-sizing: content` で入力に合わせて伸ばし、最小と最大の高さを `lh` 単位の行数で決めます。高さを行数だけで書けるように、`box-sizing` を `content-box` に戻しています（`field-sizing-for-textarea`）。同意のチェックボックスは、色をティールにするだけなので、作り直さずに `accent-color` で色を変えます（`accent-color-for-color-only`）。

## 要件が変わる

入力の誤りを、項目ごとに示す要件が加わりました。誤りのある項目には、何をどう直せばよいかを、その下の赤い太字の文章で示し、入力欄の枠線も赤くします。同意のチェックボックスは、枠線を変えずに文章だけで示します。ただし、ページを開いた時点や、その項目に初めて入力している途中には表示しません。誤りを表示するのは、入力して次の項目へ移ったあとと、送信しようとしたあとです。一度表示した項目は、入力し直している間も、正しい値になった時点で表示を消し、誤った値になればその場で表示します。スクリーンリーダーにも、誤りがあることと、その文章を伝えます。Safari 26.0から26.3では、`@scope` の中のルールが `<input>` と `<textarea>` に当たらないので、それらの枠線は赤くならず、標準の見た目のままになります。本書では、この版の見た目の差を許容し、誤りの文章による通知と操作だけを保ちます（「[17-7 フォーム部品](/interaction/forms/)」）。

本文を読む前に、誤りの見た目をどの擬似クラスで選ぶかを考えてみてください。`:invalid` で選ぶと、ページを開いた時点で何が起きるでしょうか。誤りの文章を、CSSだけで表示したとき、スクリーンリーダーに伝わるかも予想してから読み進めます。

## 変更後の合格条件

次のデモが、要件の変更を終えた時点のお問い合わせのフォームです。誤りの文章を入力欄に関連付ける処理は、デモに含めたスクリプトで動きます。

<Demo base="exercise" scheme="light" title="要件の変更を終えたお問い合わせのフォーム：入力したあとにだけ、誤りを色と文章で示す" html={contactFormChangedHtml} css={contactFormChangedCss} js={contactFormChangedJs} />

ページを開いた時点では、誤りは1つも表示されません。何も入力せずに「送信する」を押すと、必須の5つの項目のそれぞれの下に誤りの文章が表示されます。枠線が赤くなるのは、お名前、メールアドレス、お問い合わせの種類、お問い合わせ内容の4つの入力欄です。Safari 26.0から26.3では、お名前、メールアドレス、お問い合わせ内容の枠線が赤くならなくても、誤りの文章が表示されれば、この条件を満たします。同意のチェックボックスの枠線は変わりません。ページを開き直し、メールアドレスに「name」と入力している途中には誤りが表示されず、次の項目へ移ると、その項目だけに誤りが表示されます。メールアドレスの入力欄に戻って続きを入力し、メールアドレスの形式に合った時点で、入力している途中でも誤りが消えれば完成です。

## 誤りは :user-invalid で選ぶ

誤りの見た目は、`:invalid` ではなく `:user-invalid` に指定します。`required` を付けた空の入力欄は、何も入力していなくても `:invalid` に当てはまるので、ページを開いた時点で、すべての必須の項目が赤くなります。`:user-invalid` は、入力して離れたあとか、送信しようとしたあとにだけ当てはまります（`user-invalid-for-errors`）。一度当てはまるようになった入力欄では、入力し直している間も、値が正しいかどうかに合わせて、その場で切り替わります。要件で、表示しないのを初めて入力している途中に限ったのはこのためです。入力し直している途中も誤りを隠すには、入力中かどうかをスクリプトで管理することになり、表示の条件がCSSの1か所に収まらなくなります。

```css title="🙆‍♂ Recommended: 入力欄の枠線と誤りの文章を、:user-invalid と aria-invalid の両方で切り替える" use="diff" from="exercise/contact-form-2"
@scope (.scoped.contact-form) to (.scoped) {
  ._text-control {
    border-color: var(--border--strong);

    &:is(:user-invalid, [aria-invalid="true"]) {
      border-color: var(--foreground--danger);
    }
  }

  ._error {
    display: none;
    color: var(--foreground--danger);
    font-weight: var(--font-weight--bold);

    &:is(._field:has(:is(:user-invalid, [aria-invalid="true"])) *) {
      display: block flow;
    }
  }
}
```

誤りの文章は、HTMLに書いておき、項目の中に誤りのある入力欄があるときだけ表示します。誤りは赤い色だけでなく、何をどう直せばよいかの文章でも伝えます（`no-color-only-information`）。

同意のチェックボックスには `._text-control` を付けていないので、枠線は赤くなりません。チェックボックスは、`accent-color` で色だけを変えた標準の部品のままにしています（`accent-color-for-color-only`）。枠線を誤りの色にするには、`appearance: none` で作り直すことになりますが、誤りは文章で伝わるので、作り直すほどの理由はありません。チェックボックスの誤りは、下の文章だけで伝えます。

## 誤りの文章を入力欄に関連付ける部分だけをスクリプトに任せる

`:user-invalid` で付けた赤い枠線は、見た目を変えるだけで、意味を足しません。誤りがあるという状態は、`required` 属性などによるブラウザの制約の検証が、支援技術にも伝えます。一方、CSSで表示した誤りの文章は、表示しただけでは入力欄の説明として関連付けられません。そこで、誤りのある入力欄の `aria-describedby` に、スクリプトで誤りの文章の `id` を足します（「[17-7 フォーム部品](/interaction/forms/#user-invalid-による入力エラーの表示)」）。

あわせて `aria-invalid="true"` も付けます。サーバーで検証した結果のように、ブラウザの制約の検証の外で決まる誤りも、同じ属性で伝えられるようにするためです。ただし、属性を付けても、誤りの文章が表示された瞬間に読み上げられるとは限りません。`aria-describedby` で関連付けた文章は、入力欄にフォーカスしたとき、説明として読み上げられます。{/* 要検証: ブラウザ。VoiceOverでの入力エラーの通知（ネイティブ検証の invalid、aria-describedby のエラー文） */}

スクリプトが受け持つのは、`aria-describedby` と `aria-invalid` の2つの属性だけです。見た目は、CSSが `:user-invalid` と `[aria-invalid="true"]` のどちらでも同じになるように、`:is()` でまとめて指定しています（`native-and-aria-state-together`）。サーバーで検証した結果を、HTMLの `aria-invalid="true"` として返す場合も、同じ見た目になります。

## 振り返り

直したのは、各項目に誤りの文章を足したHTMLと、入力欄の枠線と誤りの文章の指定、誤りの文章を入力欄に関連付けるスクリプトです。フォームの並び、ラベル、必須の印、送信ボタンは直していません。最初の要件で、入力欄に共通の `._text-control` を付けていたので、誤りの見た目も1か所に書けました。

予想と見比べたら、自分の変更を次の3つの点で見直します。

- 誤りの見た目を `:user-invalid` で選ぶと予想できたか。`:invalid` で書いていたなら、ページを開いた時点の表示を確かめたか。
- 誤りが、色だけでなく文章でも伝わっているか。誤りの文章が入力欄の説明として関連付けられているかを、開発者ツールのアクセシビリティの表示で確かめたか。
- スクリプトが見た目を変えていないか。見た目の条件が、CSSの1か所にまとまっているか。

## 判断の問い

### 問い1

「必須」の印を、ラベルに `data-required` 属性を付け、`::after { content: "必須"; }` で入れる書き方にしたい、と言われました。どう答えますか。

HTMLに書くように答えます。必須であることは入力する人が知る必要のある情報で、生成コンテンツの文字は、スクリーンリーダーやブラウザによって読み上げられないことがあり、コピーもできません（`no-meaningful-generated-content`）。印の見た目は、HTMLに書いた `<span class="_required">` のCSSでそろえます。

### 問い2

誤りの文章を、`._error` に `hidden` 属性を付けておき、スクリプトで外して表示する書き方にすると、何が変わりますか。

<details>
{/* textlint-disable ja-technical-writing/ja-no-mixed-period */}
<summary>答えと解説</summary>
{/* textlint-enable ja-technical-writing/ja-no-mixed-period */}

誤りを表示するかどうかを、スクリプトが受け持つようになります。スクリプトが読み込めなかった環境では、`:user-invalid` が当てはまっても文章が表示されず、枠線の色だけが変わります。この節の書き方では、表示はCSSの `:user-invalid` が受け持ち、スクリプトは誤りの文章を入力欄に関連付ける属性だけを付けるので、スクリプトがなくても見た目の誤りの表示は動きます。

</details>

## この節で使ったルール

- [`no-meaningful-generated-content`](/pseudo/generated-content/#rule-no-meaningful-generated-content)：必須の印のように、読み手が知る必要のある文字を、生成コンテンツで入れません。
- [`input-font-size-min-1rem`](/interaction/forms/#rule-input-font-size-min-1rem)：入力欄の文字サイズは、1rem（16px相当）以上にします。
- [`field-sizing-for-textarea`](/interaction/forms/#rule-field-sizing-for-textarea)：`<textarea>` には `field-sizing: content` を指定し、最小と最大の高さを `lh` 単位で決めます。
- [`accent-color-for-color-only`](/interaction/forms/#rule-accent-color-for-color-only)：チェックボックスの色を変えるだけなら、`accent-color` を使います。
- [`user-invalid-for-errors`](/interaction/forms/#rule-user-invalid-for-errors)：入力エラーの見た目は、`:invalid` ではなく `:user-invalid` に指定します。
- [`native-and-aria-state-together`](/pseudo/form-states/#rule-native-and-aria-state-together)：同じ状態をネイティブの属性とARIA属性で表すときは、まとめて指定します。
- [`no-color-only-information`](/color-media/forced-colors/#rule-no-color-only-information)：入力エラーのような情報を、色の違いだけで伝えません。
- [`hover-operable-in-any-hover`](/interaction/states-and-focus/#rule-hover-operable-in-any-hover)：ホバーは、`&:enabled:hover` のように操作できる状態に限定します。
