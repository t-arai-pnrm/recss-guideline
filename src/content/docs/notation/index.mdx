第9章は、CSSの「書き方」の規約をまとめた章です。クラス名の付け方と名前に使う語の意味、`@scope` とネストの分担、ネストの深さと何をネストするかの判断、宣言の並び順、新しい記法への統一、コメントの書き方を定めます。この中には、表記をそろえるための規約と、意図しない適用や上書きを防ぐための規約があります。命名、名前に使う語、コメントは表記をそろえる規約で、そろっていないと、コードを読むたびに書いた人の癖を読み解くことになります。スコープの下限、ネストのセレクタと詳細度、宣言とネストしたルールの並び順、論理プロパティは、どの要素に当たるかや表示の結果に関わります。

規約は、ツールで検査できる形にします。宣言の並び順や `display` の書き方は、機械的に判断できます。こうしたものはStylelintに任せ、人はレビューで命名や設計の判断に集中します。ただし、本書のStylelintの設定で検出できるのは、この章の規約のうち、並び順や色の関数の書き方のような一部です。

ただし、ツールに従えば安全というわけではありません。私のテンプレートでは、Stylelintの並び順の設定に従った結果、メディアクエリで上書きできないコンポーネントをいくつも作っていました。規約とツールの設定は、ブラウザでの実際の動きと照らして見直す必要があります。この章には、その経験から生まれた規約も含まれています。

命名も、何度か変えてきました。ブログではPascalCaseのBEMを使い、テンプレートでは `scoped PascalCase` の形を経て、現在は `scoped kebab-case` の形に落ち着いています。この章では、いちばん新しい書き方を紹介します。

## この章で判断できるようになること

この章を読むと、クラス名を見ただけでコンポーネントのルート、子要素、ユーティリティのどれかを見分け、名前に使った語が意味に合っているかを判断できるようになります。範囲を `@scope` で区切るかネストで表すか、ネストを何層までにし、条件付きのアットルールをどこに書くかを、どの要素に当たるかと詳細度への影響から決められます。規約のうちStylelintに任せられるものと、命名や設計のようにレビューで人が判断するものも分けられます。

## 名前の前提になる2つの考え方

この章の命名は、第10章で詳しく扱う2つの考え方を前提にしています。先に要点だけを押さえておくと、名前の記号が何を区別しているのかを読み取れます。

1つ目は、部品の境界です。本書では、カードやボタンのようにHTMLの構造をまとめて管理する部品を「コンポーネント」と呼び、その見た目の責任をコンポーネントの中に閉じ込めます。ルートに付ける `scoped <名前>` は境界の始まりを、子要素の `_` は「この部品の中だけで意味を持つ名前」を示します。境界の外にある親は、子の部品の中の要素に直接スタイルを書きません。

2つ目は、外から変える値です。親が子の部品の見た目を変えたいときは、中の要素を選ばず、子が受け付けると約束した値だけを渡します。本書では、この値を `--<コンポーネント>--<プロパティ>` のカスタムプロパティ（公開プロパティ）にし、部品の中だけで使う値は `--_` で始めて区別します。何をコンポーネントにするかは「[10-1 何をコンポーネントにするか](/components/what-is-a-component/)」で、境界の守り方は「[10-2 コンポーネントの境界を守る](/components/boundaries/)」で、値の受け渡しは「[10-5 公開プロパティと内部プロパティ](/components/custom-properties/)」で説明します。

## 最初に押さえるルール

次のルールを先に押さえ、ほかのルールは、該当する場面で付録A「[ルール一覧](/appendix/rules/)」から引けば足ります。

- [`scoped-class-on-root`](/notation/scope-and-nesting/#rule-scoped-class-on-root)：スコープのルートになる要素には、必ず `scoped` クラスを付けます。
- [`child-class-underscore`](/notation/naming/#rule-child-class-underscore)：コンポーネントの子要素のクラス名は、`._title` のように `_` で始まるkebab-caseにします。
- [`name-by-role`](/notation/naming/#rule-name-by-role)：コンポーネント、子要素、パターンの名前は、見た目ではなく役割で付けます。
- [`nest-own-states`](/notation/nesting/#rule-nest-own-states)：要素自身の擬似クラス、擬似要素、属性の状態は、主語のセレクタに連結せず、主語のルールの中に `&:popover-open` のようにネストして書きます。
- [`no-nesting-concatenation`](/notation/nesting/#rule-no-nesting-concatenation)：`&__title` のように、`&` に文字をつなげてクラス名を作りません。

## 判断の問い

この章の内容で答えられる問いを2つ置きます。1つ目は本書の命名で書く問い、2つ目は本書の命名を持ち込むかどうかを決める問いです。

### 本書の命名でクラスを付ける

答えを開く前に、各要素に付けるクラスを予想してください。

お知らせのカードを、コンポーネントとして作ります。カードの中の要素は一律の間隔で縦に積み、タグの一覧は横に並べて入りきらなければ折り返し、末尾の注記だけを中央揃えにします。編集者が選んだお知らせは特集として、見出しを大きく表示します。次のHTMLのどの要素に、どの種類のクラスを付けますか。特集はどこで表しますか。

```html
<article>
  <h3>営業時間の変更について</h3>
  <p>店舗の改装に伴い、営業時間を変更します。</p>
  <ul>
    <li>お知らせ</li>
    <li>店舗</li>
  </ul>
  <p>掲載から1年が過ぎたお知らせは削除します。</p>
</article>
```

<details>
{/* textlint-disable ja-technical-writing/ja-no-mixed-period */}
<summary>答えと解説</summary>
{/* textlint-enable ja-technical-writing/ja-no-mixed-period */}

ルートに `scoped news-card` を、2つの段落に `_lead` と `_note` を付け、見出しと一覧には子要素のクラスを付けません。縦に積む配置とタグを折り返す配置は、ルートと `ul` に重ねるコンポジションの `stack` と `cluster` に任せ、注記の中央揃えはユーティリティの `-text-center` で重ねます。1つの要素に種類の違うクラスが並ぶところは、ルート、子要素、コンポジション、パターン、ユーティリティの順に `|` で区切ります（「[9-1 命名規則](/notation/naming/)」）。

```html
<article class="scoped news-card | stack" data-variant="featured" style="--stack--gap: calc(var(--spacing--sm) / 16 * 1rem)">
  <h3>営業時間の変更について</h3>
  <p class="_lead">店舗の改装に伴い、営業時間を変更します。</p>
  <ul class="cluster" style="--cluster--gap: calc(var(--spacing--xxs) / 16 * 1rem)">
    <li>お知らせ</li>
    <li>店舗</li>
  </ul>
  <p class="_note | -text-center">掲載から1年が過ぎたお知らせは削除します。</p>
</article>
```

子要素のクラスを付けるのは、同じ種類の要素を役割で区別するときだけです。段落は2つあって役割が違うので `_lead` と `_note` で区別し、1つしかない `h3` と `ul` は、スコープの中のタイプセレクタで選びます。特集は、`news-card--featured` のような修飾子や、見出しに付ける別のクラスでは表しません。ルートに `data-variant="featured"` を付け、`:scope` の中の `&[data-variant="featured"]` で内部プロパティの値を切り替えます。見出しを選ぶセレクタにルートの条件が加わらないので、詳細度は上がりません（「[9-2 BEMからの書き直しとバリエーション](/notation/variants/)」）。

</details>

### 既存のBEMのサイトに部品を足す

BEMで書かれた既存のサイトに、お知らせのカードを1つ足します。既存のCSSは `.news-list__item` のような名前で書かれていて、`@scope` は使っていません。チームは命名をBEMで合意していて、本書の規約はまだ知りません。新しいカードのクラスは、本書の形（`scoped news-card` と `_lead`）とBEMのどちらで付けますか。

<details>
{/* textlint-disable ja-technical-writing/ja-no-mixed-period */}
<summary>答えと解説</summary>
{/* textlint-enable ja-technical-writing/ja-no-mixed-period */}

既存のBEMに合わせて付けます。本書の命名を持ち込まないことが、この場面での正しい判断です。

```html
<article class="news-card">
  <h3 class="news-card__title">営業時間の変更について</h3>
  <p class="news-card__lead">店舗の改装に伴い、営業時間を変更します。</p>
</article>
```

本書の短い子要素の名前は、`@scope` で範囲を閉じることを前提にした約束です。`@scope` を使っていないサイトで `._lead` のような名前を使うと、ページ全体で衝突します。部品を1つ足すために命名を変えると、2つの命名が混ざり、読む人が両方の規則を見分けることになります。BEMのままでも、部品の中を外から選ばないことと、外から変える値を公開プロパティで受け取ることは取り入れられます（「[9-1 命名規則](/notation/naming/#補足と注意点)」）。名前を本書の形へ変えるのは、サイトが `@scope` へ移るときに合わせます（「[19-6 既存のサイトに段階的に導入する](/operations/adoption/)」）。

</details>

## この章の判断のまとめ

スタイルがほかのコンポーネントにまで当たるなら範囲の問題なので、`@scope` の下限とルートの `scoped` を確かめ、要素自身の状態やバリエーションをまとめたいならネストを選びます。条件付きの指定が効かないときは、詳細度を上げる前に、`@media` や `@container` がセレクタの中にあるか、ネストしたルールの後ろに宣言を足していないか、詳細度の違うセレクタリストの中でネストしていないかを調べます。ネストするかどうかはHTMLの階層ではなく、そのルールが親のセレクタなしで意味を持つかで決め、子自身の見た目は子のルールに書きます。

名前に迷ったら、見た目ではなく、その要素が何なのかを1文で書いて役割の語を選び、HTMLやCSSで意味の決まった語はその意味でだけ使います。並び順や記法のように機械で判断できるものはStylelintに任せ、レビューでは名前の役割とルールの持ち主を確かめます。
