CSSファイルの先頭には、そのファイルの責務と使い方を `/** */` の説明ブロックで書きます。外から値を変えられる公開プロパティがあれば、`@prop` に型、デフォルト値、説明を並べます。`/** */` の形式を使うのは、この説明ブロックだけです。

コードの途中のコメントには、「なぜそう書くのか」と「なぜ別の書き方をしないのか」だけを書きます。何をしているかはコードを読めば分かるので、書きません。変更の経緯や日付、コメントアウトしたコードも残しません。

コメントは、多ければよいものではありません。コードだけでは伝わらない判断が、必要な場所に過不足なく残っていることが大切です。

## コードを言い換えたコメントの問題

コメントの多いコードは丁寧に見えますが、内容によってはかえって読む妨げになります。次のコメントは、どれもよく見かけるものです。

```css title="🙅‍♂ Not Recommended: コードの言い換えと経緯を書いたコメント" issue="convention"
/* 🙅‍♂ Not Recommended */
/* カードのスタイル */
.card {
  /* グリッドにする */
  display: block grid;

  /* 余白を16pxにする */
  padding: 24px;

  /* 2025/04 デザインの変更で 8px から 12px に変更 */
  border-radius: 12px;

  /* box-shadow: 0 2px 4px rgb(0 0 0 / 10%); */
}
```

「グリッドにする」は、`display: block grid` を日本語に言い換えただけで、新しい情報がありません。「余白を16pxにする」のほうは、すでにコードと食い違っています。値を変えたときにコメントを直し忘れたのでしょう。コードの言い換えは、コードを変えるたびにコメントも直さなければなりません。直し忘れれば、その時点で誤った情報です。

変更の経緯を書いたコメントも同じです。いつ何を変えたかはバージョン管理に残っているので、コメントに書く必要はありません。コメントアウトしたコードは、消し忘れなのか、いずれ戻す予定なのかが読み手には分からず、判断を迷わせるだけです。

私も、ある案件でソースコード全体のコメントを見直したことがあります。日付、作業の段階、計画書の節番号、以前の実装から移した経緯、コードの動きを言い換えたコメントを削除し、ファイル先頭の説明とTODO、lintの無効化の指示だけを残しました。コードの行は1行も変えず、コメントだけを整理しています。

AIに書かせたコードには、宣言を1つずつ言い換えたコメントが付いてくることがよくあります。レビューのときに、このようなコメントは削除してください。

## コメントに書く「なぜ」

コメントに書くのは、コードを読んでも分からないことです。コードから分かるのは「何をしているか」までで、「なぜそうしたのか」や「なぜほかの書き方をしなかったのか」は分かりません。この2つだけをコメントに書きます。

```css title="🙆‍♂ Recommended: 理由と、ほかの方法をとらない理由を書く"
@layer reset {
  :where(ul, ol, menu) {
    /*
     * Safari では list-style: none にすると、スクリーンリーダーが
     * リストとして読み上げないため、マーカーだけを消す。
     * @see https://matuzo.at/blog/2023/removing-list-styles-without-affecting-semantics
     */
    list-style-type: "";
  }
}

@scope (.scoped.filter-chip) to (.scoped) {
  :scope {
    /* 強制カラーモードでは背景色が消えるので、透明な枠線で範囲を残す */
    border: 1px solid transparent;
    background-color: var(--background--surface);
  }
}
```

1つ目は、本書が使うリセットCSSのkiso.cssにあるコメントと同じ内容です。`list-style: none` という一般的な書き方を使わない理由を説明しています。コメントがなければ、後から読んだ人が「`list-style: none` のほうが分かりやすい」と書き換えてしまうかもしれません。根拠になる資料は `@see` で示します。2つ目のコメントは、見えない枠線を残す理由を説明しています。コメントがなければ、見た目に影響しない宣言として消されるかもしれません。どちらも、コードだけでは伝わらない判断です。

「なぜ別の方法をとらないか」は、一見すると不自然なコードほど必要になります。論理プロパティの規約に反して物理プロパティを使う、ベンダープレフィックスを書く、Stylelintのルールを無効にするといった箇所です。理由が書かれていなければ、読んだ人は規約どおりに直してよいのか判断できません。反対に、規約どおりの書き方には理由を書く必要はありません。

値の根拠も「なぜ」に含まれます。「[13-2 ブレイクポイントの決め方](/responsive/breakpoints/)」で説明したように、`calc()` の式が何列・何個分の幅を表すのかは、コメントで補足してかまいません。

一方で、何をしているかを説明したくなったら、先に名前を見直します。たとえば、角丸の内側の半径を `calc()` で求める式は、`--_inner-radius` のような名前のカスタムプロパティにすれば、コメントなしで意図が伝わります。

```css title="🙆‍♂ Recommended: コメントの代わりに名前で意図を伝える"
._card {
  --_outer-radius: 16px;
  --_padding: 8px;
  --_inner-radius: calc(var(--_outer-radius) - var(--_padding));

  padding: var(--_padding);
  border-radius: var(--_outer-radius);
}
```

`--_inner-radius` という名前を読めば、外側の角丸から余白を引いて、内側に置く要素の角丸を求めていることが分かります。計算の結果だけを `8px` と書くと、その値の由来をコメントで説明するしかありません。名前で伝えられることは名前で伝え、名前では伝えられない理由だけをコメントに残します。式の値に名前を付ける考え方は、第6章の「[6-3 計算関数で根拠を式に残す](/values/math-functions/)」でも説明しています。

## ファイル先頭の説明ブロック

ファイルの先頭には、後からファイルを開いた人のための説明を書きます。最初の1〜2文で、何のためのスタイルで、どこで使うものかを説明します。ほかのファイルが受け持つことを書いておくと、責務の境界も伝わります。

```css title="🙆‍♂ Recommended: 責務と公開プロパティを説明ブロックに書く"
/**
 * 画像と本文を並べたカード。
 * 記事の一覧や関連記事のように、幅の違う場所に置ける。
 * 一覧としての並べ方は、置く側のレイアウトが受け持つ。
 *
 * @prop {length} --media-card--radius [8px] - 角丸の大きさ
 * @prop {color}  --media-card--accent [currentColor] - 見出しの色
 *
 * @example
 * <article class="scoped media-card" style="--media-card--radius: 16px">
 *   ...
 * </article>
 */

@scope (.scoped.media-card) to (.scoped) {
  :scope {
    --_radius: var(--media-card--radius, 8px);
    --_accent: var(--media-card--accent, currentColor);

    border-radius: var(--_radius);
  }

  h2 {
    color: var(--_accent);
  }
}
```

公開プロパティがあるときは、`@prop` の後に、型を波括弧で、デフォルト値を角括弧で書き、最後に説明を続けます。使う人は、CSSの中身を読まなくても、外から何を変えられるのかと、何もしなければどうなるのかが分かります。使用例は `@example`、参考資料は `@see` で示します。`@use` はJSDocの標準にないタグで、本書では使用例を1行で示すときの `@example` の代わりとして使います。使用例が1行で済むときは、`@use` の後ろに1行で書くこともあります。`@prop` の行が多いときは、型、名前、デフォルト値の位置を縦にそろえておくと読みやすくなります。公開プロパティの名前の付け方は、第10章の「[10-5 公開プロパティと内部プロパティ](/components/custom-properties/)」で扱います。

公開プロパティのないファイルでも、説明は省きません。ベーススタイルのファイルなら「リセットの後に当てる要素の既定のスタイル。ルート要素の色とフォント、見出しの組版、フォーカスリングを定義する」のように、何を置く場所なのかを書きます。後から別の人がスタイルを足すとき、どのファイルに書くべきかの判断材料になります。

`/** */` をこの説明ブロックに限るのは、コードの途中のコメント（`/* */`）と記法で見分けるためです。これで、ファイル全体の説明なのか、その場の補足なのかが分かります。Astroのコンポーネントのように、CSSをマークアップと同じファイルに書く場合は、コンポーネントの説明として先頭に書きます。

## 変更の経緯とコメントアウトしたコード

変更の経緯は、コメントではなくバージョン管理に残します。「以前はこう書いていた」「いつ、どの計画に沿って移した」といった情報は、書いた直後には役に立ちそうに見えます。しかし、読む人が知りたいのは、今のコードがなぜこうなっているかです。

```css title="🙅‍♂ Not Recommended: 移植の経緯と計画書の番号を書く" issue="convention"
/* 🙅‍♂ Not Recommended */
._award {
  padding-block-end: 16px;
  border-block-end: 1px solid var(--border--base);

  /*
   * 以前のテンプレートでは、先頭の項目の上余白だけを 0 にしていた。
   * 2025/08 に計画書 6.4 に沿って、2つ目以降に上余白を付ける形へ移植した。
   */
  &:not(:first-child) {
    padding-block-start: 16px;
  }
}
```

```css title="🙆‍♂ Recommended: 今のコードの理由だけを書く"
._award {
  padding-block-end: 16px;
  border-block-end: 1px solid var(--border--base);

  /* 先頭の項目の上には罫線がないので、上の余白は罫線のある2つ目以降にだけ付ける */
  &:not(:first-child) {
    padding-block-start: 16px;
  }
}
```

書き直したコメントでは、経緯を消し、「上の余白を2つ目以降にだけ付ける理由」だけを残しています。コードは変えていません。先頭の余白を打ち消さずに2つ目以降にだけ付ける理由は、「[2-3 保守しやすさを最優先にする](/design-mindset/maintainability/)」で説明しています。計画書の番号やタスクの番号は、その文書を知らない人には意味が通りません。文書が更新されれば、番号そのものが古くなります。

コメントアウトしたコードも、残さず削除します。必要になったら、バージョン管理の履歴から戻せます。例外は、ブラウザの不具合の報告のように、今の書き方の根拠になる資料です。これは `@see` で示しておけば、不具合が直ったときに回避策を外す手がかりにもなります。

## 見出しのコメントの3段階

1つのファイルの中にいくつかのまとまりがあるときは、見出しのコメントで区切ります。見出しには3つの段階があり、記法で見分けられるようにします。

```css
/* ======================================================
 *
 *   大見出し
 *   補足のテキスト
 *
 * ====================================================== */

/* ==----------------------------------------------------
 * セクション見出し
 * ---------------------------------------------------- */

/*
 * 小見出し
 */

/* 1行のコメント */
```

大見出しは、上下を `=` の線で囲みます。1つのファイルが1つの責務だけを持つなら、先頭の説明ブロックがいちばん上の見出しの代わりになるので、大見出しは要りません。使うのは、1つのファイルに大きなまとまりが複数あるときだけです。

セクション見出しは、`==` に続く線でまとまりを区切ります。小見出しは、装飾を付けずに複数行のコメントで書きます。コメントの幅は、インデントを含めて60文字を目安に折り返します。見出しの記法をそろえておくと、ファイルの構造がひと目で分かります。

セクション見出しがよく役立つのは、1つのコンポーネントの中に、役割の違う子要素のまとまりが複数あるときです。たとえば、記事のカードの見出しまわり、本文、操作部の前にセクション見出しを置くと、どこからどこまでが何のための指定なのかを追いやすくなります。見出しで区切っても読みにくいほどまとまりが増えてきたら、内側の部品を別のコンポーネントとして切り出し、ファイルも分けます（「[10-2 コンポーネントの境界を守る](/components/boundaries/)」）。

どの段階のコメントも、`/* */` で書きます。Sassでは `//` で1行のコメントを書けますが、素のCSSでは `//` はコメントとして扱われません。後ろの宣言やルールが無効になってしまうので、Sassから移ってきたコードに `//` が残っていないかを確認してください。記法を `/* */` にそろえておけば、CSSとSassの間でコードを移しても、コメントの見た目は変わりません。

## TODOとlintの無効化

あとで対応が必要な箇所には、`/* TODO: … */` のように、コメントの先頭に `TODO`、`FIXME`、`HACK` を大文字で書きます。表記をそろえておけば、未完了の作業や一時的な対処を、検索でまとめて見つけられます。私の案件でコメントを見直したときも、小文字で書いていた `todo:` を大文字にそろえ、作業の段取りの説明を消して、何を直すのかだけを残しました。

```css title="🙆‍♂ Recommended: TODO は先頭に大文字で書く"
._heading {
  /* TODO: 見出しの文言が確定したら、折り返しの指定を見直す */
  @supports (word-break: auto-phrase) {
    text-wrap: balance;
    word-break: auto-phrase;
  }
}
```

Stylelintのルールを無効にするコメントも、残してよいコメントです。無効にするのは必要なルールだけにして、なぜ無効にするのかを直前のコメントに書きます。範囲は `stylelint-disable-next-line` とルール名で、必要な1行と1つのルールに絞ります。ファイル全体やすべてのルールを無効にすると、同じ場所にある別の誤りまで見逃してしまうからです。

具体的な例は、「[9-9 論理プロパティと論理値](/notation/logical-properties/)」の物理でしか書けない値の項と、「[9-8 モダンな記法にそろえる](/notation/modern-syntax/)」のベンダープレフィックスの項にあります。Stylelintの運用は、「[19-1 Stylelintでルールを守る](/operations/stylelint/)」で扱います。
