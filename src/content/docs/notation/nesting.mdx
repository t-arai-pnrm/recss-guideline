セレクタは2層まで、つまり親のセレクタと、その中にネストした1段までにします。ネストしたセレクタは必ず `&` で始めます。`@scope`、`@media`、`@container` などの@ルールは、層に数えません。宣言はネストしたルールより前に書き、Sassのような `&__title` の連結は使いません。ネストは、要素自身の状態や、条件によって変わるスタイルをまとめるために使います。

`@media` と `@container` は、`@scope` の直下に置かず、各セレクタの中に書きます。条件のブロックを `@scope` の先頭にまとめると、後ろにある元のルールが勝ってしまい、上書きできなくなるからです。Stylelintの並び順の設定は、何もしなければ条件のブロックを先頭へ移す並びにします。本書では、独自のルールでこれを防いでいます。

ネストの仕様は、「[4-5 CSSネストの基礎](/cascade/nesting/)」で説明しています。ネストに要素とその状態の関係を任せ、`@scope` にコンポーネントの範囲を任せるという分担は、「[9-4 @scopeとネストの使い分け](/notation/scope-and-nesting/)」で定めています。この節では、その分担にもとづいてネストをどう書くかを扱います。

## 深いネストの問題

Sassに慣れていると、HTMLの階層をそのままネストで写したくなります。見た目は整理されているようですが、このネストはHTMLの構造に強く依存します。リストを `ol` に変えたり、リンクを `button` に置き換えたりしただけで、セレクタが要素に一致しなくなります。

```css title="🙅‍♂ Not Recommended: HTMLの階層をネストで写す" issue="convention"
/* 🙅‍♂ Not Recommended */
.site-nav {
  ul {
    display: block flex;

    li {
      flex-grow: 1;

      a {
        &[aria-current="page"] {
          font-weight: 700;
        }
      }
    }
  }
}
```

詳細度も知らないうちに上がります。最も内側のルールは `.site-nav ul li a[aria-current="page"]` と同じ意味になり、詳細度は `0.2.3` です。この太さを別の場所で変えたくなると、さらに詳細度の高いセレクタが必要になり、上書きのための上書きが積み重なっていきます。

また、ネイティブのCSSのネストはSassと同じではありません。Sassでは `&__title` のように `&` に文字をつなげてクラス名を作れますが、素のCSSではこれが無効なセレクタになり、ルールごと無視されます。Stylelintの `selector-nested-pattern` は `&` で始まるかどうかしか見ないので、この誤りは検出できません。

## ネストの範囲と `&`

本書では、ネストを「そのスタイルが誰のものか」を示すために使います。ネストしてよいのは、次の4つだけです。

- 要素自身の擬似クラスと擬似要素（`&:focus-visible`、`&::before`）
- 要素自身の属性やクラスで表す状態（`&[aria-current="page"]`）
- レイアウトに欠かせない直下の子（`& > *`、`& > ._icon`）
- 条件付きのアットルール（`@media`、`@container`、`@supports`）

独自のスタイルを持つ子要素は、親のルールに入れず、同じ階層に並べます。HTMLの階層を写すことや、詳細度を上げることは、ネストの目的にしません。スコープを閉じるのは `@scope` の役割で、ネストにその代わりをさせることもしません。直下の子のネストに書いてよい宣言や、セレクタリストの中でネストしたときの詳細度など、何をネストするかの判断は「[9-6 ネストの判断基準](/notation/nesting-criteria/)」で詳しく説明します。

```css title="🙆‍♂ Recommended: 要素自身の状態と直下の子だけをネストする"
@scope (.scoped.site-nav) to (.scoped) {
  ul {
    display: block flex;
    flex-wrap: wrap;

    & > * {
      flex-grow: 1;
    }
  }

  a {
    &[aria-current="page"] {
      font-weight: var(--font-weight--bold);
    }
  }
}
```

ネストしたセレクタは、必ず `&` で始めます。`&` を省いた `a { span { … } }` も、子孫結合子を補った `a span` として動きます。しかし先頭に `&` があれば、自身の状態（`&:hover`）か、直下の子（`& > *`）か、子孫（`& span`）かを、先頭だけで読み取れます。ネストが長くなっても、親を指すのは `&` だけなので、どのセレクタが親との関係を表しているのかを読み違えにくくなります。

宣言は、ネストしたルールや条件付きのアットルールより前に書きます。要素の基本のスタイルが先頭にまとまり、状態や条件による変化が後に続くので、読む順と上書きの順が一致するからです。ルールの中の並び順は、「[9-7 プロパティの並び順](/notation/property-order/)」のルール `block-content-order` で定めています。

## 自身の状態は主語のルールの中に書く

要素自身の擬似クラス、擬似要素、属性の状態は、主語のセレクタに連結せず、主語のルールの中に `&:popover-open` のようにネストして書きます。`[popover]:popover-open` や `._link::after` のように連結して別のルールにすると、同じ要素のスタイルが複数のルールに分かれます。基本のスタイルを変えた人が、離れた場所にある状態のルールに気付かないことがあります。

```css title="🙅‍♂ Not Recommended: 状態を主語のセレクタに連結する" issue="convention"
/* 🙅‍♂ Not Recommended */
[popover] {
  transition-duration: var(--duration--fast);
  transition-property: opacity;
}

[popover]:popover-open {
  @starting-style {
    opacity: 0;
  }
}
```

AIにCSSを書かせると、この連結の形がよく出てきます。素のCSSでも正しく動くので、エラーにはなりません。しかし、`[popover]` のルールを読んだだけでは、開いたときの始まりの見た目を別のルールで指定していると分かりません。状態をネストすれば、要素がどの状態でどう見えるかを1つのルールの中で読み取れます。

```css title="🙆‍♂ Recommended: 状態を主語のルールの中にネストする"
@scope (.scoped.share-menu) to (.scoped) {
  [popover] {
    transition-duration: var(--duration--fast);
    transition-property: opacity;

    &:popover-open {
      @starting-style {
        opacity: 0;
      }
    }
  }
}
```

詳細度は、連結しても、ネストしても変わりません。親が1つのセレクタなら、`&:popover-open` を展開した結果は `[popover]:popover-open` と同じです。この規約は書く場所を決めるもので、カスケードの結果は変えません。親の状態によって子の見た目を変える書き方は、「[9-6 ネストの判断基準](/notation/nesting-criteria/)」で説明します。

## @ルールを層に数えない理由

「2層まで」は、セレクタだけを数えます。`@scope`、`@media`、`@container`、`@supports`、`@layer` は数えません。@ルールまで数えると、`@layer` と `@scope` で2段、その内側のセレクタで2段と、ネストの残り枠がファイルの構造で決まってしまいます。同じセレクタが、置く場所によって書けたり書けなかったりするので、ルールが分散して、どこまで書いてよいのかが分かりにくくなります。

セレクタだけを数えれば、数え方は単純です。`&:any-link:hover` の中に `@media (any-hover)` を入れても、セレクタは2層のままです。状態ごとにセレクタを別のルールへ分けずに済むので、要素の見た目がひとまとまりになります。

Stylelintには、この数え方に合う設定がありません。標準の `max-nesting-depth` は、アットルールも深さに数えます。`ignoreAtRules` は「数えない」ではなく、「その@ルールの中を検査しない」という動作です。`@scope` を指定すると、中で3段ネストしてもエラーになりません。そのため、本書の設定では `max-nesting-depth` を使いません。セレクタが2層に収まっているかは、レビューで確かめます。

## 条件付きのアットルールの置き場所

`@media` と `@container` を `@scope` の直下にまとめて書くと、上書きできない場合があります。例として、ナビゲーションのリンクを狭い画面では縦に積み、広い画面では横に並べるヘッダーを見てみます。

```css title="🙅‍♂ Not Recommended: 条件のブロックを @scope の先頭にまとめる" issue="behavior"
/* 🙅‍♂ Not Recommended */
@scope (.scoped.site-header) to (.scoped) {
  @media (width >= calc(640 / 16 * 1rem)) {
    ul {
      display: block flex;
    }
  }

  ul {
    display: block grid;
  }
}
```

このCSSでは、広い画面でもリンクは縦に積まれたままです。2つの `ul` のルールは、同じレイヤーの同じスコープにあり、詳細度はどちらも `0.0.1` です。`@media` は条件を付けるだけで、詳細度を上げません。条件が同じなら後に書いたルールが勝つので、画面の幅にかかわらず `display: block grid` が残ります。

誰もこんな順番で書かないと思うかもしれませんが、この順番はStylelintの並び順の設定から生まれます。本書が使っている `order/order` の設定は、ブロックの中の並びを「宣言 → `@supports` → `@container` → `@media` → ネストしたルール」と決めています。この決まりはセレクタの中だけでなく、`@scope` の中身にも当てはまります。条件のブロックを `@scope` の直下へ書くと、自動修正はそれを先頭へ移し、上書きの順番を逆転させます。

私のテンプレートでも、Stylelintに従って並べた結果、いくつかのコンポーネントでレスポンシブの指定が適用されていない箇所が後から見つかりました。エラーや警告が出ないうえ、狭い画面では正しく見えるので、気づきにくい不具合です。3つの書き方を比べた結果は次のとおりです（幅1200pxで、どれも条件に一致する状態）。

| 書き方 | 結果 |
|---|---|
| `@scope` の先頭に `@media` を置き、後ろに元のルールを書く | `grid`（上書きできない） |
| 元のルールの中に `@media` を書く | `flex`（上書きできる） |
| 元のルールの後ろに `@media` を置く | `flex`（上書きできる） |

3つ目の書き方でも上書きできますが、Stylelintの並び順と衝突します。そこで本書では、条件付きのアットルールを各セレクタの中に書きます。セレクタの中なら、`order/order` の並び順（宣言が先、条件が後）と、上書きに必要な順番が一致します。条件の中の宣言は、同じセレクタの基本の宣言より後にあるものとして扱われるので、確実に上書きできます。

```css title="🙆‍♂ Recommended: 条件をセレクタの中に書く" from="notation/conditions-inside"
@scope (.scoped.site-header) to (.scoped) {
  ul {
    display: block grid;

    @media (width >= calc(640 / 16 * 1rem)) {
      display: block flex;
    }
  }
}
```

ルート要素の条件は、`:scope` の中に書きます。`@supports` も同じ考え方で、セレクタの中に書きます。要素ごとのスタイルが1か所にまとまるのも利点です。ある要素の見た目がどの幅でどう変わるのかを、コードを上下へ行き来せずに読み取れます。

本書では、この規約をStylelintの独自ルール `book/conditions-inside-rules` で検査しています。`@media` と `@container` がセレクタの中にないと、エラーになります。`@scope` の直下だけでなく、ファイルの直下に書いた `@media` も対象です。

次の2つのデモは、同じHTMLに、条件の置き場所だけが違うCSSを当てたものです。幅を768px以上にすると、上のデモではリンクが横に並び、サイト名の文字が大きくなります。下のデモでは、サイト名の文字は大きくなりますが、リンクは縦に積まれたままです。

下のデモでも、サイト名の文字は大きくなります。`p` の元のルールは `font-size` を指定していないので、先頭の条件のブロックが負けないためです。上書きできないのは、元のルールが同じプロパティを指定しているときだけです。一部の指定だけが適用されなくなるので、見落としやすくなります。

## 条件のブロックの中の宣言

`@scope` の直下に置いた条件のブロックには、もう1つ問題があります。セレクタを書かずに、条件のブロックの中へ宣言をじかに書く書き方です。

```css title="🙅‍♂ Not Recommended: 条件のブロックの中に宣言をじかに書く" issue="behavior"
/* 🙅‍♂ Not Recommended */
@scope (.scoped.hero-section) to (.scoped) {
  @container style(--hero-section--size: --large) {
    min-block-size: calc(800 / 16 * 1rem);

    & ._title {
      font-size: calc(64 / 16 * 1rem);
    }

    ._lead {
      font-size: calc(20 / 16 * 1rem);
    }
  }
}
```

Chromeで確かめたところ、この書き方では、条件のブロックの中の宣言がすべて破棄されました。さらに、直後の `& ._title` のルールも一緒に消え、残ったのは `._lead` のルールだけでした。条件を挟まずに `@scope` の直下へ宣言を書いた場合は、Chromeではルート要素に適用されたので、条件のブロックの中だけで起きる現象です。本書はルートの宣言を `:scope` の中に書くので、`@scope` の直下へ宣言を書くこと自体をしません。

私の案件でも、この書き方をしたページで、ヒーローの高さや背景、カルーセルの配置など、主要なスタイルがまとめて適用されなくなったことがあります。Stylelintの標準のルールでは検出できず、ビルドも通ったので、ブラウザで確認するまで気づけませんでした。条件をセレクタの中に書く規約を守っていれば、この書き方は `book/conditions-inside-rules` のエラーになります。
