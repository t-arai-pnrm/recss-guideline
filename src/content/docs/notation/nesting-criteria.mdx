ネストするかどうかは、HTMLの階層ではなく、ネストしたルールが親のセレクタなしで意味を持つかどうかで決めます。要素自身の状態と擬似要素、親のレイアウトによって意味が決まる直下の子の宣言、条件付きのアットルールは、親がなければ説明できないのでネストします。独自の見た目を持つ子要素は、同じコンポーネントの中にあっても親のルールには入れず、同じ階層に並べます。

ネストしたセレクタの `&` は、親のセレクタリストを `:is()` で包んだものとして詳細度が計算されます。詳細度の違うセレクタを並べたリストの中でネストすると、詳細度の低いほうのセレクタにも、リストの中でいちばん高い詳細度が付きます。そのため、詳細度の違うセレクタリストの中ではネストしません。

この節は、「[9-5 ネストの書き方](/notation/nesting/)」で定めた規約を前提にします。セレクタは2層までにし、`&` で始め、条件付きのアットルールはセレクタの中に書くという規約です。そのうえで、何をネストするかの判断を詳しく説明します。

## 「2層まで」だけでは決まらないこと

「セレクタは2層まで」という規約を守っていても、何をネストするかの判断は残ります。同じコンポーネントの中にあるからという理由で、子要素の見た目をすべて親のルールの `& > ._icon` や `& ._title` に書くこともできるからです。層の数は2のままですが、子のスタイルが親のルールに散らばり、子の見た目を変えるたびに親のルールを探すことになります。

ネストを使う目的も、人によって違います。HTMLの階層を写すため、記述を減らすため、詳細度を上げて既存のスタイルに勝つため、ほかのコンポーネントにスタイルが漏れないようにするため、といった目的です。このうち、本書がネストに求めるのは、ルールの持ち主を示すことだけです。残りの目的は、別の仕組みが受け持ちます。範囲を閉じるのは `@scope`、カスケードの順位を決めるのは `@layer`、コンポーネントの外から値を渡すのは公開プロパティです。

ネストを持ち主の表現に限るのは、ネストが詳細度とHTMLへの依存を伴うからです。ネストしたセレクタは、親のセレクタとつながった1つのセレクタとして詳細度が計算されます。範囲を閉じる効果はなく、親のセレクタが一致する要素の中にあるという条件が付くだけです。ほかの目的でネストすると、この条件と詳細度だけが残ります。

BEMにたとえると、BlockとElementの関係（コンポーネントと、その中の子要素）は `@scope` で表します。Modifier（要素の状態やバリエーション）は、`&:focus-visible` や `&[data-variant="featured"]` のようなネストで表します（「[9-4 @scopeとネストの使い分け](/notation/scope-and-nesting/)」）。BlockのModifierがElementの見た目を変える場合は、Elementのルールの中に `&:is(:scope[data-variant="featured"] *)` と書きます（後述の「親の状態で子の見た目を変える」）。

ネストで子要素を選ぶのは、直下の子に配置の宣言を書くときだけです。これはElementの関係ではなく、親のレイアウトの一部です。

## ネストしてよい関係

ネストしてよいのは、「9-5」で挙げた関係です。ここでは、要素自身の状態と擬似要素、条件付きのアットルール、直下の子の3つに分けて説明します。どれも、ネストしたルールが親の要素について述べていて、親のセレクタを外すと意味が変わります。

1つ目は、要素自身の状態と擬似要素です。`&:hover` や `&[aria-current="page"]` は親の要素そのものを状態によって絞り込むルールです。`&::before` は親の要素がなければ存在しない擬似要素です。基本のスタイルのすぐ後ろに書けば、その要素がどの状態でどう見えるかを1か所で読み取れます。

2つ目は、条件付きのアットルールです。`@media`、`@container`、`@supports` は、セレクタの階層を増やさずに、その要素のスタイルに条件を付けます。状態の中に条件を書くこともあります。ホバーの見た目は、ホバーのできる入力装置があるときに限るので、`&:any-link:hover` のような状態の中に `@media (any-hover)` を書きます。`@starting-style` も、開いた状態のアニメーションの始まりを表すので、`&:popover-open` の中に書きます。

```css title="🙆‍♂ Recommended: 状態の中に、その状態が成り立つ条件を書く"
@scope (.scoped.share-menu) to (.scoped) {
  a {
    text-decoration-line: revert;

    &:any-link:hover {
      @media (any-hover) {
        text-decoration-line: initial;
      }
    }

    &:focus-visible {
      text-decoration-line: initial;
    }
  }

  ._panel {
    transition-duration: var(--duration--fast);
    transition-property: opacity;

    &:popover-open {
      @starting-style {
        opacity: 0;
      }
    }
  }
}
```

3つ目は、親のレイアウトに欠かせない直下の子です。次の節で、このネストに書いてよい宣言を説明します。

## 直下の子に書いてよい宣言

直下の子へのネストには、親のレイアウトによって意味が決まる宣言だけを書きます。`flex-shrink`、`grid-area`、`align-self` などです。子の大きさや色のように、子自身で決まる宣言は、子のルールに書きます。

```css title="🙆‍♂ Recommended: 親との関係だけを直下の子のネストに書く"
@scope (.scoped.choice-list) to (.scoped) {
  ._option {
    display: block flex;

    & > ._icon {
      flex-shrink: 0;
    }
  }

  ._icon {
    inline-size: 1em;
    aspect-ratio: 1;
    color: var(--foreground--muted);
  }
}
```

`flex-shrink: 0` は、`._option` がFlexboxであるときにだけ意味を持つ宣言です。親が `display: block grid` に変われば、この宣言も一緒に見直す必要があります。親のルールの中に置けば、レイアウトを変える人がその場で気付けます。一方、`inline-size` と `aspect-ratio` はアイコン自身の大きさで、どの親に置かれても変わりません。これを `& > ._icon` のネストの中で指定すると、アイコンを別の親へ移したときに大きさが失われます。

`flex-shrink` のほかにも、親のレイアウトや親のスクロールで意味が決まる宣言は、直下の子へのネストに書きます。`float`、`shape-outside`、`position: absolute` と `inset`、`scroll-snap-align`、`break-inside`、要素の外側の `margin` です。外側の `margin` には、要素の間の余白のほかに、`auto` で寄せる値と負の値も含みます。

```css title="🙆‍♂ Recommended: 親を基準にした重ね方を、親のネストに書く"
@scope (.scoped.product-card) to (.scoped) {
  :scope {
    position: relative;

    & > ._badge {
      position: absolute;
      inset-block-start: 8px;
      inset-inline-end: 8px;
    }
  }
}
```

`position: absolute` の `inset` は、位置の基準になる親の箱から測る値です。親の `position: relative` と同じ場所に置けば、基準を変えるとき、一緒に見直せます。`position: sticky` も、コンポーネントの中の要素のスクロールを基準にするなら、同じ理由で親のネストに書きます。一方、ページのルートのスクロールに沿わせる `sticky` と、ビューポートを基準にする `fixed` は、親のレイアウトで決まらないので、子のルールに書いてかまいません。

```css title="🙅‍♂ Not Recommended: 子自身の見た目まで親のネストに書く" issue="convention"
/* 🙅‍♂ Not Recommended */
@scope (.scoped.choice-list) to (.scoped) {
  ._option {
    display: block flex;

    & > ._icon {
      flex-shrink: 0;
      inline-size: 1em;
      aspect-ratio: 1;
      color: var(--foreground--muted);
    }
  }
}
```

この分け方は、コンポーネントの境界の考え方と同じです。「[10-2 コンポーネントの境界を守る](/components/boundaries/)」では、子のコンポーネントの配置は置く側の親が決め、見た目は子が決めるという分担を定めています。直下の子へのネストは、同じコンポーネントの中の子要素について、この分担を表す書き方です。ただし、直下にあることがたまたまのマークアップの都合にすぎないなら、`& >` は使いません。ラッパーを1つ足すだけで、セレクタが一致しなくなるからです。

## ネストせずに並べる要素

子要素が次のどれかに当てはまるなら、親のルールには入れず、同じ階層の独立したルールにします。子自身の状態のルールがある、子の中にもネストが必要になる、親以外の場所でも使われる、親のレイアウトではなく子自身の見た目を指定している、のいずれかです。どれも、子が自分のスタイルを持っていることを示しているので、子のルールが持ち主になります。

ほかのコンポーネントの内部をネストで選ぶことも、本書の書き方ではできません。`@scope (.scoped.<名前>) to (.scoped)` の範囲は、入れ子のコンポーネントのルートで止まり、ルートそのものも範囲の外です（「[4-4 @scopeでスタイルを閉じ込める](/cascade/scope/)」）。子のコンポーネントの見た目を親から変えたいときは、子が用意した公開プロパティに値を渡します（「[10-5 公開プロパティと内部プロパティ](/components/custom-properties/)」）。

記述を減らすためのネストもしません。見た目の似た要素を1つの親のルールに集めると、片方だけを変えたいときに、セレクタを分けるか、詳細度で上書きするかを迫られます。共有したいのが値なら、デザイントークンやカスタムプロパティで共有します。既存のスタイルに勝つ目的で、親のセレクタを重ねることもしません。詳細度で勝っても、次に上書きしたい人がさらに詳細度を上げることになるからです。順位の問題は `@layer` で、値の切り替えはカスタムプロパティで解決します。

## 親の状態で子の見た目を変える

開閉のボタンを開いたときにアイコンを回転させるなど、親の状態に応じて子の見た目を変えたい場合があります。親の状態と子を `:scope[aria-expanded="true"] ._icon` という1つのセレクタでつなげると、子の見た目を子のルールとは別の場所で指定することになります。かといって、`&[aria-expanded="true"]` の中に `& ._icon` を入れると、セレクタが3層になります。

本書では、祖先の状態によって変わるスタイルを、子のルールの中に `&:is(<祖先のセレクタ> *)` の形で書きます（「[4-2 セレクタで詳細度を設計する](/cascade/selectors/)」のルール `is-for-ancestor-context`）。`&:is(:scope[aria-expanded="true"] *)` は、「`aria-expanded="true"` を持つスコープのルートの子孫である、この要素」という意味です。子の見た目が状態によるものも含めて子のルールにまとまり、セレクタは2層に収まって `&` で始まります。

```css title="🙆‍♂ Recommended: 祖先の状態を子のルールの中に書く"
@scope (.scoped.accordion-trigger) to (.scoped) {
  ._icon {
    &:is(:scope[aria-expanded="true"] *) {
      rotate: 180deg;
    }
  }
}
```

この書き方では、`._icon` のルールを読むだけで、アイコンがどの状態でどう見えるかが分かります。祖先の状態は子の側から見た条件の1つで、`&:hover` のような自身の状態と同じ位置に並びます。擬似要素も同じで、`<details>` が開いたときに `summary` の記号を変えるなら、`summary` のルールの中に `&:is(:scope[open] *)::after` と書きます。ただし、祖先のホバーとフォーカスで変わる見た目は、この形では書きません。祖先で `--_hocus` のフラグを立て、子の側で `@container style(--_hocus: --true)` と問い合わせます（「[10-6 スタイルクエリで状態を伝える](/components/style-queries/)」）。

## `&` が表すもの

`&` は、親のルールに一致した要素を表します。`&:hover` は親の要素自身のホバーで、`& > ._icon` は親の直下の子です。先頭に `&` と結合子のどちらもないセレクタをネストすると、親との間に子孫結合子があるものとして解釈されます。

```css title="🙅‍♂ Not Recommended: & を省いた擬似クラス" issue="behavior"
/* 🙅‍♂ Not Recommended */
._submit-button {
  :focus-visible {
    background-color: var(--_background--hocus);
  }

  :hover {
    @media (any-hover) {
      background-color: var(--_background--hocus);
    }
  }
}
```

この `:hover` は `._submit-button :hover` と同じ意味になり、ボタンの中でホバーされている要素に一致します。`:focus-visible` も同じで、ボタンの中でフォーカスされている要素に一致します。ボタン自身には当たらず、エラーにもなりません。本書でネストしたセレクタを必ず `&` で始めるのは、このような取り違えを防ぎ、自身の状態か、直下の子か、子孫かを先頭で読み分けるためです。子孫を選ぶことがその要素の前提なら、`& ._title` と明示します。

`&` の詳細度は、親のセレクタリストを `:is()` で包んだものと同じです。`:is()` の詳細度は、引数の中でいちばん高いセレクタの詳細度になります（「[4-2 セレクタで詳細度を設計する](/cascade/selectors/)」）。親が1つのセレクタなら、ネストした結果は親とネストしたセレクタをつないだものと変わりません。親が詳細度の違うセレクタのリストだと、どのセレクタで一致した要素にも、いちばん高い詳細度が付きます。

```css title="🙅‍♂ Not Recommended: 詳細度の違うセレクタリストの中でネストする" issue="behavior"
/* 🙅‍♂ Not Recommended */
@scope (.scoped.action-bar) to (.scoped) {
  button,
  ._selected-count {
    background-color: var(--background--surface);

    &:enabled {
      background-color: var(--background--inverse);
    }
  }

  button {
    &[data-variant="danger"] {
      background-color: var(--background--surface);
      color: var(--foreground--danger);
    }
  }
}
```

このバーには、操作のボタンと、選択中の件数を示す `._selected-count` が並んでいます。2つは背景色を共有しているので、1つのセレクタリストにまとめています。`&:enabled` は `:is(button, ._selected-count):enabled` と同じ意味になり、詳細度は `0.2.0` です。`button` で一致した要素にも、`._selected-count` の `0.1.0` が使われます。後ろにある `button[data-variant="danger"]` は `0.1.1` なので負け、削除のボタンの文字は赤になりません。親が `button` だけなら、どちらも `0.1.1` になり、後ろに書いた赤が勝ちます。

```css title="🙆‍♂ Recommended: ネストするルールはセレクタごとに分ける" from="notation/nesting-split-list"
@scope (.scoped.action-bar) to (.scoped) {
  button,
  ._selected-count {
    background-color: var(--background--surface);
  }

  button {
    &:enabled {
      background-color: var(--background--inverse);
    }

    &[data-variant="danger"] {
      background-color: var(--background--surface);
      color: var(--foreground--danger);
    }
  }
}
```

宣言だけのセレクタリストは問題ありません。リストの各セレクタは、それぞれの詳細度で比べられるからです。問題になるのは、リストの中でセレクタをネストしたときだけです。条件付きのアットルールは詳細度を変えないので、リストの中にネストしてもかまいません。

## セレクタの深さとブロックの深さ

ネストの深さには、2つの数え方があります。セレクタの深さは、親のセレクタを何段引き継いでいるかで、詳細度とHTMLへの依存に関わります。ブロックの深さは、`@media` などのアットルールを含めて波括弧が何段重なっているかで、読みやすさに関わります。「2層まで」はセレクタの深さの規約です。

先ほどのホバーの例は、`a`、`&:any-link:hover`、`@media` と3段のブロックですが、セレクタは2層です。ホバーの状態と、ホバーのできる入力装置という2つの条件で1つの見た目が成り立っているので、まとめて読めるほうが分かりやすくなります。

ただし、ブロックが深くなるほど、どの条件の組み合わせで宣言が適用されるのかを読み取りにくくなります。状態の中に `@media` があり、その中にさらに `@supports` や `@container` が重なるなら、条件を `and` でまとめるか、ルールを分けます。条件ごとの値をローカルのカスタムプロパティに入れ、宣言の側では `var()` で受け取る書き方もあります。条件の判定と、値を使う宣言が分かれるので、ブロックを重ねずに済みます。

## 宣言とネストしたルールの順番

ルールの中では、宣言をネストしたルールより前に書きます（「[9-7 プロパティの並び順](/notation/property-order/)」のルール `block-content-order`）。CSSの文法では、ネストしたルールの後ろに宣言を書くこともできます。この宣言は、その位置に置かれた別のルール（`CSSNestedDeclarations`）として扱われ、書いた順番がカスケードに影響します。

```css title="🙅‍♂ Not Recommended: ネストしたルールの後ろに宣言を足す" issue="behavior"
/* 🙅‍♂ Not Recommended */
._links {
  display: none;

  @media (width >= calc(640 / 16 * 1rem)) {
    display: block flex;
  }

  display: block grid;
}
```

この例は、ルールの末尾へ `display: block grid` を後から足したものです。末尾の宣言は `@media` より後ろにあるものとして扱われるので、画面の幅を問わず `grid` が使われ、`@media` の中の `flex` は使われません。以前の実装では、後ろの宣言を先頭へ移して扱っていたので、ブラウザによって結果の違う時期がありました。{/* 要確認: 出典なし */}

本書のStylelintの設定では、`order/order` がこの並びを報告し、自動修正で宣言を先頭へ移します。移した後は、広い画面で `flex` が勝つので、自動修正だけで表示が変わります。自動修正で結果が変わらないように、宣言は初めから前に書きます。

## ネストする前に確かめること

ネストするかどうかは、次の順に確かめます。1つ目から3つ目のどれにも当てはまらないなら、ネストせず、同じ階層に並べます。

1. ネストするのは、親の要素自身の状態、または擬似要素か。
2. 直下の子へのネストなら、書くのは親のレイアウトで意味が決まる宣言だけか。
3. 条件付きのアットルールは、親の要素かその状態だけを変えるか。
4. 子要素が自分の状態やネストを持っていないか。持っているなら、子のルールにする。
5. 親が詳細度の違うセレクタリストではないか。
6. ネストを展開したセレクタを、1文で説明できるか。ラッパーを1つ足しても一致し続けるか。

レビューでは、問題の深刻さで指摘を分けます（「[19-2 レビューの進め方](/operations/review/)」）。セレクタリストの中のネストで上書きできないなら、不具合なので `MUST` です。子自身の見た目を親のネストに書いているだけで、今は正しく表示されているなら、本書の規約を採用したプロジェクトでは `MUST`、そうでなければ `IMO` として伝えます。直下の子の `& >` がマークアップの都合なのか意図した制約なのかがコードから読み取れないときは、`Q` で尋ねます。

```text title="レビューの指摘の例"
[MUST] `button, ._selected-count` の中の `&:enabled` は、詳細度が 0.2.0 になり、後ろの `button[data-variant="danger"]`（0.1.1）に勝ってしまいます。削除のボタンの文字が赤くなりません。`&:enabled` は `button` のルールに移してください（`no-nesting-under-selector-list`）。
```

ネストの深さ、詳細度、宣言の順番はツールで検査できますが、ネストしたルールの持ち主が正しいかどうかは、ツールでは判断できません。本書の設定で機械的に検査しているのは、`&` で始まるかどうかと、条件付きのアットルールの位置と、ルールの中の並び順です。この節の判断は、レビューで確かめます。
