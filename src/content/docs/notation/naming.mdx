クラス名は5種類に分け、先頭の記号と名前の種類で見分けます。コンポーネントのルートは `class="scoped <名前>"`、コンポーネントの子要素は `._main-link` のように `_` で始め、ユーティリティは `.-visually-hidden` のように `-` で始めます。`.cluster` のようなコンポジション（配置のパターン）と、`.section-heading` のようなパターン（静的な見た目の断片）には、接頭辞を付けません。コンポジションには配置の名前を、パターンには役割の名前を付けて区別します。

どの種類でも、名前は見た目ではなく役割で付けます。`container` や `button` のように、HTMLやCSSで意味が決まっている語は、別の意味で使いません。また、`@keyframes` の名前やグリッドのエリア名のように、自分で付けて値として使う名前は `--` で始めます。

カスタムプロパティの名前の付け方は、第10章の「[10-5 公開プロパティと内部プロパティ](/components/custom-properties/)」で扱います。`inner` と `container`、`gutter` と `gap` のように、名前の中に入れる語の意味と使い分けは、「[9-3 名前に使う語](/notation/terminology/)」でまとめています。BEMからの書き直しと、バリエーションを `data-variant` 属性で表す書き方は、「[9-2 BEMからの書き直しとバリエーション](/notation/variants/)」で扱います。

## ページ全体で共有される名前の問題

CSSのクラス名は、ページ全体で共有される1つの名前空間に属します。別々のコンポーネントで同じ `.title` という名前を使うと、片方のために書いたスタイルがもう片方にも当たります。この衝突を避けるために広く使われてきたのが、BEMのように、コンポーネントの名前を子要素の名前の先頭に付ける方法です。

```css title="🙅‍♂ Not Recommended: 名前の衝突を、コンポーネント名を繰り返す規則で避ける" issue="convention"
/* 🙅‍♂ Not Recommended */
.media-card__image {
  aspect-ratio: 16 / 9;
}

.media-card__title {
  font-size: calc(18 / 16 * 1rem);
}
```

この書き方で衝突は防げますが、代わりに名前が長くなります。子要素の名前に繰り返し現れる `media-card` は、衝突を避けるためだけの情報です。HTMLの `class` 属性も長くなり、どれがどの要素の名前なのかを読み取りにくくなります。

この方法は、全員が名前の規則を守っている間だけ衝突を防げます。誰かが `media-card` を付け忘れた `.title` を書けば、その名前はページ全体で衝突します。BEMはバリエーションを修飾子のクラスで表すので、詳細度が積み上がるという問題も抱えます。BEMの名前を本書の命名に書き直す手順と、修飾子の代わりにバリエーションを属性で表す書き方は、「[9-2 BEMからの書き直しとバリエーション](/notation/variants/)」で説明します。

## 5種類のクラス名

本書では、衝突を名前で避けるのではなく、`@scope` でスタイルの届く範囲を閉じ込めて防ぎます。範囲が閉じていれば、子要素の名前は `._main-link` のように短くてかまいません。そのうえで、クラス名を次の5種類に分け、先頭の記号と名前の種類で見分けられるようにします。

| 種類 | 書き方 | 例 |
|---|---|---|
| コンポーネントのルート | `scoped <名前>` | `scoped media-card` |
| コンポーネントの子要素 | `_` で始める | `._main-link`、`._nav-links` |
| ユーティリティ | `-` で始め、段階や種類は `--` で続ける | `.-visually-hidden`、`.-fluid-text--md` |
| コンポジション | 接頭辞を付けず、配置の名前にする | `.cluster`、`.switcher` |
| パターン | 接頭辞を付けず、役割の名前にする | `.section-heading`、`.icon` |

ルートの `scoped` は、そこからコンポーネントが始まるという目印です。`@scope (.scoped.media-card) to (.scoped)` と書くと、スタイルは `media-card` のルートから、内側にある次の `scoped` の要素（別のコンポーネントのルート）の手前までに届きます。`@scope` の仕組みは第4章の「[4-4 @scopeでスタイルを閉じ込める](/cascade/scope/)」で、下限を具体的な名前ではなく `.scoped` にする理由は「[9-4 @scopeとネストの使い分け](/notation/scope-and-nesting/)」で説明します。

`scoped` の後ろに続く名前は、kebab-caseにします。CSSのファイル名やPHPのテンプレートのファイル名もkebab-caseなので、ルートの名前とファイル名をそのまま対応させられます。`media-card` のルートのスタイルを `media-card.css` に書いておけば、HTMLで見つけた名前からコンポーネントのファイルをたどれます。ページ固有のスタイルは、`scoped page-about` のように `page-` を付けたルートにまとめます（「[9-4 @scopeとネストの使い分け](/notation/scope-and-nesting/)」のルール `page-scope-root`）。

子要素の `_` は、「このコンポーネントの中だけで意味を持つ名前」という印です。内部用のカスタムプロパティを `--_` で始めるのと同じ考え方で、外から触れるものではないことを示します。ただし、子要素のすべてにクラスを付けるわけではありません。スコープの中の要素は `ul` や `a` のようなタイプセレクタで選び、子要素のクラスは、同じ種類の要素を役割で区別するときと、意味を持たない `div` と `span` に役割を示すときだけ付けます。そのときは、`._main-link` と `._sub-link` のように、役割と要素の役割の語を組み合わせて名付けます。`._list` や `._link` のように要素の種類を言い換えただけの名前は付けません（「[10-2 コンポーネントの境界を守る](/components/boundaries/)」）。

ユーティリティの `-` は、どのコンポーネントからでも使える単機能のクラスであることを示します。`.-fluid-text--md` のように、段階や種類は `--` で続けます。コンポジションは、`.cluster`（折り返して並べる）や `.switcher`（幅に応じて横並びと縦積みを切り替える）のように、配置のパターンの名前をそのまま使います。パターンは、`.section-heading`（セクションの見出し）や `.icon`（文字に添えるアイコン）のように、繰り返し使う静的な見た目の断片に付けるクラスです。

コンポジションとパターンは、どちらも接頭辞を付けないので、記号では見分けられません。そこで、名前の種類で区別します。コンポジションは `stack`、`cluster`、`switcher`、`sidebar` のように、子をどう並べるかを表す配置の名前にします。パターンは `section-heading` や `icon` のように、その要素がページの中で何であるかを表す役割の名前にします。`class="cluster"` は子の並び方を、`class="section-heading"` は要素自身の見た目を決めるクラスだと、名前から読み取れます。何をユーティリティ、コンポジション、パターンにするかは、第10章の「[10-3 コンポジションとユーティリティ](/components/compositions-and-utilities/)」で扱います。

```html title="🙆‍♂ Recommended: 記号と名前の種類で、ルート、子要素、ユーティリティを見分ける"
<section class="scoped news-section">
  <h2 class="section-heading">お知らせ</h2>
  <p class="_lead">店舗からのお知らせです。</p>
  <ul class="stack">
    <li>
      <article class="scoped news-card">
        <h3>営業時間の変更について</h3>
      </article>
    </li>
  </ul>
  <p class="_note | -text-center">掲載から1年が過ぎたお知らせは削除します。</p>
</section>
```

このHTMLは、`class` 属性を見るだけで読み解けます。`_lead` と `_note` は `news-section` の子要素、`-text-center` はユーティリティ、`stack` はコンポジション、`section-heading` はパターンです。`stack` と `section-heading` はどちらも接頭辞がありませんが、配置の名前と役割の名前なので取り違えません。2つの `p` は役割が違うので子要素のクラスで区別し、1つしかない `h2` と `ul` には子要素のクラスを付けていません。`scoped news-card` から先は別のコンポーネントなので、`news-section` のスタイルは届きません。`news-card` の中に `news-section` と同じ名前の子要素や同じ種類の要素があっても衝突しません。

## `class` 属性の中で種類ごとに区切る

1つの要素に種類の違うクラスを付けるときは、種類ごとにまとめて `|` で区切ります。並べる順番は、コンポーネントのルート、子要素、コンポジション、パターン、ユーティリティです。種類が1つだけなら、`|` は書きません。

```html title="🙆‍♂ Recommended: 種類ごとにまとめて、| で区切る"
<section class="scoped news-section | stack">
  <h2 class="section-heading">お知らせ</h2>
  <div class="_body | stack">
    <p class="_lead | -fluid-text">店舗からのお知らせです。</p>
    <ul class="cluster">
      <li><a href="/tags/notice/">お知らせ</a></li>
      <li><a href="/tags/event/">イベント</a></li>
    </ul>
    <p class="_note | -text-center">掲載から1年が過ぎたお知らせは削除します。</p>
  </div>
</section>
```

`|` は、クラスの種類の境目を示すための文字で、スタイルは持ちません。区切りがあれば、`_body | stack` の前半がこの要素の正体（`news-section` の中の本文の区画）で、後半が外から重ねた配置だと、位置で読み取れます。記号で種類を見分けられるクラスでも、3つ、4つと並ぶと、どこまでが要素の正体で、どこからが重ねたものなのかを1つずつ確かめることになります。

順番は、要素の正体に近いものから並べます。ルートと子要素のクラスは、その要素がどのコンポーネントの何であるかを決めます。コンポジションは子の並べ方を、パターンは重ねる見た目の断片を、ユーティリティは例外的な調整を受け持ちます。後ろのクラスほど、外しても要素の正体は変わりません。並びが決まっていれば、レビューでは末尾を見るだけで、ユーティリティが増えていないかを確かめられます。AIが書いたHTMLで並びが崩れていれば、それにも気付けます。

ルートと子要素のクラスが同じ `class` 属性に並ぶことはありません。親のコンポーネントの中に子のコンポーネントを置くときは、子のルートに親の子要素のクラスを付けず、親の子要素の要素で包むからです（「[10-2 コンポーネントの境界を守る](/components/boundaries/)」のルール `parent-owns-child-placement`）。CMSが出力するブロックのクラス（`wp-block-group` など）は、ルートのグループの先頭に置きます（「[19-5 CMSのWYSIWYG本文にスタイルを当てる](/operations/wysiwyg/)」）。

## 階層を名前に映さない

HTMLの入れ子が深くなっても、子要素のクラス名は平らなままにします。コンポーネントの直下にある要素も、その下の下にある要素も、同じ `._kebab` の形で付け、親の名前を連結して階層を表しません。孫にあたる要素には、その要素の役割を名前にします。

```html title="🙅‍♂ Not Recommended: 階層を名前につなげる" issue="convention"
<!-- 🙅‍♂ Not Recommended -->
<article class="scoped news-card">
  <ul class="_tags">
    <li class="_tags-item">
      <a class="_tags-item-link" href="/tags/notice/">お知らせ</a>
    </li>
  </ul>
</article>
```

```html title="🙆‍♂ Recommended: 孫にあたる要素にも、役割の名前を平らに付ける"
<article class="scoped news-card">
  <ul class="_tags">
    <li class="_tag">
      <a class="_tag-link" href="/tags/notice/">お知らせ</a>
    </li>
  </ul>
</article>
```

階層を名前に写すと、名前が要素の位置を表してしまいます。`<li>` を別の要素に替えたり、リンクを1つ外側に出したりしたときに、HTMLの構造に合わせてクラス名も、CSSのセレクタも変えなければなりません。役割の名前なら、構造が変わっても名前は変わりません。セレクタも、`._tag-link` のように1つのクラスで選べるので、詳細度は上がりません。なお、この例では名前の付け方を示すために `ul` と `li` にもクラスを付けています。カードの中にほかのリストがなければ、クラスを付けずにタイプセレクタで選びます。

## 見た目の名前と役割の名前

名前は、見た目ではなく役割で付けます。`._red-text` や `._big-title` のような見た目の名前は、デザインが変わった時点で実態とずれます。赤かった文字が青になれば、`._red-text` という名前は実態と食い違います。`._notice` や `._heading` のように役割で名前を付けておけば、見た目を変えても名前を変えずに済みます。

CSSでは、デザインが変わる前から、見た目の名前が実態とずれることもあります。同じ要素が、画面やコンテナの幅、文字の大きさの設定によって姿を変えるからです。`._two-columns` は狭い画面では1列になり、`._large-card` は狭い画面ではほかのカードと同じ大きさになります。名前が表すのは広い画面で書いたときの姿だけで、狭い画面で見た人には、実態と違う名前に見えます。{/* 要確認: 出典なし */}

ただし、使う側が選んだ値を表す名前は、見た目の語でも実態とずれません。`data-size="small"` は、幅にかかわらず小さい版を選んだことを表すからです（「[9-2 BEMからの書き直しとバリエーション](/notation/variants/)」）。避けるのは、幅や設定によって変わる結果を名前にすることです。

```html title="🙅‍♂ Not Recommended: 見た目や汎用の語で名前を付ける" issue="convention"
<!-- 🙅‍♂ Not Recommended -->
<div class="scoped contact-section">
  <div class="_wrapper">
    <p class="_red-text">受付は平日のみです。</p>
    <a class="_button" href="/contact/">お問い合わせ</a>
  </div>
</div>
```

同じ理由で、HTMLやCSSで意味が決まっている語を、別の意味で使いません。上の例の `<a>` は見た目がボタンでも、役割はページを移動するリンクなので、名前には `_contact-link` のように `link` の語を使います。`button` は `<button>` 要素のための名前です。`container` はCSSの `container` プロパティを持つ要素に、`columns` は段組み（マルチカラム）のレイアウトに使う語なので、ただの入れ物やFlexboxの横並びには使いません。`.container` のクラスについては、「[13-3 コンテナサイズクエリ](/responsive/container-size-queries/)」でも説明しています。

`wrapper`、`block`、`module`、`widget` のような総称も避けます。何のための要素なのかが名前から分からず、責務の境界もあいまいになるからです。内容の幅を制限して中央に寄せる要素は `_section-inner`、外側との余白や配置を調整する要素は `_card-outer` のように、責務を表す名前を付けます。`_inner` だけでは何の内側なのかが分からないので、`inner`、`outer`、`container` には必ず「何の」を併記します（「[9-3 名前に使う語](/notation/terminology/)」）。

総称の名前は、要素を置いた理由から名付けたときに生まれます。「中身を何かで包む必要がある」から名付けると `wrapper` になり、「何を、何のために包むのか」から名付けると `_section-inner` になります。名前に書くのは、要素が必要になった事情ではなく、その要素が受け持つ責務です。{/* 要確認: 出典なし */}

```html title="🙆‍♂ Recommended: 役割と責務で名前を付ける"
<div class="scoped contact-section">
  <div class="_section-inner">
    <p class="_notice">受付は平日のみです。</p>
    <a class="_contact-link" href="/contact/">お問い合わせ</a>
  </div>
</div>
```

この例では、名前の付け方を示すために `p` と `a` にもクラスを付けています。実際のコンポーネントで、ほかに同じ種類の要素がなければ、クラスを付けずにタイプセレクタで選びます。

見た目の名前を付けてよいのは、ユーティリティだけです。ユーティリティは1つのことしかしないので、`.-text-center` のように、その効果をそのまま名前にするのがいちばん分かりやすいからです。コンポーネントや、繰り返し使う静的な部品（パターン）には、`section-heading` や `status-badge` のように役割の名前を付けます。`big-title` や `blue-link` のような名前は付けません。

名前に迷ったときは、そのコンポーネントや要素が何なのかを、日本語で1文に書いてみます。その文に出てくる特徴的な語が、名前の候補になります。「商品の画像と価格と購入ボタンをまとめたもの」なら `product-detail`、「記事の一覧」なら `article-list` です。`text-box` や `center-box` のように、見た目や配置だけを表す名前は、何のための部品なのかが分からないので避けます。

その1文で「〜して、〜して」と責務がいくつも並ぶなら、1つの要素が責務を抱えすぎていないかを確かめます。「内容の幅を制限して中央に寄せ、背景を塗り、上下に余白を取る」要素なら、幅の制限と中央寄せは `_section-inner` が、背景と上下の余白は区画のルートが受け持つように分けられます。責務が1つにまとまれば、名前も短い語で言い表せます。責務を別のクラスとして切り出し、ほかの場所でも使うかどうかは、「[10-3 コンポジションとユーティリティ](/components/compositions-and-utilities/)」で扱います。{/* 要確認: 出典なし */}

名前は、`._btn` や `._ttl` のように省略せず、`._card-1` のような番号も付けません。省略してよい略語の範囲と、番号の代わりに使う書き方は、「[9-3 名前に使う語](/notation/terminology/)」で説明しています。

## 自分で付ける名前の `--`

`@keyframes` の名前、グリッドの線とエリアの名前、アンカーの名前、スタイルクエリで比べる値のように、自分で付けて値として使う名前は `--` で始めます。コンテナの名前も同じ規則です。コンポーネントのルートをコンテナにするときは、ルートのクラス `scoped` と同じ語の `--scoped` を名前にします。`._body` のような子要素をコンテナにするときは、クラス名から下線を除いた `--body` にします（「[13-3 コンテナサイズクエリ](/responsive/container-size-queries/)」）。

```css title="🙆‍♂ Recommended: 自分で付ける名前を -- で始める"
@keyframes --fade-in {
  from {
    opacity: 0;
  }
}

@scope (.scoped.media-card) to (.scoped) {
  :scope {
    display: block grid;
    reading-flow: grid-rows;
    grid-template-areas:
      "--image"
      "--body";

    & > ._image {
      grid-area: --image;
    }

    & > ._body {
      grid-area: --body;
    }
  }
}
```

理由は4つあります。1つ目は、近年のCSSで、自分で付ける名前に `--` を求めるプロパティが増えていることです。`anchor-name` やスクロール連動アニメーションのタイムラインの名前は、`--` で始めないと無効になります。2つ目は、すべての名前を `--` で始めておけば、「このプロパティでは `--` が必要か」を個別に覚えなくて済むことです。

3つ目は、将来CSSに新しいキーワードが追加されても、自分で付けた名前と衝突しにくいことです。CSSのキーワードは `--` で始まらないので、`--` を付けておけば見分けられます。4つ目は、コードを読んだときに、自分で付けた名前だとすぐに分かることです。`fadeIn` や `image` のような名前は、CSSのキーワードと見た目の区別がつきません。

```css title="🙅‍♂ Not Recommended: キーワードと見分けにくい名前" issue="convention"
/* 🙅‍♂ Not Recommended */
@keyframes fadeIn {
  from {
    opacity: 0;
  }
}

._layout {
  grid-template-areas:
    "image"
    "body";
}
```

グリッドのエリアの名前は、そのエリアに置く子要素のクラス名とそろえます。`._image` を置くエリアは `--image` です。こうしておくと、`grid-template-areas` の図と、各要素の `grid-area` の対応をすぐに読み取れます。グリッドのエリアの使い方は、「[7-8 Gridの基礎](/layout/grid-basics/)」で扱います。

`--` を付けるのは、値として書く名前だけです。`@layer` のレイヤー名のように、プロパティの値として使わない名前には付けません。`@keyframes` の名前をコンポーネントごとにどう分けるかといった設計は、「[18-6 @keyframesを設計する](/motion/keyframes/)」で説明します。本書のStylelintの設定では、`@keyframes` の名前を `keyframes-name-pattern` で検証しています。

## 補足と注意点

この命名を採用すると、クラス名を読む人は5種類の見分け方を覚えることになります。`scoped`、`_`、`-` の3つは記号で見分けられますが、記号のないコンポジションとパターンは、配置の名前か役割の名前かで判断するので、慣れるまで迷いやすいところです。自分で付けて値として使う名前を `--` で始める約束も、BEMやFLOCSSにはありません。

子要素の名前は短く、コンポーネントをまたいで重なってよいので、`._title` をプロジェクト全体で検索すると、ほかのコンポーネントの同じ名前の要素も見つかります。子要素のスタイルを探すときは、HTMLでその要素を囲む最も近い `scoped` のルートの名前を見て、`media-card.css` のように同じ名前のファイルを開き、その中で検索します。BEMの名前なら1回の検索で済んだ作業が、2段階になります。

短い子要素の名前が安全なのは、`@scope` の範囲の中に書くときだけです。`@scope` の外に書くCSSで `._title` のような名前を使うと、ページ全体で衝突します。そのため、`@scope` を前提にできない環境では、名前が長くなっても名前で衝突を避けるBEMのほうが確実です。たとえば、対象のブラウザが `@scope` に対応していない版を含む場合です（「[4-4 @scopeでスタイルを閉じ込める](/cascade/scope/)」の「対応状況と注意点」）。CSSを変換・結合するツールが `@scope` を扱えないなど、CSSを読み込む仕組みに制約がある場合も同じです。既存のBEMの資産が大きいサイトや、チームがすでにBEMで合意しているサイトも、BEMを保つ条件に当たります。名前だけを本書の形へ変えても衝突の防ぎ方は変わらず、2つの命名が混ざって、読む人が両方の規則を見分けることになるからです。{/* 要確認: 出典なし */}

本書がBEMを採らないのは、本書の対象のブラウザがすべて `@scope` に対応していて、名前の規則を人が守らなくても、範囲で衝突を防げるからです。上の条件のどれかに当たるなら、BEMの名前のまま、部品の中を外から選ばないことと、外から変える値を公開プロパティで受け取ることだけを取り入れれば足ります（「[19-6 既存のサイトに段階的に導入する](/operations/adoption/)」）。修飾子による詳細度の積み上がりも、修飾子のクラスで内部プロパティだけを切り替える形にすれば避けられます（「[9-2 BEMからの書き直しとバリエーション](/notation/variants/)」）。名前を本書の形へ変えるのは、`@scope` へ移るときに合わせます。

チームに導入するときは、`@scope` を書くのに欠かせないルートの `scoped <名前>` と子要素の `_` から始めます。ユーティリティの `-` と、コンポジションとパターンの区別は、それぞれのクラスを作るときに足せます。値として使う名前の `--` は、Stylelintの `keyframes-name-pattern` のように機械で検証できるものから守らせると、レビューで指摘する手間が減ります。{/* 要確認: 出典なし */}

`class` 属性を `|` で区切る約束は、HTMLを書く人とテンプレートを組み立てるコードの手間を増やします。`|` はクラスの1つとして `classList` にも入るので、`className` を文字列のまま比べるJavaScriptがあれば、書き直しが要ります。StylelintはHTMLを読まないので、並び順は本書の `pnpm lint:classes` のような別のスクリプトで確かめます。区切りがなくても5種類は記号と名前で見分けられます。この約束で得るものが大きいのは、1つの要素に3つ以上のクラスを並べることの多いプロジェクトです。

区切りを使わない代案は、並べる順番だけを決めておく方法です。`_tags cluster` のように、ルート、子要素、コンポジション、パターン、ユーティリティの順にそろえれば、記号のないコンポジションとパターンも、位置からある程度は見分けられます。`classList` やテンプレートの処理を変えずに済むのが利点です。区切りを使うと加わるのは、どこまでが要素の正体かという境目が、クラスの名前を知らなくても見えることです。1つの要素に付けるクラスが2つ程度に収まるプロジェクトや、`className` を文字列のまま扱う処理を書き直せないプロジェクトでは、順番を決めるだけにとどめます。{/* 要確認: 著者の判断。区切りを使わない代案を認める範囲 */}
