同じ要素の同じプロパティに複数の値が指定されたとき、どの値を使うかは「カスケード」という手順で決まります。カスケードは、レイヤー、詳細度、スコープの近さ、書いた順番などを決まった順に比べ、最初に差がついたところで勝ち負けを決めます。

本書では、この仕組みのうちレイヤーと書いた順番で優先順位を設計し、詳細度はできるだけ低く一定に保ちます。`!important` は、詳細度の競争に勝つためには使いません。

この節のコード例は、カスケードの仕組みだけを見せるために、`.cta-link` のような素のクラスで書いています。本書の規約で決めているレイヤーの構成と `@scope` の書き方は、「[4-3 カスケードレイヤーで順位を決める](/cascade/layers/)」と「[4-4 @scopeでスタイルを閉じ込める](/cascade/scope/)」で、仕組みを説明したあとに示します。

## 詳細度で上書きを重ねると何が起きるか

ベーススタイルに、リンクの色を次のように書いたとします。一見すると問題のない指定ですが、この書き方が後の上書きを難しくします。

```css title="🙅‍♂ Not Recommended: 詳細度の高いベーススタイルを、さらに高い詳細度で上書きする" issue="convention"
/* 🙅‍♂ Not Recommended */
a:link,
a:visited {
  color: var(--foreground--accent);
}

/* 0.1.0 なので、上の 0.1.1 に負ける */
.cta-link {
  color: var(--foreground--inverse);
}

/* 勝つために祖先のクラスを足す */
.site-header .cta-link {
  color: var(--foreground--inverse);
}

/* それでも負ける場面が出たので !important を付ける */
.site-header .cta-link[data-size="small"] {
  color: var(--foreground--inverse) !important;
}
```

`a:link` の詳細度は、タイプセレクタ1つと擬似クラス1つで「0.1.1」になります。ボタンの形をしたリンクのクラス `.cta-link` は「0.1.0」なので、その文字色を変えられません。そこで祖先のクラスを足して「0.2.0」にし、さらに負ける場面が出ると `!important` を付ける、という流れが生まれます。

こうした上書きは、1回ごとには小さな対応です。しかし、次に誰かが上書きするときには、さらに高い詳細度か `!important` が必要になります。上書きする側は、上書きされる側より強くなければならないので、詳細度の競争は一方向にしか進まず、最後は `!important` 同士の競争になります。私は、この詳細度の問題こそがCSSを破綻させるいちばんの原因だと考えています。

問題の出発点は、優先順位を詳細度の高さで決めようとしたことです。カスケードには、詳細度より先に比べられる仕組みがあります。それを使えば、詳細度を上げなくても、意図した順番でスタイルを勝たせられます。

## カスケードが値を決める順番

カスケードは、次の順に宣言を比べます。上の段階で差がつけば、下の段階は比べません。

1. オリジンと重要度：ブラウザのデフォルトスタイル、ユーザーのスタイル、作者のスタイルの区別と、`!important` の有無
2. コンテキスト：Shadow DOMの内側と外側の区別
3. `style` 属性：要素に直接書いたスタイル
4. レイヤー：`@layer` の順番
5. 詳細度：セレクタの強さ
6. スコープの近さ：`@scope` のルートと要素との距離
7. 出現順：後に書いた宣言が勝つ

<Figure src="cascade/cascade-order" alt="カスケードが宣言を比べる7つの段階を、上から順に並べたフローチャート。比べる順は、上から、オリジンと重要度、コンテキスト、style属性、レイヤー、詳細度、スコープの近さ、出現順。各段階の右には、差がつけば勝者が決まってそこで終わることを示す枠がある。差がつかなければ、下向きの矢印で次の段階へ進む。最後の出現順では、後に書いた宣言が必ず勝つ。レイヤーと出現順の2つは、本書が優先順位の設計に使う段として色を付けて強調している。" />

レイヤーは、詳細度より先に比べられます。同じオリジンの、`!important` を付けていない宣言どうしでは、レイヤーが違えば、詳細度がどれほど高くても、後ろのレイヤーの宣言が勝ちます。`!important` を付けた宣言どうしでは、この順番が逆になります。詳細度は、同じレイヤーの中で初めて比べられる値です。

レイヤーに入れていないスタイルは、すべてのレイヤーより後ろにある「暗黙の最後のレイヤー」として扱われます。そのため、`!important` を付けていない宣言どうしでは、レイヤーの外のスタイルが常に勝ちます。この性質がCMSの環境で問題になる理由は、「[4-3 カスケードレイヤーで順位を決める](/cascade/layers/)」で説明します。

詳細度は、IDの数、クラス・属性・擬似クラスの数、タイプセレクタ・擬似要素の数という3つの数で表し、左の数から比べます。本書では、これを「0.1.1」のようにドットでつないで書きます。

```css
/* 詳細度（IDの数.クラスなどの数.タイプセレクタなどの数） */
p {}                      /* 0.0.1 */
.cta-link {}              /* 0.1.0 */
a:link {}                 /* 0.1.1 */
.site-header .cta-link {} /* 0.2.0 */
#main {}                  /* 1.0.0 */
:where(a:link) {}         /* 0.0.0 */
```

スコープの近さは、`@scope` とともに加わった比べ方です。詳細度が同じ宣言どうしでは、スコープのルートが対象の要素に近いほうが勝ちます。レイヤー、詳細度、スコープの近さのすべてで差がつかなかったときに、最後に書いた宣言が勝ちます。`@scope` の使い方は「[4-4 @scopeでスタイルを閉じ込める](/cascade/scope/)」で説明します。

`style` 属性は、レイヤーと詳細度より先に比べられるので、オリジンと重要度が同じ宣言どうしなら、セレクタで書いたどのルールにも勝ちます。`!important` を付けていない `style` 属性の宣言は、作者の `!important` を付けた宣言には負けます。本書では、`style` 属性をコンポーネントの公開カスタムプロパティに値を渡す用途に限って使います。この方法は、第10章「[10-5 公開プロパティと内部プロパティ](/components/custom-properties/)」で説明します。

## 優先順位はレイヤーと書く順番で決める

本書では、優先順位を次の方針で設計します。まず、スタイルの役割ごとにレイヤーを分け、「リセットよりベース、ベースよりコンポーネント、コンポーネントよりユーティリティが強い」という順番をレイヤーで決めます。同じレイヤーの中では詳細度をそろえ、書いた順番で勝ち負けが決まるようにします。

詳細度の目安は2つです。ベーススタイルは、`base` レイヤーに素のセレクタで書きます。後のレイヤーの指定は詳細度に関係なく勝つので、`a:any-link`（0.1.1）のままでも、コンポーネントのクラス1つで上書きできます。コンポーネントの中は、クラス1つ分（0.1.0）を基本にします。本書では、コンポーネントのスタイルを `@scope` の中に書くので、クラスを1つ書けばちょうど0.1.0になります（「[4-4 @scopeでスタイルを閉じ込める](/cascade/scope/)」）。セレクタの書き方は「[4-2 セレクタで詳細度を設計する](/cascade/selectors/)」で詳しく説明します。

リセットCSSのkiso.cssは、全称セレクタなどの一部を除き、セレクタを `:where()` で包んで詳細度を0にしています。レイヤーなしで読み込まれても上書きしやすくするためです。CMSと共存する場合のようにレイヤーを使えない環境では、ベーススタイルのセレクタも同じように `:where()` で包みます（[4-2 セレクタで詳細度を設計する](/cascade/selectors/)）{/* CMSの節を公開したらリンクする: /operations/cms/ */}。

```css title="🙆‍♂ Recommended: 順番はレイヤーで決め、詳細度は低くそろえる" from="cascade/layer-over-specificity"
@layer base {
  a {
    &:any-link {
      color: var(--foreground--accent);
    }
  }
}

@layer components {
  .cta-link {
    color: var(--foreground--inverse);
  }
}
```

このコードでは、ベースのリンクの色が0.1.1、`.cta-link` の色が0.1.0です。詳細度ではベースのリンクの色のほうが高くても、`components` レイヤーが `base` レイヤーより後ろにあるので、`.cta-link` の色が勝ちます。レイヤーで順番を決めておけば、上書きのために詳細度を上げる工夫は要りません。

次のデモでは、ボタンの形をしたリンクの文字が `.cta-link` の文字色になり、`base` レイヤーのリンクの青は使われません。

<Demo title="base の a:any-link（0.1.1）より、components の .cta-link（0.1.0）の色が勝つ" html={layerOverSpecificityHtml} css={layerOverSpecificityCss} frame={layerOverSpecificityFrame} widths={[]} />

なお、この節のほかのコード例では、説明に関係しない `@layer` の記述を省略しています。

## 継承されるプロパティとされないプロパティ

カスケードは、「要素に当てはまる宣言のうち、どれを使うか」を決める仕組みです。当てはまる宣言がひとつもないプロパティは、継承されるプロパティなら親の値を受け継ぎ、継承されないプロパティなら初期値になります。

継承されるのは、主に文字に関わるプロパティです。`color`、`font-family`、`font-size`、`line-height`、`letter-spacing` などがこれに当たります。一方で、`margin`、`padding`、`border`、`background-color`、`display` のように、ボックスやレイアウトに関わるプロパティは継承されません。カスタムプロパティは、`@property` で `inherits: false` を指定しない限り継承されます。継承した値を `var()` で参照したときに、どの時点で値が置き換わり、どの場合にフォールバックが使われるかは、「[4-6 カスタムプロパティの基礎](/cascade/custom-properties-basics/)」で説明します。

継承で受け継いだ値には、詳細度がありません。要素に直接当てはまる宣言がひとつでもあれば、詳細度0の `:where()` の指定であっても、継承した値より優先されます。親に色を指定したのに子の色が変わらないときは、子に当てはまる宣言がどこかにないかを確認します。

継承があるので、文字の色やサイズは `:root` やコンポーネントのルートでまとめて指定し、子要素では継承を使います。子要素ごとに同じ値を書き直すと、ルートの値を変えたときに直す場所が増えるからです。

<Demo title="継承するプロパティはルートでまとめて指定する" html={inheritRootHtml} css={inheritRootCss} widths={[]} />

この例では、カードの中の文章はすべてルートの色とサイズを受け継ぎ、見出しだけが違う値を持ちます。デモでは、段落と日付がルートの灰色の14pxで、見出しだけが濃い色の20pxで表示されます。本文の段落や日付にクラスを付けて、色を指定し直す必要はありません。

## 戻したい先をキーワードで選ぶ

指定した値を元に戻したいときは、具体的な値を書き直すより、どのプロパティにも使えるキーワードを使います。キーワードによって戻る先が違うので、意図に合うものを選びます。

- `initial`：プロパティの初期値に戻す
- `inherit`：親の値を受け継ぐ
- `unset`：継承されるプロパティなら `inherit`、継承されないプロパティなら `initial` として働く
- `revert`：サイトのCSSの指定を取り除いた値に戻す（ユーザーのスタイルがなければブラウザのデフォルトスタイル、ブラウザにも指定がなければ継承または初期値）
- `revert-layer`：ひとつ前までのレイヤーで決まる値に戻す

注意したいのは `initial` です。`display` の初期値は、要素の種類に関係なく `inline` です。`div` の `display` を `initial` にすると、インライン要素になってしまいます。ブラウザのデフォルトスタイル（`div` なら `block`）に戻したいなら、`revert` を使います。

リセットCSSで消したものを一部の場所だけ元に戻すときにも、`revert` を使います。kiso.cssはリストのマーカーを `list-style-type: ""` で消しているので、記事の本文のようにマーカーが必要な場所では、次のように戻します。

```css title="🙆‍♂ Recommended: リセットで消したマーカーと字下げを、ブラウザのデフォルトに戻す" from="cascade/revert-keywords"
@scope (.wysiwyg) {
  ul,
  ol {
    padding-inline-start: revert;
    list-style-type: revert;
  }
}
```

`.wysiwyg` は、CMSで入力する本文エリアに付けるクラスです（「[19-5 CMSのWYSIWYG本文にスタイルを当てる](/operations/wysiwyg/)」）。kiso.cssはリストの字下げも消しているので、マーカーを表示する場所がなくならないように、`padding-inline-start` も一緒に戻します。

ここで `list-style-type` に `revert-layer` を使うと、kiso.cssを入れた `reset` レイヤーの値（マーカーなし）に戻るので、マーカーは表示されません。どちらのキーワードも「元に戻す」ものですが、戻る先が違います。次のデモでは、2つのリストの違いは `list-style-type` のキーワードだけです。`revert` のリストには項目の先頭にマーカーが表示され、`revert-layer` のリストにはマーカーが表示されません。

<Demo title="revert はブラウザのデフォルトに、revert-layer は reset レイヤーの値に戻る" html={revertKeywordsHtml} css={revertKeywordsCss} widths={[]} />

これらのキーワードは、`all` プロパティと組み合わせると、`direction`、`unicode-bidi`、カスタムプロパティを除くすべてのプロパティをまとめて戻せます。このとき `all: unset` は使いません。`unset` は、継承されないプロパティを初期値に戻すので、`display` は `inline` になり、ブラウザのデフォルトスタイルのうち必要なもの（`<ul>` の余白や `<button>` のフォーカスリングなど）まで消えます。どのプロパティの初期値が何かを覚えていないと、何が起きるのかを予測できません。まとめて戻すなら、レイヤーを使うプロジェクトでは `all: revert-layer`、使わないプロジェクトでは `all: revert` を指定します。戻る先がひとつ前のレイヤーや（ユーザーのスタイルがなければ）ブラウザのデフォルトスタイルなので、要素が本来の表示を保ったまま、上書きだけが消えます。

```css title="🙆‍♂ Recommended: まとめて戻すときは、戻る先が分かるキーワードを使う"
.embed-content {
  all: revert-layer;
}
```

## `!important` を使ってよい場面

`!important` は、カスケードの最初の段階である「オリジンと重要度」の順位を変える指定です。`!important` が付いた宣言は、付いていない宣言に、レイヤーや詳細度に関係なく勝ちます。スタイルの宣言どうしで比べる限り、これを打ち消せるのは、同じように `!important` を付けた宣言だけです。例外は実行中のトランジションで、その値は `!important` を付けた宣言よりも優先されます（`@keyframes` のアニメーションは優先されません）。

さらに、`!important` を付けた宣言どうしでは、レイヤーの順番が逆になります。前のレイヤーの `!important` ほど強く、レイヤーの外の `!important` がいちばん弱くなります。前のレイヤーで `!important` を付けた指定は、後ろのレイヤーから上書きできません。

<Figure src="cascade/important-order" alt="レイヤーの強さの順番を、!importantなしの場合とありの場合で並べた比較図。左の列は!importantなしで、上ほど強く、上から順に、レイヤーの外、utilities、patterns、components、pages、compositions、vendors、base、reset、tokens。右の列は!importantありで、順番が逆になり、上から順に、tokens、reset、base、vendors、compositions、pages、components、patterns、utilities、レイヤーの外。レイヤーの外とresetは色を付けて強調し、2つの列で同じレイヤーを線で結んでいる。レイヤーの外は、!importantなしでは最も強く、ありでは最も弱い。resetは、なしでは下から2番目、ありでは上から2番目になる。下の注記は、!importantを付けた宣言は、付けていない宣言のすべてに勝つ、というもの。" />

本書では、詳細度や読み込み順の競争に勝つ目的で `!important` を使いません。どのような上書きにも負けてはいけない指定に限って使います。代表的なのは、kiso.cssの `hidden` 属性の指定です。

```css title="🙆‍♂ Recommended: !important は、hidden 属性のように必ず反映する状態に限る"
[hidden]:not([hidden="until-found" i]) {
  display: none !important;
}
```

`hidden` 属性を付けた要素は、どのコンポーネントが `display` を指定していても隠れなければなりません。kiso.cssを `reset` レイヤーに入れると、この `!important` は、後ろにある `base` 以降のどのレイヤーの `!important` よりも強くなります。後ろのレイヤーで `display: block !important` と書いても、要素は隠れたままです。kiso.cssは、閉じている `<dialog>` と開いていないポップオーバーにも、同じ理由で `!important` を使っています。

このほかに `!important` を使う場面は3つあります。強制カラーモードでSVGの色をシステムカラーに固定する場合、CMSが要素に直接出力する `style` 属性を打ち消す場合、レイヤーを使えない既存のサイトで壊れた既存のCSSから新しいコンポーネントを切り離す場合です。どれも、セレクタでは勝てない相手を上書きするための例外です。1つ目は「[15-5 強制カラーモードとコントラスト](/color-media/forced-colors/)」で、3つ目は「[4-3 カスケードレイヤーで順位を決める](/cascade/layers/)」で扱います。2つ目の場合は、打ち消す対象と理由をコメントに残し、後から消してよいかを判断できるようにします。

以前の私は、ユーティリティクラスだけは `!important` を使ってよいと考えていました。いまは、ユーティリティクラスにも `!important` を付けません。`utilities` を最後のレイヤーにすれば、`!important` なしでコンポーネントのスタイルに勝つからです。

AIにスタイルの修正を頼むと、上書きが効かない原因を調べずに `!important` を足したコードが返ってくることがあります。`!important` が含まれていたら、詳細度やレイヤーの順番で解決できないかを先に確認してください。
