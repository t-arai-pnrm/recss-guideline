この章では、同じ要素の同じプロパティに複数の値が指定されたとき、どの値が使われるかを扱います。スタイルの優先順位は、詳細度の高さで競わせず、「どのレイヤーに書くか」と「どの範囲に適用するか」で先に決めます。詳細度そのものは、できるだけ低く一定に保ちます。

私は2020年に、`!important` を使わずにスタイルを上書きする技として、同じクラスを連結して詳細度を上げる書き方を紹介していました。当時は、詳細度を調整する手段がセレクタしかなかったからです。いまはカスケードレイヤー、`:where()`、`@scope` がすべての主要なブラウザで使えるので、上書きの技そのものが要らない設計にできます。この章では、上書きで困ってから対処するのではなく、困らない順番と範囲を最初に決めておく設計を扱います。

ただし、新しい仕組みにも向き不向きがあります。私自身、2024年のブログではITCSSにならった7つのレイヤーを使い、2025年に公開したリセットCSSのkiso.cssでは「レイヤーに頼らなくても上書きしやすい」ことを優先しました。現在、Astroで作るサイトのテンプレートでは9つのレイヤーを使っていますが、CMSの案件ではレイヤーをやめています。こうした経験から、レイヤーを使う基準と使わない基準の両方を示します。

## この章で判断できるようになること

この章を読むと、宣言が適用されないときに、レイヤー、詳細度、スコープの近接度、出現順のどれで負けているかを切り分けられるようになります。上書きが要るときは、詳細度を上げる代わりに、書くレイヤーを変えるか、`@scope` で範囲を絞るかを選べます。CMSのようにレイヤーに入っていない外部のCSSと共存する環境では、`@layer` を使わないと判断でき、`!important` を使ってよい場面かどうかも見分けられます。`var()` を使った宣言が効かないときは、参照先が未定義なのか、置き換えた値がプロパティに合わないのかを見分けられます。

## 初めて読むとき

この章は、本書のほかのすべての章の前提になるので、すべての節を読んでください。

## 最初に押さえるルール

次のルールを先に押さえ、ほかのルールは、該当する場面で付録A「[ルール一覧](/appendix/rules/)」から引けば足ります。

- [`layer-order-declaration`](/cascade/layers/#rule-layer-order-declaration)：レイヤーの順序は、読み込むCSSの先頭で、9つのレイヤーを並べた `@layer` 文で宣言します。
- [`no-unlayered-styles`](/cascade/layers/#rule-no-unlayered-styles)：レイヤーを使うプロジェクトでは、`@layer` の外にスタイルを書きません。
- [`no-important-for-specificity`](/cascade/cascade-basics/#rule-no-important-for-specificity)：`!important` は、詳細度や読み込み順の競争で勝つ目的には使いません。
- [`no-specificity-hacks`](/cascade/selectors/#rule-no-specificity-hacks)：上書きのためだけに詳細度を上げるセレクタ（`.a.a` や、祖先を足したセレクタなど）を書きません。
- [`scope-with-donut`](/cascade/scope/#rule-scope-with-donut)：コンポーネントのスタイルは `@scope (.scoped.<名前>) to (.scoped)` の中に書きます。

## 判断の問い

この章の内容で答えられる問いを1つ置きます。答えを開く前に、どの宣言が勝つかを予想してください。

次のCSSで、`<article class="card"><h2 class="title | -text-muted">…</h2></article>` の見出しは何色になりますか。

```css
@layer base, components, utilities;

@layer components {
  .card .title {
    color: var(--foreground--accent);
  }
}

@layer utilities {
  .-text-muted {
    color: var(--foreground--muted);
  }
}

h2 {
  color: var(--foreground--danger);
}
```

最後の `h2` の色（`--foreground--danger`）になります。`h2` のルールはどのレイヤーにも入っていないので、すべてのレイヤーより後ろの「暗黙の最後のレイヤー」として扱われます。`!important` のない宣言どうしでは、レイヤーの順番が詳細度より先に比べられます。そのため、詳細度0.0.1の `h2` が、0.2.0の `.card .title` にも、`utilities` の `.-text-muted` にも勝ちます（「[4-3 カスケードレイヤーで順位を決める](/cascade/layers/)」）。

`h2` のルールを `@layer base { … }` に入れると、答えは `--foreground--muted` に変わります。3つのレイヤーのうち最も後ろにある `utilities` が勝つからです。ユーティリティクラスが効かないときに、まずレイヤーの書き忘れを疑うのは、このためです。

</details>

## 手を動かす課題

判断の問いでは、宣言の勝ち負けを説明できるかを確かめました。ここでは、「[最小の構成で始める](/introduction/quick-start/)」で作ったお知らせのカードに、実際に負ける宣言を作り、原因を突き止めて直します。

既存のサイトから引き継いだ `css/legacy.css` を、エントリーポイントの `style.css` の最後に `@import url("./legacy.css");` を書いて読み込んだ場面で考えます。`legacy.css` には、`h2 { color: var(--foreground--muted); }` の1つのルールだけが書かれています。読み込むと、カードの見出しが濃い文字色から灰色に変わります。`news-card.css` と `legacy.css` の中身は変えずに、見出しを濃い文字色に戻してください。`!important` や、詳細度を上げるセレクタは使いません。

合格の条件は2つです。カードの見出しが濃い文字色に戻ることと、開発者ツールのスタイルのパネルで、直す前に勝っていた宣言と、それが勝った理由（レイヤー、詳細度、出現順のどれか）を言えることです。

`legacy.css` をレイヤーに入れて読み込みます。中身は素のタイプセレクタで見出しの色を決める1つのルールだと分かっているので、要素のデフォルトの見た目を決める `base` レイヤーが合います。中身を確かめていない既存のCSSをまとめて引き継ぐときは、サードパーティのCSSと同じく `vendors` レイヤーに入れます（「[19-6 既存のサイトに段階的に導入する](/operations/adoption/)」）。どちらに入れても、`components` より前のレイヤーなので、コンポーネントの宣言が勝ちます。

```css title="🙆‍♂ Recommended: 引き継いだCSSを base レイヤーに入れて読み込む" use="diff" from="tasks/04-cascade/css/style.css"
@layer tokens, reset, base, vendors, compositions, pages, components, patterns, utilities;

@import url("kiso.css") layer(reset);
@import url("./tokens/colors.css") layer(tokens);
@import url("./tokens/sizes.css") layer(tokens);
@import url("./legacy.css") layer(base);
@import url("./components/news-card.css") layer(components);
```

直す前に勝っていたのは、`legacy.css` の `h2` の宣言です。レイヤーの外で読み込んだ宣言は、すべてのレイヤーより後ろの暗黙のレイヤーとして扱われます。レイヤーの順番は詳細度より先に比べられるので、この宣言が勝ちます。`news-card.css` の `h2` も詳細度は同じですが、比べる前にレイヤーの順番で負けています。`base` に入れると、`components` の宣言がレイヤーの順番で勝つので、見出しは濃い文字色に戻ります（「[4-3 カスケードレイヤーで順位を決める](/cascade/layers/)」）。

`news-card.css` の中で `h2` のセレクタの詳細度を上げても、レイヤーの外で読み込んだ `legacy.css` の宣言には勝てません。詳細度を上げて直そうとして効かなかったときは、まずレイヤーの書き忘れを疑います。

答えの例のファイル一式は、[補足サイト](/book-support/index.html)のサンプル一式の `tasks/04-cascade/` にあります。

</details>

## この章の判断のまとめ

宣言が効かないときは、カスケードが比べる順に、レイヤー、詳細度、スコープの近さ、出現順のどこで負けたかを確かめます。上書きが要るときも詳細度は上げず、優先順位の問題ならレイヤーの順番を、上書きされる側の詳細度が高すぎるなら `:where()` を、入れ子のコンポーネントにスタイルが漏れるなら `@scope` の下限を見直します。ただし、`@scope` が限るのは自分のルールが当たる範囲なので、外から入ってくるスタイルは、レイヤーとCSSの読み込み方の問題として扱います。`var()` を含む宣言は、カスケードで勝った後に、無効と分かることがあります。勝っているのに値が反映されない宣言では、置き換えた後の値がプロパティに合うかを確かめます。

レイヤーを使うかどうかは、レイヤーの外で出力される外部のCSSがあり、その読み込み方を変えられないかで決めます。`!important` は、どのような上書きにも負けてはいけない指定に限ります。宣言がどの段階で負けたかを切り分ける判断は、前の「判断の問い」で確かめられます。
