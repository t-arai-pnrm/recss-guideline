カスケードレイヤーを使うと、スタイルの優先順位を、詳細度ではなくレイヤーの順番で決められます。後に宣言したレイヤーのスタイルは、詳細度に関係なく、前のレイヤーのスタイルに勝ちます。詳細度を比べるのは、同じレイヤーの中だけです。

本書では、この仕組みを使って、スタイルの役割ごとに9つのレイヤーを決めています。ただし、レイヤーを選ぶのは、読み込むCSSをすべて自分で管理できる環境です。レイヤーに入っていないCSSは、詳細度に関係なくレイヤーの中のCSSに勝つので、CMSのようにレイヤーの外のCSSを避けられない環境では、レイヤーを使いません。

## 詳細度で役割の強さを表せるか

スタイルには、役割による強さの違いがあります。リセットCSSはベーススタイルに上書きされるべきで、コンポーネントのスタイルはユーティリティクラスに上書きされるべきです。しかし、詳細度はセレクタの形で決まる値なので、この役割の違いを表せません。

たとえば、要素を視覚的に隠すユーティリティクラス `.-visually-hidden` は、どのコンポーネントの要素に付けても適用されなければなりません。レイヤーがなければ、ユーティリティとコンポーネントのクラスはどちらも0.1.0なので、頼れるのは書いた順番だけです。読み込む順番が変わっただけで適用されなくなるので、以前はユーティリティに `!important` を付けるのが一般的でした。

```css title="🙅‍♂ Not Recommended: 読み込む順番に左右されないよう、ユーティリティに !important を付ける" issue="convention"
/* 🙅‍♂ Not Recommended */
.-visually-hidden {
  position: absolute !important;
  overflow: hidden !important;
  inline-size: 1px !important;
  block-size: 1px !important;
  clip-path: inset(50%) !important;
  white-space: nowrap !important;
}
```

すべての宣言に `!important` を付けると、このクラスを上書きできるのは、同じように `!important` を付けた宣言だけになります。詳細度の競争を、`!important` どうしの競争に持ち越しただけです。`!important` を付けない定義は「[17-5 要素を隠す方法を選ぶ](/interaction/hiding-elements/)」にあります。

私も2024年のブログでは、ITCSSという設計手法にならった7つのレイヤーを使っていました。全称セレクタで指定した詳細度0の文字サイズが、リセットCSSの `inherit` の指定に負けてしまうおそれがあり、それをレイヤーの順番で解決したのがきっかけです。詳細度の低いセレクタでも、後ろのレイヤーにあれば勝てます。レイヤーを使えば、優先順位を「役割の順番」として宣言できます。

## レイヤーの仕組み

レイヤーは、`@layer` 文で名前と順番を宣言し、`@layer 名前 { … }` のブロックにスタイルを入れて使います。順番は、その名前が最初に現れた順で決まります。次の例では、`components` と `utilities` の2つのレイヤーを、この順番で宣言しています。

```css title="🙆‍♂ Recommended: 2つのレイヤーで、後のレイヤーが詳細度に関係なく勝つ" from="cascade/utility-layer"
@layer components, utilities;

@layer utilities {
  .-text-muted {
    color: var(--foreground--muted);
  }
}

@layer components {
  .notice ._lead {
    color: var(--foreground--accent);
  }
}
```

`.notice ._lead` の詳細度は0.2.0で、`.-text-muted` の0.1.0より高く、ブロックも後ろに書いています。それでも、両方のクラスを持つ要素の文字色は `--foreground--muted` になります。カスケードはレイヤーの順番を詳細度より先に比べ、後に宣言した `utilities` のほうが強いからです。詳細度と書いた順番を比べるのは、同じレイヤーの中の宣言どうしだけです。

次のデモは、本書の規約に沿って書いたコンポーネントで、同じことを確かめます。デモでは、`utilities` レイヤーのルールを、`components` レイヤーのルールより前に書いています。どちらも0.1.0ですが、ユーティリティクラスを付けた2つ目の段落は灰色になります。コンポーネントの指定だけの1つ目の段落は、`components` レイヤーの青のままです。順番は先頭の `@layer` 文で決まっているので、ルールを書いた位置には左右されません。

<Demo title="前に書いた utilities のクラスが、後に書いた components の指定に勝つ" html={utilityLayerHtml} css={utilityLayerCss} widths={[]} />

仕組みとして押さえておくのは、この3点です。レイヤーの順番は最初に現れた順で決まること、後のレイヤーほど強いこと、レイヤーの順番は詳細度より先に比べられることです。以降の見出しでは、この仕組みを本書でどう使うかを説明します。

## 本書の9つのレイヤー

ここからは、本書の規約です。本書では、すべてのCSSを自分で読み込める環境を前提に、スタイルの役割ごとに9つのレイヤーを決めています。CMSの本体やプラグインのCSSのように、レイヤーの外で読み込まれるCSSを避けられない環境では、この構成を使わず、後述の「[CMSでのレイヤー](#cmsでのレイヤー)」のとおり、読み込む順番で9つの分類を保ちます。

本書の基本のレイヤーは、次の9つです。前に書いたレイヤーほど弱く、後ろに書いたレイヤーほど強くなります。

1. `tokens`：デザイントークン。`:root` のカスタムプロパティだけを置く
2. `reset`：リセットCSS（kiso.css）
3. `base`：HTML要素のデフォルトの見た目、`@font-face`、グローバルな `@keyframes`、`@property`
4. `vendors`：自分で読み込むサードパーティのCSS
5. `compositions`：stack、cluster、sidebarなど、レイアウトの再利用パターン
6. `pages`：ページ固有のセクション
7. `components`：複数の場所で使うコンポーネント
8. `patterns`：静的で再利用できる見た目のパターン
9. `utilities`：単機能の補助クラス

<Figure src="cascade/layer-stack" alt="9つのレイヤーと、レイヤーの外のスタイルを、強い順に縦に積んだ図。いちばん上が最も強く、下へ行くほど弱くなる。上から順に、レイヤーの外（レイヤーに入れていないCSS。破線の枠で強調している）、9番目のutilities、8番目のpatterns、7番目のcomponents、6番目のpages、5番目のcompositions、4番目のvendors、3番目のbase、2番目のreset、1番目のtokens。番号は先頭の@layer文で宣言する順番で、前に宣言したレイヤーほど弱く、後ろほど強い。右側の括弧は役割のまとまりを示し、utilitiesとpatternsが重ねて使うもの、components、pages、compositionsがページの組み立て、base、reset、tokensが土台。" />

最初の3つは、すべてのページの土台です。`tokens` を最も弱いレイヤーにしているのは、トークンの中身がカスタムプロパティの定義だけだからです。後ろのレイヤーで同じ名前のトークンを定義し直せば、そちらが優先されます。`reset` の後ろに `base` を置くのは、kiso.cssのデフォルト（`line-height: 1.5` など）をベーススタイルで上書きできるようにするためです。

`vendors` は、スライダーのようなサードパーティのCSSを入れるレイヤーです。自分たちのコンポジションやコンポーネントより前に置くので、サードパーティのCSSの見た目を、自分たちのCSSから上書きできます。

`compositions`、`pages`、`components` は、ページを組み立てるためのレイヤーです。ページ固有のセクションは `pages` に、複数の場所で使うコンポーネントは `components` に書きます。この区別は、レスポンシブ対応の手段の選び方とも対応しています。`pages` ではメディアクエリを、`components` ではコンテナサイズクエリを優先します（[13-1 検討する順番](/responsive/escalation/)）。コンポジションとユーティリティの中身は、第10章「[10-3 コンポジションとユーティリティ](/components/compositions-and-utilities/)」で説明します。

`components` は、自分の構造とスコープと状態を持つ部品で、`patterns` は、それらを持たない静的な見た目の断片です。`patterns` は、コンポーネントの要素に重ねて使います。`components` より後ろにあるので、`class="_label | status-badge"` のようにコンポーネントの子要素に付けると、パターンの指定が勝ちます。コンポーネントの状態や `@container` の中の指定でも、同じプロパティは変えられません。そのため、パターンにはコンポーネントが変えないプロパティだけを書き、変える値は公開プロパティで受け取ります（「[10-3 コンポジションとユーティリティ](/components/compositions-and-utilities/#rule-pattern-leaves-component-properties)」）。最後の `utilities` は、どこに付けても適用されなければならない補助クラスなので、最も強いレイヤーにします。`.-visually-hidden` も、`!important` なしでコンポーネントのスタイルに勝ちます。

## レイヤーの順番の宣言と `@import` での割り当て

レイヤーの順番は、そのレイヤーの名前が最初に現れた順で決まります。そこで、読み込むCSSの先頭で、すべてのレイヤーの順番を `@layer` 文で宣言します。その後ろで、各ファイルを `@import … layer()` の形で読み込みます。

```css title="🙆‍♂ Recommended: 本書の規約として9つの分類に割り当てる"
@layer tokens, reset, base, vendors, compositions, pages, components, patterns, utilities;

@import url("kiso.css") layer(reset);
@import url("./tokens/colors.css") layer(tokens);
@import url("./tokens/sizes.css") layer(tokens);
@import url("./base/generic.css") layer(base);
@import url("./vendors/slider.css") layer(vendors);
@import url("./compositions/cluster.css") layer(compositions);
@import url("./utilities/a11y.css") layer(utilities);
```

この例では、kiso.cssを `tokens` のファイルより先に読み込んでいます。それでも、`reset` は `tokens` より強いレイヤーのままです。順番は先頭の `@layer` 文で決まっているので、`@import` を書く順番には左右されません。順番を宣言しなければ、先頭で読み込んだ `reset` が最も弱いレイヤーになってしまいます。

`@import` に `layer()` を付けると、読み込んだファイルの中身がすべてそのレイヤーに入ります。各ファイルの中で `@layer base { … }` のように包む必要はありません。どのファイルがどのレイヤーに入るのかを、エントリーポイントのファイルの1か所で確認できます。kiso.cssを `reset` レイヤーに入れる理由は、第8章「[8-1 壊さないリセット](/reset/kiso/)」で説明します。

`@import` は、`@layer` 文を除くすべてのルールより前に書く必要があります。ほかのルールの後ろに書いた `@import` は無視されるので、エントリーポイントのファイルには、レイヤーの宣言と `@import` だけを置きます。

ただし、この `@import` はブラウザに実行させず、ビルド時に展開します。ブラウザが `@import` の読み込みを始められるのは、それを書いたファイルをダウンロードして解析した後です。読み込んだファイルの中にさらに `@import` があれば、その分だけ待ちが重なります。CSSは読み込みが終わるまでページの描画を止めるので、この直列の待ちが、そのまま最初の表示の遅れになります。

Astro（Vite）は、ビルド時に `@import` の読み込み先の中身をエントリーポイントのファイルに埋め込み、`layer()` の指定を `@layer` のブロックに置き換えます。フレームワークを使わない環境では、postcss-importのようなPostCSSのプラグインで同じように展開できます。展開した後もレイヤーの順番とファイルの割り当ては変わらないので、ソースのファイルでは、上の例のように `@import … layer()` で書けます。CMSの案件でも、自分で書いたCSSはビルドを通してから配信します。例外は、「[最小の構成で始める](/introduction/quick-start/)」のように、学習や検証のため、ビルドせずに手元で試す場合だけです。

学習用の構成から実務の配信へ移るときは、ビルドの道具を1つ通すだけで足ります。ここでは、「[最小の構成で始める](/introduction/quick-start/)」のお知らせのカードを、ファイルを変えずにViteでビルドします。ファイルの配置、`index.html`、`css/style.css` とそこから読み込む4つのファイルは、そのページのとおりです。`css/style.css` では、9つのレイヤーの順番を宣言し、kiso.css、2つのトークンのファイル、`news-card.css` を `@import … layer()` で割り当てています。

Viteは、HTMLの `<link>` から読み込んだCSSも処理の対象にします。`index.html` のある場所で、Viteを入れてからビルドします。

```bash
npm install --save-dev vite
```

```bash
npx vite build
```

ビルドすると、`dist/index.html` と、`dist/assets/` に1つのCSSファイルができます。`dist/index.html` の `<link>` は、`css/style.css` ではなく、このファイルを指すように書き換わります。出力の中には `@import` が残らず、読み込んだ各ファイルの中身が、`layer()` で指定したレイヤーのブロックに入ります。次の出力は、骨組みが分かるように改行し、中身の一部を省略したものです。

```css
@layer tokens {
  :root {
    --color--neutral--100: oklch(97% 0 0);
    /* ... colors.css と sizes.css の残りのトークン */
    --rounded--md: 8px;
  }
}
@layer reset {
  /* ... kiso.css の中身 */
}
@layer base, vendors, compositions, pages;
@layer components {
  @scope (.scoped.news-card) to (.scoped) {
    /* ... news-card.css の中身 */
  }
}
@layer patterns, utilities;
```

2つのトークンのファイルは1つの `:root` にまとまり、中身のないレイヤーは名前の宣言だけが残ります。先頭の `@layer` 文は、最小化のときにこうして書き直されますが、レイヤーが最初に現れる順番は宣言のとおりなので、優先順位は変わりません。最小化では、`display: block grid` が `display: grid` に、`calc(20 / 16 * 1rem)` が `1.25rem` になるような、意味を変えない書き換えも起きます。ビルドの後は、`npx vite preview` で `dist/` を配信し、ソースと同じカードが表示されることを確かめます。`dist/index.html` はCSSを `/assets/…` のようにサイトのルートから参照するので、ファイルを直接ブラウザで開くとCSSが読み込まれません。そのうえで、出力のCSSに `@import` が残っていないことと、レイヤーの並びが宣言どおりであることを確かめます。

`<head>` の中の `<style>` のように `@import` で読み込まないCSSには、`@layer components { … }` の形でレイヤーを自分で書きます。

## 宣言していないレイヤー名の扱い

レイヤー名を打ち間違えても、エラーにはなりません。先頭の `@layer` 文にない名前は、その場で新しいレイヤーとして作られ、それまでに現れたすべてのレイヤーの後ろに加わります。次の例では、`components` を `component` と書いたことで、`utilities` よりも後ろの、より強いレイヤーができてしまいます。

```css title="🙅‍♂ Not Recommended: 本書の規約と異なるレイヤー名で順位が変わる" issue="behavior"
/* 🙅‍♂ Not Recommended */
@layer component {
  /* ... */
}
```

この打ち間違いは、見た目ではすぐに気づけません。コンポーネントのスタイルはほぼ意図どおりに表示され、ユーティリティクラスを付けたときだけ適用されないという形で現れます。`@import url("…") layer(utility);` のように、`@import` の `layer()` で打ち間違えた場合も同じです。

そのため、`@layer` と `layer()` には、先頭で宣言した9つの名前だけを使います。{/* 要確認: 出典なし */} この確認は、Stylelintに任せられます。Stylelintの `layer-name-pattern` は、`@layer` と `@import` の `layer()` に書いたレイヤー名を正規表現で検証するルールです。stylelint-config-standardのデフォルトは、名前がケバブケースかどうかしか調べません。本書の設定では、9つの名前を列挙した `^(tokens|reset|base|vendors|compositions|pages|components|patterns|utilities)$` のようなパターンを指定しています。これで、宣言していない名前を検出できます。本書のStylelintの設定は、「[19-1 Stylelintでルールを守る](/operations/stylelint/)」で説明しています。

## レイヤーの外に書いたスタイルの扱い

レイヤーを使うプロジェクトでは、すべてのスタイルをいずれかのレイヤーに入れます。レイヤーに入っていないスタイルは、すべてのレイヤーより後ろにある「暗黙の最後のレイヤー」として扱われるからです。`!important` を付けていない宣言どうしなら、レイヤーの外のスタイルは、詳細度に関係なくすべてのレイヤーに勝ちます。

`@layer` を書き忘れたスタイルは、`utilities` のユーティリティクラスよりも強くなります。ユーティリティクラスを付けたのに効かないときは、レイヤーの書き忘れを疑います。1か所の書き忘れで、9つのレイヤーで決めた順番が崩れてしまいます。

次のデモの2つのカードは、同じ指定で段落を青くし、同じユーティリティクラスを付けています。違いは、2つ目のカードのルールを `@layer components { … }` で包み忘れたことだけです。1つ目の段落は灰色になり、2つ目の段落は青のままです。

<Demo title="@layer を書き忘れたコンポーネントには、ユーティリティクラスが効かない" html={forgottenLayerHtml} css={forgottenLayerCss} variant="not-recommended" widths={[]} />

サードパーティのCSSも同じです。`<link>` 要素などを使ってレイヤーの外で読み込むと、そのCSSはどのレイヤーよりも強くなり、自分のコンポーネントからは上書きできません。自分で読み込むサードパーティのCSSは、前の見出しのコード例のように `@import url("…") layer(vendors);` で `vendors` レイヤーに入れます。

この「レイヤーの外のCSSが勝つ」という性質は、自分で読み込み方を決められないCSSがある環境で、大きな問題になります。その代表がCMSです。

## CMSでのレイヤー

多くのCMSでは、CMSの本体やプラグインの出力するCSSが、レイヤーに入っていない状態で読み込まれます。この環境で自分のテーマのCSSだけをレイヤーに入れると、テーマのCSSは構造的に負けます。どれほど詳細度を上げても、レイヤーの外にあるプラグインのCSSには勝てません。

次のデモでは、テーマのCSSを `components` レイヤーに入れ、見出しにクラスで色と大きさを指定しています。一方、プラグインを想定したCSSは、レイヤーの外にタイプセレクタ `h2` で書いています。詳細度はテーマのCSSのほうが高いのに、見出しにはプラグインの色と大きさが使われます。見出しは、テーマで指定した青の20px相当ではなく、プラグインの赤の28px相当で表示されます。

私も、CMSの案件を始めたときは、Astroのテンプレートと同じレイヤーの構成で書き始めました。しかし、CMSの本体やプラグインのCSSとの関係でこの問題があるため、数日後にはレイヤーの使用をやめています。本書のレイヤーの構成は、すべてのCSSを自分で管理できる環境を前提にしたものです。

レイヤーを使わない環境でも、9つの分類そのものは捨てません。ディレクトリを分類ごとに分け、エントリーポイントの `@import` を9つの分類の順番に並べます。レイヤーがなければ、優先順位は詳細度と書いた順番で決まります。ベーススタイルを `:where()` で詳細度0にし、コンポーネントの中をクラス1つ分にそろえておけば、読み込む順番がレイヤーの代わりになります。この `@import` も、ビルド時に展開してから配信します。

```css title="🙆‍♂ Recommended: CMSでは、読み込む順番で9つの分類を保つ"
@import url("kiso.css");
@import url("./tokens/shapes.css");
@import url("./base/generic.css");
@import url("./compositions/cluster.css");
@import url("./pages/about.css");
@import url("./components/site-header.css");
@import url("./utilities/a11y.css");
```

CMSの本体と衝突しにくくするために、テーマのスタイルは `@scope` と独自のクラス名で範囲を限ります。CMSが出力するクラス名にスタイルを書く場面を減らせば、詳細度の競争に巻き込まれにくくなります。詳細度をそろえる書き方は「[4-2 セレクタで詳細度を設計する](/cascade/selectors/)」で、`@scope` は「[4-4 @scopeでスタイルを閉じ込める](/cascade/scope/)」で説明しています。

## 例外：壊れた既存のCSSから新しいコンポーネントを守る

レイヤーを使わない環境にも、例外が1つあります。既存のCSSがIDセレクタの連結や `!important` で固められていて、新しく追加するコンポーネントにまでスタイルが当たる場合です。既存のCSSを直せないなら、詳細度を上げて対抗するより、コンポーネントを外のスタイルから切り離すほうが確実です。

切り離しには、`!important` を付けた宣言どうしではレイヤーの順番が逆になる性質を使います（「[4-1 カスケード・詳細度・継承](/cascade/cascade-basics/)」）。レイヤーの中で、コンポーネントの要素すべてに `all: revert-layer !important` を指定すると、この宣言はレイヤーの外のスタイルに、`!important` の付いたものも含めて勝ちます。`revert-layer` の戻り先はひとつ前のレイヤーなので、同じレイヤーの中に入れ子の無名レイヤーを作り、コンポーネント自身のスタイルはそこに書きます。

```css title="🙆‍♂ Recommended: 既存のCSSを遮断し、自分のスタイルだけを入れ子のレイヤーから戻す"
@layer components {
  @layer {
    @scope (.scoped.campaign-banner) to (.scoped) {
      h2 {
        color: var(--color--accent--700);
      }
    }
  }

  @scope (.scoped.campaign-banner) to (.scoped) {
    :scope,
    * {
      all: revert-layer !important;
    }
  }
}
```

コンポーネントの要素の値は、入れ子のレイヤーに書いた値か、それがなければブラウザのデフォルトスタイルになります。既存のCSSが `#page#page p` のような詳細度で `color` や `padding !important` を指定していても、コンポーネントの中には当たりません。`all` は継承を止めないので、文字の色やフォントのように指定しなかった値は、親から受け継ぎます。`@scope` の `to (.scoped)` があるので、中に置いた子のコンポーネントは切り離しの対象外です。

遮断できないものもあります。`all` が戻すのは、カスタムプロパティと `direction`、`unicode-bidi` を除くプロパティです。既存のCSSが `:root` のトークンやコンポーネントの公開プロパティの値を書き換えていると、その値はそのまま届きます。また、`:scope` と `*` は擬似要素を選ばないので、既存のCSSが `::before` や `::after` に付けた装飾は残ります。擬似要素も遮断するならセレクタに `*::before, *::after` を加え、トークンの値を守りたいなら、コンポーネントの入れ子のレイヤーで使う値を定義し直します。

この書き方は、`!important` を例外に限る本書の方針の中でも、さらに例外の位置づけです。後ろのレイヤーやユーティリティクラスも同じように遮断されるので、コンポーネントの見た目はすべて入れ子のレイヤーの中で完結させる必要があります。`style` 属性に `!important` を付けた指定だけは、レイヤーの中の宣言より強いので防げません。既存のCSSを直せる見込みがあるなら、そちらを先に検討します。

## レイヤーを使うかどうかの判断基準

レイヤーを使うかどうかは、「レイヤーに入っていない外部のCSSがあるか」と「そのCSSを自分でレイヤーに入れられるか」の2点で判断します。

- すべてのCSSを自分で書くか、サードパーティのCSSも自分で `@import` できる：レイヤーを使い、サードパーティのCSSは `vendors` に入れる
- CMSの本体やプラグインのように、外部のCSSがレイヤーの外で出力され、読み込み方を変えられない：レイヤーを使わず、読み込む順番で9つの分類を保つ

AstroのようにすべてのCSSを自分で管理できる静的サイトは、前者に当たります。CMSのテーマやプラグインは、後者に当たります。迷ったときは、ブラウザの開発者ツールでページに読み込まれているCSSを確認し、自分が書いていないCSSがレイヤーの外にあるかどうかを調べます。

レイヤーは優先順位を宣言する便利な仕組みですが、詳細度を低くそろえる設計ができていれば、読み込む順番でも同じ結果を得られます。kiso.cssを `:where()` で書き、「レイヤーに頼らなくても上書きしやすい」ことを重視したのも、レイヤーを導入しにくい環境があるからです。

## 補足と注意点

9つのレイヤーを採用すると、CSSを書く人は、新しいスタイルをどのレイヤーに入れるかを毎回判断することになります。`compositions` と `components`、`components` と `patterns` の線引きは、名前だけでは決まらないので、慣れるまで迷いやすいところです。詳細度と書いた順番で優先順位を考えてきた人は、まずレイヤーの順番で勝ち負けを読み、同じレイヤーの中でだけ詳細度を比べる読み方に切り替える必要があります。

ある宣言がどのレイヤーにあるかは、エントリーポイントのファイルの `@import … layer()` の一覧で確かめます。レイヤーはファイル単位で割り当てているので、ファイルの置き場所が分かればレイヤーも決まります。`<style>` の中などに直接書いたレイヤーは、`@layer` で検索して探します。ブラウザの開発者ツールでは、スタイルの欄で、各ルールの上に、そのルールの属するレイヤーの名前が表示されます。{/* 要検証: ブラウザ。Chrome、Firefox、Safariの開発者ツールで、ルールの属するレイヤーの名前を表示すること */}意図しない宣言が勝っているときは、そのルールのレイヤーと、レイヤーの外に書かれていないかを先に確かめます。

レイヤーを使わないほうがよいのは、前の見出しの判断基準のとおり、レイヤーの外で出力される外部のCSSと読み込み方を変えられない場合です。サイトが小さく、9つのうち使わないレイヤーがあっても、スタイルを持たないレイヤーは優先順位に影響しないので、先頭の `@layer` 文から外す必要はありません。{/* 要確認: 出典なし */}

新しいプロジェクトでは、最初にレイヤーの導入を検討します。既存のプロジェクトに入れるときは、一部のCSSだけをレイヤーに入れると、残りのレイヤーの外のCSSにすべて負けます。そこで、最初の段階で既存のCSSを含むすべてのファイルをいずれかのレイヤーに割り当て、Stylelintの `layer-name-pattern` を有効にします。{/* 要確認: 出典なし */}`components` と `patterns` のような細かい線引きは、そのあとでファイルを移しながらそろえます。{/* 要確認: 出典なし */}
