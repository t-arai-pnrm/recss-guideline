本書が対象にするブラウザは、Safariが現行のメジャーバージョンから2つ前の最終版以降、Chrome、Edge、Firefoxが最新版です。2026年9月時点ではSafari 27が最新なので、Safari 18系の最終版である18.6以降が対象になります。新しい機能を使うときは、まずSafariの対応状況を確認します。

対象のブラウザの一部しか対応していない機能は、プログレッシブ・エンハンスメントとして使えるかどうかで判断します。未対応の環境でも内容を読めて操作でき、対応した環境ではより良い体験になるものだけを使います。分岐には `@supports` と `scripting` メディア特性を使い、表示の確認はChromeだけで済ませません。

## Safariを基準に対象を決める

Chrome、Edge、Firefoxは自動で更新されるので、多くのユーザーが最新版を使っています。一方、SafariはOSのアップデートと一緒に更新されるため、古いバージョンを使い続けるユーザーが一定数残ります。そのため、対象のブラウザの中で最も保守的な基準になるのがSafariです。新しいプロパティを使うときも、最初に確認するのはSafariの対応状況です。

バージョンの数え方には注意が必要です。Safariのバージョンは18の次が26で、番号が連続していません。そのため「2つ前」は番号の引き算ではなく、実際に出たメジャーバージョンを数えて求めます。2026年9月14日にSafari 27が出たので、1つ前が26、2つ前が18です。18系の最後のバージョンは18.6（2025年7月）なので、対象はSafari 18.6以降になります。

| 時期 | 最新のメジャーバージョン | 対象の下限 |
| --- | --- | --- |
| 2024年9月〜2025年9月 | Safari 18 | Safari 16.6 |
| 2025年9月〜2026年9月 | Safari 26 | Safari 17.6 |
| 2026年9月〜 | Safari 27 | Safari 18.6 |

対象の下限は、新しいメジャーバージョンが出るたびに1つずつ上がります。次のメジャーバージョンが出たら、下限はSafari 26系の最終版です。iOSのSafariも同じ番号で考えます。

この基準は、本書のコード例とルールの前提です。案件で動作環境が決まっている場合は、案件の基準に従います。案件の基準がより古いSafariを含むなら、本書で「そのまま使える」としている機能にも、フォールバックが必要になることがあります。ただし、`@scope` に対応していないブラウザ（Safari 17.3以前など）を含む案件は、本書の対象外です。本書の書き方は、コンポーネントの範囲を `@scope` で区切ることを前提にしているからです。

## 案件の基準を決めるとき

案件の基準を決める場合は、対応率の数字だけで「使ってよい」と判断せず、3つの観点を合わせて見ます。1つ目は、未対応の環境で何が起きるかです。宣言が無視されるだけなのか、内容を読めなくなったり操作できなくなったりするのかで、許される範囲が変わります。

2つ目は、そのサイトを使う人のブラウザです。Can I Useのような全体の数字は世界中の利用者の平均なので、自サイトのアクセス解析とは大きく異なることがあります。学校の端末で使われる教材サイトと、最新の端末を使う人が多い開発者向けのサイトでは、同じ機能でも未対応の割合が違います。3つ目は、使えなかったときの害の大きさです。予約や手続きに代わりの手段がない行政や医療、金融のサービスは、趣味の読み物のサイトよりも対象を広げて考えます。

「何%の対応率なら使ってよい」という数字は、この3つを抜きにしては決められません。本書がSafariを基準に対象を固定しているのは、案件の基準がないときの出発点です。案件に基準があるなら、それを優先します。

基準を決めたあとは、プログレッシブ・エンハンスメントとして使う機能の確認方法も決めておきます。未対応のブラウザを手元に用意しなくても、その宣言をコメントアウトして、表示が読めて操作できるかを確かめれば、未対応の環境での見え方を推定できます。同じ機能を複数の箇所で使っているなら、箇所ごとに確認します。宣言を外すと表示が崩れる箇所は、フォールバックを足すか、その機能を使わないと決めます。

「広く利用可能」と表示される機能は、すべての主要なブラウザで対応してから長い時間がたっているので、本書の対象でもそのまま使えます。「新しく利用可能」と「一部のブラウザのみ」の機能は、Safariの欄のバージョンが18.6以下かどうかを確かめます。「一部のブラウザのみ」の機能は、Chrome、Edge、Firefoxの欄が空いていないかも確かめます。どれかが空いていれば、Safariが対応していても、プログレッシブ・エンハンスメントとして使えるかを判断します。上のコンテナスタイルクエリは、2026年5月に「新しく利用可能」になったばかりですが、Safariは18で対応しているので、本書の対象ではそのまま使えます。

## プログレッシブ・エンハンスメントとして使いやすい機能

対象の一部しか対応していない機能でも、プログレッシブ・エンハンスメントとして使えるものがあります。判断の基準は2つあります。1つは、未対応の環境で従来どおりに表示されるか、簡単なフォールバックを用意できることです。もう1つは、対応した環境で、より良い体験を提供できることです。未対応のブラウザは、理解できない宣言を無視します。無視されても困らない機能なら、使わない理由はありません。

| 機能 | 未対応のブラウザ | 未対応の環境での表示 |
| --- | --- | --- |
| `text-wrap: pretty`（英文の段落） | Firefox、Safari 18系 | 通常の折り返しになる |
| `word-break: auto-phrase` | Safari、Firefox | 文節で区切らずに折り返す |
| `field-sizing` | Safari 26.1以前 | 入力欄が内容に合わせて伸び縮みしない |
| `text-box`（`cap` や `alphabetic` を指定した場合） | Firefox | 宣言が無効になり、文字の上下の余白が残る |
| ドキュメント間のビュートランジション | Firefox | アニメーションせずにページが切り替わる |

この表は2026年9月時点のものです。和文には `text-wrap: pretty` を指定しません（「[14-4 文字サイズと改行](/typography/size-and-line-breaks/#rule-no-text-wrap-pretty-for-japanese)」）。`text-box` のように、未対応の環境で余白の大きさが変わる機能は、レイアウトが崩れたり、表示が大きく変わったりしない範囲で使います。

対象の下限が上がると、プログレッシブ・エンハンスメントとして扱っていた機能が、そのまま使える機能に変わります。たとえば `::details-content` はSafari 18.4で対応したので、下限がSafari 17.6だった2026年1月の時点では対象外でした。下限がSafari 18.6になった現在は、本書の対象のすべてで使えます。

## プログレッシブ・エンハンスメントとして使いにくい機能

反対に、未対応の環境での影響が大きく、プログレッシブ・エンハンスメントとして使いにくい機能もあります。未対応の環境でブロックごと無視されるアットルールと、無視されたときに表示の崩れが大きくなるレイアウト関連の機能です。アンカーポジショニングと、絶対配置の要素への `place-self`（どちらもSafari 26で対応）がこれに当たります。`sibling-index()` と `sibling-count()`（Safari 26.2で対応）も同じです。

アットルールでは、以前はコンテナスタイルクエリがこの例でした。`@scope` も未対応の環境では中身がまとめて無視されますが、本書の対象はすべて対応しているので、前提の機能として使っています。ただし、対象に含まれるSafari 26.0〜26.3では、`@scope` の中のルールが `<input>` と `<textarea>` に適用されません。入力欄は、これらの版で標準の見た目になっても、入力と操作ができることを確かめます。詳しくは「[4-4 @scopeでスタイルを閉じ込める](/cascade/scope/)」と「[17-7 フォーム部品](/interaction/forms/)」で説明します。

<Baseline id="anchor-positioning" compatKey="css.properties.anchor-name" name="アンカーポジショニング（anchor-name）" />

たとえば、アンカーポジショニングでツールチップをボタンの横に配置したとします。未対応の環境では配置の指定が無視され、ツールチップは意図しない場所に表示されて、ほかの内容に重なることがあります。レイアウトの要になる機能は、対象のすべてが対応するまで待つか、別の方法で実現します。

ただし、使いにくいのは、その機能をレイアウトの要として使う場合です。ホバーしたカードに背景が滑らかに追従するような装飾的な演出なら、未対応の環境向けに従来の表現を用意して使えます。次の例は、アンカーポジショニングに未対応の環境でだけ、ホバーしたカードに直接背景色を付けるものです。

```css title="🙆‍♂ Recommended: 未対応の環境では、従来のホバーの表現に切り替える"
._card {
  &:has(:any-link:hover) {
    @supports not (anchor-name: --card) {
      @media (any-hover) {
        background-color: var(--background--hover);
      }
    }
  }

  &:has(:focus-visible) {
    @supports not (anchor-name: --card) {
      background-color: var(--background--hover);
    }
  }
}
```

## Chromeだけで確認しない

表示の確認は、Chromeだけで済ませません。Chromeは、既存のプロパティの新しい仕様を、ほかのブラウザより先に実装することがよくあります。Chromeの最新版だけで確認していると、Chromeでしか成り立たない書き方に気づけません。

たとえば、`justify-self` と `justify-items` は、ブロックレイアウトでも使えるように仕様が広がりました。しかし、対応しているのはChromeとEdgeだけです。

<Baseline id="justify-self-block" name="ブロックレイアウトの justify-self" />

```css title="🙅‍♂ Not Recommended: ブロックレイアウトの要素を justify-self で中央に寄せる" issue="behavior"
/* 🙅‍♂ Not Recommended */
._article {
  & > ._more-link {
    justify-self: center;
  }
}

._more-link {
  display: block flow;
  inline-size: fit-content;
}
```

このコードは、Chromeでは要素が中央に寄りますが、SafariとFirefoxでは `justify-self` が無視され、左に寄ったままです。対応データでは、ブロックレイアウトの `justify-self` に対応しているのは、Chrome 130以降とEdgeだけです。ブロックの中央寄せには、どのブラウザでも同じ結果になる `margin-inline: auto` を使います。レスポンシブ対応で `display` をgridからブロックに戻す場合も、`justify-items` や `justify-self` が残っていないかを確かめます。

```css title="🙆‍♂ Recommended: ブロックの中央寄せには margin-inline: auto を使う"
._article {
  & > ._more-link {
    margin-inline: auto;
  }
}

._more-link {
  display: block flow;
  inline-size: fit-content;
}
```

ほかにも、単位つきの値どうしの割り算は、ブラウザによって対応の時期が大きく異なります。`vw` も、Chrome 145から条件によってスクロールバーを除いた幅で計算されるようになりました（2026年2月時点では、SafariとFirefoxは従来どおりです）。どちらも「[6-4 計算関数を応用する](/values/advanced-math-functions/)」と「[6-2 ビューポート単位とコンテナ単位](/values/viewport-and-container-units/)」で扱います。

開発中はChromeを使っていてもかまいません。ただし、作業を終える前に、Safari（iOSを含む）とFirefoxでも表示を確かめます。対象の下限にあたる古いSafariは手元で用意しにくいので、対応状況のデータでの確認と組み合わせます。

## 未対応の環境に備える書き方の詳細

ここまでで、対象のブラウザと、未対応の環境で守ることは決まります。以降は、その判断をコードにするときの詳細です。`@supports` の使いどころ、フォールバックを書く位置の選び方、JavaScriptがない環境への備えを順に説明します。前から通して読むときは、案件の基準を決めたあと、必要になった節から読めば足ります。

### `@supports` で対応した環境だけを変える

`@supports` は、ブラウザが宣言を理解できるかどうかで分岐します。未対応の宣言はもともと無視されるので、新しいプロパティそのものを `@supports` で囲む必要はありません。`@supports` が必要になるのは、新しい機能に合わせて、既存の宣言も一緒に変えるときです。

`<textarea>` に `field-sizing: content` を指定すると、入力した量に合わせて入力欄が伸び縮みします。自動で伸び縮みするなら、ユーザーが手でサイズを変える機能（`resize`）は不要です。ただし、`resize` を無条件に止めると、未対応の環境では入力欄の高さが固定され、手で広げることもできなくなります。最大の高さも同じです。無条件に付けると、未対応の環境では、ユーザーの広げられる範囲が狭まります。そこで、手動のリサイズを止める指定と最大の高さを、`field-sizing: content` と一緒に `@supports` の中に書きます。

```css title="🙆‍♂ Recommended: 自動で伸び縮みする環境でだけ、手動のリサイズを止め、最大の高さを付ける" from="principles/field-sizing"
@scope (.scoped.inquiry-form) to (.scoped) {
  textarea {
    --_rows: 3lh;
    --_max-rows: 8lh;

    min-block-size: var(--_rows);

    @supports (field-sizing: content) {
      max-block-size: var(--_max-rows);
      resize: unset;
      field-sizing: content;
    }
  }
}
```

次のデモで入力欄に改行や文章を足すと、対応しているブラウザでは入力欄が伸び縮みし、未対応のブラウザでは右下のつまみで高さを変えられます。どちらの環境でも、入力するという目的は損なわれません。

反対に、対象のすべてが対応した機能のフォールバックは消します。次の例は、`lh` 単位に未対応の環境のために書いていたものです。`lh` はSafari 16.4で対応しているので、本書の対象ではこの分岐が使われることはありません。

```css title="🙅‍♂ Not Recommended: 対象のすべてが対応している機能のフォールバックを残す" issue="convention"
/* 🙅‍♂ Not Recommended */
:root {
  --icon-size: 1lh;
}

@supports not (top: 1lh) {
  :root {
    --icon-size: 1.5em;
  }
}
```

使われないフォールバックは、読む人に「まだ対応していないブラウザがある」と思わせ、消してよいかの判断を迷わせます。対象の下限を上げたときは、こうした分岐も見直します。なお、`@supports selector(::-webkit-scrollbar)` のように、`selector()` を使えばセレクタの対応状況でも分岐できます。

### フォールバックの書き方を選ぶ

未対応の環境のための書き方には、新しい宣言をそのまま書く、従来の宣言を前に書く、`@supports` の中に書く、の3つがあります。どれを選ぶかは、未対応の環境で新しい宣言がいつ無効になるかと、一緒に変える宣言があるかで決まります。判断を誤ると、未対応の環境で従来の値まで失われます。

新しいプロパティそのものは、そのまま書きます。未対応のブラウザは、知らないプロパティの宣言を構文の段階で捨てるだけで、ほかの宣言には影響しません。`text-wrap: pretty` がこれに当たります。前の節の例で `field-sizing` を `@supports` の中に書いているのは、一緒に変える宣言とまとめて読めるようにするためです。外に書いても、未対応の環境では同じように捨てられるので、結果は変わりません。

既存のプロパティに新しい値や関数を使い、宣言に `var()` を含まない場合は、従来の宣言を前に書くか、新しい宣言を `@supports` の中に書きます。未対応のブラウザは、新しい値を含む宣言を構文の段階で無効とみなして捨て、前の宣言を使うので、どちらでも結果は同じです。「[6-5 if()とattr()で条件と属性を値にする](/values/if-and-attr/)」の `if()` の例は前者、「[12-3 cluster](/compositions/cluster/)」の `flex-wrap: balance` は後者で書いています。前者で書くなら、同じプロパティが2回並ぶと誤記に見えるので、前の宣言には「未対応の環境で使う値」であることをコメントで書きます。

宣言に `var()` を含む場合は、`@supports` の中に書きます。`var()` を含む宣言は、構文の検査が値の計算まで先送りされます。未対応の関数があると分かった時点では、前の宣言はもう使えないので、宣言は「計算値の時点で無効」になり、プロパティの初期値か継承した値が使われます。型付きの `attr()` は `var()` と組み合わせることが多いので、6-5では `@supports` の中に書いています。

新しい機能に合わせて、ほかの宣言もまとめて切り替える場合も、`@supports` の中に書きます。`display` でレイアウトの方式を切り替えると、`grid-template-columns` や子の `aspect-ratio` のように、ほかの宣言の意味も変わるからです。「[11-11 grid-lanesで石積みのレイアウトを組む](/layout-practice/masonry/)」で `display` を2つ並べずに `@supports` を使うのは、このためです。`@supports` の条件は検索できるので、対象のすべてが対応した時点で、分岐をまとめて消せます。

### `scripting` メディア特性でJavaScriptのない環境に備える

JavaScriptで表示を切り替える前提のスタイルは、`@media (scripting: enabled)` の中に書きます。典型的なのが、画面に入ったらふわっと表示するアニメーションです。表示する前の状態で要素を待たせておき、画面に入ったらJavaScriptが再生を始めます。

```css title="🙆‍♂ Recommended: JavaScriptが使える環境でだけ、表示する前の状態で待たせる"
@scope (.scoped.feature-list) to (.scoped) {
  li {
    /* 監視を始めた JavaScript がルートに付ける属性があるときだけ待たせる */
    &:is(:scope[data-motion-mode="motion"] *) {
      @media screen and (prefers-reduced-motion: no-preference) and (scripting: enabled) {
        animation-name: --fade-in, --translate-from;
        animation-duration: var(--duration--reveal);
        animation-fill-mode: both;
        animation-play-state: paused;
      }
    }

    &[data-revealed]:is(:scope[data-motion-mode="motion"] *) {
      animation-play-state: initial;
    }
  }
}
```

この条件がないと、JavaScriptが無効な環境では再生を始める処理が動かず、要素がいつまでも透明なままになります。ただし、`scripting: enabled` はJavaScriptが有効なことしか表しません。スクリプトの読み込みに失敗したり、実行の途中でエラーが起きたりしても、条件は当てはまります。そこで、待たせる条件には、JavaScriptが初期化に成功した時点で付ける属性（ここでは `data-motion-mode="motion"`）も加えます。画面に入ったら、JavaScriptが `data-revealed` を付けて再生します。属性が付く前に処理が止まれば、要素は最初から表示されたままです。待たせる指定は `screen` のメディアに限ります。印刷ではスクロールしないので、画面に入っていない要素に `data-revealed` が付かず、透明のまま印刷されるからです。待機中の見た目を `@keyframes` に任せる書き方と、動きを減らす設定との組み合わせは、「[18-9 スクロールに合わせて動かす](/motion/scroll-driven/)」で説明します。

<Baseline id="scripting" name="scripting メディア特性" />

同じように、JavaScriptでカード全体をクリックできるようにしているなら、`cursor: pointer` を `scripting: enabled` のときだけ指定します。反対に、`@media (scripting: none)` を使えば、JavaScriptが動かない環境で読み込み中の表示を隠すこともできます。以前はiOS 17より前のSafariが `scripting` に対応していなかったため、属性で代わりに判定する工夫が必要でした。現在の本書の対象では、その必要はありません。
