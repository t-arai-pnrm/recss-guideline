写真と、エッジや形が大事な画像はAVIFで書き出し、テキストの下に敷くLCPの候補の写真や画質を重視する写真には、JPEG XLをAVIFの代わりとともに使います。`srcset` と `sizes` の属性で、レイアウトの中で表示される幅に合った大きさの画像を読み込ませます。表示される幅はCSSのレイアウトで決まるので、`sizes` の値は手で計算せず、ツールで確かめて決めます。

ファーストビューに表示される画像には `loading="lazy"` を指定せず、LCPの候補になる画像にだけ `fetchpriority="high"` を指定します。`decoding` 属性は書かず、デフォルトの `auto` に任せます。どれも、画像をいつ、どの大きさで読み込むかをブラウザに伝える指定で、表示の速さに関わります。

画像の比率と切り取り方、`<img>` の `width` と `height` の属性、背景の写真を `<img>` で置く理由は、「[16-1 画像の配置と比率](/decoration/images/)」で説明しています。

## 画像の形式

画像の形式は、画像の役割で選びます。写真と、ロゴや図表のようにエッジや形の正確さが大事な画像は、AVIFで書き出します。テキストの下に背景として敷くLCPの候補の写真や、画質を重視する写真は、JPEG XLを優先し、対応していない環境のためのAVIFを添えます。イラストやアイコンのような図形で描けるものは、画像のファイルではなくSVGで描きます（「[16-3 アイコンとSVG](/decoration/icons-and-masks/)」）。

AVIFは、2024年1月にすべての主要なブラウザで使えるようになりました。同じ写真を同じくらいの画質で書き出したとき、WebPより10〜30%ほど小さくなるのが目安です。素材と品質の設定で差は変わるので、自分の画像で書き出して比べます。可逆圧縮と透過にも対応しているので、以前ならPNGで書き出していた、エッジや形がはっきりした画像にも使えます。

ただし、AVIFが可逆圧縮に対応していることと、書き出した画像が可逆になることは別です。変換のツールの多くは、既定で非可逆に書き出します。たとえば、画像処理のライブラリsharpの `avif()` は、既定で `lossless` が `false`、`quality` が50です。エッジや形が大事な画像は、可逆圧縮を指定して書き出します。Webページで表示する画像では、ブラウザの対応を理由にJPEGやPNGを主な形式にする必要はもうありません。

<Baseline id="avif" />

```js title="sharpで、エッジの大事な画像を可逆圧縮のAVIFに書き出す"
import sharp from 'sharp';

await sharp('logo.png').avif({ lossless: true }).toFile('logo.avif');
```

非可逆で書き出すときも、`quality` を上げるだけでなく、色の情報を間引かない設定（sharpでは `chromaSubsampling` のデフォルト値の `'4:4:4'`）のままにします。間引くと、細い線や文字の縁に色のにじみが出ます。書き出した画像は、元の画像と等倍で並べ、エッジのにじみや色のずれがないか、ファイルの大きさが元の形式より小さくなっているかを確かめます。可逆圧縮のAVIFは、図形の多い画像ではPNGより大きくなることもあるので、そのときはPNGのまま使うか、SVGで描けないかを考えます。{/* 要確認: 出典なし。可逆圧縮のAVIFがPNGより大きくなる画像と、そのときの選び方 */}

JPEG XLは、AVIFより高度なプログレッシブ表示ができる形式です。読み込みの途中から、粗い全体像を表示し、データが届くにつれて細部を描き足していきます。ページでいちばん大きく表示され、テキストの下に敷くヒーローの写真のように、早く何かを見せたい画像ほど、この性質が生きます。JPEG XLの画像は、可逆圧縮のまま画質を保つこともできます。

ただし、JPEG XLはまだBaselineではありません。web-featuresのデータでは、対応しているのはSafari 17以降だけで、ChromeとFirefoxの安定版は対応していません。{/* 要確認: 出典なし。Chrome、Edge、Firefox が JPEG XL に対応する版と時期 */}そのため、JPEG XLは `<picture>` の `<source>` に `type="image/jxl"` を付けて置き、`<img>` にはAVIFを書きます。ブラウザは、`<source>` を上から順に調べ、対応している形式の最初のものを選びます。どれにも対応していなければ `<img>` の画像を使います。

<Baseline id="jpegxl" name="JPEG XL" />

```html title="🙆‍♂ Recommended: LCPの候補の写真を、JPEG XLを先に、AVIFを代わりにして渡す"
<picture>
  <source
    type="image/jxl"
    srcset="hero-800.jxl 800w, hero-1600.jxl 1600w"
    sizes="100vw"
  />
  <img
    src="hero-800.avif"
    srcset="hero-800.avif 800w, hero-1600.avif 1600w"
    sizes="100vw"
    width="1600"
    height="900"
    alt=""
    fetchpriority="high"
  />
</picture>
```

`<source>` には、`<img>` と同じ `srcset` の幅と `sizes` を書きます。`<source>` が選ばれても、`width` と `height`、`alt`、`fetchpriority` は `<img>` の属性が使われます。CSSの `background-image` で形式を出し分けるときは、`image-set()` の `type()` で同じことができます。ただし、背景の写真を `background-image` で敷く書き方には、読み込みの遅れなどの問題があります（「[16-1 画像の配置と比率](/decoration/images/#背景の写真も-img-で置く)」）。

AVIFへの変換は、同じ画像と同じツールで比べると、WebPの2倍以上の時間を要することがあります。差は、画像の大きさと変換の設定（sharpの `effort` など）で変わります。画像の多いサイトでは、ビルドの時間を見積もっておきます。ビルドを頻繁に繰り返すプロジェクトや、画像の差し替えが続く開発の段階では、変換の速いWebPを使う選択肢もあります。これは見る人ではなく作る側の都合による選択なので、公開する画像の形式を、ビルドの時間と見比べてあらためて決めます。

## レスポンシブ画像

画面の幅や解像度に合わせて、大きさの違う画像を出し分けるには、`srcset` と `sizes` の属性を使います。`srcset` には画像の候補とその幅を、`sizes` には画像がレイアウトの中で表示される幅を書きます。ブラウザは、表示される幅と画面の解像度から、ちょうどよい候補を選んで読み込みます。

```html
<img
  src="photo-800.avif"
  srcset="photo-400.avif 400w, photo-800.avif 800w, photo-1200.avif 1200w"
  sizes="(width >= 1024px) 50vw, 100vw"
  width="1200"
  height="800"
  alt="川沿いの桜並木"
/>
```

難しいのは `sizes` です。表示される幅はCSSのレイアウトで決まるので、余白、段組み、コンテナサイズクエリによる切り替えまで考えて、ビューポートの幅との関係を書き出す必要があります。私は、`sizes` を手で計算しません。仮の値を入れたページでRespImageLintのブックマークレットを実行し、提案された値を採用しています。

RespImageLintが提案する `sizes` の値は、`vw` を使って書かれています。`sizes` はCSSのプロパティではなくHTMLの属性で、画像を選ぶ時点のビューポートの幅を基準にします。本書では、`sizes` の中の `vw` を、`vw` を使わないという規約（「[6-2 ビューポート単位とコンテナ単位](/values/viewport-and-container-units/)」）の例外として扱います。

`<picture>` の `<source>` にある `media` 属性は、ビューポートを基準にした条件しか書けません。コンテナサイズクエリで配置を切り替えるコンポーネントでも、画像の切り替えはビューポートを基準にして書くしかありません。この制約は「[13-3 コンテナサイズクエリ](/responsive/container-size-queries/)」でも取り上げています。

幅によって構図の違う画像に切り替えるときも、`<img>` を2つ置いて片方を `display: none` で隠すのではなく、`<picture>` の `<source>` で出し分けます。`<img>` の画像を読み込むかどうかはCSSの表示と関係なく決まるので、隠した画像も読み込まれ、使わない画像の分だけ転送量が増えます。`loading="lazy"` を付ければ、表示領域に近づくまで読み込みを待つので隠した画像は読み込まれませんが、ファーストビューの画像には付けられません（「[読み込みの優先度と遅延読み込み](#読み込みの優先度と遅延読み込み)」）。Chromeで確かめたところ、`display: none` の `<img>` は読み込まれました。`loading="lazy"` を付けた `display: none` の `<img>` と、条件に合わない `<source>` の画像は読み込まれませんでした。{/* 要確認: 出典なし。隠した img の代わりに picture で出し分ける判断 */}{/* 要検証: ブラウザ。Firefox と Safari で、loading="lazy" を付けた display: none の img が読み込まれないこと */}

## 読み込みの優先度と遅延読み込み

ファーストビューに表示される画像には、`loading="lazy"` を指定しません。遅延読み込みにすると、ページでいちばん大きな要素の表示が遅れるからです。スクロールしないと見えない画像と `<iframe>` にだけ、`loading="lazy"` を付けます。

そのうえで、LCPの候補になる画像（ヒーロー画像のように、ファーストビューでいちばん大きく表示される画像）にだけ、`fetchpriority="high"` を指定して優先して読み込ませます。ファーストビューの画像すべてに指定すると、優先する画像どうしで帯域を奪い合い、肝心の画像の読み込みが早まりません。

<Baseline id="loading-lazy" />

遅延読み込みは、通信やデコードの仕事をなくすのではなく、あとへ先送りするだけです。先送りした先がスクロールや操作の最中だと、通信、デコード、レイアウトの処理が同じ時間に重なり、操作への応答（INP）や体感を悪くすることがあります。ページ内のすべての `<img>` に一括で付けると、この状態を作りやすくなります。ファーストビューの直下の画像にまで付けるかどうかは、実測で決めます。

遅延読み込みする画像や埋め込みにも、`width` と `height` の属性か `aspect-ratio` で場所を確保しておきます。確保しないと、読み込んだ瞬間にレイアウトがずれます。場所を確保する書き方と、読み込むまでの箱に背景色を付ける書き方は、「[16-1 画像の配置と比率](/decoration/images/)」で説明しています。なお、遅延読み込みの画像で `sizes` を自動で決める `sizes="auto"` は、Safariが対応していません。

## decoding 属性

`<img>` には `decoding="async"` を指定せず、デフォルトの `auto` に任せます。`decoding` は、画像のデコードをほかの内容の表示とそろえるか（`sync`）、待たずにほかの内容を表示するか（`async`）を伝えるヒントで、`auto` ならブラウザが選びます。キャッシュのない通常の読み込みでは、`sync` と `async` に目立った性能の差はありません。一方、キャッシュのある状態で `async` を指定すると、画像以外を先に表示して画像をあとから描くので、画面がちらつきます。
