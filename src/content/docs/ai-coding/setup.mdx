AIにCSSを書かせる前に、2種類の規約を読ませます。1つは本書のルールで、スキルかMCPサーバーで読ませます。もう1つはプロジェクトの判断基準で、`CLAUDE.md` のような、AIが作業のたびに読む指示のファイルに書きます。

指示のファイルには、本書のルールを写しません。本書のルールはIDで参照し、書くのは、選択肢があるときにこのプロジェクトがどちらを選ぶかと、本書と違う独自の規約だけです。既存のプロジェクトでは、書き足す前に、AIにCSSの構成を説明させ、自分の理解とのずれを直します。

## 書く前にルールを読ませる理由

AIが学習した知識は、学習した時点で止まっています。「`@scope` はまだ使えない」のように、その後に対応が進んだ機能を未対応とみなすことがあります（「[20-7 AIが誤りやすいパターン](/ai-coding/pitfalls/)」）。また、`scoped` のルートのクラスや `--_density` のフラグのような本書の規約は、学習したコードにほとんど含まれていません。

本書の規約とプロジェクトの判断基準を伝えるため、AIには書く前に関係するルールを読ませます（`ai-read-rules-first`）。読ませなければ、AIは本書の規約を知らないまま書きます。

## 本書のスキルとMCPサーバー

本書は、AIのコーディングエージェントに参照させるドキュメントを兼ねています。そのために、ルールはすべて1か所のデータ（YAMLのファイル）で管理しています。各ページの「ガイドライン」、付録A「[ルール一覧](/appendix/rules/)」、AI向けのスキルとMCPサーバーは、どれも同じデータから作られます。人が読むルールとAIに渡すルールは食い違いません。

AIが古い書き方や誤った書き方をしがちなルールには、印を付けています。ページのガイドラインでは「AIが生成するコードで誤りやすいルールです」という注意が表示されます。スキルでは、こうしたルールを1件1行の一覧にまとめ、CSSを書く前に必ず読ませています。

本文の書き方にも、AIが読むことを前提にした約束があります。各ページは単体で意味が通るように書き、ほかのページに触れるときはリンクと一言の要約を添えます。ブラウザの対応状況のように時間で変わる記述は、確かめたブラウザとツールの版を「[本書の読み方](/introduction/how-to-read/#確認した環境)」にまとめます。コードを省略するときは `/* ... */` と書き、推奨のコード例はすべてStylelintで検証しています。

AIツール向けの配布物は、スキル、MCPサーバー、`llms.txt` の3つです。Claude Codeでは、プラグインを1つ入れると、スキルとMCPサーバーの両方が使えます。Cursor、Codex、GitHub Copilotのようなほかのツールにも、スキルとMCPサーバーを設定できます。スキルとMCPサーバーは提供に向けて準備中で、いま使えるのは `llms.txt` です。提供の状況とツールごとの設定方法は、付録J「[AIツールで使う](/appendix/ai-tools/#提供の状況)」にまとめています。

どの形で読ませても、AIにさせることは同じです。書く前に関係するルールを引き、書いた後に検査し、判断の根拠をルールのIDで示させます。スキルは、手順と章の索引を最初に読み込み、ルールは必要な章のファイルだけを開きます。MCPサーバーがあれば、AIはルールを語句や章で検索し、書いたCSSを本書のStylelintの設定で検査できます。

ただし、MCPサーバーの検査で見つかるのは、Stylelintで確かめられるルールの違反だけです。検査を通ったことは、ルールを守っていることの証明にはなりません。lintを通っても残る誤りの例は「[20-8 生成したコードを確かめ、教訓を残す](/ai-coding/verify-output/)」で示します。AIへの指示でも、「`no-vw-vh` に従って」のようにルールのIDで伝えると、どのルールのことかが正確に伝わります。

## `CLAUDE.md` に書くこと

プロジェクトの事情は、本書のスキルとは別の文書に書きます。Claude Codeは、プロジェクトの `CLAUDE.md` を作業のたびに読みます。`CLAUDE.md` がなければ、条件によっては代わりに `AGENTS.md` を読みます（条件は付録J「[AIツールで使う](/appendix/ai-tools/)」）。Codex、Cursor、GitHub Copilotは `AGENTS.md` を読みます。複数のツールを使うチームでは、内容を `AGENTS.md` へまとめます。`CLAUDE.md` も置く場合は、`@AGENTS.md` で読み込み、同じ内容を2か所で持たないようにします。

書くのは、選択肢があるときの判断基準です。「あなたはCSSの専門家です」という役割の指定だけでは、採用する規約もプロジェクト固有の判断基準も伝わりません。選択肢があるときに何を基準に選ぶかを、具体的に書きます。たとえば、ブレイクポイントをいくつ置くか、トークンにない値をその場に書くかトークンを足すか、どの幅で確かめるかは、プロジェクトごとに答えが違います。これらを書いておかなければ、AIはその場で選び、選んだ理由も残りません。

本書のルールで足りることは、IDで参照し、本文を写しません。写すと、本書の版が上がってルールが変わったときに、`CLAUDE.md` の文面だけが古いまま残ります。本書と違う規約を採るときは、どのルールより優先するかが分かるように、ルールのIDと理由を添えます。CSSに関わる部分の例を、次に示します。

私が案件で使っているテンプレートでは、`CLAUDE.md` にコマンド、ディレクトリの構成、検証の手順を書き、CSSの規約は単位、不要な記述、コンポーネントの設計のように、話題ごとのファイルに分けています。CMSの案件では、ネストやモーションの規約を書き足し、「下位の手段を選ぶときは、上位の手段で満たせない理由を説明する」のように、AIに判断の理由を求める書き方もしています。

指示のファイルは、書き足すだけでなく、要らなくなった指示を消すことも必要です。モデルの版が上がると、以前は書かなければ守れなかった指示を、書かなくても守れるようになることもあります。古い指示が残ると、読ませる量が増えるうえに、新しい規約と食い違う指示が混ざります。見直す機会は、タスクを終えるときに設けます（「[20-8 生成したコードを確かめ、教訓を残す](/ai-coding/verify-output/)」）。

## `DESIGN.md` に値で表せない判断を書く

トークンのファイルから分かるのは、使える値の一覧です。どの値をどこに使うかは、トークンからは読み取れません。たとえば、accentの色のトークンがあっても、それをリンク、フォーカスリング、選んだ状態にだけ使うという判断は、トークンのファイルのどこにも書かれていません。この判断を知らないAIは、目立たせたいボタンの背景にもaccentを使います。値はすべてトークンで書かれていてlintも通るので、この食い違いは検査では見つかりません。

こうした値で表せない判断は、`DESIGN.md` に書いてAIに読ませます（`design-md-without-values`）。書くのは、色の役割と使う場面、文字の役割の使い分け、面と角丸の使い分け、部品の種類と変種です。値は書かず、トークンを名前で参照します。色、文字サイズ、余白、角丸の値はトークンのファイルを正本にします（「[10-4 デザイントークン](/components/design-tokens/)」）。値を2か所で持つと、トークンを変えたときに文章の側だけが古いまま残り、AIがどちらに従えばよいかが決まらなくなるからです。名前の参照も古くなることはありますが、なくなった名前は検索すれば見つかります。

`CLAUDE.md` と分けるのは、読ませる場面が違うからです。`CLAUDE.md` は作業のたびに読まれるので、トークンのファイルの場所と、トークンにない値をどう扱うかのように、どの作業にも要る判断基準だけを書き、短く保ちます。`DESIGN.md` は、UIを書く前とplanを書く前に読ませ、そのことを `CLAUDE.md` に1行で書きます。

節の立て方は、Google Labsが公開しているDESIGN.mdの仕様から借ります。借りるのは、Overview、Colors、Typography、Layout、Elevation & Depth、Shapes、Components、Do's and Don'tsの8つの見出しです。見出しをそろえておけば、プロジェクトが変わっても、どの節に何を書くかで迷いません。ただし、この仕様は、YAMLのfront matterに色や文字の値を書き、その値を正本として扱います。front matterは省けるので、本書ではfront matterを書かず、見出しの構成だけを借ります。仕様はまだalpha（試験的な段階）で、見出しや書式が変わることもあります。

## 既存のプロジェクトで最初にすること

すでにCSSがあるプロジェクトでAIに書かせ始めるときは、最初の作業として、AIにCSSの構成を説明させます。説明させる項目は、レイヤーの順番、トークンの置き場所と名前の付け方、コンポーネントの命名とスコープの書き方、ブレイクポイントとコンテナサイズクエリの使い方です。

```md title="AIへの依頼の例"
このリポジトリのCSSの構成を説明してください。レイヤーの順番、トークンの置き場所と名前の付け方、コンポーネントの命名とスコープの書き方、ブレイクポイントとコンテナサイズクエリの使い方を、根拠になるファイルのパスを添えて説明し、本書のルールと違う点を挙げてください。コードは変更しないでください。
```

説明を読んで、自分の理解と違う点があれば、どちらが正しいかをコードで確かめます。AIの説明が誤っていれば、誤解の元になった箇所を `CLAUDE.md` に書きます。自分の理解が誤っていれば、そのまま学べます。本書と違う規約が見つかったら、本書に合わせるか、プロジェクトの規約として残すかを決め、残すものを `CLAUDE.md` に書きます。

この作業を飛ばすと、AIは新しいコンポーネントを、既存の規約を確かめないまま書きます。デザインに合わせることだけを追って、既存のコンポーネントの書き方と違うスコープの書き方を持ち込む、といった手戻りが起きます。本書の規約を既存のサイトにどの範囲から入れるかは、「[19-6 既存のサイトに段階的に導入する](/operations/adoption/)」で説明しています。

## lintと、許可とフック

規約のうち機械的に判断できるものは、Stylelintで検査します。AIには、CSSを変えたらlintを実行させ、エラーを消すためにルールを無効にすることを禁じます（`no-disabling-to-silence`）。本書の設定と、プロジェクトへの入れ方は「[19-1 Stylelintでルールを守る](/operations/stylelint/)」で説明しています。

Claude Codeの許可の設定（`.claude/settings.json` の `permissions`）では、読むだけのツールを許可しておくと、作業のたびに確認を求められる回数が減ります。たとえば、FigmaのMCPサーバーのデザインを読むツールや、本書のMCPサーバーのツールは、ファイルを書き換えないので許可してかまいません。`mcp__<サーバー名>` と書くとそのサーバーのすべてのツールを、`mcp__<サーバー名>__<ツール名>` と書くと1つのツールを許可します。サーバー名は、MCPサーバーを登録したときの名前です。

```json title=".claude/settings.json（抜粋）"
{
  "permissions": {
    "allow": [
      "mcp__recss-guideline",
      "mcp__figma__get_design_context",
      "mcp__figma__get_screenshot"
    ]
  }
}
```

取り返しのつかない操作には、フックで確認を挟みます。フックは、ツールを使う前後に、決めたコマンドを実行する仕組みです。私の案件では、AIが作業の途中で、ローカル環境の管理者のパスワードを無断で変えたことがありました。それ以来、パスワードを変えるコマンドを実行する前に、必ず人の確認を求めるフックを入れています。人が書いたファイルをAIの書き込みから守るフックは、「[20-4 タスクの単位で進める](/ai-coding/tasks/)」で示します。
