AIが生成するCSSには、繰り返し現れる誤りがあります。本書では、こうした誤りに当たるルールへ「AIが誤りやすい」の印を付け、CSSを書く前の段階でスキルから読ませています。誤りは、書き方そのものの誤り、本書の前提と食い違う古い知識、レイアウトの手法の偏り、デザインツールの出力から生じる誤りの4つに分けられます。これとは別に、状態や条件の見た目を書き落とす型もあります。

型を知っておくと、AIの出力をレビューするときに、どこを重点的に見ればよいかが分かります。lintで見つかるものもありますが、多くはlintを通るので、レビューで確かめます（「[20-8 生成したコードを確かめ、教訓を残す](/ai-coding/verify-output/)」）。

## 書き方の誤り

本書で「AIが誤りやすい」の印を付けたルールのうち、書き方そのものの誤りは、大きく5つに分けられます。1つ目は、古い単位と記法です。`vh` や `vw`、`rgba()`、`display: flex` の1値の構文、`transform: translateX()`、`min-width` のメディアクエリなどです。

2つ目は、詳細度で解決しようとする書き方です。上書きが効かない原因を調べずに `!important` を足したり、セレクタを重ねたりします。原因の宣言を確かめてから直させる手順は、「[19-4 表示の崩れを開発者ツールで調べる](/operations/devtools/)」で説明しています。

3つ目は、不要な指定です。何にでも `width: 100%` を付ける、中央寄せに `margin: 0 auto` を使う、リセットCSSが済ませているリストの `padding: 0` を書き直す、といったものです。Tailwind CSSを使うと、`w-full` や `h-full` がとくに乱用されがちです。4つ目は、アクセシビリティを損なう指定で、`outline: none` や `list-style: none` が代表です。

5つ目は、仕組みの理解が必要な機能の誤用です。名前のないコンテナ、コンテナにした要素そのものを条件にしたクエリ、クエリの条件の中の `var()`、Sassの書き方をまねた `&__title` がこれに当たります。CMSのテーマに `@layer` を持ち込むのも、この仲間です。フラグを宣言した要素が、自分のフラグをスタイルクエリで問い合わせる誤りもあり、lintを通るので計算値で確かめます（「[20-6 実装と検証を回す](/ai-coding/implementation/)」）。

## 本書の前提と食い違う古い知識

AIの知識は学習した時点で止まっているので、その後に変わった前提を古いまま持ち込むことがあります。1つ目は、「`@scope` はまだ使えない」という知識です。AIはこれを理由に、BEMの長いクラス名やCSS Modulesを選びがちです。{/* 要確認: 出典なし */}`@scope` の基本の動作はSafari 17.4で対応していて、機能全体も2026年3月にBaselineの「新しく利用可能」になりました。本書の対象のブラウザはすべて対応しているので、コンポーネントは `@scope` で書きます（`scope-with-donut`）。

<Baseline id="scope" />

2つ目は、Tailwind CSSのユーティリティだけで組み、コンポーネントのクラスを書かない前提を持ち込むことです。{/* 要確認: 出典なし */}本書では、コンポーネントはクラスと `@scope` で作り、ユーティリティは `.-visually-hidden` のような単機能のクラスに限ります（`utility-single-purpose`）。私のテンプレートのAI向けの規約でも、明示的な要求がない限りTailwind CSSやCSS-in-JSは使わないと定めています（`no-unrequested-css-framework`）。

3つ目は、アンカーポジショニングやView Transitionsを「未対応」とみなし、位置の計算や画面の切り替えをJavaScriptで作り直すことです。{/* 要確認: 出典なし */}`anchor-name` は2026年1月に、同じページの中のView Transitionsは2025年10月に、主要なブラウザの最新版がそろいました。本書の対象のSafari 18系でアンカーポジショニングが使えないのは事実です。それでも、未対応の環境向けの表示をCSSで用意すれば、プログレッシブ・エンハンスメントとして使えます（[11-8 アンカーポジショニング](/layout-practice/anchor-positioning/)、[18-11 View Transitionsで画面の切り替えをつなぐ](/motion/view-transitions/)）。「未対応」という判断は、対応状況を確かめてから受け入れます（`verify-support-claims`）。

4つ目は、レイヤーを使うプロジェクトで、`@layer` の外にスタイルを書くことです。レイヤーに入っていないスタイルは、詳細度に関係なくすべてのレイヤーに勝つので、決めたレイヤーの順番が崩れます（`no-unlayered-styles`）。CMSのテーマに `@layer` を持ち込む誤りとは反対の向きですが、どちらもレイヤーの外のCSSが最も強いという仕組みを知らないことから起きます。詳しくは「[4-3 カスケードレイヤーで順位を決める](/cascade/layers/)」で説明しています。

## レイアウトの手法の偏り

書き方の誤りとは別に、レイアウトの手法の選び方にも偏りがあります。AIは、配置をFlexboxで組み、要素を重ねるときは `position: absolute` を選びがちです。学習したコードにその書き方が多いからだと私は考えています。結果として、Gridなら親の1か所で決まる配置が、子要素の幅の計算に散らばります。

レイアウトを書かせるときは、先に「配置は `grid-template-areas` で定義し、エリアに名前を付ける」と指示します（`ai-layout-with-grid-areas`）。エリアの名前が付いた配置は、生成されたコードを読む側にとっても、デザインカンプと見比べやすくなります（[7-8 Gridの基礎](/layout/grid-basics/)）。

## デザインツールの出力に由来する誤り

Figmaのようなデザインツールの出力を経由すると、誤りの型が増えます。代表は、幅と高さを固定すること、オートレイアウトの外の要素を絶対配置の座標で置くこと、出力のTailwindのクラスやカンプの値をそのまま書くことの3つです。どれも、カンプの1つの幅と1つの内容でしか成り立たない書き方で、見出しが長くなる、狭い置き場所に置かれる、といった変化で崩れます（`no-verbatim-design-output`）。

これらは、lintでは一部しか見つかりません。本書の設定では、`width` や `height` は論理プロパティを使うよう警告されますが、自動修正で `inline-size` に直すと、固定の値は規約に沿った見た目のまま残ります。`position: absolute` と座標の組み合わせは、lintでは誤りと判定できません。デザインの値を、書く前にトークンへ対応づけさせる進め方は、「[20-5 Figmaのデザインから計画を立てる](/ai-coding/from-figma/)」で説明しています。

デザインに合わせることだけを追うと、既存のコンポーネントの規約を確かめずに書くことも起きます。たとえば、既存のコンポーネントとは違うスコープの書き方や命名で、新しいコンポーネントを書きます。既存のプロジェクトでは、書き始める前の段階で、CSSの構成をAIに説明させて規約を確かめさせます（「[20-2 AIに読ませる規約を用意する](/ai-coding/setup/)」）。

## 書き落としやすい状態と条件

ここまでの型は、書いたコードの誤りでした。AIの出力には、書くべきものが抜けているという型もあります。カンプとbriefに描かれた1つの状態と1つの内容だけを実装し、ほかの状態と条件の見た目を書かずに終えるものです。書かれていないコードはlintで見つからず、表示を確かめても、その状態を再現しなければ気付きません。

抜けやすいのは、次の4つです。1つ目は、`:focus-visible` の見た目です。ホバーの見た目だけを書き、キーボードで操作したときに何も変わらないことがあります（「[17-1 ホバーとフォーカスを表す](/interaction/states-and-focus/)」の `hover-with-focus-visible`）。2つ目は、無効の状態です。ホバーのセレクタを `&:enabled:hover` に絞らず、押せないボタンでもホバーで見た目の変わることがあります（同じ節の `hover-operable-in-any-hover`）。

3つ目は、内容と文字サイズが変わったときの表示です。カンプの長さの見出しでしか確かめず、長い単語や200%の文字サイズで、はみ出しや欠けが残ります。原因になりやすいのは、高さを `block-size` で固定する指定です（「[11-3 サイズと内容の変化に耐える](/layout-practice/defensive/)」の `min-block-size-over-fixed-height`）。確かめ方は「[19-3 表示と操作を確かめる](/operations/verification/)」の `verify-text-resize-200` にあります。4つ目は、動きを減らす設定です。トランジションやアニメーションを、`prefers-reduced-motion: no-preference` の外に書いたまま終えることがあります。書く場所は「[18-2 動きを減らす設定に対応する](/motion/reduced-motion/)」の `motion-only-with-no-preference` で決めています。

これらは、書かせる前にbriefの「デザインから読み取れないこと」で状態と内容の変化を決めておき、完了の条件に入れれば、AIが自分で確かめられます（「[20-4 タスクの単位で進める](/ai-coding/tasks/)」）。すでに書かれたCSSでは、状態を視点にした監査で、抜けている箇所を一覧にします（「[20-9 既存のCSSの監査と移行をAIに任せる](/ai-coding/audit/)」）。
