Figmaのデザインは、計画の段階で読みます。AIは、デザインの値をトークンに対応づけた「値の対応表」と、Figmaのノードを要素に対応づけた「ノードの対応表」を `plan.md` に書きます。トークンに当たらない値は例外として理由とともに書き出し、トークンに近いがずれる値は、確認事項として人に尋ねます。

承認されたplanで実装するときは、AIは値を対応表から取ります。新しい情報が必要になったら計画を見直し、Figmaを再取得して値が変わる場合も、draftに戻して承認し直します。値の判断は、planのレビューで人が確かめます。また、planの手順には触るファイルと影響範囲を書かせ、トークンやベーススタイルのように全ページに及ぶ変更は、その手順の前に人が確かめた記録を残します。

````md title="tasks/article-cards/plan.md（抜粋）"
## 懸念・確認事項

### Q1. 広い形の見出しの文字の大きさ

- 宛先：デザイナー
- Figma の値は19px。最も近いトークンは title（20px）
- 選択肢：A. title で書く／B. 19px を例外として直接書く
- 推奨：A。一覧のほかの見出しと同じ役割で、1px の差に意図があるかは Figma からは読み取れない
- 回答：A（デザイナーに確認済み）
````

このplanでは、実装に使う値がすべて表に出ています。例外は、サムネイルの幅の1つだけで、トークンにしない理由が書いてあります。見出しの19pxは、トークンの20pxに近いがずれる値なので、AIは推測で選ばず、確認事項にしています。

レビューする人は、表の「書く値」の列と、例外の理由を読めば、デザインの値がどう扱われるかを確かめられます。実装が始まってから値の扱いを指摘するより、ここで指摘するほうが、直す範囲は小さく済みます。

## Figmaを読む手順

AIにFigmaを読ませる手順は、4つの段階に分かれます。大きなフレームを一度に読ませると、出力が長くなり、細部の値を省いて返すことがあるからです。

1つ目は、`get_metadata` でフレームの中のノードの一覧を取り、カードの広い形と狭い形のように、読む単位に分けることです。2つ目は、ノードごとに `get_design_context` で、並び方と値を読むことです。出力はReactとTailwind CSSのコードなので、AIには、クラスに書かれた値（`gap-[20px]` の20pxなど）を読み取らせ、値の対応表に写させます。一覧のように同じ部品が並ぶフレームでは、部品の数だけ同じマークアップが展開されるので、1つのノードだけを読ませます。

3つ目は、`get_variable_defs` で、ノードが使っているFigmaの変数とスタイルを読むことです。変数の名前（`text/muted` など）が分かれば、値が同じでも、どの役割の値なのかを手がかりにトークンを選べます。4つ目は、`get_screenshot` でノードの画像を取ることです。この画像は、完了を確かめるときに見比べる基準として使います。ツールの役割は「[20-3 MCPサーバーを役割で使い分ける](/ai-coding/mcp-servers/)」で説明しています。

## 値をトークンに対応づける

デザインの値は、CSSを書く前に、対応するトークンを決めておきます（`figma-values-to-tokens`）。カンプの値を1つずつ写すと、トークンと少しずつ違う値が増えます。

```css title="🙅‍♂ Not Recommended: カンプの値をそのまま写す" issue="behavior"
/* 🙅‍♂ Not Recommended */
@scope (.scoped.article-cards) to (.scoped) {
  ._card {
    row-gap: 11px;
  }

  h3 {
    font-size: 19px;
    line-height: 26px;
  }

  time {
    color: #767676;
  }
}
```

この書き方では、`row-gap` の11pxがトークンの12pxと違うことも、見出しが19pxであることも、意図した差なのかが分かりません。文字色の `#767676` も、どの役割の色なのかが読み取れず、ダークモードで値を切り替えることもできません。同じことが別のカードでも起きると、デザインの共通のルールがコードから読み取れなくなります。

```css title="🙆‍♂ Recommended: 対応表のとおり、トークンで書く"
@scope (.scoped.article-cards) to (.scoped) {
  ._card {
    row-gap: calc(var(--spacing--xs) * 1px);
  }

  h3 {
    font-size: calc(var(--text--title--font-size) / 16 * 1rem);
    line-height: var(--text--title--leading);
  }

  time {
    color: var(--foreground--muted);
  }
}
```

対応づけの手がかりは、Figmaの変数です。`get_design_context` の出力では、変数に結び付いた値は `var(--変数名, 値)` の形で、結び付いていない値は `#171717` のような値だけで出ます。変数の名前があれば、その名前からトークンを選び、値だけのものは、`get_variable_defs` の一覧と値を突き合わせて選びます。

トークンに当たらない値は、例外として書き出します。トークンを増やすのではなく、その場に値を直接書き、planの表に理由を残します。サイト全体で意味を持つ値だけをトークンにする理由は、「[10-4 デザイントークン](/components/design-tokens/)」で説明しています。

迷うのは、トークンに近いがずれる値です。15pxと16pxのような差は、デザインの意図である場合も、Figmaでの作業の途中で生じた誤差である場合もあります。どちらかはFigmaのデータからは決められないので、AIには推測させず、確認事項として選択肢と推奨を書かせます。デザイナーに確かめる観点は「[3-1 ピクセルではなく意図を再現する](/design-reproduction/intent/)」で説明しています。

値がトークンに当たっていても、使い方が `DESIGN.md` に書いた判断と食い違うことがあります。たとえば、accentの色をボタンの背景に使っているデザインは、accentをリンクとフォーカスと選んだ状態にだけ使うという判断と合いません。この場合も、AIにはどちらかに合わせて埋めさせず、確認事項に書かせます。デザインが判断を改める意図なのか、デザインの誤りなのかは、デザイナーに確かめなければ決まらないからです。`DESIGN.md` に書くことは「[20-2 AIに読ませる規約を用意する](/ai-coding/setup/#designmd-に値で表せない判断を書く)」で説明しています。

## 出力から読み取ること、読み取らないこと

`get_design_context` の出力のうち、読み取るのは、要素の並び方と値です。Figmaのオートレイアウトは、要素を縦か横に並べ、間隔と内側の余白を指定する機能で、CSSのFlexboxやGridの考え方に近いものです。出力でも、オートレイアウトの部分は `flex flex-col gap-[20px]` のようにFlexboxと `gap` で表されるので、向きと間隔は `display: block grid` や `gap` の指定に置き換えられます。

読み取らないのは、絶対配置の座標と、固定の幅と高さです。オートレイアウトを使っていないフレームの要素は、フレームの左上からの座標で配置されていて、出力にもその座標が出ます。座標は、カンプの幅と内容でしか成り立たない値なので、計画の段階で、通常のフローやGridの並び方に読み替えます。オートレイアウトの部分の出力にも、カードの幅（`w-[380px]`）や、見出しを2行分で切る高さ（`h-[45px]` と `overflow-hidden`）、折り返しを止める `whitespace-nowrap` の混ざることがあります。どれもカンプの幅と文字数でしか成り立たないので、写しません（「[20-3 MCPサーバーを役割で使い分ける](/ai-coding/mcp-servers/)」の `no-verbatim-design-output`）。

文字は、Figmaの文字のスタイルの名前と、文字の役割のトークンを対応づけます。大きさと行の高さを別々の値として拾うと、同じ役割の見出しどうしで、値の食い違うことがあります。フォントは `Noto_Sans_CJK_JP:Regular` のようなFigmaのスタイル名で出るので、プロジェクトのフォントの指定に読み替えます。文字の役割のトークンは「[14-5 文字の役割と色](/typography/text-roles/)」で説明しています。

## 全ページに及ぶ変更を分ける

planの「触るファイル」には、ファイルごとに影響範囲を書かせます。コンポーネントのファイルの変更は、そのコンポーネントの中で閉じます。一方で、トークン、ベーススタイル、レイヤーの順番、コンポジションの変更は、そのファイルを読み込むすべてのページに及びます（`escalate-shared-changes`）。

全ページに及ぶ変更は、コンポーネントの中で閉じる変更と分けます。そして、その手順を始める前にAIを止め、人が確かめます。全ページに及ぶ変更は、作っているカードでは正しく見えても、ほかのページの見出しや余白を変えることがあります。カードのテストページだけを見ていては、その変化に気付けません。止まったときに、変える理由と影響するページを確かめれば、トークンを足すのではなく例外として書く、といった判断もその場でできます。

同じ考え方は、AIに作業を並行させるときにも当てはまります。サブエージェントに複数のコンポーネントを同時に書かせるなら、共有のファイルを触らない作業に限り、同じファイルを2つのエージェントに書き換えさせません。このルールは「[20-9 既存のCSSの監査と移行をAIに任せる](/ai-coding/audit/)」の `single-writer-per-file` です。2つの作業で同じトークンのファイルを書き換えると、後の変更で先の変更を上書きして、どちらの意図とも違う値を残すおそれがあるからです。コンポーネントの境界の考え方は「[10-2 コンポーネントの境界を守る](/components/boundaries/)」で説明しています。

## デザイナーへの確認を依頼する

確認事項のうち、デザインの意図に関わるものは、デザイナーに確かめます。AIには、確認事項ごとに宛先を書かせ、宛先がデザイナーやディレクターの問いは、`/confirm-request` で、そのまま送れる確認依頼の文面にさせます。`/task-start` も、planを書いて止まるときと、実装の途中で止まるときに、同じ手順で文面を作ります。AIは文面を作るだけで、送るのは人です。

<Code code={requestMd} lang="md" title="確認依頼のひな形" />

文面は、「[3-2 実装の前にデザイナーと確かめること](/design-reproduction/designer-questions/)」の質問の例と同じく、確かめることを1つずつ、選択肢の形で尋ねます。選ぶだけで答えられる質問は、答えるまでの時間が短く、回答をplanの回答欄にそのまま写せます。選択肢には、実装する側の推奨と理由を添えます。推奨がないと、デザイナーは実装の手間を知らないまま選ぶことになるからです。

文面には、実装の用語を使わせません。「コンテナサイズクエリの閾値」ではなく「置き場所が狭いとき」、「`gap`」ではなく「見出しと日付の間」と書かせます。対象は、FigmaのノードのURLで示し、実装を始めた後の便には、Figmaと同じ幅で撮ったいまの画面のスクリーンショットを添えます。カンプのない幅での振る舞いは、いまの見え方を見せなければ伝わりにくいからです。

1通に入れる質問は5問までにします。質問が多いほど、すべてに答えてもらえるまでの時間が延びるので、実装を止めている質問から順に入れます。宛先がディレクターの質問（文言、件数、CMSで編集する範囲）は、別の1通にします。文面は、送る人が読んで直してから、自分の質問として送ります。

回答を受け取ったら、人がplanの回答欄に貼るか、チャットでAIに伝えます。チャットで伝えた回答は、AIが回答欄と決定ログに記録してからplanに反映します。回答がbriefの「デザインから読み取れないこと」に当たるときは、人がbriefも直します。briefは完了の条件を決める文書なので、AIには直させません（「[20-4 タスクの単位で進める](/ai-coding/tasks/)」）。

回答が「未定」のこともあります。依頼文では、仮の形で進めるとは約束せず、仮の案と進め方をこちらから提案すると伝えます。仮の値を決めるのは人です。AIには、選択肢の中から仮の案を推奨と理由を添えて示させ、人が選んだ値を、値の対応表に種類「仮」として、どの問いの回答待ちかと一緒に書かせます。値の対応表が変わるので、planはdraftに戻り、人が承認し直してから実装に使います。仮の値は、完了の報告にも一覧で残させ、回答が届いたら差し替えます。

## planのレビューで見ること

planのレビューでは、4つの点を見ます。1つ目は値の対応表で、例外の理由が、トークンにしない理由として成り立っているかを確かめます。2つ目は確認事項で、回答のない問いが残っていないか、推奨の理由が妥当かを確かめます。

3つ目は触るファイルで、影響範囲が全ページに及ぶ変更が紛れていないかを確かめます。4つ目は手順で、各手順に検証が書かれ、その検証で手順の結果を確かめられるかを見ます。「スタイルを整える」のように、終わったかどうかを判定できない手順があれば、分け直させます。

4つを確かめたら、`/task-approve` で承認します。承認の後に範囲が変わったら、AIはplanをdraftに戻して止まります（「[20-4 タスクの単位で進める](/ai-coding/tasks/)」）。

## 補足と注意点

Figma MCPが使えないときもあります。認可が切れている場合や、シートの種類による呼び出しの回数の上限に達した場合です。そのときは、人がFigmaから書き出した画像と値を `refs/` に置き、AIにはそこからplanを書かせます。Figmaと突き合わせられなかった項目は、planと完了の報告に「未確認」として残させます。

画像やアイコンのような素材は、`download_assets` で取得すると、一時的なURLが返ります。URLのままコードに書くと、期限が切れた後に表示されなくなるので、ダウンロードしてリポジトリに置きます。私の案件では、書き出したSVGに背景の矩形が入っていたり、ブレンドモードが失われていたりしたことがありました。素材は、書き出した後に画面で確かめます。
