動きの負荷は、変えたプロパティのせいでブラウザがレイアウト、ペイント、合成のどこから処理をやり直すかで決まります。動かすプロパティは、合成だけで処理できる `opacity`、`translate`、`scale`、`rotate` を優先します。`clip-path`、`background-color`、`filter` は、ブラウザと値によっては描き直しを避けられる候補で、DevToolsで確かめてから使います。影を動かすときは、`box-shadow` ではなく `filter: drop-shadow()` を動かします。`inline-size` や `inset` のようにレイアウトが変わるプロパティは、ほかに方法がない場合（アコーディオンの高さなど）に限ります。

`will-change` はCSSへ書いたまま残さず、どうしても必要なときだけ、動きの直前からJavaScriptで付けて、終わったら外します。`backdrop-filter` の大きなぼかしや、継承するカスタムプロパティの毎フレームの更新のように、指定の仕方によって負荷が大きく増えるものもあります。`contain: content` のような負荷を抑える指定にも副作用があるので、効果をDevToolsで確かめてから使います。

## 同じ見た目の動きでも負荷が違う理由

ブラウザは、スタイルが変わると、レイアウト、ペイント、合成の順に処理をやり直します。レイアウトは要素の位置と大きさを計算する処理、ペイントは文字や背景や影を画素に描く処理、合成は描いた層を重ねて画面に出す処理です。どこからやり直すかは、変えたプロパティで決まります。`inline-size` を変えると、その要素と周りの要素の位置を計算し直し、描き直し、重ね直します。`color` や `box-shadow` はペイントから、`opacity` と `translate` は、条件が合えば合成だけで済みます。

処理を担うスレッドも違います。レイアウトとペイントは、JavaScriptと同じメインスレッドで行われます。合成はコンポジタのスレッドで行われるので、合成だけで済む動きは、メインスレッドがJavaScriptの処理で埋まっているときにも止まりにくくなります。たとえば、ページの読み込み中にスクリプトの実行が長引いても、`rotate` で回しているスピナーは動き続けることが多く、`inline-size` で伸びるバーは止まります。

動きを滑らかに見せるには、画面を書き換えるたびに、この処理を時間内に終える必要があります。1秒に60回書き換える画面では、1フレームに使える時間は約16ミリ秒で、120Hzの画面ではその半分です。レイアウトからやり直す動きは、要素の数が多いページや性能の低いスマートフォンでこの時間を超え、フレームが落ちてかくつきます。開発に使うパソコンでは滑らかに見えても、利用者の端末で同じとは限りません。そのため、動かすプロパティは見た目ではなく、起きる処理で選びます。

## 動かすプロパティの優先度

私は、動かす方法を次の表の優先度で選んでいます。上の段ほど負荷が小さく、下の段ほど、使う前に別の方法がないかを検討します。表では、フレームごとに描き直しが起きるか（DevToolsのPaint）と、アニメーションの進行をどのスレッドで計算するかを分けています。2つは別の性質で、描き直しが起きなくても、進行の計算がメインスレッドに残る場合があるからです。

| 優先度 | 方法 | フレームごとの描き直し | 進行を計算するスレッド |
| --- | --- | --- | --- |
| 高 | `opacity`、`translate`、`scale`、`rotate`、これらを動かすスクロール駆動アニメーション | 起きない | コンポジタ |
| 確かめて使う | `clip-path`、`background-color`、`filter` の `brightness()` など | 値によっては起きない（Chrome） | 値によってはコンポジタ（Chrome） |
| 確かめて使う | `filter` の `drop-shadow()`、`blur()` | 起きない（Chrome） | メイン（Chrome） |
| 中 | JavaScriptから毎フレーム変形や不透明度を更新する方法 | 起きない | メイン |
| 中 | FLIP | 測るときに1回レイアウトが起き、再生中は起きない | 再生をトランジションやWeb Animations APIで行えばコンポジタ |
| 低 | `color`、`border-color`、`box-shadow` など | 起きる。負荷は描く面積による | メイン |
| 避ける | `inline-size`、`block-size`、`padding`、`inset` など | レイアウトから起きる | メイン |
| リスク大 | 大きな `blur()` や `backdrop-filter`、巨大な合成レイヤー、グローバルなカスタムプロパティの毎フレームの更新、`scrollTop` を毎フレーム読む実装 | 条件しだいで大きく重くなる | 条件による |

優先度が高いのは、主要なブラウザで合成だけで動かせる `opacity` と変形です。スクロール駆動アニメーションも、動かすのが `opacity` や変形なら、スクロールの位置に合わせてコンポジタのスレッドで処理できます。`clip-path`、`background-color`、`filter` は、従来はペイントが起きるプロパティでした。Chromeでは、これらのアニメーションでも描き直しを避けられる場合がありますが、ブラウザと値によって結果が変わるので、基本の候補とは分けています。{/* 要検証: ブラウザ。Firefox と Safari で、clip-path、background-color、filter のアニメーションで描き直しが起きるか、進行がコンポジタのスレッドに移るか */}

Chromeで、それぞれを1秒間トランジションさせ、パフォーマンスのトレースで描き直し（Paint）の回数と、アニメーションがコンポジタのスレッドに移ったかを調べました。`clip-path`、`background-color`、`filter` の `brightness()`、`drop-shadow()`、`blur()` は、動き出すときの数回を除いて描き直しが起きませんでした。`box-shadow` と `color` は毎フレーム描き直されました。進行がコンポジタのスレッドに移ったのは、`clip-path`、`background-color`、`brightness()` です。`drop-shadow()` と `blur()` は、描き直しは起きませんが、進行の計算はフレームごとにメインスレッドで行われました。Chromiumの実装には、画素を移動するフィルター（`drop-shadow()`、`blur()` など）をコンポジタでアニメーションさせない判定があるからです。そのため、メインスレッドが詰まると止まる点が、`opacity` や変形と違います。

ここでいう描き直しは、DevToolsのPaintに記録される、メインスレッドで画素を描く処理のことです。描き直しが起きなくても、GPUの側でフィルターを当てる処理は毎フレーム行われるので、`filter` の負荷がなくなるわけではありません（後の見出しの「`filter` と `backdrop-filter` のコスト」）。

同じ版で、角丸を付けた切り抜きを大きさ0から動かす場合（`inset(0 100% 0 0 round 12px)` から `inset(0 round 12px)` へ）は、毎フレーム描き直しが起き、進行もメインスレッドで計算されました。角丸のない `inset()` や、0にならない範囲の間で動かす場合は、描き直しは起きませんでした。切り抜きを動かしたら、後の見出しで説明するPaint flashingを使って確かめます。

中の段の1つ目は、JavaScriptで毎フレーム値を計算し、変形や不透明度として反映する方法です。値の計算はメインスレッドで行われますが、レイアウトとペイントは起きません。FLIPは、変化の前後で要素の位置を測り、その差を `translate` と `scale` で打ち消してから、打ち消しを解いて動かす方法です。位置を測るときに一度だけレイアウトが起きますが、動いている間は変形しか変わらず、打ち消しを解く動きをトランジションやWeb Animations APIで再生すれば、進行はコンポジタのスレッドで計算されます。

ペイントが起きるプロパティは、負荷が描く面積で決まります。ボタンのホバーで文字色を変えるような、小さい要素の短い変化なら問題になりません。避けたいのは、大きくぼかした `box-shadow` を動かすことです。ぼかしを含む影は描くのに時間がかかり、動いている間は描き直しが続きます。影を動かすときは、`box-shadow` の代わりに `filter: drop-shadow()` の値を動かします。`drop-shadow()` と `box-shadow` の見た目の違いと、影のトークンとの関係は「[16-5 面・影・角丸](/decoration/surfaces/)」で説明しています。

レイアウトが起きるプロパティは避けますが、アコーディオンの高さのように、ほかに方法のない場合は例外です。開閉の動きは「[18-7 出現と退場](/motion/entry-and-exit/)」で扱います。`scrollTop` を毎フレーム読む実装を避ける方法は「[18-9 スクロールに合わせて動かす](/motion/scroll-driven/)」で扱います。

## 位置を変形で動かす

下へスクロールしたとき、固定ヘッダーを隠す動きで比べます。次の例は、ヘッダーの `inset-block-start` を動かして画面の外に出しています。見た目は意図どおりに動きますが、`inset-block-start` を変えるとレイアウトが起きるので、毎フレーム位置の計算と描き直しが行われます。隠す量にヘッダーの高さを書く必要もあり、高さが変わるたびに値を直さなければなりません。

```css title="🙅‍♂ Not Recommended: inset-block-start を動かして隠す" issue="behavior"
/* 🙅‍♂ Not Recommended */
@scope (.scoped.site-header) to (.scoped) {
  :scope {
    @media (height >= calc(600 / 16 * 1rem)) {
      position: sticky;
      inset-block-start: 0;
    }

    @media (prefers-reduced-motion: no-preference) {
      transition-duration: var(--duration--base);
      transition-property: inset-block-start;
      transition-timing-function: var(--ease--in-out-quint);
    }

    &[data-hidden="true"] {
      inset-block-start: -4rem;
    }
  }
}
```

同じ動きは `translate` で作れます。`translate` の割合は要素自身の大きさが基準なので、`-100%` と書けば、ヘッダーの高さが変わっても全体を隠せます。トランジションの間は変形しか変わらないので、合成だけで動きます。すでに画面にあるものを動かすので、イージングはease-in-out系にしています（「[18-3 イージングと再生時間](/motion/easing-and-duration/)」）。ヘッダーを固定するのは、ビューポートの高さが十分なときだけです（「[11-7 固定ヘッダー](/layout-practice/sticky-header/)」）。

```css title="🙆‍♂ Recommended: translate を動かして隠す"
@scope (.scoped.site-header) to (.scoped) {
  :scope {
    @media (height >= calc(600 / 16 * 1rem)) {
      position: sticky;
      inset-block-start: 0;
    }

    @media (prefers-reduced-motion: no-preference) {
      transition-duration: var(--duration--base);
      transition-property: translate;
      transition-timing-function: var(--ease--in-out-quint);
    }

    &[data-hidden="true"]:not(:focus-within) {
      @media screen {
        translate: 0 -100%;
      }
    }
  }
}
```

隠す条件には `:not(:focus-within)` を加え、ヘッダーの中のリンクにキーボードでフォーカスが移ったときは画面に戻します。隠したまま画面の外でフォーカスを受けると、どこにフォーカスがあるのか見えなくなるからです。印刷ではスクロールの向きに意味がないので、隠す指定は `@media screen` に限ります。

変形は、`transform` の関数ではなく、`translate`、`rotate`、`scale` の個別のプロパティで書きます。変形ごとに値を変えられ、トランジションの対象も `transition-property: translate` のように動かす変形だけに絞れるからです。理由の詳細は「[9-8 モダンな記法にそろえる](/notation/modern-syntax/)」で説明しています。合成で処理されるのは、`transform` でも個別のプロパティでも同じです。

<Baseline id="individual-transforms" name="個別の変形プロパティ" />

ただし、次の場合は `transform` を使ってかまいません。個別のプロパティは常に移動、回転、拡大・縮小の順に適用されるので、「回転してから、回転した向きに移動する」ように順番を変えたい場合です。`skewX()` のように個別のプロパティがない変形と、X軸とY軸の回転を重ねるような3Dの複合指定も、`transform` で書きます。`rotate` プロパティは1つの軸の回転しか表せないので、2つの軸の回転を重ねるには `transform` に関数を並べるしかありません。

```css title="🙆‍♂ Recommended: 2つの軸の回転を重ねるときは transform で書く"
@scope (.scoped.flip-card) to (.scoped) {
  :scope {
    transform: perspective(800px) rotateX(8deg) rotateY(-16deg);
  }
}
```

## `filter` と `backdrop-filter` のコスト

`filter` は、ハードウェアで高速化される場合があっても、負荷が低いわけではありません。`blur()` は、ぼかしの半径が大きいほど、1つの画素を求めるために参照する周りの画素が増えます。`filter` を動かすと、この計算が毎フレーム行われます。半径の小さい `blur()` で短く動かす程度なら許容できますが、ぼかしの半径そのものを大きく変化させるアニメーションは避けます。目安として、動かす要素に掛けるぼかしは数pxにとどめ、止まっている要素でも半径は20px未満にします。{/* 要確認: 出典なし。20px未満という目安 */}クロスフェードの重なりを目立たなくするために、切り替わる要素へ小さなぼかしを掛ける方法は「[18-5 トランジションを応用する](/motion/transition-techniques/)」で説明しています。

`backdrop-filter` は、さらに負荷が大きくなりがちです。要素の背後に描かれているものを毎回取り込んでからぼかすので、背面の面積全体を描き直すことになります。背後の内容がスクロールで動くだけでも、ぼかしの計算はやり直されます。大きな要素やモーダルの背景で画面全体をぼかすと、性能の低い端末ではスクロールが滑らかでなくなることもあります。

そのため、次の条件が重なる使い方を避けます。ぼかしの半径が大きい、ぼかす面積が広い、ぼかしを掛けた要素そのものが動いている、複数のエフェクトが重なっている、の4つです。たとえば、すりガラスのパネルをスライドさせながら表示したい場合は、ぼかしを掛けたまま動かさず、背景を不透明な色にして動かし、止まってからぼかしに切り替える方法があります。{/* 要確認: 出典なし。止まってからぼかしに切り替える方法 */}すりガラスの背景の作り方と、ぼかしに混ざる範囲の注意点は「[16-5 面・影・角丸](/decoration/surfaces/)」で説明しています。

## カスタムプロパティを毎フレーム更新するとき

ポインターに追従する光の効果のように、JavaScriptからカスタムプロパティを毎フレーム書き換える実装があります。このとき、値を `:root` のようなグローバルな場所に書き込むと、ページ全体のスタイルが毎回計算し直されます。登録していないカスタムプロパティは継承するので、ルートの値が変わると、その値を受け継ぐすべての子孫の要素が、計算のやり直しの対象になるからです。

```js title="🙅‍♂ Not Recommended: ポインターの位置をルートのカスタムプロパティに書き込む" issue="behavior"
/* 🙅‍♂ Not Recommended */
document.addEventListener('pointermove', (event) => {
  document.documentElement.style.setProperty('--pointer-x', `${event.clientX}px`);
  document.documentElement.style.setProperty('--pointer-y', `${event.clientY}px`);
});
```

値は、それを使う要素だけに書き込みます。さらに、`@property` で `inherits: false` を指定して登録し、子孫に値を受け継がせないようにします。こうすると、値が変わっても計算し直すのはその要素だけです。名前は公開プロパティの形にしています。`@property` の登録は文書全体に及ぶので、内部用の短い名前で登録すると、同じ名前を別の意味で使うほかのコンポーネントにも型が適用されるからです（「[18-5 トランジションを応用する](/motion/transition-techniques/)」）。

```css title="🙆‍♂ Recommended: ポインターの位置を、継承しないカスタムプロパティで受ける" from="motion/spotlight"
@property --spotlight--x {
  syntax: "<length>";
  inherits: false;
  initial-value: 0;
}

@property --spotlight--y {
  syntax: "<length>";
  inherits: false;
  initial-value: 0;
}

@scope (.scoped.spotlight) to (.scoped) {
  :scope {
    --_glow: color-mix(in oklab, var(--foreground--base) 15%, transparent);

    background-image: radial-gradient(circle 160px at var(--spotlight--x) var(--spotlight--y), var(--_glow), transparent);
  }
}
```

```js title="ポインターの位置を、使う要素だけに書き込む JavaScript の例"
const spotlight = document.querySelector('.scoped.spotlight');
let rect = null;

// スクロールやリサイズで位置が変わったら、測った値を捨てる
const clearRect = () => {
  rect = null;
};
document.addEventListener('scroll', clearRect, { capture: true, passive: true });
window.addEventListener('resize', clearRect);

spotlight.addEventListener('pointermove', (event) => {
  rect ??= spotlight.getBoundingClientRect();
  spotlight.style.setProperty('--spotlight--x', `${event.clientX - rect.left}px`);
  spotlight.style.setProperty('--spotlight--y', `${event.clientY - rect.top}px`);
});
```

要素の位置は一度測ったら使い回し、`pointermove` のたびには測りません。`getBoundingClientRect()` は、まだレイアウトに反映されていない変更があると、その場でレイアウトを計算させます。ポインターの動きのたびに測ると、ページのほかの処理で寸法が変わっていた場合に、この計算を何度も強制することになります。

`getBoundingClientRect()` が返すのはビューポートを基準にした位置なので、スクロールやリサイズのあとは測った値が古くなります。そのため、`scroll` と `resize` で測った値を捨て、次の `pointermove` で測り直します。スクロールする祖先の要素が `window` 以外のこともあるので、`scroll` はキャプチャで `document` に登録します。上にある内容が増えて位置がずれる場合は、この方法でも追従できないので、位置の変わらない要素に使います。

なお、この効果は背景のグラデーションを描き直すので、ペイントは毎回起きます。面積の大きい要素に使うと負荷が増えるので、カードのような小さい要素に限ります。

次のデモは、上のCSSとJavaScriptをそのまま使っています。カードの上でポインターを動かすと、光がポインターに追従します。開発者ツールでカードの中の段落を調べると、`--spotlight--x` は継承されず、初期値の `0px` のままです。

動かすカスタムプロパティは `inherits: false` で登録し、`opacity` や `translate` だけを動かすならカスタムプロパティを介しません。この2点は、ルール [`animated-property-no-inherit`](/components/custom-properties/#rule-animated-property-no-inherit) で定めています。理由は「[10-5 公開プロパティと内部プロパティ](/components/custom-properties/)」で説明しています。

## `will-change` は動いている間だけ付ける

`will-change` は、これから変わるプロパティをブラウザに予告する指定です。`will-change: translate` と書くと、ブラウザは動き出す前にその要素を合成レイヤーに分けて準備します。動き出す瞬間にレイヤーを作る処理が間に合わず、最初の数フレームがかくつく場合に、この準備が役に立ちます。

しかし、CSSへ書いたまま残すと逆効果になります。合成レイヤーは、要素ごとに描いた画像をGPUのメモリで保持するので、動いていない間もメモリを使い続けます。カードの一覧のように多くの要素に指定すると、不要なレイヤーが大量に作られ、かえって描画が遅くなったり、スマートフォンでメモリが不足したりします。また、`will-change: translate` のように書いただけで、その要素は固定配置の子孫の包含ブロックになり、スタッキングコンテキストも作ります（「[7-10 positionの基礎](/layout/positioning/)」）。

そのため、`will-change` は原則として使いません。個別の変形や `opacity` のトランジションは、指定しなくても動き出すときに合成レイヤーが作られます。かくつきをDevToolsで確かめ、どうしても必要な場合だけ、動きの直前にJavaScriptで付け、終わったら外します。次の例は、パネルを開閉する直前に `will-change` を付け、トランジションが終わったら外しています。

```js title="動きの直前に will-change を付け、終わったら外す JavaScript の例"
const panel = document.querySelector('.scoped.side-panel');
const button = document.querySelector('[aria-controls="side-panel"]');
const motionQuery = window.matchMedia('(prefers-reduced-motion: no-preference)');

const removeWillChange = (event) => {
  if (event.target !== panel || event.propertyName !== 'translate') return;
  panel.style.removeProperty('will-change');
};

panel.addEventListener('transitionend', removeWillChange);
panel.addEventListener('transitioncancel', removeWillChange);

// 要求された状態はクリックのたびに同期的に更新し、描画への反映だけを遅らせる
let isOpen = panel.dataset.open === 'true';
let frame = 0;

const applyState = () => {
  frame = 0;
  const next = String(isOpen);
  // 状態が変わらなければトランジションが起きないので、ここで外す
  if (panel.dataset.open === next) panel.style.removeProperty('will-change');
  panel.dataset.open = next;
};

button.addEventListener('click', () => {
  isOpen = !isOpen;
  button.setAttribute('aria-expanded', String(isOpen));

  // トランジションが起きない設定では、will-change を付けない
  if (!motionQuery.matches) {
    cancelAnimationFrame(frame);
    applyState();
    return;
  }

  // 予約が残っていれば、その予約が最新の状態を反映する
  if (frame) return;

  panel.style.setProperty('will-change', 'translate');
  // レイヤーが用意されたフレームの次で、動きを始める
  frame = requestAnimationFrame(() => {
    frame = requestAnimationFrame(applyState);
  });
});
```

開閉の状態は、クリックした時点で変数と `aria-expanded` に反映し、パネルの `data-open` への反映だけを2フレーム後に遅らせます。クリックのたびに `data-open` を読んで反映まで待つと、描画の前に2回クリックしたとき、どちらも閉じた状態を読んで両方が開く処理になります。反映の予約は1つだけにし、実行する時点の最新の状態を書き込みます。

外す処理は、`transitionend` だけでなく `transitioncancel` にも登録します。途中で逆向きに操作されるなどしてトランジションが中断されると、`transitionend` は発生しないからです。動きを減らす設定でトランジションを指定していない場合も、どちらのイベントも発生しないので、最初から `will-change` を付けません。`@keyframes` のアニメーションなら、`animationend` と `animationcancel` で外します。

## `contain: content` で影響の範囲を区切る

`contain` は、要素の中のレイアウトやペイントを外から切り離すことをブラウザに約束する指定です。`contain: content` は、レイアウト、ペイント、スタイルの3つの封じ込めをまとめた値で、サイズの封じ込め（`size`）は含みません。中身が頻繁に変わる独立した領域へ指定すると、内側の変化で要素自体の大きさが変わらない限り、ブラウザは要素の外まで計算し直さずに済みます。中身の変化で要素の高さや幅が変われば、その変化は外のレイアウトに伝わります。

```css title="🙆‍♂ Recommended: 中身が頻繁に変わる独立した領域に contain: content を指定する"
@scope (.scoped.live-score) to (.scoped) {
  :scope {
    contain: content;
  }
}
```

ただし、次の副作用があるので、機械的に指定しません。1つ目に、中にある `position: fixed` の要素は、トップレイヤーに表示されるものを除き、ビューポートではなくこの要素を基準にするので、`absolute` のように振る舞います（「[7-10 positionの基礎](/layout/positioning/)」）。はみ出しの対策に `contain: paint` を使わない理由も、これと同じです（「[11-4 はみ出しとスクロール](/layout-practice/overflow/)」）。2つ目に、ペイントの封じ込めによって、要素からはみ出した影やポップアップが切り取られます。3つ目に、スタッキングコンテキストが作られるので、中の要素の `z-index` は外の要素と比べられなくなります（「[11-6 重なりと全幅](/layout-practice/layering/)」）。

また、合成だけで動く動きには、`contain` を指定しても効果がありません。封じ込めが減らすのはレイアウトとペイントの範囲で、合成だけの動きはもともとその処理を起こさないからです。指定するのは、DevToolsでレイアウトやペイントが要素の外まで広がっていることを確かめた場合に限ります。

## `content-visibility: auto` で画面外の描画を後回しにする

長いページでは、最初の画面より下にある内容も含めて、ページ全体のレイアウトが読み込みの時点で計算されます。`content-visibility: auto` を指定した要素は、画面から離れている間は中身のレイアウトとペイントが省かれ、画面の近くまで来たときに描画されます。記事の下に続く長いコメントの一覧や、項目の多いアーカイブのように、大きくて最初は見えないブロックに指定すると、最初の描画にかかる時間を減らせます。

描画を省いている間、要素にはサイズの封じ込めが掛かり、中身の大きさは0として扱われます。そのままでは、画面の近くまで来るたびに要素が本来の高さへ広がり、スクロールバーの長さとスクロールの位置が飛びます。そこで、`contain-intrinsic-block-size` で、描画していない間の高さの見積もりを指定します。値に `auto` を付けると、一度描画したあとは、そのときの実際の高さを覚えておき、次に描画を省くときに使います。

```css title="🙆‍♂ Recommended: 最初の画面より下の大きなブロックで、描画を後回しにする"
@scope (.scoped.comment-list) to (.scoped) {
  ._item {
    content-visibility: auto;
    contain-intrinsic-block-size: auto 12rem;
  }
}
```

大きさは、物理の `contain-intrinsic-size` や `contain-intrinsic-height` ではなく、論理の `contain-intrinsic-block-size` で書きます。ブロックの方向に並ぶ要素の幅は親の幅で決まるので、見積もりが要るのは高さだけです。見積もりの値は、典型的な項目の高さに近づけます。実際の高さと離れているほど、画面に近づいたときのずれが大きくなるからです。

最初の画面に入る要素には指定しません。最初の描画で画面の中にあると判断された要素は、そのまま描画されるので、描画を省く効果がありません。また、`content-visibility: auto` は、描画を省いていない間も、レイアウト、スタイル、ペイントの封じ込めを掛けたままにします。`contain: content` と同じく、はみ出した影が切り取られ、スタッキングコンテキストと固定配置の包含ブロックが作られます（「[7-10 positionの基礎](/layout/positioning/)」）。

仕様では、描画を省いた中身も、ページ内検索、Tabキーでのフォーカスの移動、アクセシビリティツリーの対象に残ります。Chrome 85〜89には、描画を省いた中の見出しがスクリーンリーダーの見出しの一覧に出ない不具合があり、Chrome 90で修正されました（不具合の報告の記事で確認）。指定したら、ページ内検索、Tabキー、スクリーンリーダーの見出しの一覧で中身に届くかを確かめます。

閉じたアコーディオンのパネルのように、ユーザーが開くまで隠しておく中身には、`content-visibility: auto` ではなく `hidden="until-found"` を使います。`hidden="until-found"` は中身を隠したまま、ページ内検索で見つかったときに表示する仕組みです。`content-visibility: auto` は、見えている内容の描画の順番を変えるだけで、何も隠しません。使い分けは「[17-6 開閉するUI](/interaction/disclosure/)」で説明しています。

## 負荷をDevToolsで確かめる

動きの負荷は、コードを読むだけでは判断しきれません。同じプロパティでも、ブラウザや値によって合成で処理されるかどうかが変わるからです。ここではChromeのDevToolsの機能を紹介します。

Performanceパネルでは、動きを再生している間の処理を記録できます。記録した結果には、フレームごとにかかった時間と、Layout、Paint、Compositeといった処理が時系列で並ぶので、どの処理がフレームの時間を超えているかが分かります。CPUの速度を落とす設定（CPU throttling）を使うと、メインスレッドの処理が遅い端末での振る舞いを確かめられます。

ただし、この設定が遅くするのはCPUの処理だけです。合成やラスタライズを受け持つGPUの性能や、合成レイヤーを保持するGPUのメモリの量は、手元のパソコンのままです。そのため、`backdrop-filter` の大きなぼかしや大きな合成レイヤー、多すぎるレイヤーの負荷は、この設定では再現できません。合成やペイントの負荷は、中位のスマートフォンの実機で確かめます。

実機の記録は、パソコンのブラウザから取れます。AndroidのChromeは、端末をUSBでつなぎ、パソコンのChromeで `chrome://inspect` を開くと、端末のページをDevToolsで調べられ、Performanceパネルで記録できます。iOSのSafariは、端末の設定でWebインスペクタを有効にしてMacにつなぐと、MacのSafariの「開発」メニューからWebインスペクタを開き、タイムラインを記録できます。開発サーバーのページは、端末とパソコンを同じネットワークにつなぎ、パソコンのIPアドレスとポート番号を指定すれば端末から開けます。{/* 要検証: ブラウザ。リモートデバッグでのPerformanceパネルの記録と、Webインスペクタのタイムラインの記録 */}

Renderingパネルでは、描き直しと合成レイヤーを画面の上で確かめられます。Paint flashingを有効にすると、描き直された領域が緑色で示されます。合成だけで動いているはずの要素が動くたび緑色になるなら、どこかでペイントが起きています。Layer bordersを有効にすると、合成レイヤーの境界が枠で示されるので、`will-change` を外し忘れたレイヤーや、意図しない巨大なレイヤーを見つけられます。
