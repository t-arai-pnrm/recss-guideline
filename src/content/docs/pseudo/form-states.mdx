フォームの状態は、`:user-invalid`、`:checked`、`:disabled`、`:placeholder-shown` のような擬似クラスで選びます。ブラウザが管理する状態をそのまま参照するので、JavaScriptで状態のクラスを付け外しする必要はありません。ただし、どの擬似クラスも、名前から想像する範囲と、実際に当てはまる範囲が少しずつ違います。

`:invalid` は操作する前から当てはまり、`:read-only` は編集できないすべての要素に当てはまり、`:placeholder-shown` は `placeholder` 属性のある入力欄にしか当てはまりません。この節では、仕様（HTML Living Standardの「Pseudo-classes」の節と、Selectors Level 4）が定める条件を擬似クラスごとに確かめ、取り違えやすいものの書き方をルールにします。ARIA属性でしか表せない状態は、属性セレクタで補います。

## 名前どおりに当てはまらない擬似クラス

フォームの状態を表す擬似クラスは、名前が状態そのものを表しているので、条件を確かめずに使われがちです。しかし、`:invalid` は「ユーザーが誤った値を入力した」ときではなく、「値が制約を満たしていない」ときに当てはまります。`required` を付けた空の入力欄は、ページを開いた時点で `:invalid` です。

`:read-only` も同じです。名前からは `readonly` 属性を付けた入力欄を選ぶように見えますが、仕様では「`:read-write` に当てはまらない、すべての要素」に当てはまります。段落も、チェックボックスも、ボタンも `:read-only` です。

こうした違いは、見た目の不具合として表に出ます。ページを開いた直後にエラーの赤い枠が出る、読み取り専用の灰色の背景がチェックボックスにまで付く、といった不具合です。名前だけを見て次のように書くと、どちらも起きます。

```css title="🙅‍♂ Not Recommended: 擬似クラスの名前から条件を推し量って書く" issue="behavior"
/* 🙅‍♂ Not Recommended */
input {
  /* 「誤った値を入力した」のつもりで、開いた時点の空の必須の欄にも当たる */
  &:invalid {
    border-color: oklch(50% 0.2 25deg);
  }

  /* 「readonly を付けた欄」のつもりで、チェックボックスにも当たる */
  &:read-only {
    background-color: oklch(93% 0 0deg);
  }
}
```

どれも、擬似クラスの書き方ではなく、当てはまる条件を理解していないことから起きます。以下では、検証、選択、操作の可否、入力の有無の順に、条件を確かめます。

## 検証の結果を表す擬似クラス

`:valid` と `:invalid` は、制約の検証（constraint validation）の結果を表します。`required`、`type="email"`、`pattern`、`min` などの制約を満たしていれば `:valid`、満たしていなければ `:invalid` です。判定は値が変わるたびに行われ、ユーザーが操作したかどうかは問いません。

検証の対象にならない要素は、どちらにも当てはまりません。無効にした入力欄、`readonly` を付けた入力欄、`type="hidden"` の入力欄は、検証の対象から外れます。`required` と `readonly` を両方付けた空の入力欄は、`:invalid` になりません。一方、`<form>` と `<fieldset>` は、中に `:invalid` の要素が1つでもあれば `:invalid` です。

`:user-valid` と `:user-invalid` は、ユーザーが値を変えて入力欄を離れた後か、送信しようとした後にだけ当てはまります。エラーの見た目を `:invalid` ではなく `:user-invalid` に指定する理由と書き方は、第17章「[17-7 フォーム部品](/interaction/forms/)」のルール `user-invalid-for-errors` で説明しています。正しく入力できたことを示す見た目も、同じ理由で `:valid` ではなく `:user-valid` に指定します。

```css title="🙆‍♂ Recommended: エラーと入力済みの見た目を、ユーザーの操作の後に限る" from="pseudo/user-invalid-timing"
@scope (.scoped.contact-form) to (.scoped) {
  input {
    &:user-invalid {
      border-width: 2px;
      border-color: var(--foreground--danger);
    }

    &:user-valid {
      border-color: var(--foreground--success);
    }
  }
}
```

エラーの枠線は、色を変えるだけでなく太くしています。色の違いを見分けにくい人にも、状態の変化を伝えるためです。何が誤りかは、枠線ではなく文言で伝えます。エラーの文言の置き方は「[17-7 フォーム部品](/interaction/forms/)」で説明しています。

次のデモの2つの欄は、どちらも `required` を付けたメールアドレスの欄です。上の `:invalid` の欄は、何も操作していないうちからエラーの太い枠線で表示されます。下の `:user-invalid` の欄は、不正な値を入れて欄を離れるか、空のまま「送信する」を押すまで、エラーの見た目になりません。

`:required` と `:optional` は、`required` 属性の有無だけで決まります。値が入っているかどうかは関係しません。値によらない、入力欄自身の見た目に使います。ラベルの横の「必須」の印は、`:required` が入力欄にしか当たらず、生成コンテンツでは読み上げにも伝わらないので、HTMLに書きます（「[5-8 生成コンテンツと装飾の擬似要素](/pseudo/generated-content/)」）。`:valid` と `:invalid`、`:required` と `:optional` は、どちらも以前からすべての主要なブラウザで使えます。

## 選択とデフォルト値を表す擬似クラス

`:checked` は、チェックされたチェックボックスとラジオボタン、選ばれた `<option>` に当てはまります。参照するのは `checked` 属性ではなく、現在の状態です。ユーザーがチェックを外せば、HTMLに `checked` 属性が残っていても当てはまらなくなります。

`:default` は、反対に初期値を表します。HTMLに `checked` 属性を書いたチェックボックスとラジオボタン、`selected` 属性を書いた `<option>`、フォームの既定の送信ボタンに当てはまります。ユーザーが別の選択肢を選んでも、`:default` は初期値の選択肢に残ります。おすすめの選択肢に印を付けておき、ほかを選んだ後も、どれがおすすめだったかを示したい場合に使えます。

`:indeterminate` は、どちらとも決まっていない状態です。対象は3つあり、JavaScriptで `indeterminate` プロパティを `true` にしたチェックボックス、同じ `name` のどれもチェックされていないラジオボタン、`value` 属性のない `<progress>` に当てはまります。チェックボックスの中間の状態はHTMLの属性では書けないので、JavaScriptで設定します。

```css title="🙆‍♂ Recommended: 中間の状態はチェックボックスに限って指定する" from="pseudo/select-all"
@scope (.scoped.check-field) to (.scoped) {
  input {
    &:checked,
    &[type="checkbox"]:indeterminate {
      border-color: var(--background--accent);
      background-color: var(--background--accent);
    }
  }
}
```

上の例で `&:indeterminate` と書かずに `[type="checkbox"]` を加えているのは、ラジオボタンを除くためです。スコープの中にラジオボタンがあると、まだ何も選んでいないグループのラジオボタンが、すべて `:indeterminate` に当てはまります。中間の状態の印は、未選択のラジオボタンに付けるものではありません。

次のデモでは、お知らせの一部だけを選ぶと、スクリプトが「すべて選ぶ」の `indeterminate` を `true` にし、横線の印が付きます。下の「配信の頻度」のラジオボタンは、どれも選んでいないので `:indeterminate` に当てはまりますが、`[type="checkbox"]` で除いているので印は付きません。チェックと中間の状態は背景色が同じなので、内側の余白と横線の形で区別しています。強制カラーモードでは背景色、影、グラデーションが描かれず、3つの状態が同じ四角になるので、`appearance` を `revert` に戻してブラウザのチェックボックスで表示します。{/* 要検証: ブラウザ。強制カラーモードで、appearance: revert に戻したチェックボックスの3つの状態を見分けられること */}

## 操作できるかを表す擬似クラス

`:disabled` は、無効になっている要素に当てはまります。`disabled` 属性を付けた要素だけでなく、`disabled` を付けた `<fieldset>` の中のフォーム部品も無効です。`:enabled` は、ボタン、入力欄、`<select>`、`<textarea>`、`<option>`、`<fieldset>` などのうち、無効でないものに当てはまります。リンクや `div` は、`:enabled` と `:disabled` のどちらにも当てはまりません。

`:read-write` は、ユーザーが編集できる要素に当てはまります。`readonly` を付けておらず、無効でもないテキストの入力欄と `<textarea>` に加えて、`contenteditable` を付けた要素も対象です。`:read-only` はそれ以外のすべての要素で、編集を前提としない要素はすべて含まれます。

```css title="🙅‍♂ Not Recommended: input:read-only で読み取り専用の入力欄を選ぶ" issue="behavior"
/* 🙅‍♂ Not Recommended */
input {
  &:read-only {
    background-color: oklch(95% 0 0deg);
  }
}
```

上の指定は、`readonly` を付けたテキストの入力欄だけでなく、チェックボックス、ラジオボタン、ファイルの選択、ボタンの `input` にも当たります。`readonly` 属性は、これらの部品には適用されないからです。無効にしたテキストの入力欄も、編集できないので `:read-only` です。

読み取り専用の入力欄を選びたいときは、属性セレクタで `&[readonly]` と書きます。`readonly` と `disabled` は、意味が違います。`readonly` の入力欄はフォーカスでき、値もフォームと一緒に送信されます。`disabled` の入力欄はフォーカスできず、値も送信されません。見た目も分けて指定します。

```css title="🙆‍♂ Recommended: 読み取り専用と無効を分けて指定する" from="pseudo/read-only-scope"
@scope (.scoped.account-form) to (.scoped) {
  input {
    &[readonly] {
      border-color: transparent;
      background-color: var(--background--surface);
    }

    &:disabled {
      color: var(--foreground--muted);
    }
  }
}
```

次のデモは、同じ4つの部品を、1つ目の枠では `&:read-only` で、2つ目の枠では `&[readonly]` と `&:disabled` で選んだものです。1つ目では、赤い輪郭が、会員番号の欄だけでなく、無効にした紹介コードの欄とチェックボックスにも付きます。2つ目では、読み取り専用の欄は枠線のない面に、無効の欄は灰色の文字になり、別々の見た目になります。

<Demo title=":read-only は無効の欄とチェックボックスにも当たり、[readonly] は読み取り専用の欄だけに当たる" html={readOnlyHtml} css={readOnlyCss} />

## 入力の有無を表す `:placeholder-shown`

`:placeholder-shown` は、プレースホルダーが表示されている入力欄と `<textarea>` に当てはまります。プレースホルダーは値が空のときに表示されるので、「まだ何も入力していない」ことの判定に使えます。CSSには値の有無そのものを表す擬似クラスがないので、入力済みかどうかで見た目を変えるときに使われます。

注意したいのは、`placeholder` 属性のない入力欄には、値が空でも当てはまらないことです。そのため、`:not(:placeholder-shown)` で「入力済み」を判定すると、`placeholder` 属性のない入力欄は、空のままでも入力済みとして扱われます。

```css title="🙅‍♂ Not Recommended: :not(:placeholder-shown) を「入力済み」の意味で使う" issue="behavior"
/* 🙅‍♂ Not Recommended */
input {
  &:not(:placeholder-shown) {
    border-color: var(--foreground--base);
  }
}
```

未入力の状態は、`&:placeholder-shown` の側に書きます。`placeholder` 属性のない入力欄では何も起きないので、誤って入力済みの見た目になることはありません。どうしても `:not()` で書く必要があるときは、`&[placeholder]:not(:placeholder-shown)` のように属性の有無も条件にします。

```css title="🙆‍♂ Recommended: 未入力の状態を :placeholder-shown の側に書く" from="pseudo/placeholder-shown-scope"
@scope (.scoped.profile-form) to (.scoped) {
  input {
    &:placeholder-shown {
      border-style: dashed;
    }
  }
}
```

次のデモは、`placeholder` 属性のある「表示名」と、ない「備考」を並べたものです。1つ目の枠の `&:not(:placeholder-shown)` では、空のままの「備考」が最初から入力済みの太い枠になります。2つ目の枠の `&:placeholder-shown` では、「表示名」だけが未入力の点線になり、文字を入力すると実線に変わります。

<Demo title=":not(:placeholder-shown) は placeholder 属性のない空の欄も入力済みにする" html={placeholderShownHtml} css={placeholderShownCss} />

ラベルを入力欄の中に重ね、入力すると上に移動させる「フローティングラベル」では、判定のためだけに `placeholder=" "` と空白1文字を書く方法が知られています。本書では、この方法を使いません。`placeholder` 属性は入力の手がかりを示すためのもので、見た目の判定のために値を入れると、入力例という本来の役割と混ざるからです。{/* 要確認: 出典なし */}ラベルは入力欄の外に置き、入力例を `placeholder` に書きます。

## フォーム部品の一部を選ぶ擬似要素

`::placeholder` は、プレースホルダーの文字を選ぶ擬似要素です。ブラウザの既定のプレースホルダーは薄い色で、Chromeは `darkgray`、Firefoxは入力欄の文字色を54%の不透明度にした色を使います（MDN）。どちらも、白い背景とのコントラスト比が、WCAGが本文の文字に求める4.5:1に届かないことがあります。

プレースホルダーの色は、`color` で背景とのコントラスト比が4.5:1以上になる色を指定します。`opacity` で薄くすると、背景の色が透けて見え、背景が変わるたびにコントラスト比も変わります。本書が推奨するkiso.cssは、`::placeholder` の `opacity` を初期値に戻して、ブラウザの差をなくしています（「[8-1 壊さないリセット](/reset/kiso/)」）。

<Baseline id="placeholder" />

`::file-selector-button` は、`<input type="file">` の「ファイルを選択」のボタンを選ぶ擬似要素です。入力欄全体ではなく、ボタンの部分だけに枠線や背景色を指定できます。kiso.cssは、このボタンにもほかのボタンと同じ枠線とフォントの初期値を指定しています。

## ネイティブの状態とARIA属性の使い分け

状態のスタイルは、まずネイティブの擬似クラスで書きます。`disabled` 属性や `required` 属性で表せる状態は、ブラウザが操作の可否や検証の結果まで管理し、支援技術にも伝えるからです。状態のクラスを使わず、擬似クラスかARIA属性をセレクタにする方針は、第17章「[17-3 状態を属性で表す](/interaction/state-attributes/)」のルール `state-by-pseudo-class-or-aria` で定めています。

ただし、同じ状態を、ネイティブの属性ではなくARIA属性で表す場面があります。送信ボタンを `disabled` にすると、フォーカスの順序から外れ、Tabキーでボタンにたどり着けなくなります（MDN）。そこで、フォーカスを残したまま `aria-disabled="true"` で無効を伝えることがあります。サーバーで検証した結果のエラーも、ブラウザの制約の検証では表せないので、JavaScriptで `aria-invalid="true"` を付けます。

`aria-disabled="true"` を付けた要素は `:disabled` に、`aria-invalid="true"` を付けた要素は `:user-invalid` に当てはまりません。ARIA属性は支援技術に状態を伝えるだけで、ブラウザの状態は変えないからです（MDN）。片方にだけ見た目を指定すると、同じ「無効」や「エラー」の状態でも、見た目の変わらない要素が出ます。

```css title="🙆‍♂ Recommended: ネイティブの状態と ARIA 属性の状態に、同じ見た目を当てる" from="pseudo/aria-states"
@scope (.scoped.profile-form) to (.scoped) {
  input {
    &:is(:user-invalid, [aria-invalid="true"]) {
      border-width: 2px;
      border-color: var(--foreground--danger);
    }
  }

  button {
    &:is(:disabled, [aria-disabled="true"]) {
      background-color: unset;
      color: var(--foreground--muted);
    }
  }
}
```

kiso.cssも、`:where(:disabled, [aria-disabled="true" i])` に `cursor: default` を指定して、両方を同じ状態として扱っています。なお、`aria-disabled="true"` はクリックやキー操作を止めません。操作を止める処理は、JavaScriptで別に書きます。

次のデモでは、「登録する」ボタンに `aria-disabled="true"` を付けておき、利用規約に同意するとスクリプトで `false` に変えます。隣の「下書きを保存する」は `disabled` 属性で無効にしたボタンです。2つの見た目は同じですが、Tabキーでフォーカスできるのは「登録する」だけです。「サーバーのエラーを再現する」を押すと、ユーザー名の入力欄に `aria-invalid="true"` が付き、メールアドレスを空のまま登録しようとしたときの `:user-invalid` と同じ太い枠線になり、下にエラーの文言が出ます。
