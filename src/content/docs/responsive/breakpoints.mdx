ブレイクポイントは、スマートフォンやPCのようなデバイスの分類ではなく、内容が成り立たなくなる幅から決めます。値はremで指定し、閾値は「列の最小幅×列数＋隙間×隙間の数」のように、レイアウトが成り立つ条件を `calc()` の式で書きます。式にしておけば、閾値の根拠がコードに残り、列数や隙間を変えたときに直す場所も分かります。

この決め方は、ページ全体の段組みを切り替えるメディアクエリ（「[13-5 メディアクエリ](/responsive/media-queries/)」）と、コンポーネントの中を切り替えるコンテナサイズクエリ（「[13-3 コンテナサイズクエリ](/responsive/container-size-queries/)」）に共通です。クエリを書く前に、クエリを使わずに済まないかを確かめる順番は「[13-1 検討する順番](/responsive/escalation/)」で説明しています。

## デバイスの分類から決めたブレイクポイントの問題

よく見かけるのは、スマートフォン、タブレット、PCという分類からブレイクポイントを決め、その境目の幅をそのまま条件に書く方法です。表示を切り替えるクラスにも、`sp` や `pc` のようなデバイスの名前が付きます。

```css title="🙅‍♂ Not Recommended: デバイスの分類で決めた幅を、そのまま条件に書く" issue="behavior"
/* 🙅‍♂ Not Recommended */
.sp-only {
  @media (width >= 768px) {
    display: none;
  }
}

._card-list {
  display: block grid;

  @media (width >= 768px) {
    grid-template-columns: repeat(2, 1fr);
  }

  @media (width >= 1024px) {
    grid-template-columns: repeat(3, 1fr);
  }
}
```

現在、Webサイトが表示される画面の幅は2,000種類以上あると言われます。スマートフォンでも幅はまちまちで、折りたたみ端末もあり、PCのブラウザは好きな幅に変えられます。スマートフォンを横向きにすれば、タブレットと同じくらいの幅になります。デバイスの分類は画面の幅の実態と一致しないので、`sp` という名前のスタイルが大きなタブレットに当たるといったずれが、時間とともに増えていきます。

もう1つの問題は、768pxや1024pxという数値に、このカードの一覧に関わる根拠がないことです。根拠の分からない数値はマジックナンバーと呼ばれます。カードに必要な幅を変えても閾値は変わらないので、閾値のすぐ上の幅でカードが窮屈になっても、コードからはその理由が読み取れません。

`.sp-only` や `.pc-only` のような表示を切り替えるクラスも、同じ理由で使いません。コードには、デバイスの名前ではなく、表示を変える条件を残します。「今年のブレイクポイントはこれで決まり」のような、その年に多い画面の幅から値を選ぶ記事を追いかける必要もありません。画面の幅の流行は毎年変わりますが、レイアウトが崩れる幅は、内容と配置が変わらない限り変わらないからです。

## 崩れる幅を内容から見つける

ブレイクポイントは、レイアウトが崩れる幅から決めます。実装したページの幅を少しずつ狭めていくと、どこかで文字が詰まりすぎたり、要素が重なったり、余白のバランスが崩れたりします。その幅が、切り替えるべき幅です。この考え方は、メディアクエリとコンテナサイズクエリに共通です。

崩れたかどうかの判断は、実装者だけでは決めきれません。カンプが用意されているのは2つか3つの幅だけで、その間の幅で何を保つかは、デザインの意図によって変わるからです。本文の読みやすさ、1画面に入る情報の量、画像の縦横比のように保つものと、カラムの数を変える時点のように崩れとみなす基準を、実装の段階でデザイナーとすり合わせて決めます。確かめておくことは「[3-2 実装の前にデザイナーと確かめること](/design-reproduction/designer-questions/)」に、カンプの比率でページ全体を拡大・縮小しない理由は「[13-7 カンプの幅で全体を拡大・縮小しない](/responsive/design-comp-pattern/)」にまとめています。

ただし、Tailwind CSSのように、ブレイクポイントをデフォルトで変数として持つフレームワークを使う案件では、独自の値を足さず、フレームワークの変数を使います。案件の中で値がばらばらになるのを避けるためです。この場合も、変数の名前にはデバイスの名前を使わないようにします。

## ブレイクポイントをremで書く

ブレイクポイントの値はremで指定します。ユーザーがブラウザの文字サイズを大きくすると、同じ画面の幅でも1行に入る文字数が減り、実質的に使える幅が狭くなります。remで指定すれば、閾値の幅も文字サイズに比例して広がるので、文字サイズを大きくしたユーザーには早めに1カラムのレイアウトが適用されます。pxの閾値は、ブラウザの文字サイズの設定に追従しません。

追従しないことが問題になるのは、本文の列の最小幅のように、必要な幅が文字サイズで変わるレイアウトです。画像の大きさだけで決まる並びなら、pxの閾値でも表示は崩れません。本書は、この条件に当たるかをレイアウトごとに判断しなくて済むように、すべてのブレイクポイントをremで書くと決めています。前者は仕様が定める単位の挙動から導いた要件、後者は表記をそろえるための本書の規約なので、ルールを分けています（`breakpoint-follows-font-size`、`breakpoint-in-rem`）。

値は `48rem` と書かずに、`calc(768 / 16 * 1rem)` のようにピクセル値からの変換を式で書きます。デザインカンプの値はピクセルで書かれていることが多いので、式にしておけば元の値をそのまま読み取れます。

```css title="🙆‍♂ Recommended: カンプのピクセル値を、remへの変換式で書く"
._layout {
  display: block grid;

  @media (width >= calc(640 / 16 * 1rem)) {
    grid-template-columns: repeat(2, 1fr);
  }
}
```

メディアクエリの中のremは、CSSで `html` に指定した値ではなく、ブラウザの設定の文字サイズを基準に計算されます。メディアクエリの中では `em` も同じ基準で計算されるので、`em` で書いても閾値の挙動は変わりません。MDNは文字サイズの変更に配慮して `em` を勧めていますが、本書は `calc(N / 16 * 1rem)` の式に統一するため、`rem` を選んでいます。

## 閾値を中身の条件から導く

`calc()` は、閾値を計算するための道具であると同時に、レイアウトが成り立つ条件をコードに書き残す手段です。「列の最小幅×列数」「アイテムの幅×個数＋隙間×隙間の数」「中身の幅＋`padding`＋`border`」のような、意味のある値の組み合わせで閾値を表します。そうすれば、閾値は「たまたま決めた数値」ではなく、「そのレイアウトが成り立つのに必要な幅」になります。

ページの段組みで、本文の最小幅とサイドバーの幅を560px相当と240px相当のremで、その隙間を32pxで指定したとします。文字サイズが標準なら、2カラムにできるのは合計の832px以上です。`calc(560 / 16 * 1rem + 240 / 16 * 1rem + 32px)` と書けば、この幅になる理由がコードに残り、サイドバーの幅を変えたときにどこを直せばよいかも分かります。

隙間を `32px` のまま足す理由は、後の「gapとpaddingを式から省かない」で説明します。このページ全体の段組みのデモは「[13-5 メディアクエリ](/responsive/media-queries/)」にあります。

コンテナサイズクエリでも同じです。次の例は、画像と本文を並べるカードです。画像の列は160px相当、本文の最小幅は240px相当で、その間に24pxの隙間を空け、カードの内側の左右に16pxの余白を取ります。横に並べられるのは、これらを足した幅からです。

```css title="🙆‍♂ Recommended: 画像の列、隙間、本文の最小幅、左右の余白を足した式で閾値を書く"
@scope (.scoped.media-card) to (.scoped) {
  :scope {
    container: --scoped / inline-size;
  }

  ._layout {
    display: block grid;
    gap: 24px;
    padding-inline: 16px;

    /* 画像 160px 相当・隙間 24px・本文の最小幅 240px 相当と、左右の余白 16px が並ぶ幅 */
    @container --scoped (inline-size >= calc(160 / 16 * 1rem + 24px + 240 / 16 * 1rem + 16px * 2)) {
      grid-template-columns: calc(160 / 16 * 1rem) 1fr;
    }
  }
}
```

文字サイズが標準なら、閾値は456pxです。画像の列と本文の最小幅はremの変換の式で、隙間と余白はpxで指定しているので、閾値の式でも同じ単位で足しています。

切り替えるのは `._layout` の配置の1か所なので、クエリは `._layout` のルールに直接書いています。同じ閾値で画像の縦横比や見出しの大きさも変えるなら、クエリはフラグを立てる1つのルールにまとめます（「[10-6 スタイルクエリで状態を伝える](/components/style-queries/)」）。列の数に応じて何段階も切り替える一覧は、「[11-5 件数で配置を組み替える](/layout-practice/quantity-layouts/)」で扱います。

## gapとpaddingを式から省かない

閾値の式には、レイアウトが成り立つ条件に関わる `gap`、`padding`、`border` を省かずに含めます。上の例で隙間と余白を省いて `calc(160 / 16 * 1rem + 240 / 16 * 1rem)` と書くと、閾値は400pxになります。本文の列が240pxを保てるのは、隙間24pxと左右の余白32pxを足した456pxからです。400pxから456pxの間では、条件が当てはまって画像と本文が横に並ぶのに、本文の列が240pxより狭くなり、文字が詰まります。

`padding` と `border` も同じです。コンテナの内側で並べる要素に左右の `padding` があるなら、その分も式に足します。ボタンのように中身の幅で閾値を決める部品なら、「アイコンの幅＋隙間＋ラベルの幅＋左右の `padding`」が閾値です。どれか1つを省くと、閾値は実際に並べられる幅より狭くなり、切り替わった直後の幅で中身がはみ出したり詰まったりします。

式の各項は、その値を宣言したときの単位で書きます。remで指定した幅は `560 / 16 * 1rem` のように変換の式で書き、pxで指定した `gap`、`padding`、`border` は `32px` のようにpxのまま足します。ユーザーが文字サイズを大きくすると、remで指定した幅は広がりますが、pxで指定した隙間は広がりません。pxの値までremに換算すると、閾値の中でだけ隙間が広がり、閾値が実際に並べられる幅とずれます。

前の「ブレイクポイントをremで書く」で説明したとおり、メディアクエリの中のremは、ブラウザの設定の文字サイズを基準にします。本書はルートの文字サイズを変えないので、ページの中のremも同じ大きさです。そのため、各項を宣言したときの単位で書けば、文字サイズを変えたときにremの項は中身の幅と同じ割合で広がり、pxの項は隙間と同じく変わらないので、閾値と実際に並べられる幅がずれません。

式が長くなっても、項を省いて短くはしません。一度しか使わない長い式には、どの幅を足したのかをコメントで補います。上の例のコメントがそれに当たります。コメントに書くのは、式が表している条件です（「[9-10 コメントの書き方](/notation/comments/)」）。

## calc()で書くかどうかの判断基準

閾値を `calc()` の式にする基準は2つあります。1つは、根拠を式で表すと意図を読み取りやすくなるときです。もう1つは、列数、個数、隙間、最小幅を後で変える可能性のあるときです。どちらかに当てはまれば、式で書きます。値が本当に固定で、分解しても意味が増えない場合は、単純な値をそのまま書いてかまいません。

避けるのは、根拠のない数値を `calc(48rem)` のように包むだけの書き方です。式の形をしていても、根拠は何も残りません。一度しか使わない巨大な式を、コメントなしでその場に書くのも避けます。

そもそも、イントリンシックなレイアウトで解決できる問題を、クエリと `calc()` で解こうとしないことが前提です。列数が増減するだけなら、`repeat()` の `auto-fit` と `minmax()` で、クエリなしに組めます（「[13-1 検討する順番](/responsive/escalation/)」）。上の例でクエリを書いているのは、画像の列を本文の横に置くか上に積むかという、途中の状態のない切り替えだからです。

## クエリの条件にvar()を書かない

閾値を使い回そうとして、クエリの条件の中に `var()` を書くのは誤りです。AIが生成するコードにもよく見られます。

```css title="🙅‍♂ Not Recommended: コンテナサイズクエリの条件に var() を書く" issue="behavior"
/* 🙅‍♂ Not Recommended */
@scope (.scoped.card-group) to (.scoped) {
  ul {
    --_column-width: calc(160 / 16 * 1rem);

    @container --scoped (inline-size >= calc(var(--_column-width) * 4)) {
      grid-template-columns: repeat(4, 1fr);
    }
  }
}
```

メディアクエリの条件では、カスタムプロパティを参照できません。条件の構文が `var()` を受け付けないので、その条件は成り立ちません。一方、コンテナサイズクエリの条件では、現在の仕様の草案が `var()` を認めていて、値は問い合わせるコンテナの計算値で解決されます。ただし、仕様どおりに動くのはFirefoxだけで、ChromeとSafariは仕様のテストの一部にしか通りません（WPTで確認）。

上の例には、もう1つ問題があります。`--_column-width` を定義しているのは `ul` 自身ですが、条件の中の `var()` は、問い合わせるコンテナ（ルートの `--scoped`）の値で解決されます。コンテナに同じプロパティがなければ、仕様どおりに動くブラウザでも条件の結果は不明になり、スタイルは適用されません。

そこで本書では、メディアクエリとコンテナサイズクエリの条件には、リテラルの値を書きます。対象のブラウザでそろって動かないことに加え、閾値がその場に書いてあれば、どの幅で切り替わるのかをすぐに確かめられるからです。{/* 要確認: 出典なし */}プロパティの値の中では、これまでどおり `var()` を使えます。スタイルクエリの `style(--a: var(--b))` のように、カスタムプロパティどうしを比べる条件は、仕様で認められていて主要なブラウザでも動くので、このルールの対象にしません。コンポーネントの中で同じ閾値を何度も使うときは、閾値を1か所のコンテナサイズクエリに書いて `--_density` のようなフラグを切り替え、子孫の要素はそのフラグをスタイルクエリで読みます。この書き方は「[10-6 スタイルクエリで状態を伝える](/components/style-queries/#rule-density-via-style-query)」で説明しています。

## AIが書いた閾値を確かめる

AIにレスポンシブ対応のコードを書かせると、`768px` のような慣習の値を閾値にしたり、条件の中に `var()` を書いたりすることがよくあります。生成されたクエリは、そのまま採用せず、少なくとも次の3点を確かめます。

1. `@media` と `@container` の条件の中に `var()` が入っていないか
2. 閾値が、デバイスの幅の慣習の値ではなく、レイアウトが成り立つ条件になっているか
3. 隙間、列数、`padding` のように、成り立つ条件に必要な値が、宣言したときの単位のまま式に含まれているか

1つ目に当てはまれば、そのコードは誤りなので、リテラルの値に直します。2つ目と3つ目は、動作はしても、閾値の根拠が失われているか、閾値が実際の幅とずれています。この観点はレビューでも使えます。レビューの進め方は「[19-2 レビューの進め方](/operations/review/)」で説明しています。
