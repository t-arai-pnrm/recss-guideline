複数の場所に置かれるコンポーネントは、ビューポートではなく、置かれた場所の幅で切り替えます。そのための仕組みがコンテナサイズクエリです。コンポーネントのルートをコンテナにするときは `container: --scoped / inline-size` と書いて `@container --scoped (…)` で問い合わせ、外側のコンポーネントのコンテナは問い合わせません。

コンテナサイズクエリを選ぶのは、幅の違う複数の場所に置かれるコンポーネントです。ページに1か所しかないセクションや、ページ全体の骨組みは、ビューポートの幅で決まるので、メディアクエリで足ります（「[13-1 検討する順番](/responsive/escalation/)」）。

この節では、コンテナの名前と書き方の規約に加えて、同じ閾値を子孫の要素で使い回す方法、画面に対する割合で切り替える方法、想定より狭い場所に置かれたときの最後の手段を説明します。コンテナにした要素は幅を中身から決められなくなるので、コンテナは問い合わせる要素にだけ指定します。この副作用と、コンテナの幅を基準にした単位 `cqi` は、「[13-4 コンテナの副作用とコンテナ単位](/responsive/container-units-and-side-effects/)」で説明します。

`@container` で問い合わせられるのは、サイズだけではありません。祖先の要素のカスタムプロパティの値を調べるスタイルクエリ（`@container style(…)`）と、スクロールの状態を調べるスクロール状態クエリ（`@container scroll-state(…)`）もあります。本書では、この3つをまとめてコンテナクエリと呼び、サイズを問い合わせるものをコンテナサイズクエリと呼んで区別します。

## ビューポートの幅では足りない理由

画像と本文を並べたカードを考えます。メインエリアに置いたときは、幅に余裕があるので画像と本文を横に並べたく、サイドバーに置いたときは、幅が狭いので縦に積みたいという要件はよくあります。

メディアクエリでは、この要件を満たせません。メインエリアとサイドバーは同じページにあるので、ビューポートの幅はどちらも同じだからです。結局「サイドバー用」の属性（`data-placement="sidebar"` など）を用意し、置き場所ごとにスタイルを出し分けることになります。

```css title="🙅‍♂ Not Recommended: 置き場所ごとに属性で出し分ける" issue="convention"
/* 🙅‍♂ Not Recommended */
@scope (.scoped.media-card) to (.scoped) {
  :scope {
    display: block grid;

    @media (width >= calc(768 / 16 * 1rem)) {
      grid-template-columns: calc(160 / 16 * 1rem) 1fr;
    }

    &[data-placement="sidebar"] {
      @media (width >= calc(768 / 16 * 1rem)) {
        grid-template-columns: 1fr;
      }
    }
  }
}
```

この方法では、置き場所が増えるたびに属性の値も増え、コンポーネントと置き場所が強く結びつきます。カードの配置を決める条件が、カード自身ではなく、カードを置く側が付ける属性にあるためです。コンテナサイズクエリを使えば、カードは自分が使える幅だけを条件に配置を決められます。

コンテナサイズクエリに対応していない環境では、`@container` の中のスタイルが適用されず、クエリの外に書いたスタイルだけが残ります。そのため、基本のスタイルは狭い幅で成り立つように書きます。広い幅でも狭いレイアウトのままになりますが、崩れではなく縮退に収まります。この考え方は、「[13-5 メディアクエリ](/responsive/media-queries/)」で説明するモバイルファーストの書き方と同じです。

## ルートを--scopedという名前のコンテナにする

コンポーネントのルートをコンテナにし、ルートの子孫でその幅を問い合わせます。コンテナ自身は自分の幅を問い合わせられないので、条件はルートの子孫に書きます。コンテナ自身が条件の結果で幅を変えると、条件の成否が循環してしまうためです（さらに詳しくは「[10-6 スタイルクエリで状態を伝える](/components/style-queries/#コンテナサイズクエリの基本)」）。ここからは、その書き方の規約を決めます。ルートのコンテナの名前は、どのコンポーネントでも `--scoped` にそろえます。ルートに付けるクラス `scoped` と同じ語なので、どの要素のコンテナなのかを覚える必要がありません。`--root` という名前は、`:root` と紛れるので採りません。

```css title="🙆‍♂ Recommended: ルートを --scoped のコンテナにし、中の要素で判定する" from="responsive/container-card"
@scope (.scoped.media-card) to (.scoped) {
  :scope {
    container: --scoped / inline-size;
  }

  ._layout {
    display: block grid;

    @container --scoped (inline-size >= calc(400 / 16 * 1rem)) {
      grid-template-columns: calc(160 / 16 * 1rem) 1fr;
    }
  }
}
```

コンテナサイズクエリを書くのは、コンポーネントの中で `._layout` のルールだけです。この例で幅によって変わるのは `._layout` の配置だけなので、クエリを `._layout` のルールに直接書き、フラグは作りません。同じ閾値でほかの子孫も切り替えるときは、`._layout` がフラグを立て、子孫はそのフラグを読みます。この書き方は「[同じ閾値をスタイルクエリで子孫に伝える](#同じ閾値をスタイルクエリで子孫に伝える)」で説明します。

コンテナには必ず名前を付け、`@container` の条件でもその名前を指定します。名前を省略した `@container` は、いちばん近い祖先のコンテナを参照するので、コンテナが入れ子になると、どのコンテナを参照しているのかがコードから読み取れません。どのルートも同じ名前にしても、参照先は曖昧になりません。名前を指定した `@container` は、その名前を持ついちばん近い祖先を参照します。そして `@scope` の下限（`to (.scoped)`）が内側のコンポーネントを範囲から外すので、`--scoped` は常に、そのスタイルを書いたコンポーネント自身のルートを指します。

ルート以外の子要素をコンテナにするときは、クラス名から下線を除いた名前を付けます。`._body` をコンテナにするなら `container: --body / inline-size` と書き、`@container --body (…)` で問い合わせます。外側のコンポーネントのコンテナは問い合わせません。ページのレイアウトのコンポーネントが子要素 `._aside` のコンテナ `--aside` を内側のカードが問い合わせると、カードはそのコンポーネントの定義に依存し、別の場所へ移したときに条件が成り立たなくなります。外側の状況で変えたい値は、外側のコンポーネントの要素で公開用のカスタムプロパティ（`--media-card--gap` など）を宣言し、継承で渡します（「[10-5 公開プロパティと内部プロパティ](/components/custom-properties/)」）。

ルート自身のスタイルに `@container --scoped (…)` を書くのも誤りです。上で述べたとおり、ルートの `:scope` に書いた条件は、ルート自身ではなく、さらに外側のコンポーネントのルートを参照します。そのため、コンテナサイズクエリとフラグは、上の例の `._layout` のようなルートの子孫に置きます。ルート自身の見た目を変えたいときは、外側から公開用のカスタムプロパティで値を受け取ります。

名前は `--` で始めます。近年のCSSでは、`anchor-name` のように、自分で付ける名前に `--` を求めるプロパティが増えています。すべての名前を `--` で始めておけば、プロパティごとに `--` が必要かどうかを覚えずに済み、自分で付けた名前だとすぐに分かります。将来CSSに新しいキーワードが追加されても衝突しません。本書のStylelintの設定では、`container-name-pattern` でこの形を検証しています。

コンテナの指定には、`container-type` を単体で書かず、`container` ショートハンドで名前と種類をまとめて書きます。名前と種類が1つの宣言に入るので、名前の付け忘れが起きません。また、条件には `width` ではなく `inline-size` を使います。物理方向の `width` は書字方向が変わると意味がずれるので、書字方向に依存しない `inline-size` を選びます。

AIが生成するコードでは、次のように名前のないコンテナと `width` の条件の組み合わせをよく見かけます。動作はしますが、ここまでに挙げた点がすべて守られていません。

```css title="🙅‍♂ Not Recommended: 名前のないコンテナと width の条件" issue="behavior"
/* 🙅‍♂ Not Recommended */
@scope (.scoped.media-card) to (.scoped) {
  :scope {
    container-type: inline-size;
  }

  ._layout {
    display: block grid;

    @container (width >= 400px) {
      grid-template-columns: calc(160 / 16 * 1rem) 1fr;
    }
  }
}
```

このコードでは、ルートと `._layout` の間に別のコンテナが入ると、判定の基準がそちらに変わります。条件の値もpxなので、ユーザーが文字サイズを大きくしても切り替わる幅は変わりません。コンテナサイズクエリを書くたびに、コンテナの名前、`container` ショートハンド、`inline-size`、remへの変換式の4点を確認します。閾値の決め方は「[13-2 ブレイクポイントの決め方](/responsive/breakpoints/)」で説明しています。

次のデモでは、同じカードのコンポーネントをメインエリアとサイドバーに置いています。ページ全体の段組みはメディアクエリで、カードの中の配置はコンテナサイズクエリで切り替えています。幅を768pxか1024pxにすると2カラムの表示になり、メインエリアのカードでは画像と本文が横並びに、サイドバーのカードでは縦積みのままになります。1280pxではサイドバーの幅も400pxを超えるので、どちらのカードも横並びになります。1カラムの480pxでは2枚とも横並びに、320pxでは2枚とも縦積みになり、同じカードの配置を決めているのが画面の幅ではなく置かれた場所の幅であることが分かります。

<Demo title="同じカードが、置かれた場所の幅に合わせて配置を切り替える" html={cardHtml} css={cardCss} />

切り替えられるのは、配置だけではありません。アイコンと「この記事をシェアする」のラベルを並べたシェアボタンを、本文の下とサイドバーの両方に置くとします。狭いサイドバーではラベルを隠してアイコンだけにしたい場合も、置き場所用の属性を足さずに書けます。

```css title="🙆‍♂ Recommended: 置かれた場所が狭いときだけ、ラベルを視覚的に隠す" from="responsive/share-button"
@scope (.scoped.share-button) to (.scoped) {
  :scope {
    container: --scoped / inline-size;
  }

  a {
    --_density: --compact;

    position: relative;
    display: block flex;
    column-gap: 1em;
    padding-inline: 24px;

    /* アイコン 24px 相当・隙間 16px 相当・ラベル 160px 相当と、左右の余白 24px が並ぶ幅 */
    @container --scoped (inline-size >= calc(24 / 16 * 1rem + 16 / 16 * 1rem + 160 / 16 * 1rem + 24px * 2)) {
      --_density: --spacious;
    }
  }

  ._label {
    @container style(--_density: --compact) {
      position: absolute;
      overflow: clip;
      inline-size: 4px;
      block-size: 4px;
      opacity: 0;
      pointer-events: none;
    }
  }
}
```

ここでは、ラベルを隠すスタイルを `@container style(--_density: --compact)` の中に書いています。広いときの見た目を `--spacious` の側で書く形では、隠すために指定した `position` や `inline-size` などを、すべて元に戻す宣言が要るからです。スタイルクエリに対応していない環境では、ラベルが表示されたままになります。

ラベルは `display: none` で消さずに、視覚的にだけ隠しています。アイコンのSVGは `aria-hidden="true"` で読み上げの対象から外しているので、ラベルまで消すと、リンクの名前がなくなるからです。隠し方は、4pxの透明な箱にするユーティリティの `.-visually-hidden`（「[17-5 要素を隠す方法を選ぶ](/interaction/hiding-elements/)」）と同じ考え方です。ユーティリティはHTMLに付けるクラスで、クエリの条件で付け外しできないので、同じ種類の指定をコンポーネントの中に書いています。ユーティリティは、祖先の配置に左右されないように `position: fixed` で画面の左上に置きます。ここでは、ラベルの箱をリンクの中へ収めたいので、`position: relative` の `a` を基準とする `position: absolute` を使っています。

閾値は、アイコン、隙間、ラベル、左右の `padding` が1行に並ぶ幅を式で書いています。アイコンと隙間は `em` で指定し、ラベルは文字の幅なので、どれも文字サイズに合わせて大きくなります。そこでこの3つはremに換算し、pxで指定した左右の `padding` はpxのまま足しています（「[13-2 ブレイクポイントの決め方](/responsive/breakpoints/)」）。

<Demo title="同じシェアボタンが、置かれた場所の幅に合わせてラベルを隠す" html={shareHtml} css={shareCss} />

デモでは、同じシェアボタンを本文とサイドバーに置いています。幅を768pxにすると2カラムの表示になり、サイドバーのボタンだけがラベルを隠してアイコンだけになります。1カラムになる幅や、サイドバーが広くなる1024px以上の幅では、どちらのボタンにもラベルが表示されます。

コンテナサイズクエリでは、デザイナーとのやり取りが増えやすくなります。メディアクエリなら、切り替わる幅はページで共通なので、画面の幅ごとのカンプで確認できます。コンテナサイズクエリでは、コンポーネントごとに切り替わる幅が違い、その幅はページのカンプからは読み取れません。{/* 要確認: 出典なし */}コンポーネントがどの幅でどう変わるのかは、実装の前にデザイナーと確認しておきます（「[3-2 実装の前にデザイナーと確かめること](/design-reproduction/designer-questions/)」）。

## 同じ閾値をスタイルクエリで子孫に伝える

1つの閾値で、コンポーネントの中の複数の要素を切り替えたい場面があります。画像の縦横比、見出しの文字サイズ、本文の文字サイズを、同じ幅でそろって変えるような場合です。それぞれの要素に同じ `@container --scoped (…)` を書くと、閾値が3か所に分かれ、変えるときに1か所でも直し忘れると切り替わりがずれます。

そこで、コンテナサイズクエリを書くのは、ルートの子孫の1つの要素（ここでは `._body`）のルールだけにします。`._body` はクエリの外でデフォルト値の `--_density: --compact` を宣言し、クエリの中で `--spacious` に切り替えます。ほかの子孫は、狭い幅の見た目をクエリなしで書き、広い幅の見た目をスタイルクエリ（`@container style(--_density: --spacious)`）の中に書きます。

```css title="🙆‍♂ Recommended: 閾値はフラグを宣言する要素に1回だけ書き、子孫はスタイルクエリで切り替える"
@scope (.scoped.news-card) to (.scoped) {
  :scope {
    container: --scoped / inline-size;
  }

  ._body {
    --_density: --compact;

    display: block grid;
    gap: 16px;

    /* 画像 160px 相当・隙間 16px・本文の最小幅 240px 相当が並ぶ幅 */
    @container --scoped (inline-size >= calc(160 / 16 * 1rem + 16px + 240 / 16 * 1rem)) {
      --_density: --spacious;

      grid-template-columns: calc(160 / 16 * 1rem) 1fr;
    }
  }

  ._title {
    font-size: calc(16 / 16 * 1rem);

    @container style(--_density: --spacious) {
      font-size: calc(20 / 16 * 1rem);
    }
  }
}
```

`._body` 自身の配置を同じサイズクエリの中で変えているのは、スタイルクエリでは自分自身を問い合わせられないからです。狭いときの見た目をクエリの外に書き、広いときの見た目だけをスタイルクエリの中に書くので、閾値を直す場所は `._body` の1か所です。デフォルト値を明示する理由、スタイルクエリがどの要素を問い合わせるか、ホバーとフォーカスを同じ形で伝える方法、複数の要素がそろって切り替わるデモは、「[10-6 スタイルクエリで状態を伝える](/components/style-queries/)」で説明しています。

## 画面に対する割合で切り替える

コンテナサイズクエリの条件には、ビューポート単位も書けます。`@container --scoped (inline-size >= 70svi)` は、コンテナの幅が画面の幅の7割以上かどうか、つまり、その要素が画面のどれだけを占めているかを調べます。メディアクエリは画面の幅だけを、remやpxの閾値のコンテナサイズクエリはコンテナの幅だけを見るので、この割合はどちらでも表せません。メディアクエリに `width >= 70svi` と書いても、`width` は画面の幅そのものなので、常に成り立ちます。

この条件を使うのは、「1カラムのときは画像を横長にする」のように、要素が画面の幅のほとんどを占めるときの見た目が決まっている場合です。2カラムのセクションに置いた画像だけなら、ページの段組みと同じメディアクエリで切り替えられます。しかし、同じ画像の部品を `flex-wrap: wrap` の並びにも置くと、何個目がどの幅で折り返すかはブラウザが決めるので、閾値を書けません。同じ画面の幅でも、1行目に並んだ画像と、折り返して1行を1つで占める画像とで、見た目が分かれます。remやpxの閾値も使えません。320pxの画面で縦に積んだ272pxの画像を横長にし、1024pxの画面で2つ並んだ480pxの画像はそのままにしたいので、幅の大小が要件と逆になるからです。

```css title="🙆‍♂ Recommended: 画面の幅の7割以上を占めるときだけ、画像を横長にする" from="responsive/screen-ratio-image"
@scope (.scoped.adaptive-image) to (.scoped) {
  :scope {
    container: --scoped / inline-size;
  }

  ._image {
    aspect-ratio: 4 / 3;

    /* 横に並ぶと画面の幅の5割未満、1つで1行を占めると8割以上になる。その間の7割を境にする */
    @container --scoped (inline-size >= 70svi) {
      aspect-ratio: 16 / 9;
    }
  }
}
```

境の7割は、切り替える2つの状態の割合の間にあることが根拠です。左右の余白が24pxなら、768pxの画面で2つ並んだ画像は352px（0.46）、1行を1つで占める画像は720px（0.94）です。2つの状態の割合が近いレイアウトでは、境を置く余地がないので使いません。また、基準は親ではなく画面の幅です。最大幅を決めて中央に寄せた本文の中では、広い画面ほど割合が下がり、1440pxの画面で720pxの本文の幅いっぱいに置いた画像は0.5になります。この条件は、画面に対して大きく見えるかを調べるもので、親の行を占めているかの判定には使いません。

ビューポート単位は、`vw` ではなく `svi` で書きます（「[6-2 ビューポート単位とコンテナ単位](/values/viewport-and-container-units/)」）。スクロールバーが幅を取る環境では、画面の幅とコンテナの幅の差にスクロールバーの分が入りますが、境が2つの状態の割合から離れていれば、結果は変わりません。要素の幅と画面の幅を比べて、画面いっぱいのときだけ角丸を消す書き方は、「[16-8 角の形を変える](/decoration/shapes/#画面いっぱいのときだけ角丸を消す)」で説明しています。

デモでは、2カラムのセクションと、折り返す3つの並びに、同じ画像の部品を置いています。幅を768pxにすると、セクションの画像と1行目の2つの画像は4:3のまま、折り返して1行を占める3つ目の画像だけが16:9になります。1024pxではすべて4:3に、320pxではすべて16:9になります。

## 想定より狭い場所に置かれたときのzoom

コンポーネントが、想定していた最小幅より狭い場所に差し込まれることがあります。列数を減らし、折り返し、余白を詰めても破綻を避けきれないときに限り、最後の手段として `zoom` で中身を縮小します。縮小するのは、想定の最小幅を下回ったときだけで、縮小率は `progress()` でコンテナの幅から求めます。

```css title="🙆‍♂ Recommended: 想定の最小幅を下回ったときだけ、中身を縮小する"
@scope (.scoped.article-cards) to (.scoped) {
  :scope {
    container: --scoped / inline-size;
  }

  ._body {
    /* 最小幅 200px 未満では縮小を許すが、1 を超えて拡大しない */
    @container --scoped (inline-size < calc(200 / 16 * 1rem)) {
      zoom: min(progress(100cqi, 0px, calc(200 / 16 * 1rem)), 1);
    }
  }
}
```

`progress(100cqi, 0px, calc(200 / 16 * 1rem))` は、コンテナの幅が0から200px相当までのどこにあるかを、0から1の数値で返します。コンテナが160px相当なら0.8になり、`._body` の中身は200px相当の幅で組まれたまま、0.8倍に縮小されます。`min(…, 1)` で上限を1にしているので、拡大には使いません。`zoom` を書くのは、コンテナが必ずあるルートの直下の要素です。ルート自身に書くと、`100cqi` が外側のコンテナを基準にしてしまいます。

`progress()` は2026年9月にすべての主要なブラウザで使えるようになりましたが、Safariは26からの対応です。本書の対象のSafari 18では宣言が無効になり、縮小されません。そのため、この指定はプログレッシブ・エンハンスメントとして書き、縮小されなくても中身を読めて操作できる状態を保ちます。

`zoom` は文字も含めてすべてを縮めるので、レイアウトの問題を解決せずに隠してしまいます。デザインを崩さないために乱用したり、文字サイズを縮める代わりに使ったりはしません。判断の順番は、イントリンシックなレイアウト、コンテナサイズクエリによる組み替え、最後に `zoom` です。ページ全体を `zoom` で縮小しない理由は「[13-7 カンプの幅で全体を拡大・縮小しない](/responsive/design-comp-pattern/)」で説明しています。
