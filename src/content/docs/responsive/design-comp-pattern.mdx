狭い画面用と広い画面用の2枚のデザインカンプを渡され、その間の幅では比率を保って拡大・縮小してほしいと頼まれることがあります。本書は、この要望に、カンプの幅に対する比率でページ全体を拡大・縮小する方法（フルリキッド）では応えません。文字が読めないほど小さくなる幅があり、ズームや文字サイズの設定も反映されにくくなるからです。

代わりに、ブレイクポイントは実装の段階でデザイナーと一緒に決め、コンポーネントの切り替えはコンテナサイズクエリで、ページ全体の段組みはメディアクエリで書きます。ヒーローのように拡大・縮小させたい部分があれば、その部分だけをコンテナにして、コンテナ単位（`cqi`）で組みます。

## 2枚のカンプと「768px以上はPC」という線引き

Webサイト制作の現場では、幅375pxと幅1440pxのように、スマートフォン用とPC用の2枚のカンプを渡される案件はよくあります。仕様書には「ブレイクポイントは768px」と書かれ、768px以上ではPCのカンプを、それ未満ではスマートフォンのカンプを、画面の幅に比例して拡大・縮小するよう求められます。

この要望をそのまま実装するなら、画面の幅とカンプの幅の比率を求め、ページ全体の寸法に掛けます。次の例では、画面の幅をカンプの幅で割った値を `:root` で単位として定義し、それをカンプ上のピクセル値に掛けています。

```css title="🙅‍♂ Not Recommended: カンプの幅に対する比率でページ全体を拡大・縮小する" issue="behavior"
/* 🙅‍♂ Not Recommended */
:root {
  --px: calc(100vw / 1440);

  @media (width < 768px) {
    --px: calc(100vw / 375);
  }
}

._heading {
  font-size: calc(32 * var(--px));
}

._section {
  padding-block: calc(80 * var(--px));
}
```

この方法なら、カンプの幅ではカンプと同じ寸法になり、その間の幅でも見た目の比率が保たれます。寸法をカンプからそのまま書き写せるので、実装の手間も少なく見えます。しかし、カンプの幅から離れるほど、次の節で説明する問題が大きくなります。

## 全体を比例で拡大・縮小すると起きること

1つ目の問題は、文字の大きさです。1440pxのカンプで16pxの本文は、幅768pxの画面では約8.5px、幅1024pxでも約11.4pxに縮みます。768px以上をPCのカンプの縮小にすると、縦向きのiPadでは、本文がこの大きさで表示されます。反対に、スマートフォンのカンプを拡大する側では、幅767pxの画面で本文が約33pxになり、1画面に入る情報が極端に減ります。

2つ目の問題は、ズームと文字サイズの設定です。比率をビューポート単位から求めると、文字サイズは画面の幅だけで決まり、ブラウザの文字サイズの設定を大きくしても変わりません。さらに、ビューポート単位だけで決めた値は、ズームしても画面上の大きさが変わりません。ズームするとCSSピクセルで数えたビューポートの幅が狭くなり、その分だけ値が小さく計算されるからです（「[6-2 ビューポート単位とコンテナ単位](/values/viewport-and-container-units/)」）。縮んだ文字を拡大して読もうとしても、文字は大きくなりません。文字を200%まで拡大できることは、WCAGの達成基準1.4.4（テキストのサイズ変更）が求める要件でもあります。

3つ目の問題は、どの幅でも同じ配置を縮めているだけで、画面に合わせて配置を変えていないことです。縦向きのiPadに表示されるのは、PCのレイアウトを縮小したものです。これはビューポートの幅を固定して表示全体を縮小するのと変わらず、画面の幅に合わせて配置を組み替えるレスポンシブ対応にはなっていません。

4つ目の問題は、「768px以上はPC」という線引きそのものに根拠がないことです。Webサイトが表示される画面の幅は2,000種類以上あると言われ、2枚のカンプと1本の線で、そのすべての幅での見え方を決めることはできません。カンプのない幅のどこかで、文字が詰まりすぎたり、要素が重なったりする可能性が高いでしょう。ブレイクポイントは、デバイスの分類ではなく、レイアウトが崩れる幅から決めるものです（「[13-2 ブレイクポイントの決め方](/responsive/breakpoints/)」）。

## 切り替えの基準は画面の幅から使えるスペースへ

全体を比例で拡大・縮小する方法には、コンポーネントの置き場所の問題もあります。同じカードをメインエリアとサイドバーの両方に置く場合があるように、コンポーネントの置き場所は変わります。画面の幅を基準に寸法を決めると、画面が広いという理由で、狭いサイドバーの中のカードにもPCの寸法が当てはまります。

<Baseline id="container-queries" name="コンテナサイズクエリ" />

コンテナサイズクエリは2025年8月に「広く利用可能」になりました。これで、コンポーネントの切り替えの基準を、画面の幅から、そのコンポーネントが使えるスペースの幅へ移せます。本書では、コンポーネントの切り替えをコンテナサイズクエリで書きます（「[13-3 コンテナサイズクエリ](/responsive/container-size-queries/)」）。メディアクエリを使うのは、モーダルや `position: fixed` の要素のようにビューポートに密着するものと、ページ全体の段組みです。画面そのものが基準になる場面で使うのが、メディアクエリの本来の用途です。

幅に応じて連続的に変えたい値も、全体に比率を掛けずに、値ごとに `clamp()` で範囲を決めます。最小値と最大値をremにし、推奨値をremと相対単位の和にすれば、文字サイズの設定とズームにも追従します（「[6-3 計算関数で根拠を式に残す](/values/math-functions/)」）。変える値と変えない値は、1つずつ判断します。本文やボタンの文字は、ほとんどの場合、画面の幅で大きさを変えなくて済みます。

ヒーローヘッダーのように、幅に合わせて大きさを変えると見栄えがよくなる部分もあります。そうした部分は、そこだけを名前付きのコンテナにし、コンテナの幅を基準にする `cqi` で組みます。ビューポート単位を使わないので、ヒーローがページの幅いっぱいに置かれても、2カラムのメインエリアに置かれても、置かれた場所の幅に合わせて拡大・縮小します。

```css title="🙆‍♂ Recommended: 拡大・縮小させたいヒーローだけを、コンテナの単位で組む" from="responsive/hero-cqi"
@scope (.scoped.page-hero) to (.scoped) {
  :scope {
    container: --scoped / inline-size;
  }

  ._hero-inner {
    display: block grid;
    gap: clamp(16px, 3cqi, 32px);
    padding-block: clamp(40px, 8cqi, 120px);
    padding-inline: clamp(20px, 5cqi, 80px);
  }

  h1 {
    /* コンテナの幅 375px で 32px、1440px で 72px */
    font-size: clamp(32 / 16 * 1rem, 3.756cqi + 17.92 / 16 * 1rem, 72 / 16 * 1rem);
  }
}
```

見出しの文字サイズは、`clamp()` の最小値と最大値をremにし、推奨値を `cqi` とremの和にしています。基準の幅は画面ではなくコンテナの幅で、幅375pxで32px、1440pxで72pxになるように、2点を結ぶ直線の傾きと切片を求めています。余白と隙間は文字サイズの設定に追従させる必要がないので、最小値と最大値をpxで書いています。

`cqi` は、名前付きのコンテナがあると言い切れる要素でだけ使います。有効なコンテナが見つからないと、`cqi` は小さいビューポートの単位（`svi`）として計算され、置き場所によって値の意味が変わるからです。この例では、コンテナを `:scope` に置き、`cqi` を使うのはその子孫の要素だけにしています。コンテナ自身には余白を付けず、余白は子の要素に付けます。

次のデモで幅を変えると、見出しと余白がヒーローの幅に合わせて拡大・縮小します。説明の文とボタンの文字サイズは、どの幅でも変わりません。

## ブレイクポイントをデザイナーと決める

仕様書の「ブレイクポイントは◯◯px」という記述は、実装の段階で決めることを合意したうえで、消してもらいます。カンプの段階では、レイアウトが崩れ始める幅を確かめる手段がないからです。ブレイクポイントは、実装したページの幅を変えながら、デザイナーと一緒に決めます。

すり合わせるのは、何を保つかと、どこからを崩れとみなすかの2つです。保つものには、本文の読みやすさ、1画面に入る情報の量、画像の縦横比、CTA（行動を促すボタン）の見つけやすさなどがあります。崩れとみなす基準には、カラムの数を変える時点や、幅が足りなくなったときに余白を削る順番があります。この2つが決まっていれば、カンプのない幅での見え方を、実装者が根拠を持って判断できます。

実装の前にデザイナーと確かめておくことは、「[3-2 実装の前にデザイナーと確かめること](/design-reproduction/designer-questions/)」にまとめています。カンプのない幅での振る舞いも、その1つです。

## 補足と注意点

画面の幅を `calc(100svi / 1px)` で数値に変え、そこから比率を求める書き方もあります。しかし、`vw` を `svi` に変えても、ページ全体を比例で拡大・縮小する点は同じで、前に挙げた問題はそのまま残ります。Chromeでは、長さどうしの割り算で求めた値がブラウザのズームで拡大縮小されないので（「[6-4 計算関数を応用する](/values/advanced-math-functions/)」）、文字サイズへの影響はむしろ大きくなります。

`zoom` プロパティで表示全体を縮小する方法も、同じ理由で使いません。文字も含めてすべてが縮み、レイアウトの問題を解決せずに隠してしまうからです。想定の最小幅を下回ると破綻するコンポーネントに限り、`1` を上限とする最後の保険として使う余地があります（「[13-3 コンテナサイズクエリ](/responsive/container-size-queries/)」）。

本書が表示全体の縮小を認めるのは、375pxより狭い画面だけです。300px前後の折りたたみ端末のような画面でもカンプの配置を保つ要件があるときに限り、スクリプトでビューポートの幅を375pxに固定し、表示全体を縮小します（「[13-6 375px未満の画面で配置を保つ例外](/responsive/min-viewport-width/)」）。対象を実際に狭い端末に限っているので、それより広い画面では、ここまでの方法で組んだレイアウトがそのまま表示されます。

比率を保ってほしいという要望の背景には、カンプで作った全体の印象を崩したくないという意図のある場合が多いはずです。その意図には、デザイナーとすり合わせた「保つもの」で応えます。カンプの幅でカンプと同じ見え方になるように値を決め、その間の幅では、保つものを守れる範囲で値を変えます。
