本書でメディアクエリを使うのは、3つの場面です。ビューポートを基準にするページ全体の段組み（とビューポートに固定した要素）、動きを減らすといったユーザーの設定、ホバーやポインターの精度といった入力の手段です。幅の条件は `min-width` ではなく範囲構文で書き、メディア特性は、使うもの、使わないもの、まだ使えないものに分けて選びます。

コンポーネントの中の切り替えは、先に「[13-3 コンテナサイズクエリ](/responsive/container-size-queries/)」で書けないかを考えます。ブレイクポイントの値の決め方と書き方は、「[13-2 ブレイクポイントの決め方](/responsive/breakpoints/)」で説明しています。

## 端末を調べる書き方の問題

メディアクエリでよく見かけるのは、次のような書き方です。`screen` のメディアタイプと `min-width` を組み合わせ、端末の画面の大きさを調べる `device-width` を使う例もあります。

```css title="🙅‍♂ Not Recommended: min-width と device-width で書く" issue="behavior"
/* 🙅‍♂ Not Recommended */
._main {
  @media screen and (min-width: 768px) {
    inline-size: 70%;
  }

  @media screen and (max-width: 767px) {
    inline-size: 100%;
  }
}

._nav {
  @media (min-device-width: 1024px) {
    display: block flex;
  }
}
```

`min-width: 768px` と `max-width: 767px` を組み合わせると、幅が767.5pxのように小数になったとき、どちらの条件にも当てはまらない隙間ができます。ズームしたときや、高解像度の画面でウィンドウの幅を変えたときには、幅が小数になることがあります。

`device-width` と `device-height`（`device-aspect-ratio` も同様）は使いません。これらが調べるのは端末の画面そのものの大きさで、ブラウザのウィンドウが実際に使える幅ではありません。ウィンドウを狭めたり、分割表示にしたり、ズームしたりしても値は変わらないため、レイアウトの判断に使えません。MDNも新しいプロジェクトでは避けるよう書いており、代わりに `width` を使います。

`screen` のメディアタイプも書きません。印刷のスタイルと分ける必要があるときに `print` を書けば足り、`screen and` を付けても条件が読みにくくなるだけだからです。印刷のスタイルは第16章で説明します。{/* 第16章の執筆後にリンクする: /decoration/print/ */}

## 範囲構文で書く

条件は、`>=` や `<` を使う範囲構文で書きます。範囲構文なら、条件を不等式としてそのまま読め、境界の値を含むかどうかも明確です。2つの境界の間は1つの条件で書けるので、`min-width` と `max-width` を組み合わせたときの隙間も生じません。

```css title="🙆‍♂ Recommended: 範囲構文で書き、閾値をremに変換する"
._layout {
  display: block grid;

  @media (width >= calc(720 / 16 * 1rem)) {
    grid-template-columns: 1fr calc(240 / 16 * 1rem);
  }
}
```

2つの閾値の間だけに当てはめる場合は、下限を含み上限を含まない形（`<=` と `<`）にそろえます。隣り合う範囲の境界の幅は片方の範囲だけに属するため、重複する幅と、どの範囲にも入らない幅は生じません。本書のStylelintの設定では、メディアクエリに範囲構文を使っているかを `media-feature-range-notation` で検証しています。

```css title="🙆‍♂ Recommended: 2つの閾値の間を1つの条件で書く"
._banner {
  @media (calc(640 / 16 * 1rem) <= width < calc(1024 / 16 * 1rem)) {
    padding-inline: 24px;
  }
}
```

閾値をremで書く理由と、`calc(640 / 16 * 1rem)` の形にする理由は、「[13-2 ブレイクポイントの決め方](/responsive/breakpoints/)」で説明しています。範囲構文はコンテナサイズクエリの条件にも使い、`@container --scoped (inline-size >= …)` のように書きます。

## 基本にするスタイルと広い画面の差分

メディアクエリを使うときは、狭い画面向けのスタイルを基本に書き、広い画面で必要になる差分だけをクエリの中に足します。いわゆるモバイルファーストの書き方で、条件は `width >=` の形が中心になります。

```css title="🙆‍♂ Recommended: 基本は狭い画面向けに書き、広い画面の差分を足す"
._nav-links {
  display: none;

  @media (width >= calc(768 / 16 * 1rem)) {
    display: block flex;
  }
}
```

狭い画面を基本にするのは、多くの場合、狭い画面のレイアウトのほうが単純だからです。1カラムに積んだ状態を基本にしておけば、広い画面で段組みを足す差分は小さく済みます。広い画面の複雑なレイアウトを基本にすると、狭い画面で打ち消すための指定が増えていきます。

条件付きのアットルールは、上のコード例のように各セレクタの中に書きます。条件のブロックをファイルやスコープの先頭にまとめて置くと、同じ詳細度の元のルールがその後ろに来たとき、後ろのルールが優先され、条件付きの指定が打ち消されてしまうからです。この規約は「[9-5 ネストの書き方](/notation/nesting/)」で説明しています。

次のデモは、本文とサイドバーの2カラムを、ページ全体の幅で切り替えています。閾値は、本文の最小幅とサイドバーの幅と隙間を足した式で書いています。ページの左右に余白（ガター）があるなら、その幅も式に足します。このデモはページの左右に余白を取らないので、式は3つの項だけです。

<Demo title="本文とサイドバーの段組みを、成り立つ幅でだけ2カラムにする" html={pageHtml} css={pageCss} bleed="inline" />

文字サイズが標準のとき、832pxより狭い画面では、サイドバーが本文の下に回ります。このように、ページ全体の骨組みはメディアクエリで、その中に置くコンポーネントはコンテナサイズクエリで切り替えるのが、本書の基本の役割分担です。

この役割分担は、部屋と家具にたとえると整理できます。部屋がページ（ほぼビューポート）で、家具がヘッダーや本文、サイドバーといったランドマークやセクションです。家具の配置や数、大きさは部屋の大きさで決まるので、ページ全体のレイアウト（マクロレイアウト）としてメディアクエリで扱います。家具の上に置くボタンやカードの配置は、置かれた家具の大きさで決まるので、部分のレイアウト（ミクロレイアウト）としてコンテナサイズクエリで扱います。

## 幅のメディアクエリを使う場面

幅のメディアクエリを使ってよいのは、ページ全体の段組みの切り替え、モーダルやトーストのようにビューポートに固定される要素、そして常に画面幅いっぱいに表示され、ほかの場所に置かれることがないと言い切れるブロック（ヒーローヘッダーなど）です。どれも、ビューポートの大きさそのものが判断の基準になります。モーダルやトーストは、マークアップ上のどこに書かれていても、表示されるときはビューポートを基準に配置されます。

ヒーローヘッダーのようなブロックは、「ほかの場所に置かれることがない」と言い切れるかどうかが分かれ目です。同じ見た目のブロックを記事の途中にも置く可能性があるなら、コンテナサイズクエリで書いておくほうが安全です。ブロックの幅がビューポートの幅と一致しなくなり、ビューポートを基準にした切り替えが合わなくなるからです。ビューポート単位（`svi` や `svb`）も、同じ基準で使い分けます（「[6-2 ビューポート単位とコンテナ単位](/values/viewport-and-container-units/)」）。

画面の幅で画像を差し替えるときは、CSSの `background-image` を切り替えずに、HTMLの `<picture>` の `<source>` に `media` 属性で条件を書きます。`media` 属性はビューポートを基準にするメディアクエリで、範囲構文もそのまま使えます。写真を `<img>` で置く理由は「[16-1 画像の配置と比率](/decoration/images/)」で説明しています。

```html
<picture>
  <source media="(width >= calc(768 / 16 * 1rem))" srcset="hero-wide.avif" width="1440" height="600" />
  <img src="hero-narrow.avif" alt="…" width="750" height="900" />
</picture>
```

## メディア特性の使い分け

メディアクエリは、画面の幅のほかに、ユーザーの設定や入力の手段も調べられます。本書では、メディア特性を次のように使い分けます。判断は、web-featuresの対応状況と本書のほかのルールにもとづいています。

| メディア特性 | 判断 | 理由と説明している場所 |
| --- | --- | --- |
| `width`（範囲構文） | 使う | ページ全体の段組み。この節 |
| `height`（範囲構文） | 使う | ビューポートの高さが十分なときだけヘッダーを固定する。[11-7](/layout-practice/sticky-header/#rule-sticky-header-height-query) |
| `prefers-reduced-motion` | 使う | 動きを減らす設定。[18-2](/motion/reduced-motion/) |
| `any-hover` | 使う | ホバーできる入力があるか。値なしの `(any-hover)` と書く。[17-1](/interaction/states-and-focus/) |
| `any-pointer` | 使う | 入力の精度。この節 |
| `prefers-contrast` | 使う | コントラストを上げる設定。この節 |
| `forced-colors` | 使う | 強制カラーモード。[15-5](/color-media/forced-colors/) |
| `prefers-color-scheme` | トークンでだけ使う | コンポーネントには書かず、トークンの `light-dark()` で切り替える。[15-4](/color-media/dark-mode/) |
| `scripting` | 使う | JavaScriptが使えるか。[1-2](/principles/browser-support/) |
| `print`（メディアタイプ） | 使う | 印刷のスタイル。16-11 |
| `prefers-reduced-transparency` | 追加の対策として使う | Chrome系だけが対応。この節 |
| `min-width`、`max-width` | 使わない | 範囲構文で書く |
| `device-width`、`device-height`、`device-aspect-ratio` | 使わない | 端末の画面の大きさで、使える幅ではない |
| `hover`、`pointer` | 使わない | 主な入力しか調べない。`any-hover` と `any-pointer` を使う |
| `orientation` | 使わない | 端末の向きではなく、ビューポートの縦横を比べる |
| `resolution` | 使わない | 画像の解像度は `srcset` で選ばせる |
| `screen`（メディアタイプ） | 書かない | `print` と分けるときだけ `print` を書く |
| `display-mode` | 使わない | インストールしたアプリの表示を調べるもので、Webサイトの制作では使わない |
| `color-gamut`、`dynamic-range` | 使わない | 範囲外の色はブラウザが置き換える。[15-1](/color-media/color/) |
| `inverted-colors` | まだ使えない | Safariだけが対応 |
| `prefers-reduced-data` | まだ使えない | どのブラウザも対応していない |
| `@custom-media` | まだ使えない | どのブラウザも対応していない |

`orientation` は、ビューポートの高さが幅以上なら `portrait`、そうでなければ `landscape` になります。端末の向きを調べるものではないので、縦向きのスマートフォンでもソフトウェアキーボードが出るとビューポートが横長になり、`landscape` と判定されることがあります。使える幅を知りたいなら、`width` で判定します。

{/* 要確認: 出典なし */}`display-mode` は、ホーム画面に追加したWebアプリの表示のされ方を調べるメディア特性です。本書が対象にするコーポレートサイトやLPでは分岐が要らず、`fullscreen` の値はSafariとデスクトップのFirefoxが対応していません。`color-gamut` と `dynamic-range` は対応がそろっていますが、`oklch()` で書いた色が画面で表示できる範囲を超えると、ブラウザが近い色に置き換えて描画するので、通常は分岐を書かずに済みます。

`@custom-media` は、`@custom-media --wide (width >= calc(768 / 16 * 1rem));` のように条件に名前を付けて使い回す仕様です。ブラウザが対応すれば、メディアクエリの条件に `var()` を書けない問題（「[13-2 ブレイクポイントの決め方](/responsive/breakpoints/)」）を解決できますが、どのブラウザも対応していません。

## 入力の手段を調べるany-pointer

操作の手段に合わせて変えたい指定は、画面の幅では判定しません。幅の狭いデスクトップのウィンドウはマウスで操作され、幅の広いタブレットは指で操作されるからです。入力の精度は `any-pointer` で調べます。値は `fine`（マウスやトラックパッドのように精度が高い）、`coarse`（タッチのように精度が低い）、`none` の3つです。

`pointer` は主な入力だけを、`any-pointer` は使える入力のどれかひとつでも条件に当てはまるかを調べます。タッチ操作が主なタブレットにマウスをつなぐと、`pointer` は `coarse` のままですが、`any-pointer` は `coarse` と `fine` の両方に当てはまります。そのため、`pointer: fine` で判定すると、つないだマウスを取りこぼします。ホバーの判定に `any-hover` を選ぶ理由と同じです。

```css title="🙆‍♂ Recommended: 精度の高い入力があるときだけ、ドラッグ用のつまみを表示する"
._resize-handle {
  display: none;

  @media (any-pointer: fine) {
    display: block flow;
  }
}
```

## コントラストと透明度の設定

`prefers-contrast` は、OSでコントラストを上げる、または下げる設定にしているかを調べます。値は `no-preference`、`more`、`less`、`custom` の4つです。`custom` は強制カラーモードの状態に当たり、ユーザーが選んだ配色で色が上書きされるので、色の指定は要りません。薄い灰色の境界線や補助テキストで区別や意味を伝えている部品は、`more` のときに色を濃くします。

`forced-colors` は配色を上書きするモードですが、`prefers-contrast: more` は配色を上書きせず、コントラストを上げてほしいという希望だけを伝えます。強制カラーモードに対応しただけでは、この設定のユーザーには薄い色が残ります。強制カラーモードの扱いは「[15-5 強制カラーモードとコントラスト](/color-media/forced-colors/)」で説明しています。

```css title="🙆‍♂ Recommended: コントラストを上げる設定のときに区切り線を濃くする"
._entry {
  & + & {
    border-block-start: 1px solid var(--border--base);

    @media (prefers-contrast: more) {
      border-block-start-color: var(--foreground--muted);
    }
  }
}
```

この例の区切り線は、記事の一覧の項目を見た目で分けるだけの線です。入力欄の枠線のように、UI部品の範囲を示す線は、この設定と関係なく、隣り合う色と3:1以上の差にします（「[15-5 強制カラーモードとコントラスト](/color-media/forced-colors/#コントラスト比を確かめる)」）。

<Baseline id="prefers-contrast" name="prefers-contrast メディア特性" />

`prefers-reduced-transparency` は、OSで透明度を下げる設定（macOSとiOSの「透明度を下げる」、Windowsの「透明効果」をオフにする設定）にしているかを調べます。値は `no-preference` と `reduce` の2つです。半透明の背景や `backdrop-filter` のすりガラスの上に文字を置いた部品は、背景の写真や色によって文字が読みにくくなるので、`reduce` のときは背景を不透明にします。

```css title="🙆‍♂ Recommended: 透明度を下げる設定のときに背景を不透明にする"
._overlay {
  background-color: oklch(from var(--background--surface) l c h / 70%);
  backdrop-filter: blur(12px);

  @media (prefers-reduced-transparency: reduce) {
    background-color: var(--background--surface);
    backdrop-filter: initial;
  }
}
```

<Baseline id="prefers-reduced-transparency" name="prefers-reduced-transparency メディア特性" />

`prefers-reduced-transparency` に対応しているのはChrome系のブラウザだけです。対応していない環境では条件が成り立たず、半透明のまま表示されます。そのため、半透明の状態でも文字と背景のコントラストが足りる色を選んだうえで、設定に応じてさらに読みやすくする指定として書きます。
