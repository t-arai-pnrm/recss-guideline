カルーセルは、スクロールスナップで作った横スクロールを土台にします。ページ送りのボタンは `::scroll-button()`、現在の位置を示すインジケーターは `::scroll-marker` と `::scroll-marker-group` で足し、JavaScriptは使いません。止まっていないスライドは、`scroll-state()` のコンテナクエリと `interactivity: inert` で、読み上げとフォーカスの対象から外します。

これらの擬似要素に対応しているのはChrome系のブラウザだけです。そのため、ボタンとインジケーター、スクロールバーを消す指定は `@supports` の中に書き、未対応の環境ではスクロールバー付きの横スクロールとして読めるようにします。未対応の環境でもページ送りのボタンが要件として求められるときに限り、HTMLの `<button>` から `scrollBy()` を呼ぶだけのスクリプトを足します。そのうえで、カルーセルにする必要があるのかを先に検討します。

## カルーセルを使う前に考えること

カルーセルは、限られた面積に多くの情報を詰め込める部品として、トップページのメインビジュアルや事例の紹介によく使われます。ただし、自動で再生しない限り、2枚目以降のスライドはユーザーが操作するまで表示されません。私の経験では、自動で切り替わるカルーセルでも、ユーザーが最後まで見ることはほとんどありません。

自動再生には、アクセシビリティの面でも高い敷居があります。WCAGの達成基準2.2.2は、対象を2つに分けています。動き、点滅、スクロールする情報のうち、自動で始まり、5秒を超えて続き、ほかの内容と並べて表示されるものには、一時停止、停止、非表示のいずれかの手段を求めます。自動で更新される情報には5秒の猶予がなく、自動で始まりほかの内容と並べて表示されるなら、一時停止、停止、非表示か、更新の頻度を変える手段を求めます。どちらも、その動きや更新が活動に欠かせない場合は例外です。自動で切り替わるカルーセルは、5秒より短い間隔で切り替わっても、全体としては5秒を超えて動き続けるので、前者に当たります。停止ボタンを置いても、読み上げの途中でスライドが切り替わる、キーボードで操作している途中にフォーカスしていた要素が画面の外へ流れる、といった問題が残ります。本書では、カルーセルを自動で再生しません。動きを減らす設定への対応を整理した「[18-2 動きを減らす設定に対応する](/motion/reduced-motion/)」の表でも、自動で回るカルーセルは、設定があれば動きを止める側に分類しています。

CSSだけでカルーセルを作れるようになっても、こうした問題は解決しません。変わるのは実装の手段だけです。2枚目以降が見られにくいことや、どこまで見たのか分かりにくいことは、カルーセルというUIそのものの性質です。カルーセルを選ぶ前に、カードを一覧で並べられないかを検討します。{/* 要確認: 出典なし */}4〜6件の事例なら、グリッドで並べれば一覧性が高く、すべてのカードが最初から目に入ります。

それでもカルーセルを選ぶのは、セクションの中のちょっとしたエリアで、補足的な情報を横に流して見せたいような場面です。このとき、カルーセルの機能が動かなくても内容を読めることを前提にし、ボタンやインジケーターは対応した環境で足す、プログレッシブ・エンハンスメントとして作ります。

## スクロールスナップを土台にする

カルーセルの土台は、`overflow-x: auto` の横スクロールと、`scroll-snap-type` によるスクロールスナップです。スクロールスナップは、スクロールが終わったときに、スライドの端や中央が決まった位置で止まるようにする仕組みです。すべてのブラウザで使えるので、ボタンやインジケーターに対応していない環境でも、スワイプやスクロールバーでスライドを1枚ずつ送れます。

<Baseline id="scroll-snap" />

```css title="🙆‍♂ Recommended: 横スクロールとスクロールスナップでスライドを並べる"
@scope (.scoped.css-carousel) to (.scoped) {
  ul {
    display: block grid;
    grid-auto-columns: 100%;
    grid-auto-flow: column;
    gap: 16px;
    overflow-x: auto;
    overscroll-behavior-inline: contain;
    scroll-snap-type: inline mandatory;

    @media (prefers-reduced-motion: no-preference) {
      scroll-behavior: smooth;
    }

    & > ._slide {
      scroll-snap-align: center;
    }
  }
}
```

スライドの `li` には `_slide` のクラスを付け、グリッドの列として並べ、`grid-auto-columns` で1枚の幅を決めます。`100%` なら1枚ずつ、`calc((100% - 16px * 2) / 3)` なら3枚ずつ見える形になります。`scroll-snap-type: inline mandatory` は、インライン方向のスクロールが終わったとき、必ずどれかのスライドの位置で止める指定です。`overscroll-behavior-inline: contain` は、端までスクロールしたときに、横のスワイプがブラウザの「戻る」の操作として扱われるのを防ぎます。ボタンやインジケーターを除いた横スクロールの部分は、コンポジション `reel` と同じ組み方です（「[12-12 reel](/compositions/reel/)」）。

`scroll-behavior: smooth` は、後で足すボタンやインジケーターを押したときのスクロールを滑らかにします。`::scroll-marker` を押したときは、スクロールコンテナの `scroll-behavior` が `smooth` なら滑らかに、`auto` なら即座に移動しました。動きを減らす設定のユーザーには移動を即座に済ませたいので、`prefers-reduced-motion: no-preference` の条件の中に書きます。ページ全体の `scroll-behavior` の扱いは「[8-2 ベーススタイルに書くもの](/reset/base-styles/)」で説明しています。

## `::scroll-button()` と `::scroll-marker` でボタンとインジケーターを作る

`::scroll-button()` は、スクロールコンテナに生成される、ページ送りのボタンの擬似要素です。引数の `inline-start` や `inline-end` でスクロールする方向を指定し、`content` に `none` 以外の値を書くと生成されます。押すと、スクロールコンテナのおよそ1画面分だけスクロールし、スクロールスナップがあればその先のスライドで止まります。それ以上スクロールできない方向のボタンは自動で無効になるので、`:disabled` で見た目を変えます。

<Baseline id="scroll-buttons" name="::scroll-button()" />

`::scroll-marker` は、スクロールコンテナの中の要素（ここではスライド）に生成される、インジケーターの点の擬似要素です。スクロールコンテナに `scroll-marker-group: after`（または `before`）を指定すると、点をまとめる `::scroll-marker-group` が生成され、点を押すと対応するスライドまでスクロールします。表示しているスライドの点は、`:target-current` 擬似クラスで選べます。スクロールマーカーの別の使い方として、目次のページ内リンクに `:target-current` を当てはめる方法を、このページの最後の「[発展：ページ内リンクを現在位置の印にする scroll-target-group](#発展ページ内リンクを現在位置の印にする-scroll-target-group)」で紹介します。

<Baseline id="scroll-markers" name="::scroll-marker と ::scroll-marker-group" />

```css title="🙆‍♂ Recommended: ボタンとインジケーターを、対応した環境でだけ生成する"
@scope (.scoped.css-carousel) to (.scoped) {
  ul {
    anchor-name: --css-carousel;

    /* ... */

    @supports selector(::scroll-button(*)) {
      scroll-marker-group: after;
      scrollbar-width: none;

      &::scroll-button(*) {
        position: absolute;
        inset-block-start: anchor(center);
        position-anchor: --css-carousel;
        translate: 0 -50%;
      }

      &::scroll-button(*):disabled {
        opacity: 0.3;
      }

      &::scroll-button(inline-start) {
        content: "←" / "前の事例";
        inset-inline-start: calc(anchor(start) + 8px);
      }

      &::scroll-button(inline-end) {
        content: "→" / "次の事例";
        inset-inline-end: calc(anchor(end) + 8px);
      }
    }
  }

  ._slide {
    @supports selector(::scroll-marker) {
      &::scroll-marker {
        content: "" / attr(data-label);
        inline-size: 12px;
        min-block-size: 12px;
        border: 1px solid transparent;
        background-color: var(--border--strong);
      }

      &::scroll-marker:target-current {
        inline-size: 32px;
        background-color: var(--background--accent);

        @media (forced-colors: active) {
          background-color: CanvasText;
        }
      }
    }
  }
}
```

ボタンは、アンカーポジショニングでスクロールコンテナの左右の中央に重ねています。`content` のスラッシュの後ろは代替テキストで、ボタンや点の名前として読み上げられます。MDNによれば、ブラウザはボタンに適切な名前を自動で付けることになっていますが、日本語のページでは「前の事例」のように内容に合った名前を明示します。点の `content` を `""` だけにすると、名前が空になります。そこで、スライドの `data-label` 属性に「1件目」のような名前を書き、`attr()` で代替テキストに渡しています。

表示しているスライドの点は、色を変えるだけでなく、`inline-size` を広げて横長の形にしています。色の違いだけでは、色を見分けにくいユーザーや、色がシステムカラーに置き換わる強制カラーモードで、現在位置が分からなくなるからです。点には透明な枠線を付けておき、強制カラーモードで背景色がページの背景色に置き換わっても、輪郭が残るようにします。そのうえで、強制カラーモードでは現在位置の点だけを `CanvasText` で塗ります（「[15-5 強制カラーモードとコントラスト](/color-media/forced-colors/)」）。

キーボードでの操作も、ブラウザが用意します。Chromeで確かめたところ、Tabキーの順番は、前後のボタン、表示しているスライドの中身、カルーセルの後ろの要素の順でした。最初のスライドでは「←」のボタンが無効なので、飛ばされます。MDNは、点のグループがタブのリストとして扱われ、矢印キーでスライドを切り替えられると説明していますが、この確認ではTabキーで点のグループに移動しませんでした。キーボードで操作するユーザーには、前後のボタンを必ず用意します。

## 隠れているスライドを読み上げとフォーカスから外す

横スクロールで隠れているスライドも、DOMの中には残っています。何もしなければ、スクリーンリーダーは画面に見えていないスライドの中身まで読み上げ、Tabキーでは隠れているスライドのリンクにフォーカスが移ります。見えている1枚の後に、見えていない数枚分の読み上げとフォーカスが続くので、カルーセルの後ろにある内容までなかなかたどり着けません。

そこで、スライドを `scroll-state` のコンテナにし（名前は、クラス名から下線を除いた `--slide`）、スナップして止まっていないスライドの中身を `interactivity: inert` にします。`interactivity: inert` は、HTMLの `inert` 属性と同じ不活性の状態を、CSSから指定するプロパティです。不活性になった要素は、クリックとフォーカスができなくなり、アクセシビリティツリーからも外れます。`inert` の別の使い方として、ドロワーを開いている間に背面を操作できなくする方法を「[17-6 開閉するUI](/interaction/disclosure/#ドロワーの背面を不活性にする方法)」で説明しています。

<Baseline id="container-scroll-state-queries" name="scroll-state() のコンテナクエリ" />

<Baseline id="interactivity" name="interactivity" />

```css title="🙆‍♂ Recommended: 止まっていないスライドの中身を不活性にする" from="interaction/css-carousel"
@scope (.scoped.css-carousel) to (.scoped) {
  ul {
    /* ... */

    & > ._slide {
      scroll-snap-align: center;
    }
  }

  ._slide {
    container: --slide / scroll-state;
  }

  article {
    @container --slide not scroll-state(snapped: inline) {
      interactivity: inert;
    }
  }
}
```

`scroll-state(snapped: inline)` は、コンテナの要素が、インライン方向のスナップで止まっている位置にある間だけ成り立つ条件です。`not` で反転し、止まっていないスライドだけを対象にします。コンテナクエリで変えられるのはコンテナの子孫だけなので、`interactivity` はスライド（`._slide`）ではなく、その中のカード（`article`）に指定します。Chromeで確かめたところ、最初は1枚目のカードだけが `auto` で残りは `inert` でした。1枚分スクロールすると、2枚目だけが `auto` に変わりました。

この挙動は、JavaScriptのカルーセルのライブラリ（Splideなど）が、隠れているスライドに対して行っている処理と同じです。見えているスライドのリンクでTabキーを押すと、隠れているスライドのリンクを飛ばして、カルーセルの後ろの要素に移ります。読み上げも、見えている1枚だけで済みます。

この方法は、スライドを1枚ずつ表示するカルーセルを前提にしています。「スナップして止まっている」と「画面に見えている」は、別の状態だからです。`grid-auto-columns` を3枚ずつ見える幅にすると、スナップの位置で止まっているのは先頭の1枚だけになり、隣に見えている2枚は `inert` になります。{/* 要確認: 出典なし */}見えているのに、クリックとフォーカスのできないスライドができてしまいます。複数枚を表示するときは、不活性にする条件を見直すか、`interactivity: inert` を使わずに、フォーカスが移ったスライドまで自動でスクロールする振る舞いに任せます。

`interactivity` は継承するプロパティで、不活性にした要素の子孫は、`interactivity: auto` を指定しても操作できるようになりません。Chromeで、`inert` の要素の中にある `auto` のリンクにフォーカスできないことを確かめました。不活性にするのは、操作させたくない範囲をちょうど包む要素だけにします。

次のデモは、施工事例を1件ずつ見せるカルーセルです。左右のボタンで1件ずつ送り、下の点で任意の事例に移動できます。最初の事例では「←」のボタンが無効になり、薄く表示されます。

<Demo title="::scroll-button() と ::scroll-marker で作った、JavaScriptを使わないカルーセル" html={carouselHtml} css={carouselCss} />

Chrome系のブラウザでは、スクロールバーが消え、ボタンと点が表示されます。Tabキーで移動すると、表示している事例の「事例を見る」のリンクだけにフォーカスが止まり、隠れている事例のリンクは飛ばされます。SafariやFirefoxで開くと、ボタンと点は表示されず、スクロールバー付きの横スクロールになります。

## 未対応の環境での見え方と `@supports`

未対応の環境では、`::scroll-button()` と `::scroll-marker` のルールは無効になり、ボタンとインジケーターは表示されません。このとき、スクロールバーまで消していると、ユーザーは横にスクロールできると気付けません。マウスで操作する環境では、スクロールする手段もほとんどなくなります。そこで、`scrollbar-width: none` はボタンと同じ `@supports selector(::scroll-button(*))` の中に書き、ボタンが表示される環境だけでスクロールバーを消します。

擬似要素のルールも、`@supports` の中に書きます。CSSの仕様では、ブラウザが知らない擬似要素を含むセレクタのルールは、そのルールだけが無効になります。しかし、Safariでは、ネストした `::scroll-button()` のルールがあると、それ以降にネストしたスタイルまで無効になることを、私は2025年5月に確認しています。`@supports` の中に入れておけば、未対応の環境はこのブロックごと読み飛ばすので、ほかのスタイルを巻き込みません。

`container: --slide / scroll-state` と、`scroll-state()` の条件、`interactivity: inert` は、未対応の環境では無視されます。隠れているスライドも読み上げとフォーカスの対象に残りますが、スクロールバーで表示でき、フォーカスが移れば、そのスライドまで自動でスクロールします。内容を読めなくなるわけではないので、`@supports` で囲む必要はありません。

## 未対応の環境でもページ送りのボタンが要るとき

ここまでの作り方では、SafariやFirefoxにページ送りのボタンが出ません。デザインの要件として、どのブラウザでもボタンが必要な場合は、スクロールスナップの土台はそのままにし、HTMLに `<button>` を置いて、押したときに `scrollBy()` を呼ぶだけのスクリプトを足します。スワイプで送る操作、スライドの位置で止める処理、滑らかに動かすかどうかは、すでにブラウザがスクロールスナップと `scroll-behavior` で受け持っています。スクリプトに任せるのは、ボタンを押したらスクロールさせることと、端にいる方向のボタンを無効にすることの2つだけです。

```html title="🙆‍♂ Recommended: ボタンをスライドの外に置き、最初は隠しておく"
<section class="scoped css-carousel" aria-labelledby="css-carousel-heading">
  <h2 id="css-carousel-heading">施工事例</h2>
  <div class="_buttons" hidden>
    <button type="button" data-carousel="prev" aria-label="前の事例">←</button>
    <button type="button" data-carousel="next" aria-label="次の事例">→</button>
  </div>
  <ul>
    <!-- ... -->
  </ul>
</section>
```

ボタンは、スクロールコンテナの `ul` の前に、スライドの外に置きます。Tabキーの順番は、`::scroll-button()` と同じく、前後のボタン、表示しているスライドの中身の順になります。スライドの中に置くと、止まっていないスライドの `interactivity: inert` に巻き込まれ、ボタンまで操作できなくなります。最初は `hidden` 属性で隠しておき、スクリプトが動いて、しかも `::scroll-button()` を使えない環境でだけ表示します。

```css title="🙆‍♂ Recommended: スクリプトで表示するボタンの見た目"
@scope (.scoped.css-carousel) to (.scoped) {
  button {
    &:disabled {
      opacity: 0.3;
    }

    &:dir(rtl) {
      scale: -1 1;
    }
  }
}
```

```js title="🙆‍♂ Recommended: 見えている幅だけ送り、止まる位置はスクロールスナップに任せる"
const carousel = document.querySelector('.css-carousel');
const scroller = carousel.querySelector('ul');
const buttons = carousel.querySelector('._buttons');
const prev = buttons.querySelector('[data-carousel="prev"]');
const next = buttons.querySelector('[data-carousel="next"]');

// ::scroll-button() を使える環境では、HTML のボタンを出さない
if (!CSS.supports('selector(::scroll-button(*))')) {
  buttons.hidden = false;

  // 1回に送るのは、見えている幅の分。止まる位置はスクロールスナップが合わせる
  const scrollPage = (step) => {
    // 右から左に書く言語では、scrollLeft と scrollBy() の left が負の向きになる
    const sign = getComputedStyle(scroller).direction === 'rtl' ? -1 : 1;
    scroller.scrollBy({ left: step * sign * scroller.clientWidth });
  };

  // それ以上送れない方向のボタンを無効にする
  const update = () => {
    const position = Math.abs(scroller.scrollLeft);
    const max = scroller.scrollWidth - scroller.clientWidth;
    const atStart = position < 1;
    const atEnd = position > max - 1;

    // 送れる方向のボタンを先に有効にして、フォーカスの移り先を作る
    if (!atStart) prev.disabled = false;
    if (!atEnd) next.disabled = false;

    // フォーカスしたボタンを無効にするとフォーカスが外れるので、反対のボタンに移してから無効にする
    if (atStart && !atEnd && document.activeElement === prev) next.focus();
    if (atEnd && !atStart && document.activeElement === next) prev.focus();

    prev.disabled = atStart;
    next.disabled = atEnd;
  };

  prev.addEventListener('click', () => scrollPage(-1));
  next.addEventListener('click', () => scrollPage(1));
  // scrollend に対応していない環境（Safari 26.1まで）では、scroll で判定する
  scroller.addEventListener('onscrollend' in window ? 'scrollend' : 'scroll', update);
  // 幅が変わると、スクロールできる量も変わる。監視を始めた時点でも1回呼ばれる
  new ResizeObserver(update).observe(scroller);
}
```

1回に送る量は、スクロールコンテナの見えている幅（`clientWidth`）にします。スライドの幅と `gap` から1枚分の距離を計算する必要はありません。`scroll-snap-type: inline mandatory` があるので、スクロールが終わると、近いスライドの位置にブラウザが合わせます。`grid-auto-columns` を変えて3枚ずつ見せる形にしても、スクリプトを直さずに、見えている枚数ずつ送れます。{/* 要検証: ブラウザ。3枚ずつ見せる幅で、clientWidth ずつ送ったときにスナップが3枚先に合うか */}

`scrollBy()` には `behavior` を渡しません。省略すると `auto` になり、スクロールコンテナの `scroll-behavior` に従います。`scroll-behavior: smooth` は、「[スクロールスナップを土台にする](#スクロールスナップを土台にする)」で `prefers-reduced-motion: no-preference` の条件の中に書きました。そのため、動きを減らす設定のユーザーには、スクリプトの側で何もしなくても即座に移動します。Chromeで、ボタンを押した直後の `scrollLeft` を読んで確かめました。`scroll-behavior` が `smooth` のときは0のまま変わらず、`auto` のときは押した直後に次のスライドの位置になりました。

ボタンの「前へ」「次へ」は、左右ではなくインライン方向の前後として扱います。右から左に書く言語（`direction: rtl`）では、スクロールの開始位置で `scrollLeft` が0になり、先へ進むほど負の値になります。そのため、`getComputedStyle()` で `direction` を読み、`rtl` なら `scrollBy()` に渡す `left` の符号を反転します。端の判定は、`scrollLeft` の絶対値で行います。Chromeで `dir="rtl"` のページを確かめたところ、`scrollLeft` は0から-990まで変わり、開始位置で `left` に正の値を渡してもスクロールしませんでした。矢印の向きも書字方向で逆になるので、CSSの `:dir(rtl)` でボタンを左右に反転しています。

ボタンを無効にする判定は、スクロールが終わったときの `scrollend` イベントで、スクロールの位置から行います（未対応の環境の扱いは後で説明します）。押した回数を数える方法では、スワイプやスクロールバーで送ったときや、隠れているスライドへフォーカスが移って自動でスクロールしたときに、ボタンの状態がずれます。位置で判定すれば、どの操作でスクロールしても、終わった時点の状態に合わせられます。Chromeで、押した「→」のボタンが最後のスライドで無効になると、フォーカスが `body` に外れました。キーボードで操作しているユーザーが位置を見失わないよう、反対のボタンへフォーカスを移してから、ボタンを無効にしています。このとき、移り先のボタンは、あらかじめ有効の状態へ戻しておきます。無効のままのボタンでは、`focus()` を呼んでもフォーカスは移りません。2枚のカルーセルで「→」を押したとき、移り先の「←」がまだ無効だと、フォーカスは `body` へ外れました。

判定は、スクロールコンテナの幅が変わったときにもやり直します。スクロールできる量は、コンテナの幅で変わるからです。`scrollend` だけで判定すると、すべてのスライドが収まる幅で両方のボタンを無効にした後、ウィンドウを狭めてスクロールできるようになっても、「→」のボタンは無効のまま残ります。`ResizeObserver` でコンテナの大きさを監視すれば、幅が変わるたびに判定し直せます。監視を始めた時点でも1回呼ばれるので、初めの状態を決める呼び出しも兼ねます。Chromeで、すべてのスライドが収まる幅では両方のボタンが無効になり、狭めると「→」のボタンが有効になることを確かめました。

<Baseline id="scrollend" />

`scrollend` イベントは、Safariでは26.2から使えます。それより前のSafariで `scrollend` だけを待つと、`update()` は幅が変わったときにしか動かないので、最初のスライドを離れても「←」のボタンが無効のままになります。本書の対象のブラウザ（Safari 18.6以降）にはこの環境が含まれるので、スクリプトでは `'onscrollend' in window` で対応を調べ、対応していなければ `scroll` イベントで同じ判定を呼んでいます。`scroll` はスクロールの途中で何度も発生しますが、判定は位置を読んで比べるだけなので、負荷はほとんどありません。端のボタンを無効にしてフォーカスを移す処理も、スクロールが端に着いた時点で1回だけ働きます。{/* 要検証: ブラウザ。Safari 18.6で、scroll で判定したときに「←」が有効になり、端でフォーカスが反対のボタンへ移るか */}

`::scroll-button()` を使える環境では、スクリプトは `CSS.supports('selector(::scroll-button(*))')` でそれを調べ、ボタンを隠したままにします。2つの仕組みを重ねると、同じ役割のボタンが2組表示されるからです。`@supports` で隠す方法もありますが、`hidden` 属性で隠しておいてスクリプトで表示すれば、スクリプトが読み込めなかった環境に、押しても動かないボタンが残りません。

止まっていないスライドを外す `interactivity: inert` は、このボタンとは独立に働きます。`scroll-state()` のコンテナクエリと `interactivity` に対応しているのも、`::scroll-button()` に対応したChrome系のブラウザだけです。スクリプトのボタンが表示されるSafariやFirefoxでは、隠れているスライドもTabキーの対象に残ります。それでも、フォーカスが移ったスライドまでブラウザがスクロールし、そのスクロールの終わりで `update()` が動くので、ボタンの状態は表示に合います。Chromeで、`interactivity` を `auto` に戻し、4枚目のリンクにフォーカスを移したところ、そのスライドまでスクロールし、「次の事例」のボタンが無効になりました。{/* 要検証: ブラウザ。Safari と Firefox で、スクリプトのボタンの scrollBy() とスクロールスナップ、dir="rtl" での符号、scrollend による無効化が Chrome と同じに動くか */}

## カルーセルで確かめる状態

カルーセルを実装したら、対応したブラウザで動くことだけでなく、未対応の環境や設定を変えた環境でも内容を読めるかを確かめます。このページで説明した振る舞いから、確かめる状態を次の表にまとめました。

| 状態 | 確かめること | 期待する結果 |
| --- | --- | --- |
| 対応したブラウザ（Chrome系） | Tabキーだけで操作する | 前後のボタン、表示しているスライドの中身、カルーセルの後ろの要素の順に移動し、隠れているスライドのリンクは飛ばされる |
| 未対応のブラウザ（Safari、Firefox） | スクロールバーとTabキーで操作する | ボタンと点は出ず、スクロールバーで横に送れる。隠れているスライドにフォーカスが移ると、そのスライドまでスクロールする |
| 未対応のブラウザで、スクリプトのボタンを足した場合 | ボタンで端まで送り、`dir="rtl"` でも送る | 1回に1画面分ずつ進み、端の方向のボタンは無効になり、フォーカスは反対のボタンに移る |
| 未対応のブラウザで、スクリプトのボタンを足した場合 | すべてのスライドが収まる幅から、ウィンドウを狭める | 両方とも無効だったボタンのうち、送れる方向のボタンが有効になる |
| 複数枚を表示する設定 | 見えているすべてのスライドをクリックし、フォーカスする | 見えているのに操作できないスライドがない |
| 動きを減らす設定 | ボタンと点を押す | スクロールが滑らかにならず、即座に移動する |
| 強制カラーモード | 点の並びと現在位置の点を見比べる | 表示しているスライドの点を、ほかの点と見分けられる |
| 200%に拡大した状態 | ボタンとスライドの中身の重なりを見る | ボタンが文字やリンクを覆い、読めない部分ができていない |

動きを減らす設定と強制カラーモードは、Chromeの開発者ツールの「Rendering」パネルで再現できます。それぞれ「Emulate CSS media feature prefers-reduced-motion」と「Emulate CSS media feature forced-colors」を切り替えます。点の現在位置は、色に加えて形の違いでも示しているので、強制カラーモードで色が置き換わっても、横長の点で見分けられます。Chromeのエミュレーションで強制カラーモードにすると、ほかの点は `CanvasText` の枠線だけの円になり、現在位置の点は横長に塗られた形で表示されました。Windowsの実際のハイコントラストテーマでの見え方は、確かめていません。{/* 要検証: ブラウザ。Windows の実際のハイコントラストテーマでの ::scroll-marker の見え方 */}

## 発展：ページ内リンクを現在位置の印にする `scroll-target-group`

ここからは、カルーセルから離れたスクロールマーカーの使い方です。リンクを並べた要素に `scroll-target-group: auto` を指定すると、その中の `<a href="#…">` がスクロールマーカーとして扱われます（CSS Overflow Module Level 5）。リンク先の要素がいま表示されているリンクには、`:target-current` が当てはまります。記事の目次で、読んでいる節のリンクを強調する表示（スクロールスパイ）を、JavaScriptを使わずに作れます。

Chromeで、目次の `<ol>` に `scroll-target-group: auto` を指定して確かめました。ページを下へスクロールすると、`:target-current` に当てはまるリンクが、表示している節のリンクへ順に移りました。

<Baseline id="scroll-target-group" />

`scroll-target-group` に対応しているのはChrome系のブラウザ（140以降）だけなので、本書は現状では採用しません。カルーセルのボタンと点はなくても横スクロールで同じ内容を読めますが、目次の強調は、デザインで求められているならすべてのブラウザで出す必要があります。Chrome系のブラウザだけをCSSで強調すると、ほかのブラウザのためにJavaScriptの実装を残すことになり、同じ表示を2つの方法で保守することになります。いまはIntersectionObserverなどのJavaScriptで強調し、SafariとFirefoxが対応してから、CSSに切り替えます。
