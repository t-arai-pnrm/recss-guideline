ホバーのスタイルは、ホバーできる入力があり、しかも操作できる状態の要素にだけ当てます。書き方は、`&:any-link:hover` や `&:enabled:hover` を `@media (any-hover)` の中に置く形です。同じ見た目を `:focus-visible` にも指定し、キーボードで操作するユーザーにも同じ手がかりを示します。

キーボードでフォーカスを移したときの変化は、トランジションを掛けずに一度で切り替えます。ホバーの変化は `opacity` で透かさず、背景色や文字色を別の色に変えて表します。ホバーで要素を動かすときは、ホバーを受ける要素ではなく子要素を動かします。文字を太くするときは、隣の要素を押さない書き方を選びます。押せる範囲の大きさは「[17-2 押せる範囲とタッチ操作](/interaction/hit-area-and-touch/)」で、選択中や展開中のような状態の表し方は「[17-3 状態を属性で表す](/interaction/state-attributes/)」で扱います。

## タッチ操作の端末でのホバー

`:hover` をメディアクエリの条件なしに書くと、スマートフォンのようなタッチ操作の端末で問題が起きます。タップした要素にホバーのスタイルが当たったまま、ほかの場所をタップするまで残り続けます。リンクによっては、1回目のタップでホバーの表示だけが変わり、2回目でようやく移動することもあります。

```css title="🙅‍♂ Not Recommended: 条件なしのホバーと、画面の幅によるホバーの判定" issue="behavior"
/* 🙅‍♂ Not Recommended */
._submit-button {
  &:hover {
    background-color: var(--_background--hocus);
  }
}

._more-link {
  &:hover {
    @media (width >= calc(768 / 16 * 1rem)) {
      color: var(--_color--hocus);
    }
  }
}
```

画面の幅で判定する2つ目の書き方も、問題を解決しません。幅の広いタブレットはタッチで操作しますし、幅の狭いウィンドウをマウスで操作することもあります。画面の幅は、入力の方法を表していないからです。

`@media (hover: hover)` や `@media (hover: hover) and (pointer: fine)` も、よく見かける書き方です。しかし、`hover` が調べるのは「主な入力」がホバーできるかどうかだけです。iPadにトラックパッド付きのキーボードをつないだ場合、主な入力はタッチのままなので、トラックパッドでカーソルを重ねてもホバーのスタイルが当たりません。

## `any-hover` と `:focus-visible` を組み合わせる

ホバーのスタイルは、`@media (any-hover)` の中に書きます。`any-hover` は、使える入力のうち「どれかひとつでも」ホバーできるかを調べるメディア特性です。トラックパッドをつないだタブレットでもホバーが有効になり、つなぐ・外すの変化にも追従します。

ホバーのセレクタは、操作できる状態の要素に絞ります。リンクは `&:any-link:hover`、ボタンやフォームのコントロールは `&:enabled:hover` と書きます。`:any-link` は `href` を持つリンクにだけ当てはまるので、`href` を外した現在のページのリンクは反応しません。`:enabled` は無効にしたボタンを除きます。押せないものが押せそうに見えるのを防ぐためです。`<summary>` と `<label>` には無効の状態がないので、条件を付けずに `&:hover` と書きます。

```css title="🙆‍♂ Recommended: ホバーを操作できる状態に絞って any-hover の中に書き、:focus-visible にも同じ見た目を指定する"
@scope (.scoped.text-link) to (.scoped) {
  :scope {
    /* 状態の色は文字色に寄せ、ライトでもダークでもコントラストを上げる */
    --_color: var(--foreground--accent);
    --_color--hocus: color-mix(in oklab, var(--foreground--accent) 70%, var(--foreground--base));

    color: var(--_color);

    /* kiso.css が消した下線を戻し、本文の中のリンクを色だけで示さない */
    text-decoration-line: revert;

    &:focus-visible {
      color: var(--_color--hocus);
    }

    &:any-link:hover {
      @media (any-hover) {
        color: var(--_color--hocus);
      }
    }
  }
}

@scope (.scoped.save-button) to (.scoped) {
  :scope {
    /* 文字色で塗るボタンは、状態の色をページの背景色に寄せて作る（後述の「ホバーの変化を透明度で表す方法」） */
    --_background: var(--background--inverse);
    --_background--hocus: color-mix(in oklab, var(--background--inverse) 80%, var(--background--base));

    background-color: var(--_background);
    color: var(--foreground--inverse);

    &:focus-visible {
      background-color: var(--_background--hocus);
    }

    &:enabled:hover {
      @media (any-hover) {
        background-color: var(--_background--hocus);
      }
    }
  }
}
```

<Baseline id="interaction" compatKey="css.at-rules.media.any-hover" name="any-hover メディア特性" />

条件は `(any-hover: hover)` と値まで書かずに、`(any-hover)` と書きます。`any-hover` の値は `none` と `hover` の2つだけです。メディア特性を値なしで書くと、値が `none` のときに偽、それ以外のときに真と評価されるので、`(any-hover)` は `(any-hover: hover)` と同じ意味になります。値を書かないほうが短く、「ホバーできる入力があるか」という問いの形がそのまま読み取れます。

ホバーで変える見た目は、`:focus-visible` にも同じように指定します。キーボードで操作するユーザーも、マウスで操作するユーザーと同じ手がかりを得られます。祖先の `overflow` でフォーカスリングの一部が切り取られた場合にも、背景色の変化でフォーカスの位置が分かります。`:focus-visible` のスタイルはメディアクエリの外に書きます。タッチ操作の端末にも、キーボードをつないで使うユーザーはいるからです。

フォーカスリングそのものは、ベーススタイルで二重のリングを定義しています（「[8-2 ベーススタイルに書くもの](/reset/base-styles/)」）。コンポーネントで指定するのは、リングに加える背景色などの変化だけです。リングを `outline: none` で消すことはしません。

リングを描いても、フォーカスした要素が固定ヘッダーの下に隠れていては見えません。WCAG 2.2の達成基準2.4.11「隠されないフォーカス（最低限）」（レベルAA）は、キーボードでフォーカスを受けた要素が、制作者の置いたコンテンツで完全に隠れないことを求めています。本書では、ベーススタイルでルートに `scroll-padding-block-start` を指定し、スクロールで見せる範囲からヘッダーの分を除いて、この問題を防いでいます（「[8-2 ベーススタイルに書くもの](/reset/base-styles/)」）。ヘッダーの高さを測って渡す方法は、「[11-7 固定ヘッダー](/layout-practice/sticky-header/)」で説明しています。

なお、タッチスクリーンを持つノートパソコンでは、マウスもあるので `(any-hover)` が当てはまります。この環境では、指でタップしたときにホバーのスタイルが残ります。入力の方法を操作ごとに見分けたい場合は、JavaScriptのポインターイベントを併用するしかありません。

`@media` は、`&:enabled:hover` のようなセレクタの中に書けます。セレクタの層には、@ルールを数えないからです（「[9-5 ネストの書き方](/notation/nesting/)」）。

## キーボード操作とトランジション

ホバーの変化にトランジションを掛けるときは、キーボードでフォーカスを移したときの変化には掛けないようにします。Tabキーで次々とフォーカスを移しているのに、背景色が遅れて変わると、入力と表示がずれて反応が遅く感じられるからです。

```css title="🙆‍♂ Recommended: トランジションを :not(:focus-visible) の中に書く"
._submit-button {
  &:not(:focus-visible) {
    transition-duration: var(--duration--fast);
    transition-property: background-color;
    transition-timing-function: var(--ease--out-quint);
  }
}
```

`:focus-visible` が当てはまっている間は、トランジションの指定がありません。そのため、フォーカスが来た瞬間に一度で色が変わります。フォーカスが離れるときとホバーのときは、`:not(:focus-visible)` が当てはまるので、なめらかに色が戻ります。色の変化では位置と大きさが変わらないので、動きを減らす設定の条件で囲みません。位置や大きさを変えるトランジションは、次の見出しの例のように条件の中に書きます。条件の範囲は、「[18-2 動きを減らす設定に対応する](/motion/reduced-motion/)」で説明します。

## ホバーの変化を透明度で表す方法

ホバーの表現として手軽なのが、`opacity: 0.7` のように要素を透かす方法です。しかし、この方法はおすすめしません。背景だけでなく文字まで透けるので、コントラストが下がって読みにくくなります。背景に画像や別の色があると、それが透けて見えるのも問題です。

```css title="🙅‍♂ Not Recommended: ホバーを透明度で表し、文字まで薄くする" issue="behavior"
/* 🙅‍♂ Not Recommended */
._submit-button {
  &:hover {
    opacity: 0.7;
  }
}
```

もうひとつの問題は、意図が伝わらないことです。コードを読んだ人には、「ホバーしたら暗くしたい」のか「目立たなくしたい」のかが分かりません。デザインで別の色が指定されているなら、その色をそのまま書いたほうが、意図とコードが一致します。

背景色や文字色を変えるときは、状態ごとの値を `--_background--hocus` のような接尾辞を付けた内部プロパティにまとめます。値には、デザインで決まっている色のトークンを使います。専用の色がない場合は、`oklch(from var(--_background) calc(l - 0.1) c h)` のように、相対カラー構文で元の色から明るさだけを変えた色を作ります。接尾辞の付け方は「[10-5 公開プロパティと内部プロパティ](/components/custom-properties/)」で、相対カラー構文は「[15-2 相対カラー構文で派生色を作る](/color-media/relative-color/)」で扱います。

メニューの項目、リストの行、選択していないタブのように背景が透明な項目には、明るさを変える元の色がありません。こうした項目には、半透明の重ね色のトークン `--background--hover` と `--background--active` を、`background-color` に直接指定します。値はライトのテーマで黒の4%と7%、ダークのテーマで白の6%と10%で、下にある面をわずかに暗く、または明るく見せます。ページ、カード、メニューのどの面に置いても同じ見え方になるので、面ごとにホバーの色を決めずに済みます。

```css title="🙆‍♂ Recommended: 背景が透明な項目には、半透明の重ね色を背景色として指定する"
:root {
  --background--hover: light-dark(oklch(0% 0 0deg / 4%), oklch(100% 0 0deg / 6%));
  --background--active: light-dark(oklch(0% 0 0deg / 7%), oklch(100% 0 0deg / 10%));
}

@scope (.scoped.option-menu) to (.scoped) {
  ._item {
    &:focus-visible {
      background-color: var(--background--hover);
    }

    &:enabled:hover {
      @media (any-hover) {
        background-color: var(--background--hover);
      }
    }

    &:enabled:active {
      background-color: var(--background--active);
    }
  }
}
```

重ね色は、`opacity` で要素を透かす方法とは別のものです。半透明なのは背景に指定した色だけで、項目の文字や枠線は透けないので、コントラストは下がりません。トークンの名前から、ホバーと押下のための色だと読み取れます。背景色のあるボタンには重ね色を使わず、相対カラー構文で明るさを変えます。`background-color` に重ね色を指定すると、ボタンの塗りが半透明の色に置き換わってしまうからです。デモが読み込んでいるトークンの値は、「[付録I デモの共通トークン](/appendix/demo-tokens/)」に載せています。「[17-2 押せる範囲とタッチ操作](/interaction/hit-area-and-touch/#ホバーで背景が付く項目の間隔)」のデモも、この重ね色を使っています。

ただし、主ボタンのように文字色で塗るボタンは、相対カラー構文で明るさを変えられません。塗りに使う `--background--inverse` の値は `light-dark()` で、ライトのテーマでは黒寄り、ダークのテーマでは白寄りの色です。黒寄りの塗りは明るくしないと、白寄りの塗りは暗くしないと、変化が見えにくくなります。`calc(l - 0.1)` のように明るさを一方向へ変える式では、片方のテーマで変化がほとんど見えません。そこで、`color-mix()` でページの背景色 `--background--base` に寄せます。ページの背景色は、文字色とコントラストを取るために塗りと反対側の明るさにあるので、1つの式で、ライトでは明るく、ダークでは暗くなります。

```css title="🙆‍♂ Recommended: 文字色で塗るボタンは、ページの背景色に寄せてホバーの色を作る"
@scope (.scoped.primary-button) to (.scoped) {
  :scope {
    --_background: var(--background--inverse);
    --_background--hocus: color-mix(in oklab, var(--background--inverse) 80%, var(--background--base));

    background-color: var(--_background);
    color: var(--foreground--inverse);

    &:focus-visible {
      --_background: var(--_background--hocus);
    }

    &:enabled:hover {
      @media (any-hover) {
        --_background: var(--_background--hocus);
      }
    }
  }
}
```

次のデモでは、ボタンとリンクにマウスを重ねたときと、Tabキーでフォーカスを移したときに、同じように色が変わります。ボタンは文字色で塗り、状態の色を上の例と同じくページの背景色に寄せて作っています。無効にしたボタンと、`href` のない現在のページのリンクは反応しません。

## ホバーで動く要素の当たり判定

ホバーで位置や大きさが変わる要素を、そのまま `:hover` の対象にすると、ちらつくことがあります。カーソルが縁にあるとき要素が動くと、ホバーが外れて要素がもとの位置に戻り、戻るとまたホバーが当たる、という繰り返しになるからです。たとえば、ホバーを受けるボタンを4px持ち上げると、下端から4px以内にあるカーソルは、持ち上がったボタンの外に出ます。カーソルを少し動かすたびに、ボタンは上下に揺れます。

```css title="🙅‍♂ Not Recommended: ホバーを受ける要素自身を動かす" issue="behavior"
/* 🙅‍♂ Not Recommended */
._submit-button {
  &:hover {
    translate: 0 -4px;
  }
}
```

ホバーを受ける要素は動かさず、動かすのは子要素（または擬似要素）にします。ホバーを受ける側は、動かない当たり判定として働きます。

次の例では、ボタンの状態を子へ伝えるため、フラグのカスタムプロパティ `--_hocus` を使います。フラグを使うのは、このように子要素や擬似要素を変えるときです。要素自身の色や背景だけを変えるなら、前の見出しまでの例のように、状態のセレクタに直接書けば足ります。

```css title="🙆‍♂ Recommended: ホバーを受ける要素は動かさず、子要素を動かす" from="interaction/hover-lift"
@scope (.scoped.lift-button) to (.scoped) {
  :scope {
    --_hocus: --false;
    --_focus-visible: --false;

    display: inline grid;

    &:focus-visible {
      --_hocus: --true;
      --_focus-visible: --true;
    }

    &:enabled:hover {
      @media (any-hover) {
        --_hocus: --true;
      }
    }
  }

  ._face {
    @container style(--_hocus: --true) {
      translate: 0 -4px;
    }

    @container style(--_focus-visible: --false) {
      @media (prefers-reduced-motion: no-preference) {
        transition-duration: var(--duration--fast);
        transition-property: translate;
        transition-timing-function: var(--ease--out-quint);
      }
    }
  }
}
```

ボタンのホバーとフォーカスは、フラグのカスタムプロパティ `--_hocus` で子の `._face` に伝えます。ボタンの状態のセレクタで `--_hocus: --true` を立て、`._face` は `@container style(--_hocus: --true)` で持ち上がります。名前なしの `style()` は親を問い合わせ、カスタムプロパティは継承するので、ボタンで立てたフラグを `._face` から読めます。ボタンにデフォルト値の `--_hocus: --false` を明示しているのは、外側の要素で立てたフラグを継承しないためです。

キーボードでフォーカスしたときは一度で持ち上げるので、トランジションも `--_focus-visible` のフラグで切り替えます。ボタンの `&:not(:focus-visible)` にトランジションを書いても、`transition` は継承しないので、動く `._face` には掛かりません。フラグとスタイルクエリで状態を伝える書き方は、「[10-6 スタイルクエリで状態を伝える](/components/style-queries/)」で説明しています。

次のデモでは、「ボタン自身を動かす」のボタンはボタン自身を、「内側の面を動かす」のボタンは内側の `._face` を、ホバーで4px持ち上げます。カーソルをボタンの下端から4px以内に置いて横に少しずつ動かすと、前者はホバーが外れては当たり、上下に揺れます。後者は、ホバーを受けるボタンが動かないので、持ち上がったままです。Chromeで確かめたところ、前者ではカーソルを動かすたびにホバーが外れ、後者ではホバーが続きました。

## ホバーで太さを変えると隣が動く

ナビゲーションのリンクをホバーで太字にすると、リンクの幅が広がり、後ろのリンクが押されて横にずれます。太い字形は、線が太くなるだけでなく、字幅も広がるからです。カーソルをリンクからリンクへ動かすたびに、並びが揺れます。

ただし、どの文字でも広がるわけではありません。和文の漢字と全角のかなは、太さを変えても1文字の幅が1emのままです。macOSのChromeで、デモと同じ16pxのゴシック体を測ったところ、「会社概要」の幅は、400と700のどちらも64pxで、「News」は42.7pxから46.4pxに広がりました。かなを `palt` で詰めた場合は、太くすると1px程度広がります。和文だけのラベルで確かめると動かないので、欧文のラベルが混ざってから気付くことがあります。

そこで、太さを変える書き方は、書体とラベルに合わせて選びます。書体に字幅を変えずに濃さを変えるグレード（`GRAD`）の軸があれば、`GRAD` で濃くします。グレードの軸を持つのは、Roboto Flexのような一部の可変フォントです。`GRAD` には対応するプロパティがないので、`font-variation-settings` で指定します（「[14-1 フォントを指定する](/typography/fonts/#font-weightの指定)」）。値の範囲は書体ごとに決まっているので、書体の説明で確かめます。Webフォントを読み込む前や代わりのフォントでは濃さが変わらないので、`GRAD` だけでホバーを表さず、色の変化と組み合わせます。

```css title="🙆‍♂ Recommended: グレードの軸で、字幅を変えずに濃くする"
@scope (.scoped.global-nav) to (.scoped) {
  a {
    &:focus-visible {
      font-variation-settings: "GRAD" 150;
    }

    &:any-link:hover {
      @media (any-hover) {
        font-variation-settings: "GRAD" 150;
      }
    }
  }
}
```

グレードの軸がない書体でも、ラベルが和文だけなら、`font-weight` を変えてかまいません。漢字と全角のかなは字幅が変わらず、`palt` で詰めたかなでも、隣が動くのは1px程度だからです。欧文のラベルが混ざり、隣が目に見えて動くときは、太字の幅を先に確保します。

```css title="🙆‍♂ Recommended: 太字の幅を先に確保してから、太さを変える" from="interaction/hover-weight"
@scope (.scoped.weight-nav) to (.scoped) {
  a {
    display: inline flex;
    flex-direction: column;

    &::after {
      content: attr(data-label) / "";
      visibility: hidden;
      block-size: 0;
      font-weight: var(--font-weight--bold);
    }

    &:focus-visible {
      font-weight: var(--font-weight--bold);
    }

    &:any-link:hover {
      @media (any-hover) {
        font-weight: var(--font-weight--bold);
      }
    }
  }
}
```

リンクの文字と同じ文字を `data-label` 属性に持たせ、`::after` に `attr()` で写します。写しは太字にし、`visibility: hidden` で見えなくして、`block-size: 0` で高さを持たせません。リンクを縦並びの `inline flex` にすると、リンクの幅は、本来の文字と太字の写しのうち広いほう、つまり太字の幅になります。ホバーで本来の文字を太くしても、リンクの幅は変わりません。

`content` の `/` の後ろは代替テキストで、空にすると、支援技術は写しの文字を読み上げません。代替テキストの書き方に対応していないブラウザでは、`content` の宣言ごと無視されるので、写しは作られず、太さだけを変える書き方と同じ表示になります。写しの文字は、リンクの文字と必ずそろえます。片方だけを直すと、確保する幅がずれます。CMSで文字を入力するなら、テンプレートで同じ値を両方に出力します。
