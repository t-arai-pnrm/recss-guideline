本書のコード例は、すべて素のCSSで書いています。ここでいう素のCSSは、CSSファイルにWeb標準の構文だけで書いたスタイルのことです。JavaScriptのオブジェクトで書くCSS-in-JSも、HTMLのクラス属性にユーティリティを並べるTailwind CSSも、Sassの独自の構文も使いません。ビルドの段階で `@import` を展開することはありますが、書く内容はブラウザが解釈するCSSそのものです。

## 静的なサイトとCMSで同じ書き方を使うため

本書が扱うのは、コーポレートサイト、ランディングページ、メディアサイトのようなWebサイト制作で、静的なサイトとCMSの両方を含みます。CMSのテンプレートが出力するHTMLや、編集者が書く本文には、JavaScriptでクラス名を生成する仕組みを持ち込めないことがあります。{/* 要確認: 出典なし。CMSのテンプレートや本文に、クラス名を生成する仕組みを持ち込めないこと */}素のCSSなら、部品のルートにクラスを1つ付けるだけで、どちらの環境でも同じ書き方で部品の範囲を区切れます。

部品の範囲、スタイルどうしの優先順位、外から変えてよい値は、どの道具を選んでも決めなければならない設計の判断です。本書は、これらをブラウザの仕組みである `@scope`、カスケードレイヤー、カスタムプロパティで表します。特定のフレームワークやビルドの道具に依存しないので、案件ごとに道具が変わっても書き方を変えずに済みます。

## どの道具を使う現場でも役に立つ知識

本書の読者として想定している実務1〜3年目のコーダーにとって、カスケード、`@scope`、カスタムプロパティ、擬似クラスは、どの道具を使う現場に移っても役に立つ知識です。Tailwind CSSのクラスも、CSS-in-JSで書いたスタイルも、ブラウザが最後に解釈するのはCSSだからです。道具に固有の記法は道具を替えると使えなくなりますが、CSSの仕組みの知識は、道具が生成したCSSを読み解くときにも使えます。{/* 要確認: 出典なし。道具に固有の記法と、CSSの仕組みの知識の比較 */}

そのため、VueやAstroのように、フレームワークが標準でスコープ付きのCSSを書く仕組みを備えているなら、それを使ってかまいません。その場合も、設計の原則と、公開プロパティで値を受け渡す方法はそのまま使えます。スコープの移植では、`:scope` や `&:is(:scope[…] *)` をルートのクラスを使ったセレクタに書き換え、入れ子にした子の部品のルートとスロットの扱いを、フレームワークの仕様に合わせます。たとえばVueのscoped CSSでは、子の部品のルート要素に親と子の両方のスタイルが当たり、子の部品のルートで止まる本書の `to (.scoped)` とは範囲が違います。違いの例は「[付録H CSS-in-JSと素のCSSの比較](/appendix/css-in-js/)」で示しています。

## 採用していない道具は持ち込まない

この判断は、AIにコードを書かせるときの規約にもなっています。本書のルール `no-unrequested-css-framework` は、プロジェクトで採用を決めていない限り、Tailwind CSSやCSS-in-JSを使わず、コンポーネントのクラスと `@scope` で書くことを求めます。AIは、指示がなくてもユーティリティだけで組む前提を持ち込むことがあるからです（[20-7 AIが誤りやすいパターン](/ai-coding/pitfalls/)）。

このルールが求めているのは、採用していない道具を持ち込まないことです。プロジェクトがTailwind CSSやCSS-in-JSを採用しているなら、その方針に従います。Tailwind CSSを使う現場で本書の考え方を生かす方法は、「[10-3 コンポジションとユーティリティ](/components/compositions-and-utilities/)」のコラムで説明しています。

ほかの道具と比べた詳しい根拠は、付録H「[CSS-in-JSと素のCSSの比較](/appendix/css-in-js/)」で説明します。CSS-in-JSやStyleXの仕組み、型安全性、スコープとグローバルなスタイルの共存、公開プロパティによる部品の再利用、見た目のロジックの分担を比べています。比較には第4章と第10章で扱う仕組みが出てくるので、それらの章を読んでから戻ると判断しやすくなります。
