ツールチップやメニューのように、ボタンの近くに表示する部品は、ポップオーバーにして、開いたボタンを暗黙のアンカーとして置きます。入力欄の説明のように、名前を付けたアンカーを持つコンポーネントを繰り返し置くときは、ルートの `anchor-scope` で名前の範囲をコンポーネントの中に限ります。カードのタグを画像の角に重ねるように、コンポーネントの中で子要素どうしを重ねるときも、基準にする子要素をアンカーにすれば、HTMLの順序を変えずに位置を決められます。ホバーした項目を背景が追いかける表現のように、なくても困らない装飾なら、未対応の環境では表示されないだけの形で使えます。

この節は、アンカーポジショニングの仕組みを前提にしています。アンカーとの結び付け方、`position-area` の9マス、`position-try-fallbacks` による位置の切り替え、包含ブロックとの関係は、「[7-11 アンカーポジショニングの基礎](/layout/anchor-basics/)」で説明しています。未対応の環境への備えも7-11で扱っており、要点は、アンカーを基準にした指定を `@supports` の中に書き、その外に未対応の環境でも読める配置を書くことです。

アンカーポジショニングをスクロール駆動アニメーションと組み合わせて、飾りが本文に近づいたら隠す技法は、「[11-9 要素どうしの重なりを検出する](/layout-practice/overlap-detection/)」で説明しています。装飾に限って使う技法なので、ポップアップを作るだけなら読まなくても足ります。

## 部品として組むときに起きる問題

アンカーポジショニングの指定を1つの要素で試すだけなら、問題は起きにくいものです。部品としてページに組み込むと、別の問題が出てきます。同じ部品を複数置いたときに別の部品のアンカーが基準に選ばれること、位置が反転したときに吹き出しの矢印が逆を指すこと、ボタンの位置によってメニューを上下のどちらに開くかが変わることです。

装飾に使うときは、別の判断が要ります。アンカーポジショニングは本書の対象のブラウザの一部が対応していないので、レイアウトの要としては使いません（「[1-2 ブラウザサポートとプログレッシブ・エンハンスメント](/principles/browser-support/)」）。一方で、なくても内容を読めて操作できる装飾なら、未対応の環境では表示されないだけで済みます。どの表現が装飾にあたるかを、部品ごとに決めておく必要があります。

名前の衝突は、ポップオーバーを暗黙のアンカーで置けば起きません。名前を付けるのは、ポップオーバーにしない要素だけです。矢印の向きとメニューを開く向きは、対象のブラウザの対応がそろっていない機能を使わずに決めます。

## ポップオーバーのツールチップ

ボタンが開くツールチップは、`popover` 属性でトップレイヤーに表示し、`popovertarget` でボタンと結び付けます。ボタンは暗黙のアンカーになるので、名前を付ける必要はありません。トップレイヤーの要素は包含ブロックがビューポートになるので、祖先の `overflow` で切り取られず、下に収まらないかどうかも画面の端で判定されます。

```css title="🙆‍♂ Recommended: 未対応の環境では画面の中央に、対応した環境ではボタンの下に表示する"
@scope (.scoped.help-tip) to (.scoped) {
  [popover] {
    margin: revert;

    @supports (position-area: block-end span-inline-end) {
      position-area: block-end span-inline-end;
      position-try-fallbacks: flip-block;
      margin-block: 4px 0;
      margin-inline: 0;
    }
  }
}
```

```html
<span class="scoped help-tip">
  <button type="button" popovertarget="help-tip-1">入力のヒント</button>
  <span id="help-tip-1" popover>半角の数字で入力してください。</span>
</span>
```

未対応の環境では、`margin: revert` で戻したデフォルトスタイルの `auto` によって、ツールチップは画面の中央に表示されます。対応した環境では、ボタンの下の行に、ボタンの行頭側の辺から行末へ伸びる形で表示し、下に収まらなければ上に反転します。`@supports` の中で `margin` を指定し直している理由は、7-11の「未対応の環境では読める位置に置く」で説明しています。

暗黙のアンカーは要素どうしの結び付きで決まるので、ツールチップを何個置いても、ほかのボタンが基準に選ばれることはありません。HTMLの `id` は、ページの中で重ならないように付けます。

## 名前を付けたアンカーを繰り返し置く

ポップオーバーではない要素をアンカーの近くに置くときは、`anchor-name` で名前を付けます。たとえば、入力欄の横に文字数を表示する部品は、入力欄をアンカーにして、文字数の表示を行末側に置きます。この部品をフォームに複数置くと、同じ名前のアンカーも複数できます。

同じ名前のアンカーが複数あると、条件を満たすもののうち、文書の順で最後の要素が選ばれます。どの部品の文字数も、最後の入力欄の横に集まります。ルートに `anchor-scope` を指定すると、名前の届く範囲はその要素の子孫に限られ、それぞれの文字数は自分の入力欄を基準にします。

```css title="🙆‍♂ Recommended: 繰り返し置く部品では、ルートで名前の範囲を限る"
@scope (.scoped.counted-field) to (.scoped) {
  :scope {
    position: relative;
    anchor-scope: --counted-field;

    & > ._count {
      @supports (position-area: inline-end) {
        position: absolute;
        position-area: inline-end;
        position-anchor: --counted-field;
        margin-inline-start: 8px;
      }
    }
  }

  input {
    anchor-name: --counted-field;
  }
}
```

ルートの `position: relative` は、文字数の表示の包含ブロックをこの部品に限る指定です。未対応の環境では、文字数は `position: absolute` ごと無視され、入力欄の後ろの通常フローに表示されます。行末側に空きがないときに表示を切り替えたいなら、7-11で説明した `position-try-fallbacks` を加えます。

`anchor-scope` は、Chrome 131、Firefox 147、Safari 26で対応しています。ポップオーバーの暗黙のアンカーには名前がないので、ツールチップには `anchor-scope` は要りません。

## コンポーネントの中のレイアウトに使う

記事カードのカテゴリーを示すタグを、画像の行末側の上の角に重ねる例で考えます。タグは記事についての情報なので、HTMLでは本文の中の見出しの前に置きます。カードは置き場所の幅によって、画像と本文を縦に積んだり横に並べたりします。カードを包含ブロックにしてタグを絶対配置すると、タグが付くのはカードの角で、画像の角ではありません。

```css title="🙅‍♂ Not Recommended: タグをカードの角に置き、横並びで画像の角からずらす" issue="convention"
/* 🙅‍♂ Not Recommended */
@scope (.scoped.article-card) to (.scoped) {
  :scope {
    position: relative;
  }

  ._content {
    & > ._tag {
      position: absolute;
      inset-block-start: 0;
      inset-inline-end: 0;
    }
  }
}
```

```html
<article class="scoped article-card">
  <div class="_body">
    <img class="_thumbnail" src="..." alt="" width="..." height="..." />
    <div class="_content">
      <p class="_tag">コーヒー</p>
      <h2 class="_title">...</h2>
      <p class="_lead">...</p>
    </div>
  </div>
</article>
```

縦に積んだときは、画像がカードの上端にあるので、2つの角はほぼ重なります。横に並べると、カードの行末側の上の角は本文の上にあり、タグは見出しに重なります。画像の角に合わせるには、並びごとに画像の幅や余白から位置を計算することになり、レイアウトを変えるたびに書き直しが要ります。

画像をアンカーにすれば、タグをHTMLの位置に置いたまま、画像の角に重ねられます。画像に `anchor-name` を付け、タグの `inset-block-start` と `inset-inline-end` を、`anchor()` で画像の同じ側の辺にそろえます。`anchor()` の `start` と `end` は、書いたプロパティと同じ軸の、包含ブロックの書字方向から見た始まりと終わりの辺です（`self-start` と `self-end` は、配置する要素自身の書字方向で決まります）。カードは一覧で繰り返すので、前の見出しで説明したとおり、ルートの `anchor-scope` で名前の範囲をカードの中に限ります。

```css title="🙆‍♂ Recommended: 画像をアンカーにして、タグを画像の角に重ねる" from="layout-practice/anchored-card-tag"
@scope (.scoped.article-card) to (.scoped) {
  :scope {
    position: relative;
    anchor-scope: --thumbnail;
  }

  ._thumbnail {
    anchor-name: --thumbnail;
  }

  ._content {
    & > ._tag {
      @supports (anchor-scope: --thumbnail) {
        position: absolute;
        inset-block-start: anchor(start);
        inset-inline-end: anchor(end);
        position-anchor: --thumbnail;
        margin: 8px;
      }
    }
  }
}
```

次のデモでは、広い場所のカードは画像と本文が横に並び、狭い場所のカードは縦に積まれます。どちらでも、タグは画像の角に付きます。幅を320pxにすると、広い場所のカードも幅が足りないので縦に積まれますが、タグは画像の右上の角に付いたままです。`anchor-scope` に未対応のブラウザでは、タグは見出しの上の通常の位置に表示されます。

<Demo title="画像と本文の並びが変わっても、タグを画像の角に重ねるカード" html={cardTagHtml} css={cardTagCss} frame={cardTagFrame} />

見た目が変わっても、読み上げの順はHTMLのとおり、タグ、見出し、説明です。タグを画像と一緒に包めば、絶対配置だけでも重ねられます。ただし、記事についての情報が画像の側へ移るので、画像のない記事では同じHTMLを使えません。{/* 要確認: 出典なし */}

`@supports` の条件を `anchor-scope` にしているのは、`anchor()` に対応していても `anchor-scope` に未対応のChrome 125〜130では、どのカードのタグも最後のカードの画像に集まるからです。未対応の環境では、タグは `position: absolute` ごと無視され、見出しの前の通常の位置に表示されます。画像に重ならないだけで内容は読めるので、アンカーポジショニングをレイアウトの要にしない方針にも反しません。

<Baseline id="anchor-positioning" compatKey="css.properties.inset-block-start.anchor" name="inset-block-start の anchor()" />

同じ書き方で、特集の表示のように、説明文を画像の下端に重ねることもできます。説明文の下端と行頭側・行末側の辺を、画像の同じ側の辺にそろえます。

```css title="🙆‍♂ Recommended: 説明文を画像の下端に重ねる"
@scope (.scoped.feature-card) to (.scoped) {
  :scope {
    position: relative;
    anchor-scope: --thumbnail;

    & > ._lead {
      @supports (anchor-scope: --thumbnail) {
        position: absolute;
        inset-inline: anchor(start) anchor(end);
        inset-block-end: anchor(end);
        position-anchor: --thumbnail;
      }
    }
  }

  ._thumbnail {
    anchor-name: --thumbnail;
  }

  ._lead {
    background-color: oklch(0% 0 0deg / 60%);
    color: oklch(100% 0 0deg);
  }
}
```

絶対配置の説明文はカードの高さに数えられないので、長くなると画像の上端を越えて伸びます。重ねるのは短い文章に限り、背景色で画像との間のコントラストを確保します。{/* 要確認: 出典なし */}

## メニューを上下の空きに合わせて開く

ナビゲーションのメニューは、ボタンの位置によって、下に開くと画面の下端からはみ出すことがあります。候補を書いた順に試す既定の動作では、下に収まらないときだけ上に開きます。項目が多く、上下のどちらにも収まりきらないことがあるメニューなら、`position-try-order: most-block-size` で、元の位置と候補のうち空きの大きいほうを選ばせます。

```css title="🙆‍♂ Recommended: 上下のうち、空きの大きいほうにメニューを開く"
@scope (.scoped.site-menu) to (.scoped) {
  [popover] {
    margin: revert;

    @supports (position-area: block-end span-inline-end) {
      position-area: block-end span-inline-end;
      position-try: most-block-size flip-block;
      min-inline-size: anchor-size(inline);
      margin: 0;
    }
  }
}
```

`position-try` は、`position-try-order` と `position-try-fallbacks` の一括指定です。`min-inline-size: anchor-size(inline)` は、メニューの幅を開いたボタンの幅以上にする指定です。`position-try-order` はFirefoxでは148から使えます。

位置が反転したときに吹き出しの矢印の向きを変える `@container anchored(fallback: flip-block)` は、Chrome 143以降だけが対応しているので、本書では採用しません。ほかのブラウザでは、反転しても矢印が吹き出しと反対の側を指すからです。位置が反転しうる吹き出しには矢印を付けないか、矢印がなくても、どのボタンの説明かが分かるデザインにします。{/* 要確認: 出典なし */}

`position-area` と `position-try-fallbacks` は離散的に切り替わるので、反転するときの位置の変化をトランジションで滑らかにはできません。アンカーが動いたときの `anchor()` の値の変化を補間できるのも、Chrome 125以降とSafari 26以降だけです。

## ホバーした項目に背景を追従させる

アンカーポジショニングは、装飾にも使えます。メニューの項目にマウスを載せると、1枚の背景が項目から項目へ移っていく表現は、ホバーしている項目をアンカーにして背景を配置すれば作れます。項目ごとに背景を付ける書き方では、背景はその場で付いたり消えたりするだけで、項目の間を移動させられません。

背景には、項目を並べたリストの `::after` を使い、`inset: anchor(inside)` でアンカーの4辺に合わせます。アンカーの名前 `--current-hocus` は、ホバーしているリンクと、キーボードでフォーカスしているリンクにだけ付けます。名前を持つリンクが変わると、背景もそのリンクの位置へ移ります。同じメニューを複数置いても名前が混ざらないように、ルートには `anchor-scope` を指定します。

<Demo title="ホバーかフォーカスした項目へ、背景が移っていくメニュー" html={hoverIndicatorHtml} css={hoverIndicatorCss} scheme="auto" />

どの項目にもホバーしていない間は、その名前のアンカーがありません。参照できるアンカーがない `anchor()` は、代わりの値を書いていなければ、宣言ごと計算値の時点で無効になります。`inset` は初期値の `auto` に戻り、中身のない `::after` は大きさを持たなくなります。そのままでは、マウスを外した瞬間に背景が消えます。そこで、リストに `--_has-hocus` のフラグを置き、どのリンクにもホバーやフォーカスがない間は `opacity: 0` にして、次に説明するトランジションで薄れさせます。擬似要素のスタイルクエリは元の要素を問い合わせるので、リストに立てたフラグを `::after` から読めます。フラグの書き方は、「[10-6 スタイルクエリで状態を伝える](/components/style-queries/)」で説明しています。

トランジションは、項目の間を移る `inset` と、薄れる `opacity` に掛け、`transition-behavior: allow-discrete` を加えています。`auto` との間は補間できず、値は離散的に切り替わりますが、`allow-discrete` を指定すると、切り替わりがトランジションの半ばまで遅れます。そのため、マウスを外したあとも、背景は最後の項目の位置に留まったまま薄れていきます。キーボードで項目を移るときは、`&:not(:has(> li > :focus-visible))::after` の条件でトランジションを外し、背景をすぐに移します。フォーカスリングは移った先にすぐ表示されるので、背景が遅れて追いかけると、現在の位置が一瞬分かりにくくなるからです。{/* 要確認: 出典なし */}

背景が項目の間を移るのは、画面の上で物が動く変化なので、動きを減らす設定では取り除きます。`inset` のトランジションは `@media (prefers-reduced-motion: no-preference)` の中でだけ指定し、`opacity` のトランジションは条件の外に書きます。位置と大きさの変わらないフェードは、動きを減らす設定でも残してかまわないからです（「[18-2 動きを減らす設定に対応する](/motion/reduced-motion/)」）。動きを減らす設定では、背景はホバーした項目へすぐに移り、メニューに入ったときと出たときだけ薄れて変わります。

ただし、`opacity` だけにすると、マウスを外した瞬間に `inset` が `auto` へ戻り、薄れる前に背景が消えます。そこで、`--_has-hocus` が `--false` の間だけは、動きを減らす設定でも `inset` をトランジションの対象に加えます。どの項目も状態を持たない間に `inset` が変わるのは、アンカーを失って `auto` に戻るときだけです。`auto` との間は離散的に切り替わるので、背景は動かずに最後の項目の位置に留まり、薄れたあとで消えます。

背景の色は、半透明の重ね色のトークン `--background--hover` です（「[17-1 ホバーとフォーカスを表す](/interaction/states-and-focus/)」）。強制カラーモードでは背景色が置き換わって見えなくなるので、透明な枠線を付けておき、枠線に色が付くようにしています（「[15-5 強制カラーモードとコントラスト](/color-media/forced-colors/)」）。

前述のとおり、`anchor()` の値の変化を補間できるのはChromeとSafariだけで、Firefox 147以降では、背景はアニメーションせずに次の項目へ切り替わります。アンカーポジショニングに未対応の環境では、`@supports` の中の指定が無視されて `::after` が生成されず、ホバーした項目に背景が付かないだけになります。ホバーの手がかりは矢印の移動でも示しているので、メニューの使い方は変わりません。この背景は、なくても内容を読めて操作できる装飾なので、プログレッシブ・エンハンスメントとして使えます。

背景を移すために `inset` を動かすと、トランジションのあいだ、フレームごとに擬似要素のレイアウトが計算し直されます。`translate` のような変形なら、レイアウトを計算し直さずに動かせますが、`anchor()` で決まる位置と大きさは、`inset` で受けるしかありません。背景は絶対配置なので、動いてもほかの要素の位置は変わりません。デモのように項目が数個のメニューなら、計算し直す量は問題になりません。

### 背景を追従させる部品の条件

背景が項目から項目へ移る表現は、どの部品にも合うわけではありません。使うのは、すべての項目が押せ、項目が隙間なく並び、ホバーしている間に項目が動かない部品です。この条件がそろえば、背景の移る先はいつも押せる項目になり、背景の位置がそのまま押せる位置を示します。項目の間に隙間を作らない理由は、「[17-2 押せる範囲とタッチ操作](/interaction/hit-area-and-touch/)」の `no-gaps-between-hover-items` で説明しています。

反対に、押し間違えたときの損失が大きい部品には使いません。背景が移り終わる前に押すと、背景はまだ前の項目の近くにあり、押した項目と背景の位置がずれて見えます。削除のような取り消せない操作を含むメニューでは、項目ごとに背景を付け、ホバーした項目をすぐに示します。一部の項目だけが押せる部品にも向きません。押せない見出しや区切りの上を背景が通り過ぎるので、押せる項目と押せない項目の区別が付きにくくなります。

項目の間に広い余白がある配置では、背景が長い距離を動き、余白を通るたびに薄れて戻るので、動きばかりが目立ちます。スクロールで項目が動く部品も同じです。カーソルを止めたまま中身をスクロールすると、カーソルの下を項目が通り過ぎるたびにホバーが移り、ユーザーが手を動かしていないのに背景が動き続けます。
